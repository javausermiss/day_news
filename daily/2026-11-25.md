Superpowers is a complete software development methodology for your coding agents, built on top of a set of composable skills and some initial instructions that make sure your agent uses them.
It starts from the moment you fire up your coding agent. As soon as it sees that you're building something, it doesn't just jump into trying to write code. Instead, it steps back and asks you what you're really trying to do.
Once it's teased a spec out of the conversation, it shows it to you in chunks short enough to actually read and digest.
After you've signed off on the design, your agent puts together an implementation plan that's clear enough for an enthusiastic junior engineer with poor taste, no judgement, no project context, and an aversion to testing to follow. It emphasizes true red/green TDD, YAGNI (You Aren't Gonna Need It), and DRY.
Next up, once you say "go", it launches a subagent-driven-development process, having agents work through each engineering task, inspecting and reviewing their work, and continuing forward. It's not uncommon for your agent to work autonomously for a couple hours at a time without deviating from the plan you put together.
There's a bunch more to it, but that's the core of the system. And because the skills trigger automatically, you don't need to do anything special. Your coding agent just has Superpowers.

Fanning out

I wanted to prove this was possible to do, so I kept a constraint of a 3 GB limit for Lambdas. The whole model is 9.3 GB, so it does not fit in one. But it has 32 layers of about 225 MB each, and one layer fits. That gave me one Lambda job per layer per block of tokens.
Think of the Lambda as a simple idempotent API. A job reads inputs from S3, does the math, and writes one object back.
x = load(f"{doc}/{layer - 1}/{block}")
memory = load(f"{doc}/{layer}/{block - 1}")
y, memory = model.layers[layer](x, memory)
s3.put_object(
    Key=f"{doc}/{layer}/{block}",
    Body=pack(y, memory),
)
Each job waits on the layer above for the same block and on its own previous block. Each layer starts one step after the layer above it, like a staircase 32 layers deep.

my major advocacy is that lua is a very good general purpose language. this is not an opinion shared by all. lua’s major design goal was extending and embedding into existing programs. I think the simplicity and flexibility in design persued towards the end of that goal extends to make lua a very good language in general. that said, it does its job quite well as an embedding language, and one of its more interesting use cases (and actually, one of its oldest use cases) is as a data or configuration format.
lua’s syntax provides many niceties. for instance, lua has an infinite family of multiline strings: the most basic one starts with [[ and ends with ]]. however, any amount of equal signs can be put between the two square brackets: print([======[hello, world]======]). the only way to close a [===[ is with an accompanying ]===], not with a ]] or a ]==], or a ]====].
here is a function that for any string, creates the correct multiline string to represent it:
local function stringize(str)
    local equal_signs = ""
    for e in str:gmatch("](=*)]") do
        if #e >= #equal_signs then
            equal_signs = e .. "="
        end
    end
    return ("[%s[%s]%s]"):format(equal_signs, str, equal_signs)
end
of course, you can just use string.format with %q, but multiline strings usually provide nicer looking and more compact results. these strings are very good for representing lua code as strings in other lua code.

design and implementation choices like these come together to suit lua for this purpose. I’ve seen 3 main styles of using lua code to represent data or configuration. I think lua manages to accomodate each of them well, and each have their appropriate use.
styles of data representation
JSON style (LON?)
chunks are much like function bodies. they have return values. so, one thing that one can do is just return a big table from a lua program.
return {
    foo = "bar",
    list = {1, 2, 3},
    rule_of_thirds = true,
}
if you’re using this style, you can omit the return and then prepend it when you load the lua files. this makes any trailing statements syntactically invalid because the return statement must be the last statement in the block. keep in mind, though, that this does not prevent arbitrary code because function literals can be used instead.
return (function() arbitrary_code() end)()
trying to strip out function literals to make this technique safer is fraught and defeats the general elegance of this technique. one can fairly readily use JSON instead.
INI style
what is often missed about lua is that it’s subtly full of metaprogrammability. for instance, lua globals are just stored in a table, and which table is used can be controlled by the code itself. this table is known as the “environment”. an environment may be passed to load as an argument. the way this can be used is that you can load a chunk with an empty environment and then capture the values it sets as globals.
you can have a file like this:
-- config.lua
foo = "bar"
list = {1, 2, 3}
rule_of_thirds = true
then, you can get a table with all the configuration as simply as this:
local config = {}
assert(loadfile("config.lua", "t", config))()
imperative style
lua has a bit of sugar that allows you to shed the parenthesis on function calls to make them look cleaner. an imperative style is a very suitable means to represent data in lua, and it’s very powerful.
path "/path/to/things"
config {
    foo = "bar",
    list = {1, 2, 3},
    rule_of_thirds = true,
}

    fugiat eaque corporis eligendi officiis praesentium. Libero quo vero
    temporibus impedit sit inventore assumenda

programming in lua provides a real world example of this.
security considerations
the major problem with using an entire programming language to represent data is that untrusted data can be readily crafted to be malicious. indeed, I would not use this technique for untrusted data. with that in mind, it is possible to solve or mitigate the potential vulnerabilities.
the main technique for sandboxing lua is controlling the environment. when using lua for data representation, an empty enivronment is the most appropriate (or, an environment that only exposes data constructors). this prevents any I/O or access to the larger program’s state. preventing access to all standard library functions is safest. there are a few standard library functions that have consequences you might not expect.
another concern is denial of service. this is trickier to prevent. it’s fairly trivial to construct a lua chunk which does not return (while true do end). debug.sethook can mitigate this somewhat. even so, it’s probably possible to construct something that uses excessive amounts of memory. that said, denial of service is significantly less problematic than the vulnerabilities that are completely avoided by depriving the untrusted code of any standard library functions.
finally, make sure to reject lua bytecode. untrusted lua bytecode is not safe and may cause arbitrary nasal demons in the lua interpreter. load can accept both bytecode and lua source by default. however, passing "t" for the mode parameter prevents this.

Matrix 首页推荐
Matrix 是少数派的写作社区，我们主张分享真实的产品体验，有实用价值的经验与思考。我们会不定期挑选 Matrix 最优质的文章，展示来自用户的最真实的体验和观点。

在上期《怀旧手记》中，我为大家科普并分享了 Palm OS 阵营当中的索尼 CLIE。
本期《怀旧手记》依旧和 Palm 有关，接下来要和大家分享的是 2009 年 Palm 的「转型之作」——Palm Pre 和 webOS。
从一次「上滑」说起
在正文开始前，想必有很多人听说过 webOS 但并不了解。所以，在此我想问大家一个问题：你现在使用的是什么品牌的手机？运行的是什么操作系统？在使用手机的过程当中，最「无关紧要」但「必不可缺」的动作是什么？
我先来回答：我使用的是 vivo 的手机，运行的是基于安卓定制的 OriginOS；除此之外，我还有一台 iPhone，运行 iOS。在日常使用当中，最「无关紧要」但「必不可缺」的动作我认为是：在管理应用时，手指从屏幕底部向上滑动并短暂停留，呼出「卡片式后台」进行切换或关闭。
把时间拨回 2009 年。当时的智能手机市场，主流毫无疑问是诺基亚的塞班（Symbian）和新晋苹果的 iPhone OS。这两个系统在当时的交互逻辑截然不同：一个坚持「真后台」的多任务运转，另一个在第三方应用层面仅支持单任务。
但它们的共同点在于：在那个时代，没人知道一套直观、优雅的多任务交互逻辑究竟该怎么做。
最早把「卡片式后台」和「上滑手势」作为系统核心交互的，是以 PDA 闻名的老牌厂商Palm。以及它孤注一掷带来的全新系统——webOS。
提起 Palm 想必很多人还是和我一样会想起经典的 PDA（个人数字助理），最经典的莫过于 Graffiti 手写识别。
和苹果的 Newton 不同，Palm 在字母识别这一块，不是让机器去试图适应人的操作，而是让人学会一套固定的「动作」来操控机器。
webOS 是什么？
在详细展示之前，我想先为大家简单科普一下：什么是 webOS？
webOS 是 Palm 公司基于Linux内核开发的嵌入式操作系统，2009 年随智能手机 Palm Pre 首次亮相，被大众寄予厚望。
和 Palm 在 PDA 时代的设计思路一脉相承，webOS 也专门为系统设计了很多「动作」，让用户通过手势来操控。
与当时市面上常见的操作系统不同的是，webOS 在设计和交互上有一些很具前瞻性的理念。其标志性的「卡片式后台」以及手势操控，对后来的移动操作系统交互产生了深远影响。
本次我们就通过首款搭载 webOS 系统的手机——Palm Pre，来实际体验一番。
Palm Pre「胖梨」：一块「鹅卵石」
这台 2009 年发布的手机带着全新的操作系统亮相，引发了业界的巨大关注，甚至被部分投资人誉为「iPhone 杀手」。
在国内它还有一个非常亲切的昵称「胖梨」，这一点从手机外观上也能看出。
以现在的眼光来看，Palm Pre 十分小巧圆润，熄屏状态下手机很像一块光滑的鹅卵石。
正面非常简洁：没有前置摄像头，但有听筒，以及一块 3.1 英寸 TFT 电容触摸屏，分辨率320×480（HVGA），支持多点触控。
除此之外，屏幕下方还有一颗「小圆点」。你可能会觉得它只是一枚「Home 键」，其实不然。它真正的官方名称是「中央钮」（Center Button），并且它所在的黑色区域是触控感应区，官方称之为「手势区域」（Gesture Area）。除了可以点按中央钮，你还可以在这片手势区域（包括圆点及两侧）进行左右滑动，来实现「返回」上一级界面的操作。
所以在初代 Palm Pre 上，与其把它看作是一枚简单的「Home 键」，不如把它看作是「手势区域」的核心控制点。
翻到手机背面，我这一台的后盖是亮黑色，想必前任机主定是十分喜爱这台「胖梨」，不然不会有这么多均匀的使用痕迹。
背面有一颗 300 万像素的摄像头，上方是 LED 闪光灯。说到「胖梨」的后盖，也大有来头。Palm Pre 通常被认为是早期支持无线充电的智能手机代表之一。它通过一个名为「Touchstone」（点金石） 的磁吸式充电底座实现，这在 2009 年是极为罕见且「神奇」的功能，雷军也曾在微博上提到，这是当年他最喜欢的手机之一。
在手机的上方有一枚实体静音键，通过左右拨动的方式来操控。静音键的右边是手机的电源键，机身侧边分别是音量键和带防尘挡板的 Micro USB 口。整机重约 135 克，放在今天算轻，在 2009 年属于正常水平。
如果把手机屏幕轻轻向上一推，就会露出一块 QWERTY 键盘，虽然因为手机尺寸比较小键盘也不会特别大，好在有背光，在光线昏暗的地方也能够看清字母。
2009 年的硬件，和一块「长在机身上的屏幕」
聊完外观和操作方式，我们再来看看这台诞生于 2009 年的手机，在硬件上究竟是什么水平。
「胖梨」采用可拆卸式电池，型号 BP1；容量为 1150mAh。在配置上搭载德州仪器 OMAP 3430，芯片标称频率 600MHz（但 Palm 将其降频至 500MHz 运行）；256MB RAM，内置 8GB 存储空间。
通过电源键点亮屏幕，可以看到 3.1 英寸屏幕与手机面板的衔接相当自然，几乎融为一体。但这种看起来像是「屏幕直接长在机身上」的设计，并不是简单地把边框做窄了。
传统手机通常把屏幕嵌在有边框的「坑」里，Palm Pre 则让屏幕表面与机身正面齐平，并采用与圆润机身相呼应的弧面；熄屏时，深色屏幕又会消隐在同样深色的前盖中。再加上触摸层与显示层高度集成，正面没有暴露的层间接缝，肉眼可见的「一体感」便由此形成。
webOS 体验：卡片、手势和那些小设计
回到手机上，webOS 的解锁界面比当时的 iPhone OS 更加简洁：数字时钟配合屏幕下方的一枚圆形解锁图标。初代 iPhone 发布时，乔布斯向大家展示的是从左到右「滑动方块解锁」；而在 webOS 上，只需要将手指放在屏幕下方的解锁图标上，向上拖动，就可以解锁并进入主界面。
进入主界面之后，除了底部固定的快捷启动栏（Quick Launch），屏幕上就只剩状态栏和壁纸了。你可能会好奇，其他应用都在哪里？其实，所有应用都集中在一个名为「Launcher」的应用启动器当中。点击底部快捷启动栏里印有黑色小房子的图标，就可以进入类似「应用抽屉」的界面，查看系统预装和自行安装的第三方应用。
webOS 虽然没有传统意义上的控制中心，但也提供了一个方便管理无线连接的菜单。只需要点击屏幕右上角的连接状态区域，就可以打开「连接菜单」（Connection Menu），查看日期、电量等信息，并对电话网络、Wi-Fi 和蓝牙等连接功能进行管理。
当我打开一个或多个应用，想要切换或者管理它们时，不需要按下复杂的组合键，只需要从屏幕下方的「手势区域」（Gesture Area）向上轻扫，就可以进入「卡片式后台」（Card View）。
在这里，每一个正在运行的应用都会以独立卡片的形式呈现。向上甩出卡片即可关闭对应应用；长按卡片，待其进入可调整状态后，再拖动就能改变卡片的排列顺序。整个过程不需要进入单独的任务管理界面，操作起来相当直观。
另外，在应用中想要返回上一级，只需要在手势区域内从右向左轻轻滑动，就能触发返回手势（Back Gesture）。如果当前应用已经没有更深层的页面，这一操作还会将应用最小化，直接回到卡片视图。虽然它不像今天许多手机那样通过屏幕边缘滑动实现返回，但 webOS 将大量常用操作集中在屏幕下方的手势区域，我认为这在当时确实是一种很有特色、也相当高效的交互设计。
除了这些主要操作之外，webOS 还有几个值得分享的小设计：
比如，当我点击屏幕时，系统会给出相应的视觉反馈：触摸的位置会出现类似水波纹的效果。
在亮屏状态下收到通知时，通知会先以横幅的形式出现在屏幕下方。如果没有及时处理，它还会收缩成图标，显示在屏幕右下角。点击屏幕底部的通知区域，就能展开通知面板（Dashboard），集中查看和管理收到的通知。
另外，webOS 在文本编辑方面也有一些值得一提的设计。iPhone OS 直到 2009 年推出 iPhone OS 3.0，才加入系统级的复制、剪切和粘贴功能；而webOS 在此之前就已经提供了相应支持。除了通过应用菜单中的编辑选项完成这些操作，Palm Pre 还可以利用实体键盘实现快捷操作：选中需要处理的文本后，按住屏幕下方的手势区域，直到中央按钮亮起，再按键盘上的 C、X 或 V，就可以分别完成复制、剪切和粘贴。对于配备实体键盘的 Palm Pre 来说，这种操作方式确实相当直接。
冷启动、折腾，和绕不开的应用生态
分享完了 webOS 上的部分「亮点」，也来看看在实际体验过程当中的「小缺点」。
感受最明显的是冷启动：第一次上手这台 Palm Pre 时，从按下电源键、Palm logo 亮起，到进入主页面，整整花了约 2 分 50 秒。
这个数值确实带给了我不小的震撼，不过与其解释背后的技术原理，我更愿意称之为机器的「小特点」。毕竟在冷启动进入桌面之后，系统的操控和反应还是非常流畅和丝滑的。
而且，我相信一般情况下，也不会有人频繁地关机或者重新启动。毕竟，在这台 Palm Pre 上，长按电源键调出关机选项后，还需要再次确认才能真正关机。按照当时系统的设计思路，关机更多是为了更换 SIM 卡或者取出电池，而不是日常使用中经常需要执行的操作。（确实是非常朴素的原因。）
还有一点，webOS 的开放程度，我认为是介于塞班（Symbian）和 iPhone OS（iOS）之间的。虽不像诺基亚塞班一样，只需要调整时间或者往系统当中丢几个破解文件就可以随意安装第三方软件；但比起iPhone的绝对封闭，还是要好上不少。

煮机网：一场「时空穿越」
所以，当时在国内使用 webOS 就一定离不开「折腾」：折腾 ROM、应用移植等。而国内最有影响力的 Palm webOS 社区是——煮机网（ZooPDA）。

回到 Palm 和 webOS 上。2009 年 1 月的 CES，Palm Pre 凭借亮眼的外观和超前的系统，在正式开售前就获得了不错的口碑；同年 6 月 6 日，它由运营商 Sprint 在美国独家上市，这种独家合作限制了它的用户基础。后来 Verizon 也加入了销售，但销量仍远低于预期。

至于 Palm 和 webOS 后来的故事只能说「短暂」又「可惜」。

不过，Palm 品牌和 webOS 系统在此之后却走向了不同的道路：惠普在 2013 年 2 月，将 webOS 的源代码、相关文件、工程团队以及相关知识产权授权出售给 LG 电子。
而 LG 拿下 webOS 并非为了做手机，而是为了打造智能电视的操作系统。从此 webOS 在不同的领域找到了归宿，延续至今。
至于 Palm 品牌，直到 2015 年 1 月，TCL 才从惠普手中收购了 Palm 的品牌和域名使用权，不涉及任何员工、技术或专利。
2018 年，一款「Palm」手机悄然发布。但它和本文讲述的 Palm 已经没有什么关联，系统也并非 webOS，而是 Android 8.1。手机最大的亮点在于：尺寸小巧如同一张银行卡片，重量仅为 62.5 克。

在此之后，互联网上几乎没有再传出和 Palm 新品有关的信息了。
结语
回顾 Palm 的发展史，其实很难避开它与苹果的宿命对决。正如我上期预告所提到的，在早期的 PDA 时代，苹果的 Newton 试图让机器去适应人的操作，而 Palm 却选择用 Graffiti 手写区，让用户学习一套固定的「动作」来操控机器。这种交互理念，Palm 一直延续到了智能手机时代。
然而，在当时的智能手机市场，Palm OS 由于系统老旧，面对横空出世的 iPhone OS 显得力不从心，市场反响也大不如前。Palm 急需一次从底层开始的彻底革新，于是 webOS 应运而生。

@大大大K：迪卡侬 Fold 560 折叠自行车
- 参考价格：1949.9 元（官方二手）
搬家之后，通勤距离从原来的 15 km 缩短到了 3 km，开车变成了一个性价比极低且经常「还不如走路快」的通勤方式。在忍受了一年多共享单车开锁即坏、车把歪斜、甚至要求我在马路中央还车等一系列荒谬问题后，我决定买一辆自己的短途代步工具。考虑到终点附近充电不便，以前还有过自行车被偷的经历，所以我把目光看向了可以带上楼的折叠自行车。
选购折叠自行车，轻量便携和折叠机构的稳固可靠是两个刚性条件。其次就是购买渠道，对于我这种自行车小白来说，能够先行试车、便于维保售后的线下渠道更合适。在符合要求的品牌中，大行最主流，改装生态也好，只是价格不太美丽；喜德盛等品牌虽物美价廉，但网点位置不多且都是经销商模式。而迪卡侬作为专业领域的连锁品牌，在产品质量有保障的基础上，其服务标准也相对统一，对于普通用户来说更加友好。碰巧在某次比价过程中，我在迪卡侬小程序上刷到附近门店有一辆 A 级成色的 Fold 560，价格与个人二手卖家相差无几，却能享受门店的保养服务以及与新车相同的官方质保政策，于是我当天就前往门店，查看实车后入手。
Fold 560 在迪卡侬折叠车产品线里属于顶配车型了，车架和前叉均为铝合金材质，12 kg 的重量实际感受并不算轻，不过拎着上两级台阶没什么压力；座管长度非常充裕，我 185 cm 的身高调整到合适位置后仍有升高的余量；变速器则采用了禧玛诺的 Sora 九速变速器，虽然实际用不上这么多档位，但 9 个飞轮意味着更大的变速范围，所能应付的坡道场景也更多。
其他车辆本身的参数配置在这里就不赘述了，我更想分享的是 Fold 560 的折叠体验和一些使用细节，因为这辆车虽然看起来似乎很「粗犷」，可真到手上用起来，发现它处处都显露着「实用主义」。
首先是折叠体验上，Fold 560 的折叠锁扣足够宽大且带有着力点，头管解锁按键也正好对应大拇指的位置，解锁或锁紧操作都能单手完成。折叠之后，两个轮子会以平行姿态通过磁吸扣吸附在一起，只要位置准确，磁吸扣的力度大到展开时往往需要扭转车把才能让前轮脱离。
座垫下方单独设计了一个推行把手，推行状态下，我并不需要全手发力抬起车身，只需将推行把手挂在手掌上即可轻松前进。更省心的是，Fold 560 车架下方自带一个金属支撑架，车辆以折叠姿态停放时，我可以自然地将车身放到地面，不需要像其他两折叠车辆那样必须把座管插到底才能勉强立住。
另一个非常打动我的细节是 Fold 560 自带变速器保护架。这个保护架能够在变速器外侧形成一个支撑空间，避免变速器尾勾被磕碰挤压导致变形。虽然这不是什么专利技术，电商平台也有售卖成品，但出厂标配就这样一个配件，说明车辆已经做好了「开箱即用」的准备，尤其是对于很多有「4+2」需求而购买折叠车的人来说，哪怕提车当天放到后备箱、载去郊外骑行踏春，也不用担心后备箱杂物挤压了变速器。
当然了，这款车型也不是完美的，我最介意的一点是它没有采用标准的「猪鼻孔」，市面上通用的自行车配件都不能安装，原装座垫的舒适度也是一大痛点（骑久了真的是「痛」点）。而在骑行感受方面，折叠车受限于物理结构且为了保持轻量化，在减震、轮圈、轴距等等诸多方面都做出了妥协，尤其是在非铺装路面骑行时，其舒适度远不如全尺寸自行车或带减震的山地车。如果你也准备入手一辆折叠自行车，无论是为了通勤使用还是休闲娱乐，购买之前都要考虑好自己所在城市的非机动车道规划情况和骑行路段的路面状态。
@手动贩卖机：静电白板贴
- 入手渠道：拼多多
- 入手价格：5.94 元
虽然我已经在用 Notion 和 Obsidian 等数字工具对日常生活或工作任务进行管理，但有时候新鲜想法冒出来的时候，我通常无法即刻脱离当时的环境，去打开系统庞杂的 Notion 或 Obsidian，按格式写下我的想法。往往当我完成这套动作之后，我已经忘了我最初是要做什么了，所以最好的方式就是赶紧拿起纸笔，随手记下来。
因此，我也用着最原始的纸质本子和便利贴辅助记录，但又会遇到我在构思比如说某篇文章或视频脚本时，要罗列的零碎点太多，纸张和小小的便利贴已经满足不了我随手涂写的情况。
我考虑过购买一个可移动带支架的白板，但不能否认的是，这种白板很占室内空间，假若家里有不受管控的小孩，还需要考虑它的存在会不会造成安全隐患。
直到我偶然间看到了带货博主在推荐静电白板贴，似乎这个产品一次性解决了空间占用和安全考量这两个问题，它只需要你有一面墙就可以了，而我刚好「家徒四壁」。
所以在丈量好墙面尺寸之后，我购入了静电白板贴。
它是通过静电吸附在墙面上的，而非通过胶粘或打孔的方式固定在墙上，所以不会对墙面造成任何破坏。对于租房党来说，特别友好。在正常使用的情况下，不用力拉扯，其吸附固定的能力还是相当稳固的。
几年前，我也买过一款静电墙贴，它看起来就是一张透明的膜，我将其贴在了书桌下方的墙面上，用于避免脚踢或者脚托产品磕碰墙面造成的墙面脏污或刮伤。因为它是透明的，所以不像那些有花纹的墙纸那般要考虑和室内设计的美观相容性，量好尺寸吸附上就没有任何存在感了。
至于静电白板贴，它不是完全透明的，而是跟传统白板一样，是纯白色的，可能贴在其它地方会很明显，但贴在白色的墙上，肉眼上看起来并不会特别突出。在有光反射的情况下，能够明显看到它的存在，换个角度，又能和墙面融为一体。
并且，在白板贴上书写，墨水并不会透过白板贴渗透到墙上。
白板贴还附赠了一支笔和一条小抹布，在书写完之后，抹布打湿之后就可以在白板贴上擦拭笔迹，不过当我用商家附赠的笔时，不知是附着能力太强还是怎么回事，字写久了要擦拭干净有点困难，所以后来我自行购入了晨光的白板笔，经过实测，写了一周多的字依然清水加布一擦就能擦掉了。
总的来说，小户型或租房党如果需要白板类的产品，不管是自用还是给孩子用，静电白板贴是一种很好的平价替代品，能利用多余的墙面空间之外还能保护墙壁，不过它和白板的差别就在于没有磁性，所以无法用磁铁往上面贴东西，不过倒是可以用贴纸来替代磁铁的功能。

从Hôtel de Ville地铁站出来，巴黎市政厅就立在眼前。浅色石墙铺展开来，陡峭的屋顶、密集的窗户、中央的钟楼，还有层层排列的人物雕像，让人忍不住停下脚步仰头多看一会儿。法语里的「Hôtel de Ville」，意思就是市政厅。在巴黎看见「Hôtel」，不一定指的是酒店。在不同的词组里，它可能指公共建筑，也可能指城里的私人府邸。后面在玛黑区反复遇到的「Hôtel particulier」，指的就是贵族或富裕人家的城市宅邸。
眼前这座颇有文艺复兴气息的建筑，主要是十九世纪重建的成果。旧市政厅在1871年巴黎公社期间被大火毁坏，1882年重建，经历剧变的巴黎，重新拥有了这张隆重的城市门面。
外墙上的雕像，则像一份用石头写成的名人录。壁龛里共有108尊名人雕像，包括文学家、艺术家、科学家与政治人物，每个塑像下面都有他的名字。谁能被记住，谁能站上市政厅立面，也透露着那个时代对历史的理解。
中央钟楼的钟面附近人物则承担着另一种任务：钟面左右的人物象征劳动和教育，旁边的卧像代表塞纳河与马恩河，钟面上方的女性代表巴黎城，在下面一排三个词语「自由、平等、博爱」（Liberté, Égalité, Fraternité）。知道这些，再抬头看，满墙雕塑就不只是热闹的装饰了，有人是值得纪念的前辈，有人替一条河、一座城市或一种公共价值站在那里。
巴黎市政厅入口上方，几面蓝白红三色法国国旗簇拥着巴黎市徽（装饰性版本），盾牌里有帆船和百合花，盾牌上有城墙。
完整版的巴黎市徽如下图。其中帆船与波浪是来自中世纪塞纳河水运商人团体的标志，体现巴黎与河流、贸易的关系；蓝底金色百合花是法国王权的象征；顶部像城墙的冠饰呼应古代城市的城墙。两侧的橡树枝与月桂枝：分别象征市民的英勇行为与胜利。市徽下方还悬着三枚勋章，记录着巴黎获得的荣誉，也把近代战争与抵抗的历史，添进了这艘古老帆船的故事里。上面飘带上的拉丁文「Fluctuat nec mergitur」是巴黎的格言，意思是：
任凭风浪，亦不沉没。
它说的是徽章上的船，也逐渐成为巴黎面对灾难与动荡时坚韧精神的象征，放在当下时局倒也很应景。
了解了这些故事，再看巴黎市政厅，你是不是也感受到看似冰冷的建筑也有了温度？市政厅建筑前面留出一片广场，也让观看变得从容。人可以退远一点，把展开的建筑立面一起收入眼中，也可以什么都不研究，只在空地上站一会儿。几分钟后走进窄街，巴黎又会凑到眼前，刚才还需要仰头远看的城市，很快便近到能够看清门把手和墙上的纹路。
巴尔街的老教堂和木筋屋
绕到市政厅后面，圣热尔韦-圣普罗泰教堂（Église Saint-Gervais-Saint-Protais）是巴黎历史最悠久的教堂之一，早在六世纪便已有记载。现在这座教堂的可以说是不同时代的「缝合体」：教堂主体从1494年开始兴建，延续晚期哥特式传统，教堂内部是高耸的拱顶；而正立面在17世纪初建造，古典主义风格，三层柱头各不相同，最下面一层的多立克柱式比较简洁，往上一层的爱奥尼柱头带着卷曲的涡旋，再上面是装饰更繁复、带叶片纹样的科林斯柱式。
教堂前有一片纪念花园，是为2015年11月13日巴黎恐怖袭击的遇难者而设。眼前不断有行人经过，城市继续运转，而过往的伤痛和对逝者的怀念留在了这片安静的花园。
绕到巴尔街（Rue des Barres），街道一下子收窄，我们来这里寻找古老的木筋屋。在中世纪及近代早期的欧洲城市里，木筋屋曾是一种常见的建造方式：先用木梁、木柱搭起承重框架，再在框架之间填入其他材料。今天的巴黎仍能见到这样的房屋，巴尔街12号的木筋屋，是巴黎城郊外的莫比松修道院在进城办事时留下来的落脚点。
弗朗索瓦—米隆街（Rue François-Miron）11号与13号的两幢木筋屋，则更容易让人产生「走进旧巴黎」的感觉。之前读《巴黎历史侦探》，宫下志朗在寻找巴黎旧城墙的途中，特意绕来看看这两栋老屋。如今循着书里的地址走到这里，倒有一点与老相识碰面的亲切。
深色木梁在墙面上纵横交错，房屋的骨架清清楚楚地露在外面，与巴黎常见的石砌楼房相比，它们显得轻巧些，也更有几分古老的乡土气息。不过，这种古意同样经过了后人的整理。木梁曾被灰泥遮盖，如今外露的样貌，与1967年的修复有关。眼前的老房子，既保留着旧时的结构，也留下了后人修复与整理的痕迹，这些痕迹同样是木筋屋故事的一部分，正是一代代人的悉心维护，才让它们历经几百年的风雨，依然站在今天的街头。
再往前，博韦府邸（Hôtel de Beauvais）把同一条街带入17世纪的贵族生活，它建于1654至1660年，如今是巴黎行政上诉法院所在地。这也是玛黑区值得慢慢逛的原因，同样一条街上，窄小住宅与贵族宅邸只隔着几步，门面透露出来的生活却很不相同。有些房子几乎把自己摊开给路人看，梁柱、楼层一目了然；有些房子只露出整齐的窗户和一道大门，把庭院、花园以及更深处的生活藏在后面。散步的好奇心，也就在这些门前一点点长出来。
寻找旧巴黎，有点像翻看一件反复缝补的旧衣，后来缝进去的部分，像城市没有完全抚平的褶皱，走得慢一点，历史有时就从褶皱里露出来。《巴黎历史侦探》里这样说道：「如果说一个人脸上的皱纹印刻着他的生活轨迹，那么街道就是名为城市这张脸上的皱纹。单调的街道可能暗示着这座城市历史短浅，而那些歪曲粗陋的街巷中，往往蕴藏了最深厚的历史。带着这样的想法漫步巴黎，是我感到最为幸福的时刻。」
孚日广场，把时光交给草地
向东不远处就走到孚日广场，到这里历史先被草地上的人打断了。最先吸引我的，是那些坐着、躺着的人。有的人还讲究点坐在衣服或纸上，而大部分人都是直接在草地上或坐或躺，看书、聊天、听音乐，或者什么也不做。姿势各有各的松弛，远远看去，简直像从草坪上长出来的。
环望草地四周，建筑却格外整齐。孚日广场最初叫皇家广场，由波旁王朝国王亨利四世推动建设，1605年开工，1612年在其子路易十三统治时期落成。红砖、浅色石材与深色屋顶构成整齐而鲜明的面貌，底层是一圈可以连续步行的拱廊，柱子与拱一段段向前重复，眼前始终可以望见孚日广场中央的绿地。
广场中央是路易十三骑马像，最早的青铜骑马像于1639年立在这里。1792年法国大革命期间，作为王权象征的铜像被推倒，随后熔化铸成大炮。等到拿破仑帝国覆灭、波旁王朝重返王位，王室又为这位祖先重新立起了大理石像。同一位国王，在同一个广场上，经历了被纪念、被推倒、再被纪念。今天游人如织的广场，也藏着法国历史的几番翻覆。
说到这里，我又想起上海梧桐树下的普希金像，就在桃江路、岳阳路与汾阳路交汇的街角。它的经历更为曲折：1937年，旅沪俄侨为纪念诗人逝世一百周年集资建像；1944年被侵华日军拆毁，1947年重建，后来特殊时期又遭毁坏，直到1987年才再次立起。今天路过，很容易只把它当作街头一道安静的风景，可一旦好奇「上海为什么会有一尊俄国诗人的雕像」，便会循着它的故事，走进这座城市曾经的侨民生活与文化往来。碑身上的重建记录，也提醒着后来的人：破坏和充满痛苦的时代终将被文明和创造的时代取代，任何事物都不可能把杰出天才的名字从人们的记忆中剔除出去。
一位是法国国王，一位是俄国诗人，一个在巴黎，一个在上海。立像与被毁的缘由各不相同，却都让人看见，历史如何落在一尊雕像身上。那些静止的石与铜，也曾随着时代的起落承受着风雨。
我们继续回到巴黎孚日广场，路易十三骑马像旁有人在跟着讲解认识孚日广场，也有人已经在草地上睡着。广场规划者把建筑立面安排得严严整整，几百年后的普通人，则用最随意的姿势待在中间。
卡纳瓦莱，旧物里的巴黎往事
接着到了卡纳瓦莱博物馆（Musée Carnavalet），也就是巴黎历史博物馆。如果说旅行常常是在街上看见结果，城市历史博物馆就提供了回头寻找过程的机会：眼前这条路为什么在这里，这片街区以前住着谁，人们曾经又怎样生活。这座1880年向公众开放的博物馆，收藏着巴黎从早期聚落发展为现代都市的种种记忆。绘画、雕塑、家具、招牌、模型与日常物品，共同讲述这座城市怎样变化。它所使用的历史宅邸，本身也是展品的一部分。
卡纳瓦莱博物馆庭院中央站着的就是非常有名、自称「太阳王」（曾亲自扮演太阳神阿波罗）的路易十四，是法国波旁王朝的第三代国王，也是法国封建时代最具代表性的君主。我们看到雕像石座上有个年份「1643-1715」，路易十四于1643年继位，1715年去世，总在位时长72年110天，是有确切历史记录的、欧洲在位时间最长的独立主权君主。他在位期间将法国的君主专制推向顶峰，建立了高度集中的绝对王权，同时让法国成为当时欧洲的头号强国，法语也成为欧洲上层社会的通用外交语言。
也正因他是波旁王朝绝对王权的核心象征，法国大革命期间，全法国绝大多数路易十四的大型雕像都被民众推倒、熔毁，卡纳瓦莱的这尊能完整留存至今非常罕见，是少数躲过法国大革命时期破坏的太阳王大型雕像之一。
不过，这一天在博物馆里留下的最鲜活的记忆，来自三个少年。他们正在录一段介绍卡纳瓦莱博物馆的视频，一句「Bonjour」笑场了好几次。围观的人帮忙拍了一个结尾，三个孩子齐声说：「Merci beaucoup！」。我在法国几天就在和不同的人重复法语上面两个词——「Bonjour（你好）」和「Merci（谢谢）」，少年这几句话说得起起伏伏，鼻音、连读、句尾扬起又落下的节奏，像一小段歌。刚看过那么多石头和青铜做的人物，忽然遇见几个活泼的孩子，巴黎也跟着轻盈起来。
一路上能遇到很多巴黎市政厅立的介绍建筑与历史的牌子，很像上海老建筑墙上的「建筑可阅读」。我们在这个立牌上方又看到了熟悉的图案，前面介绍巴黎市政厅时讲到了巴黎市徽的帆船，这里立牌上方的图案就是巴黎市政府的标志。这些古朴的立牌总是让一栋原本准备匆匆略过的房子，变成值得停一会儿的地方。
蔷薇街，藏在烟火后的往事
离开卡纳瓦莱博物馆，玛黑区的周六越来越热闹。往蔷薇街走，店铺一间挨着一间，行人把路口连成流动的队伍。餐馆的红色遮篷伸向街沿，桌椅沿着店面摆开，这可真名副其实了「流动的盛宴」。
蔷薇街的名字温柔，历史却并不轻巧。它所在的玛黑区，是了解巴黎犹太文化的一处重要街区。犹太人在巴黎生活的历史可以追溯到中世纪，其间几经驱逐，又几度归来。到了十九世纪，来自阿尔萨斯等地的犹太居民陆续迁入玛黑区；十九世纪末至二十世纪前期，东欧犹太移民接踵而至，带来了意第绪语，也在这里开起作坊和商铺，渐渐织出一片热闹的街坊生活。这一带常被称为「Pletzl」，在意第绪语中意为「小广场」。
