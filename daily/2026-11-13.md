An open source design system that's fully customizable and built for how we build now: 
by people and the agents working alongside them.
Currently in Beta · Built on React 19+ and StyleX
Docs · Storybook · Sandbox · Contributing · Discord
Astryx is an open source design system that grew inside Meta over the last eight years, where it became the most-used and largest design system in the company — powering 13,000+ apps and shaped by the engineers, designers, and product teams who depend on it every day.
It ships 150+ accessible components, brand-level theming, dark mode, ready-to-ship templates, and a CLI as one cohesive system. You import pre-built CSS and use typed React components — no build plugin, no styling library to adopt — and both people and AI assistants build with the same tooling.
What makes Astryx different:
- Open internals. Components are built to be composed at any level, not locked behind a closed top-level API. The building blocks you'd reach for are exported directly, and when you need to go deeper, swizzle ejects a component's full source into your project to own.
- No styling lock-in. Astryx authors its styles with StyleX, but that's invisible to consumers. Override with className using Tailwind, CSS modules, or plain CSS — whatever your project already uses.
- Customize without wrapping. A theme is a set of CSS custom property overrides, so a designer can make Astryx unmistakably theirs without forking or wrapping component source.
- Built for people and agents. The API, docs, and CLI are designed together so a person and an AI assistant build the same way, from the same reference.
Astryx requires React 19 or later (react and react-dom are peer dependencies of @astryxdesign/core).
Install Astryx, a theme, and its peer dependencies:
# npm
npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
npm install -D @astryxdesign/cli
# pnpm
pnpm add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
pnpm add -D @astryxdesign/cli
# yarn
yarn add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
yarn add -D @astryxdesign/cli
You can also install the CLI once for your computer, so astryx works in any folder and every coding agent knows Astryx; in a project, it still runs that project's own version:
npm i -g @astryxdesign/cli
Project install, global install, or both? astryx docs global/project-global-or-both compares them (both is recommended), and astryx docs global explains how global mode works.
The simplest setup is a few CSS imports plus a theme provider — no build plugin, no PostCSS or Babel config. See the @astryxdesign/core README for the full guide (Next.js, Tailwind, Vite, and CDN).
For reliable CLI access, add a script to your package.json:
"scripts": {

}
Then use it as npm run astryx -- component --list. This avoids path errors when AI assistants or new developers invoke the CLI directly.
@astryxdesign/lab (experimental components) is used internally for Storybook and the sandbox and is not published to npm. @astryxdesign/vega (Vega/Vega-Lite chart wrapper) and @astryxdesign/charts (chart components) are published to npm only under the @canary dist-tag — there is no stable release yet.
These are the promises Astryx makes to the people building on it.
- Guidance over enforcement. Components give you capability rather than guardrails that fight you. Design opinions live in docs and examples — if you pass a value, the component renders it.
- Strong, documented conventions. Every component follows the same naming, prop, and composition rules, and every one is thoroughly documented — so once you've learned a few, the rest feel familiar, and both people and AI can predict how an unfamiliar component behaves.
- One system for humans and AI. The API, conventions, docs, and CLI are designed together so people and AI assistants build the same way. Every change that made Astryx easier for AI made it easier for people too.
- Earned by measurement. We test conventions rather than assert them, hold the results loosely, and revisit them when a new situation proves them wrong.

An agent skill that audits any codebase and writes implementation plans for other agents to execute.
The idea: use your most capable model for the part where intelligence compounds — understanding the codebase, judging what's worth doing, writing the spec — and hand execution to cheaper models. The skill never implements anything itself. The plan is the product.
you          →  /improve                    (expensive model, advises)
plans/       →  001-fix-n-plus-one.md       (self-contained specs)
other agent  →  implements, tests, ships    (cheap model, executes)
npx skills add shadcn/improve
Works in any agent that supports Agent Skills format. The plans it writes are plain markdown, so any agent (or human) can pick them up.
/improve                        full audit → prioritized findings → plans
/improve quick                  cheap pass: hotspots, top findings only
/improve deep                   exhaustive: every package, every category
/improve security               focused audit (also: perf, tests, bugs, ...)
/improve branch                 audit only what the current branch changes
/improve next                   feature suggestions — where to take the project
/improve plan <description>     skip the audit, spec one thing
/improve review-plan <file>     critique and tighten an existing plan
/improve execute <plan>         dispatch a cheaper executor, review its work
/improve reconcile              refresh the backlog: verify, unblock, retire
/improve ... --issues           also publish plans as GitHub issues
A typical first run, start to finish:
- Open your agent in the repo and run /improve (or /improve quick to keep it cheap).
- It maps the repo, audits it, and comes back with a findings table. Reply with the ones you want planned — "plan 1, 3 and 5".
- Plans land in plans/ — one file each, plus an index with the recommended order. Read them; they're meant to be reviewed.
- Hand a plan to any agent ("implement plans/001-*.md"), or let the skill run it: /improve execute 001. It dispatches a cheaper model in an isolated worktree, reviews the diff against the plan, and reports back with a verdict. Merging stays up to you.
- Next session, run /improve reconcile to clean up the backlog: verify what landed, refresh what drifted, unblock what got stuck.
Before a PR, /improve branch does the same thing scoped to just what your branch changes.

Picking #1 produced this plan — current code excerpted, exact steps, the repo's own test/lint commands as verification gates, and STOP conditions for when reality doesn't match.
Recon. Maps the repo: stack, conventions, and the exact build/test/lint commands — these become verification gates in every plan. It also ingests intent and design docs when present — ADRs (docs/adr/), PRDs, CONTEXT.md, DESIGN.md, PRODUCT.md — so decided tradeoffs aren't re-flagged as findings, direction suggestions stay grounded in stated product intent, and plans speak the repo's own vocabulary. Composes with any repo that already maintains these docs.
Audit. Fans out parallel subagents across nine categories: correctness, security, performance, test coverage, tech debt, dependencies & migrations, DX, docs, and direction (feature suggestions — every one must cite evidence from the repo itself, no generic idea-slop). Every finding carries file:line evidence, impact, effort, and confidence.
Vet. Subagents over-report, so the advisor re-reads every cited location itself before showing you anything — false positives get dropped, wrong attributions get corrected, rejections get recorded.
Prioritize. Findings land in a table ordered by leverage (impact ÷ effort, weighted by confidence). You pick what becomes plans.
Plan. One file per selected finding, written into plans/ with an index, priority order, and dependency graph.
Plans are written for the weakest plausible executor — a model that has never seen the advisor session and may be much smaller. Three properties carry that:
- Self-contained. All context is inlined: exact file paths, current-state code excerpts, repo conventions with an exemplar file, verified commands. No "as discussed above."
- Verification gates. Every step ends with a command and its expected output. Done criteria are machine-checkable. The executor never has to judge whether it succeeded.
- Hard boundaries. Explicit out-of-scope lists, and STOP conditions — "if X, stop and report" — instead of letting a small model improvise when reality doesn't match the plan.
Each plan also stamps the git commit it was written against, so executors run a mechanical drift check before touching anything.
Plans aren't fire-and-forget:
- execute <plan> spawns a cheaper executor subagent in an isolated git worktree, hands it the plan, then reviews the result like a tech lead — re-runs every done criterion, checks scope compliance, reads the diff against intent. 启程与抵达
十月中旬，我去了一趟日本。十月并非日本的旅游旺季，距离十一月的红叶尚有日子，盛夏的花火也早已结束。但这种「青黄不接」的时节对我来说刚刚好——游人稀少，台风季基本过去，早晚的空气里透着清凉。
去这一趟，也有精打细算的现实原因。日本大幅上调了多次签证价格，让我去年年底办下的那张签显得弥足珍贵，便想着一定要在到期前多去几次。
在大湾区，去香港搭乘廉航是挺常见的选择。我们选了一组性价比合适的班次，二人算上行李额折合人民币约四千元。飞机上午十一点半起飞，看起来时间充裕，但我们早晨七点便起来收拾，等到达登机口是已经开始最后召集。在路上，我们无数次庆幸没有为了省钱去订更早的班次。
当飞机滑跑离地的那一刻，我恍惚想起上一次冬日出游的场景：枯枝瘦硬，天空阴沉，偶尔飘着小雪。那是我第一次在日本自由行，生疏却印象深刻。不知道这一次夏秋之交再来，会看到怎样的景象。
到达大阪关西机场时已经是下午四点多。兑换好车票，我们顺利赶上了五点发往梅田的关空特急 Haruka 列车。日本有着浓厚的铁道文化，我们坐的 Haruka 主由 JR 西日本 281 系和 271 系担当，出于防撞与安全考量，驾驶室和前车窗位置设计得格外高。
随着一声轻响，列车准时驶离月台并慢慢加速，那一刻，我才终于有了「自己真的又来到了日本」的实感。七年前，我以为往后来日本旅游应该很常见，未曾想再次踏足这片土地，竟隔了这么久。
车厢里乘客不多，运行得安静平稳。夕阳斜照进来，将一排排阴影规律地扫过座位。邻座的女士拉下小桌，放上一个饭团，拧开饮料瓶盖，安静地吃着傍晚的茶歇。

两杯啤酒各有风味：一杯泡沫浓厚细腻，带有一股踏实的谷物香；另一杯则清爽轻盈。搭配一份芝士和牛三明治，给这个夜晚留下了相当惬意的收尾。
城迹、历史与街头
早上醒来，吃了便利店买好的意粉、饭团与热豆腐汤，便赶着开启这一天的行程。
我们要去搭乘四桥线，入口就在西梅田站。这条早在 1942 年就已运营的线路，站台呈拱顶结构，两排银白色的金属圆柱向深处延伸。冷调的光线漫射开来，把地面照得干净平整。
上了车，墨绿色的绒布座椅并没有坐满。空气里弥漫着一股像是旧家具本身的木质陈香与清洁剂混合的味道，倒有一种岁月积淀下来的独特气味记忆。
走出地铁站，映入眼帘的是大阪府警察本部大楼。整座建筑以工整的姿态矗立在天空下，两翼是简洁明快的浅色石材，中间陡然内凹，由幽黑的玻璃与格栅交织出一道深邃的弧度，破开了大楼本有的沉重感。这座出自黑川纪章之手的建筑，在我们眼里倒更像是《名侦探柯南》里经常出现的经典场景。
从地铁口走到大阪城公园得穿过一段铺满碎石的平路。跨过宽阔的护城河，便到了大手门。顺着通道往前，经过修道馆和丰国神社，折向樱门，才算真正踏入大阪城的范围。
这座城堡由丰臣秀吉于 1583 年建造，曾是丰臣氏政权的象征。丰臣秀吉过世后，德川家康相继发动「大阪冬之阵」与「大阪夏之阵」，城池失守，丰臣氏自此灰飞烟灭。如今眼前的天守阁是 1931 年重建的产物，沉重的历史兴衰藏在建筑深处，而在我们看来，它永远是服部平次自信介绍家乡时背后的标志景象。
天守阁广场上人并不多。偏侧立着一棵树龄近三百年的巨型古银杏，十月中旬依然郁郁葱葱。不一会儿，空地上来了一个表演杂耍的街头艺人，诙谐的肢体动作逗得围观游客格外热闹。
我们没有去排队登天守阁，而是顺着另一条小径折返离开。往北走，护城河静静躺在脚下，当年的血雨腥风早已褪去，只剩几艘游船在水面上缓缓泛橹。沿阶梯走下几级台阶，在城堡阴影处立着一块不起眼的石碑，标示着二十一岁的丰臣秀赖最终在火海中切腹自尽的地方。
秀赖是丰臣秀吉老来得的独子，当年为了给这个亲生儿子扫清障碍，秀吉逼迫养子秀次退位出家，甚至仍不放心，将秀次的妻妾子女三十九人尽数诛杀，家臣或杀或贬。然而如此血腥的杀伐，终究没能保住丰臣家的江户天下。随着德川家康的崛起，两家彻底决裂，二十一岁的秀赖最终在「大阪夏之阵」的火海中身亡。
顺着北门走出公园，沿途岸边有人安安静静地享受着秋日里这分难得的清凉。快走到路口时，一座红绿灯隐在密密匝匝的树丛背后，茂密的枝叶如同绿色屏障，倒像是红绿灯直接从树林里生长出来的一样，令人联想起吉卜力动画里的奇幻设定。
走出公园重新融进城市里，常常会被这里的建筑与线条吸引。那种极其严谨的秩序，让人觉得自己站在庞大的城市面前显得格外渺小；可再细看，又觉得正是这些微小、重复的元素层层叠叠地累加在一起，才最终拼凑出了眼前的景象。走到外面的大路口，街角大楼数排拱形阳台如蜂巢般重复着；干道两侧高低错落的高楼把天空挤成窄窄的一条；拐进小巷，头顶的电线交错缠绕，水泥电线杆、自动贩卖机与招牌紧紧挨着，在狭窄的空间里挤出丰富的层次。
中之岛与御堂筋的流光
走了大半天路，午餐选在了中之岛一家位于大厦二楼的烤肉店。
两份定食摆满木桌：一份是刚煎好的汉堡肉，沉沉盛在铸铁盘里，将浓郁酱汁淋上去的瞬间，触碰到加热铁盘，顿时汁水四溅、香气剧烈释放；另一份则是切片规整的烤肉定食，牛肉的大理石雪花纹理清晰可见，盘角垫着一截新鲜磨好的山葵。白米饭泛着温润光泽，蘸一点酱汁配着肉香下饭，热气蒸腾，尽是食材最原本的实感。
吃罢午饭，我们沿着中之岛散步。
中之岛是夹在堂岛川与土佐堀川之间的一道狭长沙洲。如今，大阪府立中之岛图书馆、中央公会堂与中之岛美术馆都静静立在岛上。走在街头，恍惚间竟有点像在柏林博物馆岛散步。这里几乎看不到传统的木造建筑，取而代之的是大量带着巴洛克与古典主义风致的欧式老大楼，又与现代极简风格融合在一起。
河岸边的步道被繁茂树冠遮出一片阴凉，路旁散落着鹅卵石形石凳，有人低头翻着手机，有人在河栏边静静看水。风里带着湿润微凉的气息，路边盛开着层层叠叠的黄玫瑰。不远处，一座雕着人群合力托举地球的青铜雕塑静静伫立，背后的银杏树叶已开始泛黄，衬着老建筑凝重的石柱与铁窗，透着一股岁月沉淀出的厚重与从容。
从中之岛重新走回地下，搭乘地铁来到了心斋桥站。
心斋桥站早在 1933 年就已启用，挑高的半圆拱顶上铺满了小巧规整的灰色方砖，一盏盏倒扣白色伞帽般的吊灯顺着站台一字排开，洒下柔和光线。车头带着一抹御堂筋线标志性红色的 21 系列车呼啸着驶入站台，在吞吐完乘客后轰鸣着驶入黑暗，在这一明一暗的节奏与拱顶之下，这是这座城市最熟悉的日常。
升到地面，便直接进入了核心的心斋桥商圈。鬼冢虎门前排着长龙，药妆店里挤满了游客。再往前走便到了道顿堀核心区的戎桥，身后的第六代「跑跑人」霓虹牌依然招揽着来自世界各地的目光。
女朋友去逛街采购，我便沿着御堂筋漫无目的地走走。御堂筋被誉为东方的香榭丽舍大道，1937年全线开通。
沿着这条大道一路往北，最先吸引眼球的是路易威登旗舰店。建筑师青木淳以大阪传统货船「菱垣廻船」为灵感，在楼体外围张起一面面半透明的白色玻璃「船帆」。夜幕降临时，暖黄灯光透过玻璃漫射出来，宛如一艘停泊在大道旁、正乘风破浪的巨大帆船。
没走多远，出现了一栋通体漆黑、冷峻如黑曜石般的高楼——这是安藤忠雄参与设计的 W 酒店。古老南御堂的寺门与瓦顶庭院被巧妙地完整包裹在庞大的黑色钢结构框架之下。底层是香火与飞檐，头顶是潮流与霓虹，古老与现代在这里毫不避讳地撞在一起，展现着大阪独有的包容与野心。
闹市后的小巷与天妇罗小店
避开主街密集的游人，折进心斋桥旁的小巷，喧嚣声顿时被隔在了几米之外。
巷子两侧紧密挤着各色小店。暖黄灯光透过烧肉乌冬店的木格栅窗漫射出来，悬挂着乌冬与烤肉的明亮招牌；和牛汉堡店前排着长龙，食客们捧着汉堡大口咬下，满脸都是踏实的满足。我还看到了杨国福的招牌，往里一看，生意竟然还不错。
正值饭点，我们选了一家藏在巷深处的天妇罗店。推门进去，迎面是一张温暖的木质板前台面。
隔着矮矮的木案，一身干净工作服的厨师神情专注而沉静。面前是一口宽大的深铁锅，滚油呈琥珀般的深色，漂浮着散落的金黄色面衣花。他手里握着一双极长的竹筷，极其轻柔地夹起裹好薄浆的食材滑入油锅。
油锅里发出微小而密集的「沙沙」炸裂声，老师傅微微低着头，眼神全定在锅里的食材上，拿捏着起锅的微妙时机。店堂里弥漫着滚油与炸物的香气，混杂着热气、酒杯碰撞的脆响以及客人开怀的笑声。而在这一片喧闹之中，老师傅的手起手落却依旧平稳如初，手肘举起放下，像是一个指挥奏响关于美食和满足的交响乐，又像在滚油与竹筷间编织着属于他的美食图景。
漫步海游馆与离开
在大阪的最后一天，我们退了房，去体验日本的早餐文化。自十九世纪中叶以来，西洋风尚渗入日常，吃洋食、喝早咖便成了普及的习惯。
我们选了一家常见的连锁咖啡店。正值早餐优惠，点上一杯热拿铁，店家便会附赠一份烤吐司。吐司在铁板上微微煎过，表皮金黄酥脆，内里绵软温热。拿铁奶香醇厚温润，简单的一餐，开启了干净舒爽的清晨。
随后，我们来到了大阪海游馆。
海游馆紧邻大阪港，岸边近九万吨的现代邮轮「千禧名人号」与一艘复古帆船并排停靠。海游馆本身直白地用色彩画出了自然：天蓝代表海洋，砖红代表火山，灰白代表陆地与岩石，以刚劲规整的线条收束视线。
游览海游馆全然没有迷路的顾虑——只需搭乘长梯直达最高层，随后沿着宽阔的螺旋缓坡慢慢踱步往下即可。
这是一条不走回头路的长廊。走廊幽暗安静，一侧是正在阳光下梳理毛发的水獭或疾驰而过的海豚，另一侧则是深沉的大海。水箱上方的光线经过水体层层折射，变得极其柔和，伴着天花板上微弱如星的小灯，恍惚间让人觉得正穿行在静谧的海底。
忽然，眼前光线暗了下来，水箱上方的折射光被一个庞然大物悄无声息地遮挡。
我抬起头，看到一片巨大的白色腹部缓缓滑过天空，简单的线条勾勒出极具美感的弧线，一群小鱼贴在腹下随它一同巡游。鱼鳍伸展的角度，鱼尾摆动的幅度，轻柔平缓得仿佛没有一丝多余的力量。那一刻，站在庞大的巨物阴影下，心中蓦然涌起一种对生命力的敬畏——那是巨物被玻璃禁锢，而玻璃外渺小的人类，却在向这庞大的生命力朝圣。
顺着缓坡往下，水域被分割成一个个独立的生灵画卷。最让人失神的是末端的水母区：漆黑如夜的背景里，水母透明脆弱得宛如梦境。偏偏是这样看似一触即碎的生命，却已经在地球上安然生存了超过五亿年。微弱灯光穿透轻盈的身躯，从外伞到触手产生出极有节奏的传动，像是在永恒夜色里舞蹈的精灵。
一边是缓慢移动、带着温柔与不容置疑气概的鲸鲨，一边是轻盈精巧、在黑暗中明灭翻飞的水母。站在玻璃缸前，时间仿佛都随之慢了下来。
等我们重新走出场馆，太阳已经沉了下去。天空呈现出纯净的宝蓝色，但靠近地平线的边缘散发着微温的暖光。入夜之后海风带上了几分冽意，岸边的棕榈树被吹得树影摇曳。
我们在海边找了一张木椅坐下，对着静谧的海面吹了会儿风。等身上的热气与思绪慢慢沉淀下来，便起身离开了海游馆，搭上前往神户的列车。

大涨价时代的省钱方式
9 月 Mac mini 发布时，受全球闪存供应紧张影响，Mac 产品线经历了一次普遍的价格调整，整体基础售价有所上涨的同时，按单配置的价格也有进一步的提高。

- [让老音箱焕发新生：Home Assistant Connect AUX-2 首发体验](https://sspai.com/post/118921) <sub>11-12 11:12</sub>

玩智能家居这几年，灯光、传感器和开关基本已经靠着 Matter 和 Home Assistant 打通了，唯独多房间音频（Multi-room Audio）还停留在各自为战的阶段。想让客厅的 HomePod、书房的 Sonos 和桌上的传统有源音箱同时放一首歌，往往会被不同品牌之间的生态围墙挡在门外。
为了填上这块拼图，Open Home Foundation（OHF）团队开发了全新的开源音频协议 Sendspin。在 Sendspin 1.0 标准临近发布的时刻，OHF 的商业伙伴 Nabu Casa 今天推出了全新的官方硬件来全力支持这一新的协议：Home Assistant Connect AUX-2。
你可以把它理解成一个专为 Home Assistant 和 Music Assistant 打造的音频接收盒。它的用法很纯粹，就是把家里的传统音箱或老功放接入 Home Assistant，配合 Music Assistant 实现全屋音乐同步。除了基础的无线串流，Nabu Casa 还给它塞进了 PoE 供电、模拟 / 光纤二合一输出和一堆创客扩展口，既照顾了想买来直接用的普通玩家，也给喜欢折腾 ESPHome 的极客留足了空间。
在使用了几周之后，我想聊聊这台小盒子能给国内玩家带来怎样的体验，以及它背后那个叫 Sendspin 的新协议到底解决了什么问题。
为什么有了 AirPlay，我们还需要 Sendspin？
聊硬件之前，绕不开 Connect AUX-2 的核心技术底座 Sendspin。这是由 OHF（也就是 Home Assistant 和 ESPHome 背后的非营利基金会）主导开发的开源多房间音频协议，目前已经推进到 1.0 RC1 阶段。
之所以放着现成的 AirPlay、Google Cast 和 Sonos 不用去「重造轮子」，是因为现有的商业协议太封闭了。之前我和 OHF 主席、Home Assistant 创始人 Paulus Schoutsen 聊起这个项目时他曾提到，如果你只是想自己写个程序接收音频流、做套音乐频谱灯效，或者加个自定义切歌旋钮，在封闭的商业协议里寸步难行。一年前，核心团队在芝加哥开完一场 Matter 闭门会后，在披萨店里拍板决定亲自下场，花了一年时间从头写出了这套免版税的开源协议。
和单纯的手机投屏不同，Sendspin 更像是一套跑在本地局域网里的音频协同系统。它通过在音频包里打上高精度时间戳并实时计算时钟漂移，让家里不同角落的设备先缓冲、再踩着同一个鼓点精准出声，并且能根据设备性能自动协商编码。更实用的是，依靠 Music Assistant 的桥接功能，你并不需要把家里的旧音箱全换掉，现成的 AirPlay 音箱、HomePod、Google Cast 甚至几十块钱的普通蓝牙音箱，都能被直接拉进同一个 Sendspin 群组里，和 AUX-2 一起同步放歌。
与此同时，Sendspin 在底层把发声、音源输入、切歌控制、封面显示和频谱可视化拆成了彼此独立的角色。这意味着你可以让 AUX-2 专心在电视柜上出声，让墙上的中控面板负责切歌和显示专辑封面，再让沙发底下的灯带通过 LedFx 读取音频节奏跟着音乐律动。虽然它目前还不支持杜比等家庭影院环绕声标准，但单就全屋音乐同步和声光联动来说，这套开源方案已经相当能打。
精致耐看，但离线难
回到 Connect AUX-2 本身。拆开包装的第一印象是，它终于不再是我之前体验同类方案的那种裸板，而是真正做出了消费级数码产品的精致感，纯白圆润的机身完美延续了 Nabu Casa 家族式的设计语言。
不过它的机身布局留了一个不大不小的槽点。由于接口被分散布置在了机身左右两侧，不管你把它摆在桌面还是音响架上，网线和音频线都得向左右两边劈叉伸出去，日常理线多少有点逼死强迫症。相比之前可以把线材优雅藏在身后的 Home Assistant Green，或者摆在桌上像个艺术摆件的 Connect ZBT-2，AUX-2 最好还是藏在音箱后面眼不见为净。
好在接口规格足够良心，尤其是那个模拟与数字光纤二合一的 3.5mm 输出口。你不需要进后台改任何开关，只要插上 3.5mm 转方口光纤线，机器就会自动识别并切换成数字光纤输出。我这几周一直拿它搭配宜家新款的 45 厘米 SOLSKYDD 音箱使用，实际听下来最推荐的也是光纤接法。它不仅声音底子更干净，还能彻底避开模拟音频线常见的接触不良和共地电流底噪；如果你手里有更高阶的独立 DAC 或传统功放，也能靠这个数字口无损接驳。
机身上的千兆网口同时支持 PoE 供电，一根网线就能搞定供电和音频传输，对于想把音箱装进吊顶或者弱电箱暗装的玩家来说非常友好。再往旁边看，USB 接口、串口以及国内创客很熟悉的 SEEED Studio Grove 扩展口一应俱全，看得出官方从一开始就没打算只把它当成一个单纯的音频接收器。
半分钟无感配网，把折腾留给有需要的人
如果你家里有 PoE 交换机，AUX-2 的上手过程甚至可以用「无感」来形容。插上网线通电后，Home Assistant 几乎是秒弹新设备发现提示，一路点确认，大概半分钟就能跑完整个初始化流程；就算只用 Wi-Fi，打开手机上的 Home Assistant 伴侣应用多点几步也能轻松搞定。
让我觉得很舒服的一点是，普通用户买回来日常听歌，全程根本不需要去碰 ESPHome Builder。Home Assistant 会像管理普通智能插座一样，直接在后台接管它的设置和固件更新。比起以前在社区里自己找教程、改代码、编译刷固件的野生方案，官方硬件在省心程度上确实不在一个维度。而当你哪天手痒想折腾了，随时可以在 ESPHome 里接管设备，改编码、加传感器、或者接小屏幕，底层权限完全向你敞开。
听感与稳定性：能插网线就别用 Wi-Fi
真正把音乐放起来之后，你能明显感受到 Sendspin 协议目前还在打磨期的痕迹，以及里头那颗 ESP32-S3 芯片的性能限制。最直观的体验是，每次切歌或刚点下播放时，缓冲等待的时间会比预想中长一点；在拉群或者解散多房间音箱组合时，反应速度也要比苹果自家的 AirPlay 慢上半拍。不过音质上没得挑，能达到同价位的前端该有的水平。
但只要缓冲结束、音乐正式响起，它的同步表现就非常稳了。在我家里多台设备同时开播的压力测试下，各个房间的声音对齐得严丝合缝，连续挂着放几个小时也没有出现任何声道漂移或不同步的现象。
这里有个避坑经验是，能插网线就尽量别用 Wi-Fi。国内家用的 2.4GHz 无线环境非常拥挤，用 Wi-Fi 直接推流无损 FLAC 音乐时可能会遇到卡顿，而 ESP32-S3 本身老旧的无线模块更是放大了这个短板。不得不说没能赶上乐鑫新一代芯片大批量出货适配确实有些遗憾。
如果你摆音箱的地方实在没法拉网线，强烈建议进 ESPHome Builder 配置里把带宽占用更低的 Opus 编码打开，无线环境下的流畅度会有立竿见影的改善。只需要在配置文件里加上下面这几行代码就能生效（需要注意 Opus 专利编码仅供个人测试、非商业使用）：
media_source:
  - id: !remove sendspin_source
  - platform: sendspin
    id: sendspin_source
    task_stack_in_psram: true
    static_delay_adjustable: true
    codecs: [OPUS, FLAC, PCM]

What's in 1.100.0 stable
Never type
After 10 years and 5 failed stabilization attempts, the never type is finally stable! This also completes the project goal for this work.
The never type, spelled ! in code, is the canonical uninhabited type. It represents the type of diverging computations – computations which never resolve to any value – where any code that follows is unreachable. Expressions that terminate control flow, such as return, break, and std::process::exit, also have the type !.
Since having a value of the never type is impossible, Rust permits a never-to-any coercion, allowing to turn ! into any other type (this is what distinguishes it from any other uninhabited types). This can be used, for example, to not return a value from one of the branches of a match or an if:
fn mrrrow(option: Option<u32>) {
    let value = match option {
        // `x` has type `u32`
        Some(x) => x,
        // `return` has type `!`, which is then coerced to `u32`,
        // allowing the `match` to pass type checking.
        None => return,
    };
    // ...
}
While the never type could already be used and observed this way, and even named in the return type of functions (-> !), this release allows naming the never type anywhere:
fn infallible_unwrap<T>(res: Result<T, !>) -> T {
    // ^^ writing `Result<_, !>` was not allowed before
    let Ok(v) = res;
    v
}
Additionally this release changes Infallible to be an alias to the never type. That makes all old APIs that used Infallible be compatible with using !. This was the plan ever since the introduction of Infallible and is one of the reasons why the never type stabilization was so hard (waffle gave a talk about some of the troubles of the stabilization).
Unfortunately, to allow changing Infallible, we had to introduce a breaking change. This release changes the "never type fallback" from () to ! in editions before 2024 (i.e. 2015, 2018, and 2021), similarly to what has already been done in edition 2024. This should largely be unnoticeable, but can affect code in some rare cases (for example when ignoring a result of a function returning a generic parameter). Note that this change might also make the compiler detect more code as unreachable.
We tried to minimize the impact of this breaking change as much as possible, by providing future compatibility warnings far in advance and releasing fixes to public crates that have been broken by this. If a dependency is failing due to issues with the never type, consider updating it, as a fix might have already been released for it.

This release brings about the stabilization of the core parts of allocator_api, enabling library authors to define custom allocators that can be used together with certain standard library types - currently Vec and Box. These are enabled through the newly-stabilized Allocator trait.
This is the foundation of the Allocators 1.0 project goal. A lot remains to be done still, including expanding the API surface usable with custom allocators and stabilizing their use on more collections and pointer types; with the core trait and design out of the way though, expect to see more being stabilized soon!
DropGuard: run a closure on every exit path
The Drop trait in Rust makes it possible to run code when a variable goes out of scope, regardless of whether we return, ?, or panic. Drop being a part of types means that in Rust you never have to close a socket.
Implementing Drop can however feel a little inconvenient when all you want is to run some code unconditionally when a function exits. This is why we’re introducing core::mem::DropGuard: a new helper type that runs a closure when dropped.
DropGuard takes two arguments: a variable and a closure. It implements Deref and DerefMut so you can keep working with the variable as normal. But when dropped it runs the closure and consumes the variable.
DropGuard also implements a dismiss method which returns the variable from the guard without running the destructor. This makes it possible to quickly implement all-or-nothing transaction-like APIs with a rollback. Here is an example implementing a parser which uses a guard to roll back mutations in case of failure:
use std::mem::DropGuard;
use std::num::ParseIntError;
/// Attempt to parse all `strings` and push them into `nums`.
/// If parsing any of them fails, `nums` remains unchanged.
fn parse_all(nums: &mut Vec<u32>, strings: &[&str]) -> Result<(), ParseIntError> {
    let len = nums.len();
    let mut nums = DropGuard::new(nums, move |nums| {
        nums.truncate(len);    // ← 1. Reset the vec on failure
    });
    for s in strings {
        nums.push(s.parse()?); // ← 2. If `?` returns an error, roll back
    }
    DropGuard::dismiss(nums);  // ← 3. Parsing successful, dismiss the guard
    Ok(())
}

The Chip Security Act is getting renewed attention following Nvidia CEO Jensen Huang’s resignation and reported affair with an alleged Chinese spy.
Representatives from Nvidia told Illinois representative Bill Foster that it would be technically possible to implement the anti-smuggling measures called for in the Chip Security Act, Foster told MIT Technology Review in an interview on Thursday, even while an industry group claimed they were “potentially infeasible.”
Foster, a Democrat who serves on the Committee on Science, Space, and Technology, is a cosponsor of the act, which would introduce geotracking requirements to verify the location of advanced AI chips in order to prevent their smuggling to China. It is one of three chip-security bills under consideration for inclusion in the Senate’s National Defense Authorization Act, each of which is drawing renewed attention after Nvidia CEO Jensen Huang’s resignation and reported affair with an alleged Chinese spy.
When the Chip Security Act was introduced, in May 2025, lawmakers said the technology to implement it existed, something Nvidia has not publicly confirmed. In March 2026, the Semiconductor Industry Association, of which Nvidia is a member, explicitly opposed the bill and wrote that its mandates for chip tracking were “new, untested, and potentially infeasible.”
But privately, Nvidia representatives working with Foster told the lawmaker that the company could implement them.
“They never put anything in writing,” Foster says, but during technical discussions on the possibility of such safeguards, their reaction was “yeah, of course we can do this.” This private acknowledgment to Foster goes further than anything Nvidia has previously made public.
Other technology Nvidia has built for its customers suggests that the company can indeed offer accurate tracking of its chips’ locations. In December 2025, for example, it announced a new tool called Fleet Intelligence that would allow customers to monitor how its advanced chips were performing across different data center locations. In doing so, the tool could indicate which country chips were in, Nvidia confirmed to Reuters, but the company would not elaborate on whether this technology could be used to prevent smuggling.
Nvidia did not respond to requests for comment or confirmation of Foster’s characterization.
In early October, when lawmakers were reportedly increasingly concerned about Nvidia’s role in smuggling, MIT Technology Review asked the company if Fleet Intelligence could be used to prevent the practice. It declined to answer directly, instead sending a statement: “Governments and media have found insignificant diversion of controlled US products—a drop in the bucket compared to the ocean of domestic compute China already has.”
The recent fallout at Nvidia involves a number of people and companies alleged to be involved in chip smuggling. Alice Huang, with whom Jensen Huang reportedly had an affair, runs Megaspeed, a Singaporean firm now under investigation for smuggling advanced GPUs to China. A US Commerce Department inquiry into the company was reportedly halted after invention by Nvidia. Megaspeed reportedly bought chips from Supermicro, a company that packages Nvidia’s chips onto servers.
The Chip Security Act as drafted would require a mechanism to track the locations of chips, either by inspections of facilities, attestations by companies, or ping-based location mechanisms. The ping-based technique, the hardest option to circumvent, would require the GPU to send a signal of its location when it comes online. In September, the Center for Security and Emerging Technology found it would be the most cost-effective option.
Foster said he did not ask Nvidia’s representatives why they weren’t voluntarily adopting such chip-tracking tools if they could technically do so.

The new rule would require licenses to operate advanced GPUs, and before a GPU could connect, its valid license would need to be verified.
In the meantime, the controversy at Nvidia, Foster says, has fueled support among his colleagues for the rules in the bill: “There will be a lot of political pressure, in the wake of everything that’s happened, on the companies to actually do a very good job of the geographic validation of where the chip actually is.”

What to know about this year’s UN climate talks
Climate finance and fossil fuels top the formal agenda at COP31.
It’s that time of year again: Thousands of delegates, lobbyists, and journalists are gathered for the annual UN climate talks, taking place this time in Antalya, Turkey.
COP31 officially kicked off on November 8, marking the beginning of negotiations on one of the biggest stages of the climate world. Turkey and Australia are cohosting this year’s talks, which are scheduled to wrap up on November 20.
This annual gathering can often serve as an indicator of where the world stands on addressing and adapting to the climate crisis. And this year’s talks are sure to be a doozy—expect a lot of back and forth on fossil fuels and climate finance in particular. Here’s what you should know about COP31.
In recent years, the tension always feels high when COP rolls around. (COP stands for “Conference of the Parties.”) But this year feels especially charged: The world is still grappling with the ongoing war in Iran, which has disrupted the Middle East and sent economic shock waves around the world as energy prices have spiked.
This year’s COP will be the second without a formal delegation from the US. President Trump formally withdrew the country from the Paris Agreement earlier this year and is in the process of withdrawing from the UN Framework Committee on Climate Change. That’s the treaty that allows formal participation in negotiations.
Meanwhile, things aren’t looking good for the Paris Agreement, which was established at UN climate talks 11 years ago, setting a goal of limiting warming to 1.5 °C over preindustrial levels. In a report published in September, the UN Environment Program acknowledged that global warming is set to exceed that 1.5 °C goal, “likely within the next few years.”
So as climate talks kick off, there’s an obvious, urgent question looming about how to quickly cut emissions to limit warming. There’s also the major issue of how to pay for efforts to address emissions and to help a warming world endure the inevitable damage.
Two years ago, talks ended in a goal of mobilizing $300 billion per year by 2035 to help pay to reduce emissions and adapt to climate change. (Rich nations provided $136.7 billion in 2024, according to the Organization for Economic Cooperation and Development.) And last year, the COP30 agreement included a goal of tripling the money for adaptation over that period. (Such funding has been quite flat over the past few years.)
The world got a tragic reminder of just how high the stakes are earlier this year, when a glacier collapse caused devastating flooding in the Himalayas. The flood killed approximately 1,500 people, left over 5,000 missing, and caused nearly $5 billion in damage. The UN loss and damages fund committed $20 million to helping Nepal recover (less than 1% of the total estimated cost to the country).
Another key trend to watch is how the formal negotiations engage with the topic of fossil fuels. Three years ago, the final agreement text explicitly called for a transition away from them. But it felt as if things took a step back last year, when the final agreement didn’t even mention the phrase “fossil fuels” once. This will be an interesting conversation, especially because cohosts Turkey and Australia have both faced criticism over their relationships with these fuels—Australia is a major exporter of coal and natural gas, and Turkey’s grid relies heavily on fossil fuels, including coal.
Outside the formal negotiations, COP31 president Murat Kurum, Turkey’s environment minister, is spearheading a side agenda, including two informal initiatives that will be worth watching. These wouldn’t be part of the official agreement text, but countries could sign on to signal support.
One is a pledge to make AI more sustainable; this is almost comically squishy, even as voluntary COP pledges go. The text includes explicit wording that it creates no new obligations for countries, so don’t expect anything resembling enforcement there.
The COP leadership is also pushing to make electricity a larger part of member countries’ energy use. Today, only about 23% of global energy is used in the form of electricity. Fossil fuels, like gasoline in vehicles or natural gas for heating, make up the bulk of the rest. Shifting to more electricity use, and relying on cleaner sources for that electricity, could help drive down emissions. The new pledge’s target is for electricity to make up 35% of total energy consumption by 2035.
With leadership billing this as an “implementation COP,” it would be great to see some real, tangible progress on the global challenge of addressing climate change. I’m not expecting anything groundbreaking, but we’ll be tuned in to see what the final agreement shapes up to be.

When potential mates are scarce, some types of seaweed can take reproduction into their own hands, so to speak, according to a study published on 12 November in PLoS Biology1.
“Our findings highlight that kelp are even more flexible in their reproduction than previously appreciated,” says Daniel Liesner, a marine biologist at the GEOMAR Helmholtz Centre for Ocean Research Kiel in Germany.
The brown algae, which provide food and shelter for marine life, “are really weird, they do all kinds of stuff”, says Reina Veenhof, an ecologist at the Scottish Association for Marine Science in Oban, UK. What’s interesting about the study is that it helps to explain how changes in gene activity allow kelp to reproduce in different ways, she says.
Developmental flexibility
Scientists know that kelp can reproduce asexually, with unfertilized eggs developing into offspring. This process was even documented for one male strain2 — the PLoS Biology study shows that this wasn’t a one-off.
The ability of male reproductive cells to develop without fertilization is striking, says Olivier De Clerck, a seaweed biologist at Ghent University in Belgium. This is because, unlike eggs, sperm cells are small and have few resources to support development.
The researchers focused on Laminaria pallida, a species found along the Atlantic coasts of South Africa and Namibia. In the wild, 523 individual kelp showed no clear evidence of asexual reproduction.
By contrast, both microscopic male and female L. pallida grown in separate laboratory dishes could produce offspring without fertilization. During asexual reproduction, the gene expression in males changed, making them more similar to females.
However, when they were lab-grown in the presence of a member of the opposite sex, kelp favoured sexual reproduction, suggesting they can detect nearby partners through chemical signals.
