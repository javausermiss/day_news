AG-UI is an open, lightweight, event-based protocol that standardizes how AI agents connect to user-facing applications.
Agents don't fit the request/response model. They stream tokens, call tools mid-response, update shared state, pause for a human, and spawn subagents, and every framework does it differently. AG-UI replaces that custom wiring with one bi-directional event stream: the agent emits typed events, and any client can render them, no matter which framework built the agent. The same agent can power a web app, a mobile app, a terminal, or Slack.
Important
AG-UI 1.0 is here. The protocol now has a stable, frozen specification backed by a JSON Schema, and the TypeScript, Python, and .NET SDKs are generated from it. 1.0 is backwards compatible in both directions: 0.x agents work with 1.0 clients and vice versa. What changed → · Migration guide →

Or speak the protocol directly: a 30-line agent server and client
An AG-UI agent is any HTTP endpoint that accepts a RunAgentInput and streams events back. No API keys needed for this one.
1. The agent (Python). Requires Python 3.9+.
pip install ag-ui-protocol fastapi uvicorn# server.py
import uuid
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from ag_ui.core import (
    PROTOCOL_VERSION,
    RunAgentInput,
    RunStartedEvent,
    RunFinishedEvent,
    TextMessageStartEvent,
    TextMessageContentEvent,
    TextMessageEndEvent,
)
from ag_ui.encoder import EventEncoder
app = FastAPI()
@app.post("/")
async def run_agent(input_data: RunAgentInput, request: Request):
    encoder = EventEncoder(accept=request.headers.get("accept"))
    async def events():
        yield encoder.encode(RunStartedEvent(
            thread_id=input_data.thread_id,
            run_id=input_data.run_id,
            protocol_version=PROTOCOL_VERSION,
        ))
        message_id = str(uuid.uuid4())
        yield encoder.encode(TextMessageStartEvent(message_id=message_id, role="assistant"))
        for chunk in ["Hello ", "from ", "AG-UI!"]:
            yield encoder.encode(TextMessageContentEvent(message_id=message_id, delta=chunk))
        yield encoder.encode(TextMessageEndEvent(message_id=message_id))
        yield encoder.encode(RunFinishedEvent(thread_id=input_data.thread_id, run_id=input_data.run_id))
    return StreamingResponse(events(), media_type=encoder.get_content_type())uvicorn server:app --port 8000

Your app starts a run by sending the agent a single RunAgentInput: the conversation, the tools the frontend offers, shared state, and context. The agent answers with a stream of typed events from eight families: run lifecycle, text messages, tool calls, state, reasoning, activity, subagents, and custom events (full list). It provides Office editing, calculation, collaboration, and file processing for people and existing agents, using your data and permissions. The product family covers spreadsheets, documents, presentations, relational tables, canvases, and PDFs.
Univer Office SDK has three parts:
- Web SDK is the foundation: content models, editing, rendering, formula calculation, and Facade APIs (application-facing APIs). Compose its plugins into an embedded editor or your own Office application, and reuse the content models, commands, and calculation for Headless processing without an interactive editor.
- Server SDK adds backend services for real-time collaboration, edit history, and Office file import and export.
- AI SDK connects Office capabilities to existing agents and workflows, with content tools, execution, and review integrations.
This repository provides the Web SDK's core architecture and engine implementations under Apache-2.0: content models and snapshot formats, plugin and dependency management, the command system, formula and rendering engines, Facade APIs, UI foundation, and Sheets and Docs editing capabilities. Why Cerebras is advantaged for decode
An inference request has two main stages. Prompt processing, known as prefill, processes the input and produces intermediate model state. There are many ways to split the inference workload, including draft–target and attention–FFN among others, but separating prefill from decode is uniquely advantageous when the goal is highly interactive inference.

Abstract
Language models typically increase per-token computation through deeper or looped layers and latent reasoning steps, while richer residual connections improve information flow across layers. We instead increase computational capacity: the number of active computational states a model maintains. We introduce the Lattice of Latents, a set of per-layer horizontal latent streams that run recurrently along time, alongside the vertical residual stream that flows through depth. Like hyper-connections, mHC, and attention or value residuals, the Lattice enhances the residual stream, but rather than adding or rerouting residual pathways through depth, it provides companion computational states that persist across tokens. Unlike hybrid Transformer–SSM architectures, whose recurrent states primarily serve as internal memory for sequence mixing, these latents directly condition the vertical stream’s attention, KV-cache writes, MLP computation, and decoding. These gains extend across architectural variants. The Lattice composes with prior residual-stream enhancements: with hyper-connections and input residuals, it lowers validation perplexity from 15.41 (base Transformer) and 14.22 (Transformer with same enhancements) to 13.61. On Gated DeltaNet, Mamba-2, Triadic GDN, and GDN–Mamba-2 hybrids, it improves perplexity at every tested native state size, with Lattice-GDN & Lattice-Triadic-GDN variants outperforming pure baselines with 4× larger native states. These results identify persistent per-layer state as a complementary axis for scaling language-model computation.

一直以来，我都希望能找到一台画质和便携性足够平衡的设备作为我的随身胶片机，我对它最大的期望就是可以轻松地拿在手里或者放进口袋里。在这样的条件下，理光 GR 显然该是首先被考虑的，但如今价格虚高的它显然不是一个好选择。于是，在过去一段时间内，我的随身胶片相机都是 Olympus Pen EED 这台半格相机。
其实我对 Pen EED 非常满意，无论是造型、操控上都无可挑剔，但半格相机最大的问题就是一卷胶卷要花很长时间才能拍完。于是，我把目光转向曾经种草过但并未下定决心入手的 Konica C35 EF3。
我最开始是被 C35 EF 的颜值所吸引的，在黑色相机中一抹橙红色的点缀真的深得我心。但 C35 EF 的体积还是有些不够便携，再加上这个体积依然只能使用估焦也是一大问题。而它的后续机型 C35 EF3 则将体积进一步缩小到巴掌大小，满足了我对便携性的要求。再加上它本身镜头的素质不差，很适合作为随身携带的全画幅胶片机来使用。
虽然型号一样，但 C35 EF3 其实有 4 种版本，分别是 1981 年的日产初版、1985 年后的日产改进版、1986 年北京照相机厂引进的国产版，以及后续采用国产主控芯片的国产改进版。
先说日版的两款，1981 年初版采用了 5 片 4 组镜头，而改进版则是 4 片 3 组镜头。改进版还采用了新的电路控制，与初版的区别主要体现在初版在使用自拍功能时，需要按下快门才能启动，而改进版只需要拨动自拍按钮即可启动，并且快门速度的范围也从初版的 1/60s–1/500s 提升到了 1/30s–1/800s。从外观上看，你可以观察设备底部的电池仓是否有铆钉，有铆钉的为初版，无铆钉的为改进版。
国产版与日产版最大的区别，便是胶片仓内没有 Sakura & Konica 的贴纸。国产初版与日产改进版同样采用了 4 片 3 组镜头 + 新型电路控制。而国产改进版则是将机身材料大幅国产化后的版本，最大的区别是正面 C35 EF3 的字样没有采用电镀工艺。
我更推荐入手日产初版或日产改进版，我这台是日产改进版，除了闪光充能指示灯时好时坏以外，并没有太大的问题。
C35 EF3 采用的是全自动曝光 + 估焦的模式，提供了 4 个对焦档位，分别对应 1m、1.5m、3m 和无穷远。机身只需要 2 节 5 号电池供电，在不装入电池的情况下无法触发快门。
我认为 C35 EF3 有一个很好的设计，便是将测光模块放在了镜头上，在光线不足的情况下，取景窗旁的 LED 灯会闪烁提醒。这个设计还有一个很大的作用，就是在没摘镜头盖的时候可以起到提醒作用。对于旁轴相机来说，镜头盖提醒真的很重要。
在入手之后，我试着带它出去拍了一卷照片。光从拍摄体验上来说，它会给人一种非常流畅的拍摄体验，和 Pen EED 的自动档一样，只需要大致估计距离，然后把对焦环旋转到对应的档位，然后构图拍摄即可。
虽然 C35 EF3 的镜头表现力还不错，可或许是因为全画幅的原因，估焦所带来的影响会比 Pen EED 这种半格相机要大。在 Pen EED 上，即便估焦没那么准，但冲扫出来之后的效果还是不错的。而 C35 EF3 没对上焦所带来的模糊感则会更明显。
总的来说，我对这台 C35 EF3 还是非常满意的。但我在拍摄中遇到过一个小问题，在机身计数指示器达到 36 之后，如果你像我一样想着再试着过片「偷几张」的话，可能会导致指示器无法复原。但好在它本身拆解维修并不算难，拆开来手动复位一下就行了。

- [TDS REVIEW｜Bose 有线消噪耳塞体验](https://sspai.com/post/118976) <sub>11-17 15:00</sub>

这篇文章是 TDS Studio 在少数派上的第 35 篇文章，依然是全平台首发。
早先我们评价过绯乐的虹，当时在评论区曾经有一些读者好奇它和 Bose QC20 的区别。有线降噪入耳耳机，在 TWS 时代到来之前曾经是一个非常主流的降噪耳机形态，无论是索尼、Bose 这种当下依然有成熟降噪产品的厂商，还是铁三角、AKG 等传统音频厂商，都有过这类产品。有线降噪耳塞其实在当下解码电路小型化极其常见的市场没有很多新产品推出反而是让我们觉得有点可惜的事情。这也是我们看到 Bose 要重新推出这类形态产品的消息时有些将信将疑的原因之一，毕竟 Bose 属于这些厂商里面对于「集成化」其实并不是那么热衷的一个。国行价格出炉之后，我们首发购入，结果嘛…… 算是情理之中的失望居多。
包装与配件 | Package & Accessories
非常扁平化的包装，总体的设计跟 Bose 的真无线系列差不多。内部配件包含三对耳套和两组耳翼，耳套的入耳深度非常浅，且在出音口带有滤网，与导管接触部分有专门的硬质固定环。
设计、佩戴表现与声学结构 | Design, Fit & Acoustic Structure
首发有三种颜色，分别是有蓝色点缀的黑、搭配浅绿色的白和我们手上这条「沁凉薄荷」——其实也就是深蓝绿色和浅蓝色的拼色，线材部分偏深。通体亮面塑料，做工没有什么大问题，就是常规塑料壳入耳耳机的样子。腔体体积适中，相较于 Bose QC Ultra 真无线产品要更小一些，也比我们印象里的 QC20 更加小巧。降噪麦克风的开孔面积也比 QC20 要更小，佩戴好之后几乎看不出来与传统 USB-C 耳塞有何区别。
腔体内侧的造型跟过去 QC20 那种明显分出前后腔的做法并不相同，甚至更像当下的 Bose TWS 系列，有一定的耳甲腔突起，取消了全包围式的鲨鱼鳍。Bose 有线消噪耳塞选择了分体式鲨鱼鳍和浅入耳耳套的搭配，鲨鱼鳍的可更换部分只有伸出来的耳翼，进而对于某些耳廓偏大的用户来说，可能包装这些自带配件都难以让它接触你的耳甲艇上边缘。
在后来邀请其他朋友试戴时又发现一类问题，在此感谢 F 老师协助——原版鲨鱼鳍其实由于耳翼结构是与耳套、前腔外包层几乎在统一平面上，也更容易在浅佩戴的情况下使得耳翼起作用。而 Bose 有线消噪耳塞将耳翼做成独立件之后，位置发生改变，加上相对扁平化的前腔，小耳廓用户可能会出现前腔耦合问题而导致耳翼整体露在耳廓平面外，难以起到实质作用…… 总之算是之前 Bose 耳机很少见的新问题。除去这些，耳机本体倒是佩戴相当舒服，除非是耳甲腔偏窄的，基本上都能够比较舒服、牢固地长时间佩戴。腔体有一定厚度，不建议侧躺使用。
导管属于非常短的类型，但常规的入耳耳机耳套还是能够固定上去。标称支持 IPX4 防泼溅，用于轻度的运动出汗或者小雨场景还没什么问题。
降噪/通透/通话 | ANC, Transparency & Call
Bose 有线消噪耳塞的被动隔音其实只能算是中规中矩，这一点也与比较浅的入耳深度和腔体开孔有关，我们对比下来在耦合良好的情况下比大鲨们还是高频泄漏会多一点，但在直插式浅入耳中算是还不错的。打开主动降噪之后，它对于稳定低频噪音的抑制还是相当明显的，甚至能够来到 Skyline Level 的水准上，中频也有一定的深度，人声中下盘的抑制比较明显，但音头仍有保留，频宽覆盖能力算是这个价位还不错，跟中价位几个优秀的降噪 TWS 比起来没有级差。相较于大鲨三代和四代，你也可以获得稍低的耳压感。仅从降噪这一件事情上，Bose 有线消噪耳塞做得还是符合 Bose 名号的，轻微的底噪也大多数情况下不会是个问题。
抗风噪方面，开启降噪状态下来自正面和侧面的风源会产生一些风噪干扰，但风噪频段不算高，背对风源则几乎没有此类问题。
通透模式是我们觉得比较惊讶的一项，此前 Bose 的耳塞产品大多对于通透模式不太重视，但这条有线消噪耳塞会有比较自然的环境音还原，在两端虽然还是有一点衰减，但已经能够接近于第一档的水平了。而且佩戴者自己的声音也不会过于偏闷，常规音量的交流对话无碍。通透模式下的风噪影响较弱。
通话方面，由于通话麦克风位于分线器位置，所以收音位置理论上是要比常见的线控模块更低一些，但没想到实际的收音响度和清晰度都还是不错的。不过，相较于我们经常用于举例的 EarPods USB-C 版本，它的音色会偏闷一些，且更像是过了一刺压缩器之后的感觉，动态较低。从语音通话角度倒是好事，毕竟人声更「响」。
总体来说，Bose 有线消噪耳塞的降噪相关各项都保持了 Bose 降噪产品的一贯优势，算是目前有线入耳式降噪品类里综合水平最好的，通透模式的表现尤其让人惊喜。但是，相较于部分降噪 TWS 旗舰来说，它缺少一些自适应能力和模式选项，降噪实感也跟顶尖的几个新产品有距离。考虑到售价，如果你就需要一条有线降噪在长途飞行之类的场景使用，它是可用的，也相比 QC20 省去了一些充电烦恼。它可以进入 TDS 降噪综合能力金字塔 In-Ear Skyline Level，处在此档中下层。
操作与配置 | Control & Driver
Bose 有线消噪耳塞的操控主要依靠于分线器处的三键式线控，默认定义是一组音量控制加上居中的多功能键，单击播放控制、双击/三击切歌、长按切换降噪模式。耳机内的语音提示清晰度还是不错的，跟自家的 TWS 系列类似。不过需要注意的是，Bose 有线消噪耳塞并不支持 Bose app，没有办法进行操作自定义和固件升级等操作。额外再提一句，这条线并不算柔软，再结合直插式入耳的特性，你会觉得它的听诊器效应还是比较明显的。
单元信息完全未知，经典 Bose 操作，总之作为 USB-C 耳机，我们还是可以看一些这东西的采样参数。它支持到 96kHz / 24bit 的 PCM 解码和 48kHz / 16bit 的麦克风输入 ADC，属于 USB-C 数字耳机里比较基础的配置了。
过往的有线降噪耳塞通常是有两种降噪功能的实现方式，其一是把降噪处理相关电路内置到手机或者播放器等设备中，耳机本体搭载降噪拾音麦克风，通过在模拟音频接口上增加导体极数来将收的音频传回手机，手机处理后传回耳机单元。这种方式需要依靠手机端和耳机端都有硬件层面的支持，接口也需要特殊化，比如索尼的数字降噪系列（MDR-NC31、NC750 等）就是这样，采用了五极端子的 3.5mm 音频口——自然这种耳机如果想要连接其他设备使用时就需要再拖一根转接线。
另一种就是降噪处理电路和电源都外置，在 USB-C 口有线耳塞时代以前通常解决方法都是在 3.5mm 接口之前的线材上，放一块搭载电池和电路的模块，所有的处理和电源都与手机、播放器无关，耳机与手机之间的关系和传统耳机一样。如 Bose QC20、索尼 MDR-EX750NA 等就是这样的处理方法。Bose 有线消噪耳塞的方式跟后者比较类似，只是现在集成度提高、功耗降低之后，USB-C 从手机取电也能够负担它的降噪处理和音频解码了。
声音主观描述 | Sound Description
基于 USB-C 驱动，原始耳套和耳翼。
低频量感适中，厚度和饱满度都比较少，弹性一般，下潜一般。收放速度不算快，保留了一定的残响。氛围烘托的晕染感稍多，浓郁度不足。Bose 有线消噪耳塞的低频是比较散、比较少的，好处是不会掩蔽掉人声、不轰头，但问题就是没质感、没能量、没烘托。基音位于中下盘的乐器不会有明显的前倾。
中频，人声保持了一定的距离，不会过于贴脸，口型大小适中，精致程度在上盘有一些强调，但下盘不稳。对于人声的质感和线条都表现得不算好，某种程度上也算没有什么倾向了吧…… 厚度不高，线条比较模糊但一些细节又会不自然地突出。对于男女声之间倾向性不算明显，适合的声线需要比较扎实，同时又不能过于强调厚度。音色有一些上盘的处理，听上去偏细偏刺，但又并非为了抓耳感优化。喉音位置过于靠上，气声不算丰富，听上去比较虚（终于我也用了一次「虚」这个形容词）。口水声等有所前倾，齿音也有感知，不会磨平或者整体压制。人声频段的通透度一般，有可闻的人为增亮。
乐器方面，大部分乐器也还是比较难评的状态，很难说得上什么质感，线条则处在凝聚度一般而有一些突出的状态。弦乐器中，小提琴、吉他、中提琴等的厚度较少，拉拨弦细节量在这价位属于偏少的，有轻度的突出。大提琴的形体感比较模糊，在空间里比例较小。铜管类的气势感很弱，需要亮度的小号等有稍突出的亮感（但并非厚度高）。木管类的空气感还行，自然度中规中矩。乐器的泛音比较干，同时丰富程度也比较落后。打击乐器中，Kick 的存在感不强，Snare 收得稍快，镲片类的亮度较高，有轻度的金属感和刺激感保留。
高频总体亮度中规中矩，但有两处比较突出的峰，显得刺激感并不少。极高频延伸非常一般，滚降稍早，但不至于过快而已。
声场表现是 Bose 有线消噪耳塞试图做些不同的地方，你能感知到大部分中频结像都跟耳朵拉开一些距离，横纵都能拉开一些距离，但不够充实、横纵也并非完全一致，加上略有弥散的边缘，你会觉得这个空间比较空。结合中规中矩的「高度感」，Bose 有线消噪耳塞呈现的是略呈扁椭球状的空间。人声与乐器之间的分离度一般，整体感因为高频峰的缘故表现不算好。解析能力很一般，总体信息量在六百元档属于完全落后于国产近几年有线耳塞，仅从有线 USB-C 通话耳塞这个非常窄的角度来看也没有感觉到单元素质能全方位比 IER-EX15C、CX80S 等好，还有一些不自然的「解析感」突出。动态不行，瞬态尚可。
总结评价 | Overall Impression
总体来看，我们认为 Bose 有线消噪耳塞的降噪表现还是可以的，虽然不能说比中价位手机厂 TWS 新品明显更好，但也没有级差，通透还普遍更好一点，加上有线耳塞的通话收音优势，这些东西没有什么苛责之处。我们主要要吐槽的反而是作为耳机最核心的声音和佩戴，声音素质同价位较差这点我们早已有预期，但调音如此古怪是我们没有完全预料到的。看上去似乎调节更自由的耳翼并没有实现更好的耳廓兼容能力，腔体造型也对于耳甲腔偏小的用户颇不友好。除非你就是需要一条长途飞行避免电量焦虑，同时就是不喜欢头戴降噪耳机，那么 Bose 有线消噪耳塞都不是这价位能让你掏钱包的产品。如果没有堪用的降噪，甚至它会成为我们当下少有会给出的 II 级评分案例。

缘起
从澳大利亚回国的时候，我把我用了两年的台式机拆开，扔掉带不走的组件（例如电源和机箱）放到了行李里面。只是，回国之后一直懒得把它装回去。最近终于算是有点空闲（和需求）把这台电脑装了回去。
硬件上没什么问题——当然如果你非要感叹这台带有 Ryzen 5500 和 RTX 3060、后期还加配了 32GB 内存的电脑，如今极有可能身价不菲的话，那确实也算一个「问题」。反倒是在操作系统上绕了点弯路。
这个带过来的电脑之前安装的是 NixOS。我对它的评价是，如果你是真的要用它来写代码，那么 NixOS 是一个十分 robust 的操作系统。它通过配置文件和对这个配置文件的版本管理，来实现系统的一致性和设置可复现性，这一点我挺喜欢。只是考虑到后期我需要做视频频道「游麻地」，而且当时我们的第一期视频工程还被「押」在了剪映，而剪映并不支持 Linux 上运行（明明它是 Electron 程序，却没有做全平台跨端，实在讽刺），所以我直接将整个机器重装成了 Windows 11。
麻烦也因此而来。首先是我个人的「审美洁癖」，即 Windows 的字体渲染实在是令人不敢恭维。虽然微软已经为 Windows 打了包括但不限于 ClearType 和微软雅黑等的补丁，但 Windows 上的字体渲染依然呈现一种「狗啃」一般的字体边缘。在高 DPI 甚至非 RGB 排列的屏幕上，ClearType 这种在低 DPI 的 LCD 屏幕上的「补丁」显然已不再适合。而只要为同一台显示器连接安装有 KDE Plasma 的电脑，渲染出来的文字马上就会获得质的飞跃：清晰锐利，如同打印在纸本上。
更重要的问题是，微软逐渐开始在 Windows 上「作死」：最开始是 Windows Updates 强制自动更新、裁掉 QA 再让用户免费做 QA，再后来是强行在系统里塞入 Microsoft Copilot 和 Microsoft Edge 等等用户根本用不上的功能。作为一个在买电脑里特意加钱上正版 Windows 系统的我来说，是实打实的如鲠在喉。
如果单纯只是这样，那其实也没有必要非得切换 Linux（凑合过呗，还能离咋地.jpg）。社区里也有像 Atlas OS 这种为 Windows「瘦身」（debloating）的工具，过去两年里我确实会在自己使用 Windows 期间额外加装这个工具。但是这次遇到了一些实打实的问题：Atlas OS 的 0.5.0 版本的 Playbook 会令 AppX 组件和 Microsoft Store 出现问题，致使你无法正常安装一些通过 AppX 打包、或是通过 Microsoft Store 分发的软件。我的另一台 Windows 设备是 ROG Ally X，华硕甚至将奥创中心（Armoury Crate）的更新和分发放到了 Microsoft Store 中，这就导致安装 AtlasOS 之后我根本没法儿再安装奥创中心。另外， 1Password 和 Dia 等软件都是通过这个格式分发的，自然也是装不了。
这个问题导致我在一天之内反反复复重装了六次系统。而且，Atlas OS 的 Playbook 最后更新日期是去年，这个问题也发生在去年，甚至写这篇文章的现在，26H2 更新包发布已有一段时间，而 Atlas OS 至今没有正式支持。这也在某种程度上证明 Atlas OS 这种方案在理论上并不能长期持续依赖。
所以，在剪映上结束上一轮工程之后，我开始着手将自己的电脑（再一次）重装成 Linux。
NixOS 很好，但……
我在之前提过，我从澳洲回国之前，为这台电脑安装的是 NixOS。于我而言，配置文件式设置除了有传统的一些优点之外，你还可以直接地把配置文件扔给 LLM 帮忙解决；即使改坏了，直接重启一下然后选择上一版配置文件就又是一条好汉了。加上我之前重装 Windows 之前，已经将之前使用的 NixOS 配置备份过一轮，我觉得不应该会出现问题。
直到我发现，NixOS 的 Live CD 花了接近两个小时才写完文件……
一开始我没有反应过来是怎么回事，而且我心想，反正只是慢不是完全动不了（虽然多数时候它确实表现得动不了），也没啥问题。直到后面我打开 Live CD 环境的网络面板——好家伙，安装程序一直在访问 Nix 包管理器，而且速度只有惊人的 100 KB/s 上下！
进了系统之后，我甚至没有考虑第一时间将原先备份出来的配置文件恢复回去，因为原先的配置中没有安装任何代理软件，在内地这个特殊网络环境下，我很难说恢复原有配置得多长时间。后来我在单独安装代理软件时，发现 NixOS 的「everything in configuration」的逻辑既是好事、同时也挖了大坑。由于代理配置在 Linux 上可能有一万种配置地址，包括 KDE Plasma 的设置和 ~/.config/environment.d 等目录都有对应的配置项目，而且不同应用所使用的设置也不一样。再配合 NixOS 的配置文件的逻辑（也有可能是我对配置文件不熟悉），导致每改一次配置文件就得干等几十分钟，总之就是吃了一个大瘪。
选择下一个发行版
在不太愉快而且最终失败的配置之后，我短暂回到了 Windows，打算寻找下一个发行版。我稍微梳理了一下各个发行版的专长和短板之后，我决定试试 Bazzite。
Bazzite 是一款将流畅运行 Windows 游戏作为目标的 Linux 发行版；同时，它具有「默认沙盒」的特性，通过内置改版 RPM 安装的二进制默认会进入沙盒环境中。但更重要的是，它的安装程序默认会携带显卡驱动安装包。虽然我这么多年使用 Linux 还暂时没遇到显卡驱动问题（也有可能我没有太多「开源软件洁癖」，直接点「允许闭源驱动」一把梭），但至少它能内置也能省下不少事。
（顺便提一嘴，虽然很不想这么说，但是感谢 AI 大浪潮逼着老黄为 Nvidia 显卡推出了开源驱动，这在某种程度上也省了不少事。）
对独显、游戏等场景做专门优化，对我而言也有一点额外的好处：我希望在 Linux 上使用 DaVinci Resolve 剪辑视频，对于独显的优化那自然是多多益善。社区还有一个专门的 davincibox 项目，让 DaVinci Resolve 在 Bazzite 上能够十分流畅地运行。（也有一些尚可接受的妥协……之后我会提到。）
说干就干，直接下载 ISO，拷贝到已经安装好 MultiOS-USB 的优盘上，然后直接从优盘启动即可。说句实话，多数 Linux 发行版的安装已经不像多年以前「蛋糕要自己烤」这样麻烦，Live CD 中已经内置了一个十分优雅而且简洁的安装向导。做好一些初始化设置之后，离线安装（离线是为了避免它又在没有额外设置的前提下访问包管理器镜像）就行。
即使是离线安装 Bazzite，安装流程中也会卡在「软件安装」这个步骤很长时间。如果你也遇到了一样的情况，请坐和放宽，耐心等待安装完成。
进系统之后的第一件事就是配置代理，以及 1Password 等基础软件（没这玩意我连登帐户我都登不上去）。这些安装好之后，就可以让 LLM 来帮我代劳很多东西了。
面向 LLM 的 Linux 配置方案
作为一个「text in, text out」为底层逻辑的操作系统，Linux 天生很适合让 LLM 来做很多设置工作。无论是什么指令，只要 LLM 可以读写终端输入，它就能帮你做大多数配置。也就是说，只要我把代理设置做好了（嘘……），我就可以请 ChatGPT 这类 LLM 来帮我解决绝大部分问题——只需要时常输入一下 sudo 密码即可。
说来，我在很久之前就提到过，以后的电脑，有可能是一种「面向 LLM」的。即，你只需要在电脑上输入要干嘛，然后 LLM 获得授权之后直接帮你改就万事大吉。这对于 Linux 这种操作系统而言可能是一种重大利好，毕竟，多数人对 Linux 敬而远之的重要原因，就是 TUI 实在是太晦涩了。
扯远了。总之，在整个设置过程中，LLM 的确帮了不少的忙。例如，帮我将浏览器和 1Password 安装到沙盒之外——多数 Linux 中的沙盒实现都是完全禁止应用程序之间互相沟通的，这让像 1Password app 和浏览器内的密码填充扩展之间通信成了问题。解决方案只有一种，那就是让它们脱离沙盒环境、独立安装在系统环境内。
由于 Bazzite 默认是一个沙盒式的操作系统，所以你必须依靠一些特殊手段，将浏览器和 1Password app 安装到沙盒以外，它们才能正常工作。好在这对于 LLM 来说是轻车熟路、信手拈来。
另外，内置的包管理器前端 Bazzar 似乎没办法搜索到 DaVinci Resolve 和它的兼容沙盒 davincibox。没关系，这时候 LLM 会出手：给它一个指令，它就会自动帮你从零配置好 davincibox，让 DaVinci Resolve 顺利地在 Bazzite 上启动。
当然，非要说让 LLM 代劳这些有什么缺点，可能「没办法亲自动手」这一点算一个。虽然听上去稍微有点「凡尔赛」或是有悖于「吃水不忘挖井人」的想法，但自己没有亲自动手也意味着一旦这个配置出现问题，大概率还是得请 LLM 来帮忙修，但毕竟现在的大模型还是得依靠云端大公司才能调用，要是 LLM 调用掉了链子那还是得出大问题。不过，鉴于我也并非完全没有 Linux 运维经验，加上我的目的是把这套 setup 设置到我可以正常使用的状态、而非出于兴趣去折腾，再加上 Bazzite 也算是一个对 average user 相对友好的操作系统，我目前倒也不会太担心这个事情。
一些小问题
主动选择 niche 的解决方案，自然得面对一些 niche 的问题。首先遇到的问题是，Linux 上的 DaVinci Resolve（免费版）对 H.264 和 H.265 的支持较弱，没办法在软件里直接预览。
ChatGPT 给我推荐的方案是，将素材转换为 DNxHR HQX 格式。格式转换不是问题，问题是，DNxHR HQX 的体积实在是太大了。我现有的新工程的素材在 H.265 下的体积大概是 20 GB 左右，但在 DNxHR HQX 格式下，占用空间直接干到了 500 GB。好在，我在十年前升级内存的时候同时升级了固态硬盘，所以我的电脑有 2 TB 大容量固态可供使用，至少剪辑一期节目问题不大。唯一的问题是，转换后的文件似乎没办法和原素材形成代理，不过我觉得这应该是换个封装就能解决的问题，之后我会再研究一下。
另外一个很重要的问题是，国服《最终幻想 XIV》没法启动：中国区代理方盛趣游戏在它的启动器里大量使用 IE 和 32 位 COM 等组件，这导致它在 Linux 上无法正常使用。社区多数玩家会推荐在 Linux 上使用第三方的启动器，但毕竟因为各种各样的原因，导致它经常和「外挂」有关。
我把国服 FF14 启动器安装包下载回来，尝试让 ChatGPT 试试能不能解决这个问题。它花了大概 40 分钟，最终真的成功把它启动。当我在 Linux 上看到国服启动器的登录对话框，再看到 ChatGPT 对这个问题的诊断和修复，一时之间有点语塞：看着 Windows 给开发者「擦屁股」致使催生出的这种用二十年前的组件组装出来的奇怪「产物」，很难说这到底是好事还是坏事。
结语
在写这篇流水帐的过程中，我看到一篇报道称 Steam 中 Linux 用户占比很大程度上取决于简体中文用户的数量：当某月的简中用户提升，那么 Linux 占比就会下降；反之亦然。
虽然直接下「简中用户不爱用 Linux」的结论非常武断——我这里有个很直接的反例，例如不知道为什么 Linux 下的 Steam 程序不会跟随 Steam 或者系统设置的语言，只会 fallback 到英语；我猜测这可能是致使统计数据中 Linux 用户普遍不使用简体中文的缘故——但这个判断但其中确实有一定道理。
最重要的一点是，中国和美国的游戏玩家的画像并不一致：中国平均水平玩家更多使用电脑游玩游戏，致使更多技术水平一般的用户更愿意使用更友好的 Windows 而非 Linux；美国或其他国家的一般水平游戏玩家更倾向于购买游戏主机：更便宜，更开箱即用，大部分情况下也无需纠结 Windows 还是 Linux；真正「硬核」玩家才会使用 PC 游玩游戏，而对他们而言 Linux 运维并不成问题，在 Linux 上玩游戏就成了很自然的选择。
倒也不是在说「中国玩家很 low」或是「外国玩家真有钱」这种论断，只是在说，客观而言的现阶段，无论在什么地区，Linux 依然还停留在「小众」的层面。好在，事情已经开始在发生变化。目前多数 Linux 发行版的安装和设置，已经要比十年前纯 TUI 那样要对普通用户友好很多了。至少，一个普通的用户只需要了解计算机基本原理、并稍微学习如何修改引导启动设置，就能独自完成 Linux 的安装。
更大的问题还是在于一些阻碍。除了之前提到过的设置代理问题，真正的「阻碍」其实还是在人的内心。当外部的限制开始逐渐渗透、内化到每个人的内心，另一种真正的「可能性」在现今尤为珍贵。Linux 也许就是这样的「另一种可能性」。

Hydropower hit record lows in the US Southwest this summer
Drought conditions and low reservoir levels are affecting the renewable power source.
The US Southwest generated 28% less electricity via hydropower between April and August than the 10-year average, according to new data from the US Energy Information Administration.
Most hydropower plants in the US rely on dams to hold back water, creating reservoirs. The water can be released through turbines, generating electricity on demand. But an extreme, prolonged drought in the Colorado River Basin has resulted in dangerously low water levels in the Southwest’s two largest reservoirs, affecting the availability of this power source.
Residents and farmers in the US Southwest, a region that includes Arizona, New Mexico, and parts of Nevada and California, rely on water that melts in the spring from snowpack in the mountains and is slowly allowed to flow south via dam releases. Snowfall in the Rocky Mountains provides about 85% of the annual flow of the Colorado River. And in recent years, the river has seen record-low flows.
Two reservoirs along the Colorado River, Lake Powell and Lake Mead, have struggled to stay above the minimum level required for hydropower plants. At the end of September, Lake Powell’s depth was 3,518 feet, less than 1% above the level required to run the water through turbines that produce electricity at the Glen Canyon power plant. The Hoover Dam power plant requires 950 feet in Lake Mead, and that reservoir was 9% above the minimum in September.
Together, the two plants produced nearly seven terawatt-hours of electricity in 2025, enough to serve over 2 million people.
Low water levels have been an ongoing struggle for the region, which has been in a drought for 27 years. Meanwhile, climate change is continuing to shift rainfall and snowfall patterns across the region and around the world.
The effects of climate change on hydropower aren’t entirely straightforward globally—some regions will see more rain and snow because of shifting weather patterns, while others are likely to see less.
But it’s playing a role for hydropower availability, according to one 2022 review study. Rising temperatures bring more droughts, warmer winters means less snow and ice to fill the reservoirs, and more variability in precipitation can lead to alternating floods and droughts, making the power source less reliable.
Hydropower production is likely to be at its lowest level in over a decade in 2026 and tick even lower in 2027, according to projections from the EIA.
El Niño could provide some temporary relief. Sometimes this weather pattern can mean cooler, wetter conditions for the southern US. Heavy rains brought floods to the region in October and early November, and the water levels in Lake Powell rose more than 20 feet from their mid-September low. But the water is still quite low, and it’ll take much more to help reservoirs recover from decades of drought conditions.
Even as a changing climate complicates the availability of hydropower, the decline in capacity could push greenhouse-gas emissions higher. In 2023, energy-related greenhouse-gas emissions rose by 1.1% globally. A worldwide shortfall in hydropower generation accounted for about 40% of that rise, according to a report from the International Energy Agency.

Our analysis reveals a clear trade-off: models that frequently seek clarification tend to over-clarify and prolong interactions, while assumption-driven models are more prone to misaligning with user intent. We demonstrate that system prompts optimized on these dissatisfaction signals achieve a Pareto-optimal balance across all three metrics, reducing overall error rates by up to 7.65%, underscoring the value of our framework in designing agents that ask precisely and assume wisely.
