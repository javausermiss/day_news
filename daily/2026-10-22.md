A coding-agent skill that turns your agent into a security auditor. It orchestrates isolated agents through reconnaissance, coverage-led hunting, candidate validation, structured output, independent record verification, and target-neutral reporting.
This is the skill that seeded Cloudflare's vulnerability discovery harness, described in Build your own vulnerability harness. The harness grew into a multi-stage, fleet-wide system; this skill is the single-repo starting point it evolved from.
The skill runs a structured audit in six phases:
- Reconnaissance -- map architecture, trust boundaries, input surfaces, prior evidence, and deterministic coverage in architecture.md and coverage-ledger.json.
- Coverage-led hunting -- assign isolated hunters from ledger units, record their checks, and use coverage critics to find gaps.
- Candidate validation -- give every unique candidate to a fresh verifier that tries to disprove it.
- Structured output -- write confirmed, needs_validation, and rejected records to findings.json and validate them against report-schema.json.
- Independent record verification -- fresh agents verify final source claims. Material replacements receive another independent verifier.
- Target-neutral reporting -- derive REPORT.md, FINDINGS-DETAIL.md, and NEEDS-VALIDATION.md from the verified records and coverage ledger.
The parent runs validate-coverage-ledger.cjs after creating the ledger and after each later ledger update. It runs validate-findings.cjs in Phase 4 and again after every Phase 5 replacement.
The verdicts are distinct: confirmed has a complete source trace and bounded observed result, needs_validation has an exact unresolved fact and no severity, and rejected records a disproved candidate.
Multiple runs against the same repo are additive. The skill uses prior ledgers and findings to target gaps, revalidate changed source, and carry forward current-source evidence without treating stale or unresolved work as covered.
Install the skill with the Skills CLI:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
Use --global for a user-level installation:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit \
  --global
Run npx skills --help for agent-selection and non-interactive options.
Start your coding agent in (or pointed at) the codebase you want to audit, then ask it to do a security audit:
security audit this codebase
find security vulnerabilities in ./src
do a security review, output to ~/audits/my-project
The skill activates automatically when the request matches its trigger (security audit, find vulnerabilities, pen-test the code, etc.). A direct codebase audit or pen-test request uses full audit mode. Security questions and focused vulnerability work use guidance mode unless you request report artifacts. In full audit mode, an unspecified output directory defaults to ~/security-audit-skill/<repo-name>/run-<N>. The workflow writes inside the target repository only when you explicitly select a directory that version control ignores.
- A coding agent with a model that supports tool use and parallel sub-agents
- Node.js for the zero-dependency findings and coverage-ledger validators
- An OS-enforced sandbox for target-controlled builds, tests, processes, browsers, emulators, fuzzers, and fixtures. It must disable external networking, use a sanitized allowlisted environment, enforce resource limits, and allow writes only to assigned scratch paths. Without these controls, the workflow keeps the lead as needs_validation instead of executing target code.
- Only confirm established boundary failures. Keep a source-grounded blocked lead as needs_validation with its exact unresolved fact.
- Adversarial validation. The agent that checks a finding is never the agent that found it.
- Severity requires impact. Likelihood x impact, not deviation from a checklist.
- Defense-in-depth gaps are not vulnerabilities. If Layer A prevents the attack, the absence of Layer B is a hardening note.
- Multiple runs improve coverage. In our test runs, a single run found roughly half of the vulnerabilities that repeated runs found in total.
Questions, feedback, or comparing notes on AI-driven security tooling: security-ai-research@cloudflare.com

Header Accordions: QPACK amplification attacks against HTTP/3 servers
SÃ©bastien FÃ©ry
TLDR
A remote, unauthenticated client can force an HTTP/3 server to allocate tens to thousands of times more memory than it sends. One connection is enough to OOM or pin a default-configured server. Seven of the ten implementations tested are vulnerable; several are already fixed.
QPACK compresses HTTP/3 headers to minimize traffic sent over the wire. Across the affected implementations, decoded-header limits are missing, incomplete, or applied too late. A small HEADERS frame can therefore expand into hundreds of thousands of header objects in memory. Preventing that expansion from exhausting resources requires enforcing a cumulative budget as fields are decoded and retained.
Patched as of October 20, 2026
Unpatched as of October 20, 2026
Mitigations
Bun: Don't expose HTTP/3 servers
mitmproxy: disable HTTP/3 (pass --set http3=false)
h3 crate: set a reasonable max_field_section_size
Not affected: IIS, Envoy, ngtcp2/nghttp3
Background
During recent research into the different QUIC stacks for our active TLS scanner, JA4Scan, I found the same class of vulnerability across multiple HTTP/3 implementations. A remote, unauthenticated client can send HTTP/3 traffic that forces the server to allocate far more memory than the encoded request occupies on the wire.
This investigation started after reading Gal Bar Nahum's MadeYouReset series on HTTP/2 request-cancellation DoS. That work got me looking at whether HTTP/3's QPACK header compression had similar amplification issues.
HTTP/3 compresses headers using QPACK, so repeated fields like user-agent or content-type can be sent as a small index instead of the full string. It uses two lookup tables: a static table, a hardcoded set of common fields defined by the specification, and a dynamic table, built up at runtime between a client and server as new headers are seen.
For example, a 71-byte header like strict-transport-security: max-age=31536000; includesubdomains; preload becomes a single byte: 0xFA, a static-table reference to index 58.
RFC 9114 Section 4.2.2 defines how servers should limit decoded header size:
The size of a field list is calculated based on the uncompressed size of fields, including the length of the name and value in bytes plus an overhead of 32 bytes for each field.
Some implementations tested got at least one of these wrong:
- They check the compressed frame size, not the decoded size
- They decompress everything before checking
- They omit the 32-byte overhead from their size calculation
- They default to unlimited when the setting is unconfigured
- They never enforce the setting at all, even when it is configured
How does it work?
The goal is to maximize the number of headers inside a single HEADERS frame. For this variant, I use unique names to create distinct entries in the receiving header map: a through z, aa through zz, then three and four char names until the encoded-size budget is filled. There are 676 possible two-letter names but we need to skip te as that header has special value requirements..
A 1,000,000-byte HEADERS frame holds about 160,000 unique headers this way.
What the server does with those 160,000+ headers is where it breaks.
Example request flow on quic-go
The accordion also works in the other direction. Instead of many small headers, the dynamic table variant inserts one large entry (~4 KiB) via the encoder stream, then references it thousands of times with 1-byte indexed references. Each reference forces a fresh allocation and copy of the full entry. This is how the lsquic and Bun attacks work: each 1-byte reference materializes the full entry, a ratio of 4064:1.
Implementations
quic-go
quic-go is the Go library behind Caddy, Traefik, and cloudflared. Its HTTP/3 server limits the HEADERS frame to 1 MiB (DefaultMaxHeaderBytes), but that limit applies to the compressed QPACK payload, not the decoded output. DecodeFull in qpack/decoder.go decompresses the entire block in one pass and returns a []HeaderField slice, which is then converted into an http.Header map.
The http.Header map is a map[string][]string, whose keys, value slices and internal storage add overhead beyond the encoded headers. The 1,000,000-byte QPACK block decodes into 160,075 fields and retained approximately 15 MiB in the resulting request after gc, about 15 times the encoded size.
quic-go limited the compressed HEADERS frame without enforcing a corresponding decoded-header budget.
Fix: quic-go now sends SETTINGS_MAX_FIELD_SECTION_SIZE, uses incremental QPACK decoding that checks size after each entry, and aborts with HTTP 431 on the server side.
Cloudflare quiche
quiche had two issues rolled into one CVE.

A new era of spaceflight could save astronauts time and cut exposure to cosmic radiation as they rocket to Mars—and beyond.
Just before the Artemis II crew began its historic slingshot around the moon this past April, NASA announced plans to build Space Reactor-1 Freedom. The sticking points
Running a nuclear reactor in space may sound like lunacy, but it’s not. The Soviet Union sent dozens of reactors into orbit, often to power spy satellites. And experts say there aren’t any major technical obstacles to making nuclear space propulsion happen. “I think it’s a very doable technology,” says Philip Metzger, a spaceflight engineering researcher at the Florida Space Institute.“I’m happy to see them finally doing this.”
Still, developing space propulsion using reactors has been slow going. The US has started—and terminated—several programs looking into it over the past 75 years. The latest casualty was DRACO, a collaboration between NASA and the Department of Defense, which ended in 2025. The project was canceled because of high experimentation costs, an inability to compete with conventional rocket propulsion on price, and difficulty ensuring that ground tests could be performed safely and effectively. (You are creating an incredibly powerful nuclear reaction, after all.)
The progress
After much wavering, it now appears that nuclear-powered interplanetary travel is a $2 billion bet NASA is willing to make. The agency is pursuing an approach called nuclear electric propulsion, which uses the neutrons produced in a self-sustaining, uranium-atom-splitting reaction to create heat and ultimately electricity. The electricity is used to ionize a gas, which is blasted out of the spacecraft with the help of magnetic fields, generating thrust. The approach “is very low thrust, but very efficient,” says Sebastian Corbisiero, the US Department of Energy’s national technical director of space reactor programs. “So you can use it for a long period of time.”
What might such a rocket look like? A presentation by Steve Sinacore, program director of NASA’s SR-1 program, offers some clues. So far, the concept art makes the craft look like a colossal fletched arrow. The back will house the power-and-propulsion system, while the tip will hold a uranium-filled nuclear reactor with a capacity of at least 20 kilowatts. (For context, a typical nuclear plant on Earth is about 50,000 times more powerful.) The “fletches” on SR-1 are large fins that help cool the reactor by radiating heat into space.
Like many other pieces of space hardware, the reactor will need to be put through its paces on the ground before it’s cleared for the rough rocket trip to space. “Going through the launch safely is going to be a challenge,” says Middleburgh. “You are being shaken, rattled, and rolled.” For safety reasons, the reactor will be switched on around two days post-launch, when it’s comfortably far from Earth. If SR-1 works as planned, its journey to Mars will take about a year.

Decoding how animals communicate could reveal the inner lives of other species—and give humans a window onto how they see the world.
Humans are far from the only species with a gift for gab, and our furry, feathered, and finned friends could have a lot to tell us. Decoding how animals communicate with one another could offer a window into the inner lives of other species and help humans realize that “animals are sentient creatures who think, who have hopes and dreams of their own,” says Con Slobodchikoff, the founder of Zoolingua, a company working on dog-to-human speech.
The sticking points
Teasing all this out is complex. To decipher howls, squeaks, and clicks, researchers must match the creatures making sounds with what’s happening around them. Prairie dogs, for example, utter a different series of yips when a coyote approaches than when a hawk is nearby. It’s painstaking work, especially for difficult-to-observe species, like deep-diving whales or subterranean mole rats.
There are other hurdles. Many animals communicate not just through sound but through visual cues, touch, pheromones, or a combination of signals, some of which might be difficult for us to perceive. And without a multispecies Rosetta stone, it’s hard to know if translations are accurate.
The progress
Over the past 50 years, a growing arsenal of devices has made it easier to observe the sophisticated ways animals communicate. Hydrophones at the bottom of the ocean can capture humpback whale song, and tiny wearable “biologgers” can record a bat’s every squeak.
In the last decade, advances in AI have leveled up our ability to make sense of it all. The technology can detect different calls, distinguish which sounds belong to which animal, and spot patterns. Researchers at the Earth Species Project (ESP), a nonprofit founded in 2018 to decode animal communication, recently used machine learning to detect vocalizations of carrion crows and determine which bird made which call.
They suspect that more advanced AI could translate critters’ chatter. Large language models like Claude and ChatGPT excel at finding relationships between words, explains Sara Keen, one of ESP’s behavioral ecologists. ESP hopes its own NatureLM—trained on human speech, music, and animal sounds—will be able to interpret the vocalizations of a variety of species.
That promise, however, is still theoretical. Yossi Yovel, a neuroecologist at Tel Aviv University, worries that these models will put too much emphasis on acoustic similarities and make mistakes—like lumping together similar sounds that have different meanings.
As for a two-way convo? It’s not clear when—or whether—that will happen. Still, “a lot of animals have an evolutionary structure that is similar enough that we should be able to understand what they’re saying,” Slobodchikoff says.

把 Mac 的运行状态放在一个窗口中
各项指标，一页概览
打开 Vitals 的独立窗口，首先看到的是「概览」。这里汇总了 Mac 当前的主要硬件指标，包括 CPU、内存、GPU、磁盘、网络、和电池六项硬件的使用情况。我们不需要在很多个页面之间切换，就能对整台电脑的运行状态形成初步的判断。
这些信息并非简单地堆叠在一起。Vitals 会根据不同硬件的工作方式选择相应的呈现形式，通过数字、图表、进度和状态信息等多种方式反映硬件的运行情况。我们既可以查看当前读数，也能观察指标在最近一段时间内的变化。
例如，CPU、GPU 区域展示处理器使用率及负载情况；内存区域呈现已用内存、内存压力和不同类型内存的分布；磁盘区域展示剩余容量、读写速度等数据；此外，电池、温度、风扇、声音、蓝牙设备等信息也可以纳入监控范围。
实时变化显示是概览页面的一项重要特点。CPU 使用率、网络速度和内存占用会随着应用运行而改变，图表则帮助我们观察负载变化的过程。当某个指标出现明显波动时，可以进一步进入对应的详情页面，查看更具体的数据和相关 App 的资源占用情况。
这种由整体到局部的浏览方式适合日常排查问题。例如，发现 Mac 的内存使用率持续升高，可以直接进入内存页面，检查哪些 App 占用了较多资源；如果电脑发热、风扇转速提高，则可以查看 CPU、GPU 和温度等指标，进一步判断是否存在持续高负载。
指标详情，独立页面详细分析
「概览」页面承担的是快速判断和定位问题的作用，而「指标详情」页面则负责提供进一步分析所需的信息。Vitals 为 CPU、内存、磁盘、网络、GPU、声效、蓝牙等都设计了独立的页面，并把项目（开发服务器、编译器等）也纳入监控范围。

- 内存：展示内存使用情况，并按照不同内存类型进行细分，同时列出消耗内存较多的 App。对于经常同时运行浏览器、开发环境、虚拟机或本地 AI 模型的用户，这些信息有助于理解内存压力的来源。
- 磁盘：关注容量、读写速度和规模，以及相关应用；
- 网络：展示数据上传、下载速度及应用产生的网络活动
- GPU：面向图形处理器使用的负载情况。
- 电池：提供电量、功耗和电池健康等信息，温度与风扇相关数据也能帮助判断硬件是否处于较高负载状态。

以 App 为单位分析资源消耗情况
Vitals 与传统系统监控工具的一个重要区别，是将 App 作为资源统计的主要单位。
在 macOS 上，系统自带的「活动监视器」已经能够提供相当完整的硬件监控和进程管理功能。不过，当我们希望了解究竟是哪款应用究竟消耗了资源时，则需要自己识别各个进程，并自行汇总相关数字。
Vitals 会将资源的使用都归并到所属 App 下，展示应用层面的 CPU、内存、能耗、磁盘和网络等资源使用情况。我们可以先比较不同 App 的总体消耗，再展开某个 App，进一步查看它包含的具体进程。
这种组织方式让资源分析更贴近用户实际使用电脑的方式。我们经常遇到「Chrome 占用了太多内存」或者「VS Code 编译时让电脑变得很慢」，Vitals 以 App 为单位呈现数据，能够直接回答用户最关心的问题。

从使用体验来看，Vitals 将「查看资源数字」推进到了「识别资源来源、观察变化过程、定位可能的问题」。它能够减少手动汇总进程的工作量，也让日常系统维护更容易形成一套可重复的排查流程。
集成 AI：通过 MCP 让 AI 助手读取系统状态
Vitals 的另一项重要功能，是提供 MCP（Model Context Protocol，模型上下文协议）服务器，让支持 MCP 的 AI 助手在获得授权的范围内调用工具、读取系统数据，帮助用户分析硬件问题。
Vitals 的 MCP 集成支持 Claude、Claude Code、Codex、Cursor 等工具。在设置中开启集成后，我们可以直接在这些 AI 助手的对话界面中询问 Mac 的运行情况，而不必每次都先打开 Vitals，再手动整理数据。
在应用中进入设置中的「集成」页面，启用 AI 助手查询，然后安装需要连接的 AI 工具，按照配置提示完成连接，成功后，我们就可以直接用自然语言提出问题。例如检查当前 Mac 的内存使用情况、找出 CPU 高负载的应用、检查当前运行的开发服务器等等。
这些问题都不需要预先掌握复杂的命令行操作，AI 助手可以通过 MCP 获取 Vitals 提供的数据，再结合问题组织答案。
系统监控工具能够读取应用名称、进程信息、资源占用和开发项目相关数据，因此隐私问题值得关注。根据 Vitals 官方隐私说明，应用会在本地记录系统和 App 的资源使用历史，不要求用户注册账户，也不会主动将这些监控数据发送到 Vitals 的服务器。
支持自定义外观，还有其它贴心功能
作为系统监控工具，Vitals 一改系统活动监视器的呆板风格，提供了一套简约并且可自定义的窗口界面。
在图表配色方面，Vitals 提供三种方案：Vitals、单色和辅助功能。用户可以保留应用原有的彩色图表，也可以选择更克制的单色方案，或者使用便于区分的无障碍配色。不同方案适合不同的视觉偏好和使用环境。
Vitals 在设置中还提供了丰富的自定义功能，将图表配色、数字字体、字体粗细和布局密度等选项集中在一起。字体设置同样比较灵活，包括圆体、San Francisco、SF Mono 和 New York 等选项，用户还可以选择 Mac 上安装的其他字体（比如 WWDC 26 上 hello 使用的 MacintoshSkeletal）。对于系统监控界面来说，字体的选择会影响数字的辨识度，也会改变整体界面的视觉风格。这些设置支持实时预览，调整配色、字体和间距后，可以直接观察界面变化。
Vitals 支持将监控结果导出为图片，将当前系统状态整理成适合保存或分享的图像。无论是希望展示 Mac 的整体运行情况，还是突出内存占用、CPU 使用率和主要资源消耗 App，都可以通过相应的导出形式呈现数据。对于需要更深入分析的数据，Vitals 还支持导出历史记录为 CSV。新版进一步完善了历史数据导出能力，可以分别获取按日统计的 App 数据、按小时统计的 Mac 数据，以及每五分钟记录的系统读数，方便用户在电子表格等工具中继续分析。
窗口常驻则是另一项实用设计。开启始终置顶后，Vitals 可以一直显示在其他应用窗口前方。你在进行视频剪辑、代码编译、模型推理或大型文件处理时，可以持续观察资源变化。在排查问题时无需频繁切换窗口，对于需要一边运行测试、一边观察 CPU 和内存变化的用户，这种方式尤其方便。
在菜单栏，Vitals 提供了轻量化的监控展示窗口。值得一提的是，在应用的设置中，我们可以通过 Vitals 将 CPU、内存、GPU、网络、磁盘、温度、电池、功率这几项指标常驻在菜单栏中。你关注哪个指标，就可以让哪个指标的使用情况常驻显示。对于资源使用进入到高负载水平时，Vitals 还支持将读数使用红色高亮显示，提醒你及时维护。

平板电脑的历史
想象一下，如果一台电子产品有一块可触控屏幕、些许按键、再带一支触控笔、没有实体全键盘、运行完整的操作系统——你觉得这会是什么？
用现在的眼光来看，这些特征加在一起显然就是平板电脑。在个人消费级市场，被大多数人所熟知的产品应该是 2010 年苹果发布的 iPad 初代。
但真要追溯平板电脑这个概念，它早在 2010 年就已经不是新鲜事了。1968 年，艾伦·凯 (Alan Kay) 提出的 Dynabook 概念设想了一款大小如笔记本、带有触控屏和键盘、能让儿童随时随地学习的便携电脑；到了 1989 年，公认的第一台商业化平板电脑 GRiDPad，由 GRiD Systems 公司于 1989 年 9 月正式发布上市。
这些要么是概念产品，要么是商业化产品，平板电脑概念在个人消费级市场上出现，则要等到 2000 年。微软在当年的「.NET 战略」发布会及 COMDEX/Fall 大会上，由比尔·盖茨首次展示了 Tablet PC 的原型，将其定义为一款基于完整 Windows 操作系统、支持触控笔输入的便携 PC。
6 年之后的 2006 年 3 月 9 日，微软在德国汉诺威的 CeBIT 展会上，正式公布了代号为 Origami 的计划，并推出了 UMPC（Ultra-Mobile PC，超级移动 PC）这一全新品类。
本期《怀旧手记》为大家带来的就是 2006 年微软联合英特尔、三星推出的世界首台 UMPC 设备三星 Q1（Samsung Q1）。
三星 Q1
三星 Q1 其实在 UMPC 当中也是一个比较特殊的设备，后期出现的 UMPC 设备几乎都有一个共同点：可触控的屏幕、小巧的机身，绝大多数的机器还会想办法添加 QWERTY 实体全键盘。比如索尼的 VAIO UX 系列采用了滑盖的形态，使用设备时向上一推，就会有一块紧凑的实体全键盘。
甚至包括后期三星推出的 Q1Ultra 和 Q1Ultra Premium，也在屏幕边框上添加了实体全键盘。
再回看 2006 年发布的三星 Q1，作为首台 UMPC 设备它却并没有实体键盘，交互逻辑主要依靠那一块七英寸大小的电阻式触控屏。
回到机器本身，在 Q1 上三星推出过多个子型号，并通过不同的配置跟硬件平台做区分，包括：
三星 Q1 (标准版 / V000)
- 处理器：Intel Celeron M ULV 353 (900MHz)
- 内存/存储：512MB DDR2 / 40GB HDD (4200rpm)
- 屏幕/系统：7 英寸 800×480 电阻屏 / Windows XP Tablet PC Edition
- 接口/重量：CF 卡槽、USB 2.0、VGA / 约 0.78kg
三星 Q1 SSD（和 Q1 标准版几乎完全相同，核心区别在于存储介质）
- 处理器：Intel Celeron M ULV 353 (900MHz)
- 内存/存储：512MB DDR2 / 32GB SSD
- 屏幕/系统：7 英寸 800×480 / Windows XP Tablet PC Edition
- 主要差异：用 32GB 固态硬盘替换了 40GB 机械硬盘，发布时价格约为标准版的两倍。
三星 Q1b（三星的第二款 UMPC，在续航和屏幕上做了改进，但部分接口被移除）
- 处理器：VIA C7-M ULV (1.0GHz)
- 内存/存储：512MB DDR2 / 40GB HDD
- 屏幕/系统：7 英寸 800×480 (亮度提升 30%) / Windows XP Tablet PC Edition
- 接口/差异：移除了 CF 卡槽和以太网口，改为单扬声器，电池续航约 5 小时
三星 Q1F (Pentium M)（是 Q1 标准版的性能升级款）
- 处理器：Intel Pentium M 723 (1.0GHz)
- 内存/存储：1GB DDR2 / 40GB 或 60GB HDD
- 屏幕/系统：7 英寸 800×480 / Windows Vista Home Premium
- 主要差异：CPU 支持 SpeedStep 技术，续航更好，且是 Q1 系列中少数预装 Vista 的型号。
这一次我收到的这一台就是三星 Q1F (Pentium M)，接下来跟随文章和我一起，在一台 20 年前的 Windows 掌上设备聊聊看，它都有哪些现如今平板电脑的影子？
外观
外观上，三星 Q1 正面采用黑色亮面塑料，七英寸电阻式触摸屏几乎占据正面大部分面积。放在 2006 年，这种以屏幕为主体、只保留极少量实体按键的设计无疑是超前的。
类似形态并非首创。IBM 在 1992 年就推出过 ThinkPad 700T，1994 年的 730TE 还运行过 Windows 3.1 for Pen Computing，同样没有集成键盘，靠笔操作。
但那些机器重量大多在两公斤上下，本质上还是「能抱着用的电脑」而不是随身设备。Q1 把这种形态压到 780 多克，同时保留完整 Windows PC 的扩展能力，这个组合才是它真正超前的地方。
屏幕左侧边框有一枚方向摇杆，右侧是 U1、U2、U3、U4 四个圆形按键，在不同状态下功能也有所不同。虽然完全取消实体按键外观会更接近今天的平板，但也会牺牲操作效率；Q1 的做法是在「无键盘」和「易上手」之间找平衡，摇杆和快捷键负责系统级操作，触控笔负责精细输入。就实际体验来说，我个人觉得这个平衡拿捏得不错。
电脑共有两个 USB 接口，一个 VGA 接口可以连接显示器。左侧有耳机插口，音量调节按键，上方则是 CF 卡扩展口以及 RJ45 网线接口。
翻到背面是可拆卸电池，背面材质为黑色磨砂塑料。
中间有一个支架，打开后可以把电脑立起来。这个设计值得单独说一句：同期 UMPC 想立起来，基本都得靠外接底座或保护套，索尼 VAIO UX、OQO 都是这个思路，底座本身也是额外携带的负担。Q1 直接把支架做进机身，打开就能立，收起来不增加任何携带成本。
我们在后来的微软 Surface 系列上也能看到类似的设计，Surface 的 Kickstand 和它背后的逻辑有相似之处，但 Q1 比 Surface 早了六年。
可拆卸电池、CF 卡槽、RJ45 和 VGA 这些接口，说明 Q1 本质上仍然是一台完整的 PC，扩展能力是那个时代 PC 的基本要求。但屏幕形态、触控笔交互，以及没有集成键盘的设计，又让 Q1 和传统笔记本明显不同。
配置方面
之前详细展示的部分就不再过多赘述。来看一下我这台机器的真实配置：
- Intel Pentium M 1.0GHz
- 1GB DDR2 RAM
- 40GB HDD
- 运行 Windows XP Tablet PC Edition
这个配置放在当年的 UMPC 上是属于主流偏上的，特别是 Q1F 上面的 1GB 内存让它出厂的时候可以预装 Windows Vista 并且勉强运行。英特尔奔腾 M 低电压处理器也比同时期的赛扬 M 性能更强，但同时发热和能耗更高。
系统
虽然我这一台 Q1 预装的是 Windows Vista Home Premium，但是这个配置在 Vista 系统下体验感很糟糕，光是从开机到进入桌面就要花上大约 2 分钟。
这里先和大家介绍一下 Windows XP Tablet PC Edition 和 Windows Vista。Windows XP Tablet PC Edition 其实不是一个简单的「XP 系统加笔支持补丁」，它是微软在 2000 年提出 Tablet PC 这个概念之后，第一次专门为「用笔来操作的完整 Windows 设备」做的系统。
2002 年 11 月正式上市，2004 年 8 月又更新了 2005 版，核心是一个叫「数字墨水」的东西和 Tablet PC 输入面板。跟九几年的 Windows 3.1 for Pen Computing 比，3.1 更像是在鼠标系统上硬加了一层笔输入，而 XP Tablet PC Edition 是把手写识别、墨水存储、输入面板这些都做进了系统底层。
那这台 Q1 跑 Vista 为什么这么灾难？Home Premium 有「Premium Ready」认证，要求 1GHz 处理器、1GB 内存，还有 128MB 显存的 Aero 兼容显卡。我这台 Q1 刚好卡在最低线上，但集成显卡带不动 Aero，所以 2 分钟开机是必然的。
还有一个有意思的变化，就是从 Vista 开始，Tablet PC 这个独立分支直接没了。微软把笔触控功能内置进了所有 Vista 版本里，不再单独发一个「Tablet PC Edition」。也就是说，系统不再把「笔触控 Windows」当成一个特殊品类，而是当成所有 Windows 本来就应该有的功能。
说回机器本身，刚开始收到这台机器的时候我还是比较震惊的，毕竟原装系统就这个水平。当年的体验也不一定会比现在好。
降级
我在网页档案馆找到了网友分享的原版适用于 Q1 系列的 Windows XP Tablet PC Edition 2005 的版本。一共有三张光盘镜像，最主要的就是 Windows XP 系统安装镜像，还有后续进入系统之后需要安装的原厂驱动镜像。
安装过程非常简单，因为 Q1 支持通过 USB 启动，所以我这里是通过 U 盘进入 PE 系统，通过 PE 系统内置工具安装 ISO 文件。
软件提示完成之后重启，电脑就进入正常的 Windows XP 安装环境。系统安装完成之后，因为驱动并不完全，所以还需要打开之前下载的驱动安装镜像。
在运行驱动安装镜像的 exe 程序之后，就不需要再管它了，程序会全自动安装所有的镜像并且恢复自带的壁纸。
从安装系统到还原驱动，全程大约花费一个半小时左右。我们就得到了一台系统运行流畅，自带功能正常的三星 Q1。
但是因为下载到的系统镜像是英文的，所以我们还需要安装一个适用于 Windows XP 系统的多语言环境 MUI。在多语言环境包安装完成之后就可以在控制面板当中切换为简体中文。
体验
在系统恢复完成之后，我发现 Windows XP Tablet PC Edition 的系统操作逻辑还算是比较容易上手的。
我先后为电脑安装了 Office2003、Winamp、植物大战僵尸，以及 Firefox 浏览器。实际体验过程中发现，虽然从 Vista 降级了，但系统针对触控屏的交互逻辑有所适配。不过软件层面就不是这么理想了，我看网上有一些 Windows 平板的用户也聊过类似的问题——系统支持触控，但桌面软件还是按鼠标键盘的逻辑设计的。这个矛盾到现在也没有完全解决。
比如 Office2003，如果不使用鼠标和键盘，单纯使用自带的触控笔的话，也是可以正常使用的，只是步骤比较繁琐，因为你需要通过笔去选择，虽然 XP Tablet PC Edition 有虚拟键盘，而且有中文输入识别软件，但中文输入识别的准确性并不是很高。因为屏幕尺寸比较小，虚拟键盘上面的按键如果不使用自带的触控笔笔尖，就会很难选中。
使用体验比较理想的应该是浏览器之类的了，虽然说这台 Q1 有内置 WiFi 和蓝牙，但是内置的 Wi-Fi 放到现在也很难连上现代网页。不过我尝试浏览离线网页的时候发现通过触控笔浏览网页的效率还算高，交互体验感也不错。
文章写到这我想起了 2010 年苹果发布初代 iPad 的时候，印象最深的就是乔布斯坐在发布会的沙发上，翘着腿，单手拿着 iPad 刷网页的画面。我尝试在三星 Q1 上复刻了一下，相比于 iPad，还是有点不适应。
游戏
在游戏中，我觉得三星 Q1 上面这块触摸屏发挥了不少用处。比如《植物大战僵尸》，因为没有复杂的选项，你可以全程完全使用自带的触控笔去操作，轻点、双击甚至拖动都是没有问题的。
不过像一些需要频繁使用到鼠标的游戏，比如说《生化危机》《模拟人生》《模拟城市》这一类的，Q1 的触控就有点显得力不从心了，而且这些游戏往往也没有针对触控去做单独的适配。
展示完游戏和办公的效果，让我们再来看看它在音乐的播放上表现如何。
在 MP3 音乐上，我选择了几首经典的音乐，大小均在 5~10MB，通过自带的 Media Player 或者 Winamp 均可以流畅播放。
