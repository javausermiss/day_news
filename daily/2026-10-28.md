A design skill for Claude Code, Codex, Cursor and OpenCode that refuses to look AI-generated.
usehallmark.com · fifty themes · custom on request · redesign and audit by name
Made by Together AI.
Hallmark holds a hard floor and then gets out of the way. It deals three themes from a catalog of fifty materials, builds the page around what the visitor came to do, and lints the result in a real browser against the tells that read as machine-made: the eyebrow above every heading, tracked-capital labels, one coloured word in a headline, a page of empty frames or nothing but photographs, a hero that misses its screen, an email sign-up at the end of every page, a form that says thanks without sending anything. A fresh-context reviewer gets the last word.
The gates come in tiers. The Floor never ships (contrast, focus, reduced motion, invented facts, a broken phone layout). Reflex gates are the defaults a model falls into; a build with a reason may overrule one on the record. Finish checks are craft detail that never blocks a ship.
- Fifty themes. Each is a material (paper, type, colour, surfaces, its own components and texture) with a picture of a finished page, and the build lays out its own page in it.
- Built from the job. A booking page books, a shop sells, a newsletter subscribes: the action sits where the category puts it, and the page ends on it.
- Custom. Ask for a custom page and Hallmark designs from your prompt alone, under the same rules and checks.
- Your real product. Point it at a URL, a dev server or an app and it captures the screenshots itself.
- Real photographs. 755 openly licensed photos, picked per subject and credited on the page.
- Redesign and audit. /hallmark redesign <path> rebuilds a page and keeps its content and wiring; /hallmark audit <path> only reports.
Ten of the fifty. A theme is a material, not a plan: it never says what a page contains or in what order, so two prompts in one theme make two different pages. Each is one file of at most 8 KB in references/themes/ with a picture beside it; a build reads exactly one. See them all at usehallmark.com.
Say custom and Hallmark drops the themes: no plan, no components, no palette recipe, only the floor, the gates and a short direction in direction.md to find one idea that only this client has and let it run the page.
- Pre-flight reads the project (fonts, palette, framework, a locked design.md) and asks once for the material: photos, screenshots, real numbers. Nothing is invented.
- scripts/theme.mjs deal offers three themes that fit the prompt and clear the log; draw deals the page's anatomy from its job.
- The hero is built alone, rendered and reviewed cold before the rest of the page exists.
- scripts/sloplint.mjs --render checks the page at eight widths, then a subagent reviews it with fresh eyes.
Each page is self-contained HTML and CSS, stamped in its first CSS comment with the decisions it took.
Hallmark never starts on a design that already exists unless you name it:
/hallmark redesign ./src/app
/hallmark audit ./index.html
A full redesign keeps the content and the wiring and changes the system and the layout; say keep the layout for a restyle or polish for only the tells. sloplint --before records every link, field, handler and heading first, sloplint --kept fails the redesign if one went missing, and the handoff is a side-by-side before and after.
npx skills add nutlope/hallmark -g
-g installs for every project; leave it off to install into the current one. Needs Node 18 or later. The browser checks (sloplint --render, screenshots) also need npm i -g puppeteer-core and Chrome; without them the static checks still run.
- One harness only: npx skills add nutlope/hallmark -g --agent claude-code (or codex, opencode, cursor, github-copilot).
- As a Claude Code plugin: /plugin marketplace add nutlope/hallmark, then /plugin install hallmark@hallmark (invoked as /hallmark:hallmark).
- From a clone: node skills/hallmark/scripts/install.mjs validates every theme and reference before it copies; install-hook.mjs adds an edit-time Floor check to Claude Code.
- Lint any page: node skills/hallmark/scripts/sloplint.mjs <file-or-dir> --render.
- If it does not fire on its own, name it: use hallmark to build ....
MIT. Use it, fork it, ship it.
The photo library (skills/hallmark/scripts/photos.json) lists photographs hosted on Wikimedia Commons and holds no image files. Each keeps its own licence (CC0, public domain, CC BY or CC BY-SA), and Hallmark credits every one it uses on the page. It does not use stock sites (Unsplash, Pexels, Pixabay), whose terms bar AI tools from picking their images.

Two new Raspberry Pi boards have quietly turned up in Raspberry Pi’s Linux kernel tree, and neither of them is quite what I’d have guessed. Device tree files for a Raspberry Pi Zero 3 W and a Raspberry Pi 4 Model A have landed (Phoronix spotted it first), and whilst there’s no official announcement just yet, device tree files tend to give away a surprising amount if you can decipher them and I gave it my best shot.
Table of Contents
Raspberry Pi Zero 3 W: A Pi 4 Shrunk Down?
The Raspberry Pi Zero 2 W launched almost exactly five years ago (tomorrow, in fact), so a successor has been a loooooong time coming. If you want a refresher on where things stood back then, my Raspberry Pi Zero 2 W vs Zero W benchmarks piece covers the jump from the original pretty well.
The headline from the Zero 3 W device tree is the SoC. It’s the Broadcom BCM2711, the same quad-core Cortex-A72 chip that powers the Raspberry Pi 4, replacing the Zero 2 W’s quad-core 1GHz Cortex-A53 RP3A0. If you want an idea of the sort of gap we’re talking about, it’s worth having a look at how those two compare on sbc.compare. That’s a big step up in per-core performance, and if they can get anything close to Pi 4 clocks in that tiny footprint, it’ll be a hell of a lot of compute for a Zero. I do wonder how toasty it’s going to get though, as the BCM2711 isn’t exactly known for running cool, and there’s not a lot of board for the heat to spread into. The device tree doesn’t tell us anything about clock speeds, so we’ll have to wait and see whether it’s been dialled back.
Beyond the SoC, here’s what else stood out to me:
- eMMC on a Zero? The storage controller is configured with an 8-bit bus width and a comment describing it as driving “the eMMC/SD card”, which only really makes sense for eMMC. I’d love to see it, but I’m not expecting it to make the final board, as it’d push the price up on a range that lives and dies by its price tag. My money is on this being a leftover or an option kept open during development, and microSD being what we get.
- An SPI flash bootloader. The GPIO names include SPI flash lines, which suggests the Zero 3 W gets the same EEPROM-based bootloader as the Pi 4 (the Zero 2 W never had one). That should bring the Pi 4’s boot options along with it, and the ability to update the bootloader in the usual way.
- A single HDMI output, with the second HDMI controller permanently disabled. No surprise there given the form factor.
- A power button defined on GPIO 46 and mapped to KEY_POWER, so we may be getting a physical button (or at least a header for one) much like the Pi 5.
- Wi-Fi and Bluetooth wired up in the same way as the rest of the BCM2711 family, with a single ACT LED for status.
- The usual 40-pin GPIO layout (GPIO 0-27 with the ID EEPROM pins), so your existing HATs should be fine.
There are a couple of more speculative bits too. The PCIe controller is enabled and there are lines named PCIE_PWR_EN and PCIE_DET_WAKE, and the camera side pulls in a 4-lane CSI configuration rather than the 2-lane one the Pi 4 Model B uses. It’s worth noting that both device trees share a lot of copy-and-paste DNA (the Zero 3 W even has a duplicated “PWR_GPIO” line name), so I wouldn’t read too much into either of those until we see an actual board. I’d love to see PCIe exposed on a Zero, but I’m not holding my breath.
Raspberry Pi 4 Model A: The Return of the A
The second surprise is a Raspberry Pi 4 Model A. We haven’t had a Model A since the Raspberry Pi 3 Model A+ back in 2018, and the formula has always been the same: take the Model B, strip out the bits most people can live without (RJ45, some USB ports etc), and knock a chunk off the price. The Pi 4 Model A looks to follow that recipe pretty closely, though the price comment may not quite hold. Let’s see!
- No Ethernet. The Ethernet controller isn’t enabled anywhere, and the GPIO lines that drive the Ethernet PHY on the Model B have been repurposed. Very much in keeping with previous Model A boards.
- A single HDMI output rather than the Model B’s dual micro HDMI.
- No 3.5mm audio/composite jack. The analogue audio pins are empty and the composite video encoder is disabled, so audio will be over HDMI (or USB/I2S if you’re that way inclined).
- microSD only, with the same 1.8V signalling support as the Model B for the faster UHS card modes.
- External antenna support. This is the one I find most interesting. There are two antenna control lines (ANT_CTRL1 and ANT_CTRL2) and overlay parameters named ant1, ant2 and noant, which is exactly how the Compute Module 4 switches between its onboard antenna and an external U.FL connector. If that carries over to the final board, it’d be a lovely addition for anyone sticking a Pi in a metal enclosure.
- PWR and ACT LEDs, the same SPI flash bootloader setup as the Model B, and the same power button definition as the Zero 3 W.
The device tree doesn’t tell us anything about USB. On the Model B, the USB 3 ports made use of the PCIe bus, and the PCIe controller is enabled here too, so USB 3 is possible, but the 3 Model A+ only had a single USB-A port and I’d probably expect the same here.

Four Months of Zig
2026-10-27 · 15 min · #computing
It has been about four months since I returned to Zig after being absent for a few years. In this time, I have written some software in Zig and reengaged with the community, online and in person. Projects
The first project I started in Zig was snurl. It is a library for interacting with the smallnet (Gemini, Finger, Gopher, Spartan, and such). My goal has been to provide an alternative to curl for the smallnet, with similar testing and fuzzing requirements but on a smaller scale. Something I ran into early on was that the fuzzer didn't actually work. When getting excited about fuzzing in my last post, I didn't realize that the feature had not yet been completed. After this, I wrote a two programs which I have not published yet. The first is a small TUI typer racer. It was simpler than I expected to get a minimum version working so far. The second is an n-body simulator with stellar evolution using raylib.

What I've Liked
anyzig
I love anyzig. I've had to use zig master and 0.16.0 for different projects, and anyzig has made that doable.
Unfortunately, it breaks outside of directories without a build.zig.zon, meaning if you have tooling that requires a zig command to work, it can only occur in project directories. This breaks autoformatting for my one-off Zig scripts. Maybe a default zig version could be provided in that case.
IO and Allocators
I know it frustrates some people, but I love the fact that you have to pass IO and allocator parameters to functions in Zig.
Allocators
I'll start with allocators, since they've been around longer. For each Zig function you have to accept an explicit allocator parameter. This is different from most programming languages which either use a default allocator that may be changed globally or one changed by a local context (see Odin).
I like being able to change allocators for different parts of code. You might want an arena allocator for some things but need a general purpose allocator for others. Sometimes a FixedBufferAllocator is all you need to perform an operation. Zig's style makes this all obvious to handle.
I prefer Zig's system to Odin's implicit context system since Zig keeps things explicit. It's clear whether a function allocates memory or not, and hard to accidentally pass in the wrong allocator.
This is also superior to Rust's hidden, infallible allocations that panic when memory is exhausted. They're working on adding explicit allocations, but this will be yet another feature tacked onto the language rather than something built from the ground up.
It's much easier to reason about programs that allocate memory in Zig.

How solid-state transformers could help power the AI boom
New technology could help cut power losses and reinvent a staple of the grid.
Transformers are a crucial but nearly invisible part of our grid. The devices help efficiently move power across long distances, but they’re complicated and in short supply. And given that their basic design hasn’t changed much for about a century, they could use an upgrade.
As the world races to meet rising electricity demand from EVs, data centers, and more, researchers and companies are looking to modernize transformers. New, solid-state versions could help relieve some of the supply concerns and make sure the grid can handle the growing pressure.
Conventional transformers generally rely on huge amounts of specialized steel alloys and miles of copper wire to do their work of transferring electricity between circuits. Solid-state models, in comparison, combine magnetic components with high-power semiconductors, making them more compact and allowing for more control over the flow of electricity.
These devices are still in development, and can’t replace all traditional transformers today, especially the largest ones that work at the high voltages necessary for long-distance transmission. But a new generation of transformer technology could be a crucial part of our future grid.
The grid’s backbone
Moving electricity through the grid isn’t perfectly efficient: As electricity flows through power lines, some gets lost as heat. How much varies—the higher the voltage, the lower the current, and the less electricity gets lost. So a key function for the grid is stepping voltage up and down.
Consider, for example, your local solar plant. For that electricity to efficiently travel to your home hundreds of miles away, it needs to reach a higher voltage than what’s generated by the solar plant. Enter transformers.
In its path from the power plant to your outlets, electricity might go through one transformer at the solar farm and another at a substation nearby, stepping up the voltage twice to reach a high enough level to travel on high-voltage transmission lines. Solar panels also produce direct current (DC) electricity, which needs to be converted to alternating current (AC) via an inverter before it flows into a transformer. Closer to its destination, the voltage will be stepped down again, probably at least twice: once at another substation and again at a smaller transformer in your neighborhood.
If you’re in the US, electricity from a solar plant might be converted to AC by an inverter at around 480 volts, get stepped up to 115,000 volts for the transmission lines, and finally get stepped back down to 120 volts and 240 volts for your home.
Conventional transformers do this work using what essentially amount to loops of wire. The core of a transformer is typically made of a special type of steel called grain-oriented electrical steel. Coils of copper wire sit on either end of that core.
The number of loops in each coil determines the voltage on either end of the transformer: If there are more loops on the secondary coil than the primary, the voltage steps up, and if there are fewer, it steps down. When incoming electricity passes through loops on the upstream end of the transformer, that forms a magnetic field in the core. That field induces a voltage in the loops on the other side of the device, which is what allows the energy to continue flowing at a new voltage. This process is called magnetic induction.
Transformers form the backbone of electricity transmission and distribution, says Srdjan Lukic, a professor of electrical and computer engineering at North Carolina State University. In addition to doing the job of stepping up and down voltage, transformers also often provide what’s called galvanic isolation, meaning there’s no direct electrical path flowing through them. That can help limit disturbances from moving through the grid, improving safety.
The problem is that today’s transformers are big and bulky, and they’re also difficult and expensive to replace, Lukic says.
A solid option
Solid-state transformers essentially add so-called power electronics—semiconductors that convert and control electricity to the typical blueprint of today’s transformers.
While a conventional transformer operates at the frequency of the part of the grid it’s connected to, a solid-state transformer actually controls the frequency of the current. Typically, a solid-state transformer first converts incoming AC power from the grid to DC power, and then to a higher-frequency AC power using switches made of a semiconductor like silicon carbide.
From there, a magnetic component changes the voltage. Because the advanced semiconductors allow transformers to exert so much control over the frequency and stability of the current, the magnetic core can be much smaller than in a conventional transformer. Some come in at roughly one-tenth the size but have the same capacity, Lukic says.
Finally, additional power electronics convert the electricity from high-frequency AC to its required form—generally back to DC power and finally to lower-frequency AC.
Today, stepping voltage up and down is many transformers’ only job. But solid-state transformers can do much more. They absorb the jobs of devices like rectifiers and inverters (which convert AC to DC power and vice versa), shrinking the total footprint of the electrical equipment and potentially cutting the amount of power lost in the system.
In August, the New York Power Authority and the Electric Power Research Institute (EPRI) tested a one-megawatt solid-state transformer under realistic utility conditions at EPRI’s test site. The device was built in Lukic’s lab, and it was the first such test for a transformer of that capacity, he says.
The prototype was roughly 98% efficient—meaning it lost only 2% of the energy fed in. An equivalent conventional transformer and rectifier, by comparison, would be about 96% efficient together, Lukic says.

今天就以我的威联通NAS为例，带大家完整走一遍全部配置流程。
一、威联通NAS使用USB连接UPS，作为总控设备
这一步我们把UPS的USB线缆直连威联通，让它成为整个局域网的UPS总控主机。
1. 硬件接线
首先我们将威联通NAS的电源线，插在UPS的输出插座上，然后将UPS出厂附带的USB数据线，一头接UPS主机，另一头插入威联通NAS的USB接口。
同时需要注意，我们的交换机、路由器和其他需要断电保护的设备，也需要连接到UPS。
2. 威联通控制台UPS配置
接下来咱们登录威联通QTS后台，依次打开「控制台」>「硬件」>「UPS」。
UPS连接方式选择USB，勾选「启用UPS支持」后，页面会自动识别到接入的APC UPS设备信息。
这里需要注意，自动关机时间是整套时序的核心，威联通作为NUT主控，必须是整套环境里最后关机的设备。我自己把它设置为5分钟，后续所有从属客户端的关机触发条件，都要早于这个时间。
接下来勾选「启用网络UPS服务器」，在「允许的IP地址列表」，把局域网所有需要接入UPS联动的设备IP全部填写进去，例如Windows电脑和其他NAS的IP地址，不在这个白名单内的设备，会直接被拒绝NUT服务连接。
全部设置完成点击「应用」保存。
3. 验证NUT服务是否正常工作
打开SSH工具登录威联通NAS，输入下面两条命令验证服务状态。
# 列出本机全部NUT识别的UPS设备
upsc -l 127.0.0.1
# 读取UPS完整运行参数
upsc qnapups@127.0.0.1

作为从属客户端，关机等待时间一定要短于NUT主控的关机时间，保证自己先关机，让主控留到最后。
保存配置，如果页面可以正常刷出UPS电池、电压信息，就代表网络UPS客户端连接成功。当然这个GUI可能有点bug，如果刷不出UPS信息的话，也可以用SSH工具登录NAS，将IP替换为总控NAS的地址后进行测试。
upsc qnapups@192.168.10.70
三、Windows连接NAS的UPS信息并设置
Windows系统本身没有原生NUT客户端，这里我们使用开源免费的WinNUT-Client（GH上可下载），读取NAS NUT主控的UPS数据，实现市电断开之后Windows也能安全自动关机。
1. 安装与基础连接配置
下载安装WinNUT-Client，打开软件，进入「设置」>「选项」>「连接」标签页，填写下面参数：
- NUT主机：威联通NAS内网IP，比如我这里是192.168.10.70；
- NUT端口：3493；
- UPS名称：qnapups；
- 登录：qnapups；
- 密码：123456；
- 轮询间隔：5。
然后勾选「重新建立连接」，点击「应用」>「好的」。
连接成功后主界面就会直接展示UPS实时数据，比如输入电压、电池电量、负载、预估剩余续航等。
2. 关机选项配置
切换到「关机选项」标签页，按照下面的参考进行配置：
- 如果电池低于百分比则关机：30%；
- 如果续航时间低于则关机：120（单位秒，等于2分钟）；
- 即时停机操作：不勾选；
- 停机类型：关机；
- 延时关机（秒）：60，触发条件达成后，预留60秒给我们手动保存文档再执行关机；
- 允许的延时关机时间：不勾选；
- 关闭NUT的FSD信号：严禁勾选。
以上设置的含义是，电池低于阈值或者预估续航低于阈值，满足任意一条，就会启动倒计时关机。另外FSD是NUT协议的强制关机信号。当UPS电池濒临耗尽，NUT主控会下发FSD指令。如果勾选关闭这个选项，极端低电量场景Windows不会响应强制关机，会直接掉电，存在文件损坏风险。
3. 开启桌面自启动
切换到「其他」标签页，推荐勾选最小化到系统托盘、随Windows启动当前应用。
这里需要说明，随Windows启动当前应用，仅仅是登录Windows账户之后，自动打开前台该软件的GUI程序。
如果电脑开机停留在登录界面、没有人登录账户，那么WinNUT就不会启动，市电断电之后完全无法执行关机。如果你的主机需要7×24小时无人值守，可以使用NSSM等工具手动将WinNUT部署为Windows系统服务。
