Kronos is the first open-source foundation model for financial candlesticks (K-lines), trained on data from over 45 global exchanges.
- 🚩 [2025.11.10] Kronos has been accpeted by AAAI 2026.
- 🚩 [2025.08.17] We have released the scripts for fine-tuning! Check them out to adapt Kronos to your own tasks.

Kronos is a family of decoder-only foundation models, pre-trained specifically for the "language" of financial markets—K-line sequences. Unlike general-purpose TSFMs, Kronos is designed to handle the unique, high-noise characteristics of financial data. It leverages a novel two-stage framework:
- A specialized tokenizer first quantizes continuous, multi-dimensional K-line data (OHLCV) into hierarchical discrete tokens.
- A large, autoregressive Transformer is then pre-trained on these tokens, enabling it to serve as a unified model for diverse quantitative tasks.
We have set up a live demo to visualize Kronos's forecasting results. The webpage showcases a forecast for the BTC/USDT trading pair over the next 24 hours.
We release a family of pre-trained models with varying capacities to suit different computational and application needs. All models are readily accessible from the Hugging Face Hub.
- Install Python 3.10+, and then install the dependencies:
pip install -r requirements.txt
Forecasting with Kronos is straightforward using the KronosPredictor class. It handles data preprocessing, normalization, prediction, and inverse normalization, allowing you to get from raw data to forecasts in just a few lines of code.
Important Note: The max_context for Kronos-small and Kronos-base is 512. This is the maximum sequence length the model can process. For optimal performance, it is recommended that your input data length (i.e., lookback) does not exceed this limit. The KronosPredictor will automatically handle truncation for longer contexts.
Here is a step-by-step guide to making your first forecast.
First, load a pre-trained Kronos model and its corresponding tokenizer from the Hugging Face Hub.

Create an instance of KronosPredictor, passing the model, tokenizer, and desired device.
# Initialize the predictor
predictor = KronosPredictor(model, tokenizer, max_context=512)
The predict method requires three main inputs:
- df: A pandas DataFrame containing the historical K-line data. It must include columns ['open', 'high', 'low', 'close']. volume and amount are optional.
- x_timestamp: A pandas Series of timestamps corresponding to the historical data in df.
- y_timestamp: A pandas Series of timestamps for the future periods you want to predict.
import pandas as pd
# Load your data
df = pd.read_csv("./data/XSHG_5min_600977.csv")
df['timestamps'] = pd.to_datetime(df['timestamps'])
# Define context window and prediction length
lookback = 400
pred_len = 120
# Prepare inputs for the predictor
x_df = df.loc[:lookback-1, ['open', 'high', 'low', 'close', 'volume', 'amount']]
x_timestamp = df.loc[:lookback-1, 'timestamps']
y_timestamp = df.loc[lookback:lookback+pred_len-1, 'timestamps']
Call the predict method to generate forecasts. You can control the sampling process with parameters like T, top_p, and sample_count for probabilistic forecasting.
# Generate predictions
pred_df = predictor.predict(
    df=x_df,
    x_timestamp=x_timestamp,
    y_timestamp=y_timestamp,
    pred_len=pred_len,
    T=1.0,          # Temperature for sampling
    top_p=0.9,      # Nucleus sampling probability
    sample_count=1  # Number of forecast paths to generate and average
)
print("Forecasted Data Head:")
print(pred_df.head())
The predict method returns a pandas DataFrame containing the forecasted values for open, high, low, close, volume, and amount, indexed by the y_timestamp you provided.
For efficient processing of multiple time series, Kronos provides a predict_batch method that enables parallel prediction on multiple datasets simultaneously. This is particularly useful when you need to forecast multiple assets or time periods at once.
# Prepare multiple datasets for batch prediction
df_list = [df1, df2, df3]  # List of DataFrames

pred_df_list = predictor.predict_batch(
    df_list=df_list,
    x_timestamp_list=x_timestamp_list,
    y_timestamp_list=y_timestamp_list,
    pred_len=pred_len,
    T=1.0,
    top_p=0.9,
    sample_count=1,
    verbose=True
)
# pred_df_list contains prediction results in the same order as input
for i, pred_df in enumerate(pred_df_list):
    print(f"Predictions for series {i}:")
    print(pred_df.head())

Local Code：本地优先的 AI Agent 工具
- 平台：macOS
- 关键词：本地模型、AI、代理
@化学心情下2：随着 AI 的普及，不少朋友或多或少都在自己的电脑上用起了各种 AI agent 来提高效率。不过市面上的 AI agent 几乎都是基于云端提供的模型能力，必须连接互联网才能使用大模型的推理能力。
如何用自己的电脑来运行大模型呢？动手能力不错的朋友或许习惯通过 Ollma 下载管理模型然后本地调用，但对一般使用者而言，有没有简单易懂的本地化模型部署方案呢？
Local Code 是一款适用于 Mac 平台的、本地优先的 AI Agent 工具，相比专业的模型部署工具 Ollma，Local Code 专注于为 Mac 设备提供最优解——应用一共就提供三种本地模型，初始化时会根据设备配置匹配最合适的本地模型，比如笔者的 M4 处理器的 Macbook Air 因为仅有 16GB 运存只能选择最低阶的 Qwen 3.8 27B，选好模型、下载好模型文件并完成设置后，就可以进入到 Local Code 的主界面了。
Local Code 在功能上和市面主流 AI Agent 工具并没什么太大的差距，你可以通过侧边栏中的项目文件夹来展开对话，对话支持添加图片、文档等附件，也可以使用语音方式交互；最左侧也可以对插件进行微调，比如在设置中可以选择使用设备端的模型还是云端模型，推理强度可以根据机器本身的性能调整，我这里因为性能较弱直接拉到低，至于思考预算同样也需要根据本地机器性能来选择。插件设置中还有是否启用一些权限或者功能的选项，说实话比起成熟的商业化 AI Agent 工具差距可能不是一点半点。
在侧边栏的芯片按钮中，你还可以对模型进行调整，比如是否预热、空闲多久后卸载模型、是否为 8bit S 模型使用 Apple Neural Engine 等。不清楚的话保持默认就可以。
实际模型吞吐效果方面，我这里因为设备配置一般所以体验差强人意，采用高思考模式一个简单的 GitHub 项目分析可能要接近 1 个小时，令牌生产速度几乎是个位数；简单文本总结任务中速度略快但令牌生产速度也只有几十，可见基于消费级硬件 NPU 能力跑大模型，其实完全无法达到现在商业云端模型的输出速度。
当然，如果你的 Mac 性能更高，甚至可以运行量化后的 DeepSeek 4.1 Flash 1017，那我的上述体验就不具备参考性了。
Local Code 给那些想要尝试本地运行大模型，但不清楚如何部署、下载等繁复流程的朋友一个更易上手的平台，操作上也较为傻瓜。不过对于低端的 Mac 而言，整体算力瓶颈导致的体验问题依然存在，配置一般的朋友建议尝鲜为主。Local Code 采用本地运行免费、云端模型另外收费的商业模式，如果你比较感兴趣可以在其官方网站下载。

Vimpo 的核心功能之一是自动生成双语字幕。传统的视频字幕工具通常需要依赖视频原有的字幕，或者将视频上传到云端进行语音识别，Vimpo 则采用了本机语音识别与外部大语言模型翻译相结合的方式，它内置 Whisper 语音识别模型，可以直接在 Mac 上运行并将视频中的语音识别转换成文字，因为不需要上传视频，所以本地方案也支持离线识别。
Whisper 语音识别的准确度受限于模型尺寸和准确度，Vimpo 提供了多种规格的模型选项，在我们下载视频时会推荐合适的模型。我们也可以进入应用的设置 - 语音识别，查看内置模型的大小、速度、准确度，根据自己 Mac 的硬件性能，在识别速度和准确度之间进行选择。默认情况下，推荐的 Large v3 Turbo（压缩版）可以较好地完成识别任务，不过偶尔也会出现错误，比如将 iPhone Duo 识别为 iPhone 2。

Vimpo 对字幕的智能处理功能，包括智能断句、人名纠错、术语统一等，可以让长视频的字幕更加易读。播放时可以同时显示原文和译文，并自定义字体、颜色、位置等样式。
Vimpo 将视频播放界面称为「影院」，在这里我们可以同时观看视频、阅读双语字幕和查看完整文稿。点击文稿中的某句话，播放器便会自动跳转到对应时间点。这种设计让视频观看和文字阅读形成联动。遇到听不懂的内容可以直接通过文稿定位，不必反复拖动进度条寻找。

@Peggy_：笔记类应用经过多年混战，基本形成了较为稳定的竞争局面，喜欢研究和存储各类资料的用户，可以使用支持双向链接的知识库类型的笔记应用，喜欢产出内容且对排版要求并不严苛的用户，则大多使用各类对纯文本格式支持较好的笔记应用。再进一步细分的话，是否支持网络同步、能否跨平台……都是用户选择笔记应用时的重要参考因素。

不同之处在于，org 格式的文本诞生之初便是为了解决任务管理和信息组织的问题，对任务和代办类事项的语法支持更加完善。Bloom 也恰好是一款原生支持 org 格式的笔记应用。打开应用后，Bloom 为我们准备了三个内置模板，分别是日记、快速笔记以及任务笔记，我们可以根据自己的笔记需求修改或是添加模板。

安全性方面，你可以选择将所有内容保存在手机上，或是自行使用云同步软件将相应的本地文件夹备份至云端。跨平台使用同样简单易操作，你在 Bloom 中撰写的所有文件均能在其他平台上通过支持 org 格式的编辑器打开并继续编辑。

包装与配件 | Package & Accessories
AirPods 5 的包装依然还是那个白色方形纸盒，跟四代相比只有主图换了个角度而已，没有任何配件。
设计、佩戴表现与声学结构 | Design, Fit & Acoustic Structure
仅从外观上来看，AirPods 5 这一代其实跟 AirPods 4 几乎没有肉眼可察觉的区别，依然只有白色、依然是那个易划伤的亮面塑料、依然是非常小体积的充电盒，你甚至可以把两边的耳机本体对换充电…… 不过这并不意味着什么都没改。
AirPods 5 这次虽然两个版本都有一样的主动降噪性能，但是充电盒和耳机电池部分有明显区别，基础版没有盒身的扬声器和无线充电线圈，所以看上去视觉上是更一体的，但功能的确有缩减。无线充电版本则保留了 4 ANC 上的盒身扬声器和无线充电线圈。盒身的开盖手感完全一致，有轻度的弹性反馈。USB-C 口的做工细节有一些变化，具体可以看图。配对也还是通过敲击正面两下调取，隐藏式 LED 灯也完全一致。
耳机本体在盒内固定得还是相当稳的，只是从四代以来都一直存在的不太方便取出的情况也一并延续了下来，如果你和我一样手指头偏粗，那么需要习惯一下这个过程。耳机是典型的短柄 pods 式造型，从外观上跟四代没有任何区别，但是按照 Apple 发布会上讲到的，应该是内腔做了新结构来改善单元通气量。依然是和四代完全一样的比较饱满的长扁圆腔体，纵向上有所拉伸，开口位置仍然有所偏置，而非 AirPods 3 时代（也是当下大部分半入耳 TWS）采用的比较规矩的开口。在合理的佩戴下，漏音和漏气都控制得比较好。
实际佩戴下来我们也没有感知到跟 AirPods 4 系列的差别，都是相对贴合且佩戴压力较低的状态，对于大部分中大耳廓用户来说，AirPods 4 / 5 都应该有比常规半入耳形态更加扎实稳定的佩戴感受，常规强度的运动也不至于容易掉落。而小耳廓用户依然建议先试戴再做决定，由于两代外观一致，如果之前能够佩戴好 AirPods 4 系列，5 也不必担心。
相较于 AirPods 4 的 IP54 防尘防泼溅，AirPods 5 全系和 Pro 3 一样都是耳机本体与充电盒均支持 IP57 级别防尘防水，升级显著，现在它们在最深 1 米的水下停留时间最长可达 30 分钟，一般运动场景和小雨等也就用起来更加放心一些。
操作与软件端功能 | Control & APP
AirPods 5 的机身操作依然依靠捏动柄部的触控区域进行，识别区域有专门的凹槽用于盲操。操作反馈的提示音比较清晰，反应迅速。可以识别单次、双次、三次按压以及长按操作。四代阉割了上下滑动操作，而五代加了回来，可惜只有那个五小时续航、带无线充电的版本支持，真是「等级森严」。好在，对于 AirPods 系列的操作识别准确度与识别效率，你不必担心，它仍然是非常跟手、相当准确的，提示音音量以及佩戴识别的表现都是行业第一梯队的顶尖水平。
在 iOS 27 更新之后，现在你可以通过设置实现更加复杂的功能设置，它依然保留了个性化音量、对话感知等功能，也可以开关人耳检测和进行空间音频的个性化，并且自定义操作逻辑等。头部动作的感知表现依然好用，现在也有了作为相机遥控器使用的设置项。
对，在我们手上的没有无线充电支持的版本中，苹果不光没有提供充电盒上的扬声器，连精确查找都阉割了…… 你只能购买那个定价 1149 元的无线充电版本才能获得精确查找。那么就 999 这个版本来说，它辅助查找的提示音全靠耳机发出，在盒外时这个音量其实还好，安静室内能够比较容易察觉到，但是稍微嘈杂一点的地方就不好说了（但仍比大多数依靠耳机发声辅助寻找的其他品牌耳机要更响）。放在盒内的状态，这个音量就基本上没有什么实用性可言。
降噪/通透/通话 | ANC, Transparency & Call
相较于 AirPods 4，AirPods 5 的腔体外观没有明显的改变，但是内部结构有一些变化，加上半入耳没法真正与耳廓稳定耦合的特性，我们大体上可以判断出两代产品的被动隔音能力其实相差不多，但是在佩戴状态类似的情况下，5 会比 4 略微少一点高频噪音。
作为半入耳降噪耳机，AirPods 5 提供的各项主动降噪相关模式选择跟 Pro 系列其实是一样的。在更新到 iOS 27 之后，AirPods 4 ANC、5、Pro 2、Pro 3 都有了自适应可调档位的滑钮。我们在降噪开启状态体验，AirPods 5 对于稳定低频噪音的抑制是非常明显的，即使放在入耳 TWS 里面也属于第一梯队的水准了。人声中下盘的减弱也非常显著，我们和 AirPods 4 ANC、Freebuds 7（开启智慧降噪）同时对比，AirPods 5 的中低频降噪优势都非常大，甚至接近于 AirPods Pro 2 的水平了。尽管在不经过 ab 的情况下，Freebuds 7 和 Galaxy Buds4 都能够在日常通勤过程中有不错的表现，但距离 AirPods 4 ANC 都还有点距离，更不用提 5 了。
频宽覆盖方面，受限于半入耳没法获得很好的高频隔音，那么有效频段的降噪表现几乎都需要主动降噪来参与，H2 芯片的 AirPods 产品都有着很好的降噪频宽覆盖能力，AirPods 5 亦然。它在人声基音频段的抑制能力其实与 4 ANC 不会明显好一个档次，但是对于人声吐字的细节会进一步弱化，也就会在嘈杂的咖啡厅、商场这类场所中感知到进一步减少的人声比例。背景音乐的强度也会有所下降。这一点也接近于甚至达到了很多入耳式第一档靠后的水准，非常不容易。
半入耳的耦合不稳定还会带来一个问题，就是自适应能力也会受到影响。尽管同样使用 H2 芯片，AirPods 5 对于佩戴调整或者咀嚼等情况导致的佩戴松动都有着非常迅速的补偿，比 AirPods 4 ANC 明显更快，几乎是佩戴调整后的一瞬间就完成了。目前半入耳领域最快的自适应，基本上就是来自于 AirPods 5。耳压感方面，其实与 AirPods 4 ANC 差别不是很大。尤其是在地铁、飞机这种有稳定低频噪音的环境，AirPods 4 会给你一种它一直在计算做适应的感觉，5 就明显更加自然，不会漏掉一些东西。
抗风噪方面，AirPods 5 和 4 ANC 类似，开启降噪之后都对于正面、侧面吹来的风源出现时会出现一定的风噪，但背后的影响不大，相较于 Freebuds 7 的智慧动态降噪状态，这俩对于风源的识别没有那么高效。不过在开启自适应之后，AirPods 5 的风噪会削减一些，虽不是完全干净，但也已经不怎么会影响正常听音了。
通透模式方面，AirPods 5 依然保持了和 4 ANC 在新系统下的优秀水准，自然度和对话可用性都足够高，仅有微弱的高频衰减，相较于降噪关闭的状态会有更自然的高频补足，没有对于单一频段的突出。通透模式下的风噪表现非常微弱，这也与它跟入耳 TWS 的通透需要作用全频段的设计不同有关，它基本上只在高频工作即可，避开了风噪所在的主要频段。
通话方面，AirPods 5 搭载了双波束成形麦克风。我们实际在运营商环境进行通话，AirPods 5 的通话收音响度跟上一代区别不大，清晰度也相对一致，音色仅略微偏闷，对于环境噪音的抑制还是比较明显的，且干预痕迹也比较易于感知。通话抗风噪方面，或许是初始固件的原因？目前在侧对和背对两个方向的风源下，仍然有比较明显的风噪影响，跟 AirPods 4 目前固件下以及 Freebuds 7 的状态有差距，需要进一步优化。
AirPods 5 的降噪各项能力在已经很出色的 4 ANC 基础上更进一步，在低频降噪深度、中高频深度以及自适应优化上做得更好。相较于近期的 Freebuds 7 高频还有轻微增噪的表现来说，近两代 AirPods 半入耳还是有一些优势的。AirPods 5 的降噪综合性能仍然是目前半入耳降噪耳机的最强型号，比很多第一档的入耳 TWS 还要在频宽覆盖和自适应能力以及通透表现上更好，但是它的通话抗风噪还需要进一步优化。它依然可以进入 TDS 降噪综合能力金字塔的 In-Ear Skyline Level，比 AirPods 4 ANC 排名更靠前，但在它面前仍然有一些入耳型号更优先。
额外补一句，目前的半入耳降噪能力格局基本就是 AirPods 5 和 4 ANC 处在第一档，Freebuds 7 第二档，顶多加上 Galaxy Buds4，其他现产中高端型号几乎都不是堪用的状态。在购买此类设备时还是可以有个心理预期的。
信号与续航 | Connection & Battery
蓝牙 5.3 版本结合基础的编解码器，我们认为 AirPods 5 也不应在基本的信号稳定性上出问题。连接标准测试设备 iPhone 17 和 Xperia 1 V，在 WLAN 开启或关闭的情况下近场都很难出现卡顿丢包情况，在隔墙且间隔约 11m 处开始出现丢包，12m 开外会开始出现卡顿问题。基本上可以说常规环境都有着比较出色的 AAC 信号稳定性表现。
在苹果生态之间切换时，AirPods 5 依然具备非常高的流畅度，不用担心这方面有所缩减。延迟方面，我们在默认的状态下以 AAC 编解码器连接 iPhone 17，进行流媒体视频和本地视频观看，延迟大概控制在正常语速少于半个字，和 AirPods Pro 2/3、AirPods 4 ANC 类似，都保持了非常好的生态内延迟控制。
续航方面，AirPods 5 的官方标称续航是有线充电版 4h/6h（降噪开/关）、无线充电版 5h/7h（降噪开/关），结合充电盒在开启降噪时分别可到 20h 和 22h。Apple 在测试过程中关闭了空间音频和对话感知功能，具体的测量过程在官网都有详细说明，这点一直做得不错。个人经过标准流程测试下来，基于有线充电版本，关闭电池充电优化，开启主动降噪，空间化立体声固定，不开启自适应音量，以 AAC 编解码器连接 iPhone 17，以 50% 音量（iOS 音频后台实时显示响度稳定在 58~64 dB）连续播放流媒体音乐（Apple Music Lossless）、播客节目（小宇宙），仅耳机续航为 4 小时 44 分钟，略超官方描述。

AirPods 5 搭载了「Apple 定制的高振幅驱动单元」和「定制的高动态范围放大器」——反正就是一颗直径未知、强调冲程的动圈单元以及性能不错的 DAC 和 AMP 电路。支持的编码依旧是 SBC / AAC，没有任何意外惊喜。

Apple 智能将随 iOS 27.3 登陆中国
10 月 31 日，苹果宣布，首批 Apple 智能（Apple Intelligence）的核心功能即将在中国推出。这涵盖系统全局的写作工具、照片 app 消除工具与自然语言搜索、智绘表情、邮件与通知摘要，以及无缝整合在信息、通话中的实时翻译功能。此外，Siri 升级了连贯对话与文字输入支持，并可调用千问以协助回答复杂问题或生成原创内容。

该功能支持 iPhone 16 及后续机型、iPhone Duo、iPhone Air 以及 iPhone 15 Pro 系列，设备与 Siri 语言须设为简体中文或英文。本轮更新不包含 WWDC 2026 宣布的下一代 Siri AI 功能，对 iPhone 以外其他平台的支持将在获得相关监管审批后推出。

自 2005 年推出 iPod Nano 以来，苹果长期是全球最大闪存买家，能够通过审计供应商账目确保最低采购价，并在跌价时拒收定制芯片。2023 年行业低谷期，全球闪存行业营业亏损达 190 亿美元，而苹果同年靠出售额外存储空间赚取了 140 亿美元毛利。两年前，苹果的闪存采购量还两倍于微软、亚马逊、Meta 和谷歌的总和。

成本暴涨压缩了苹果丰厚的存储升级利润。截至 2025 年，iPhone 与 iPad 存储升级业务平均毛利率超过 80%。以 256 GB 升至 512 GB 为例，去年 iPhone 17 Pro 的闪存成本仅 15 美元（售价 200 美元），今年 iPhone 18 Pro 则升至 66 美元。苹果近期已全面上调产品价格，iPhone 平均涨价 13%，连往年通常降价的旧款机型也一并提价。

据 Bleeping Computer 报道，10 月 29 日，AI 代码编辑器 Cursor 的扩展市场遭遇恶意供应链攻击，一款冒用 Anthropic 官方名义的 Claude Code 插件（版本 2.1.313）在市场上架流通约 11 小时，波及多达 5000 名开发者。该插件内嵌恶意 JavaScript 代码，试图在受害者系统中植入持久化 SSH 后门。

分析显示，百度网盘广告框架设有名为 NoShake 的变体。该变体不依赖常规的 CoreMotion 动作监听，而是调用苹果 Core Location 框架中的 CLHeading 接口，获取设备相对于磁北的朝向及三轴磁场数据。手机姿态变化引起磁力计数据波动时，广告组件即可判定设备发生晃动并触发跳转。
报告还披露了 SDK 中的免点击分支：当特定参数组合满足条件时，触发后等待约 1 秒，即便用户未点击，系统也会自动执行广告点击流程；部分参数组合甚至可在触发后直接进入点击流程。不过由于分析未采集线上真实广告响应，尚无法确认实际投放启用了哪组参数。

据《华尔街日报》报道，全球最大加密货币交易所币安（Binance）遭遇加密货币史上规模最大的黑客盗窃案，被盗资产价值达 63 亿美元。网络安全研究人员与调查机构指出，黑客通过入侵一名币安工程师的电脑等方式渗透了内网系统，初步判定幕后黑手为朝鲜黑客组织 TraderTraitor。

In China, professional postgraduate courses focus on training students to solve problems in a particular line of work rather than developing research skills, as they would in an academic degree. These reforms are a step in the right direction because students preparing for professional careers should be trained and assessed in ways that reflect those careers, says Futao Huang, a researcher of higher-education policy at Hiroshima University in Higashihiroshima, Japan. “The real challenge is to develop credible, transparent and profession-specific standards for assessing practical achievements,” Huang adds.
Real-life problems
For students pursuing a professional degree in clinical medicine, the new graduation pathway means that they can be assessed on the contribution that their research will bring to patients and society, says Zhou Feifei, a spinal surgeon at Peking University Third Hospital in Beijing. “This will encourage them to find problems in real life and to address the problem using a scientific way,” he adds.

When a developer gives an AI agent a coding task, the agent does more than answer once. It plans, generates code, runs tests, and repeats the process to correct errors. A single task can use 10 to 50 times more tokens than a basic chat prompt. The more useful the agent becomes, the more calls it makes. With per-token pricing, the workflows creating the most value can also become the most expensive.
The financial pressure is already visible. Uber reportedly exhausted its entire 2026 AI budget by April after expanding its use of Claude Code. GitHub Copilot moved from flat-rate pricing to metered credits. Gartner predicts that AI coding token costs will surpass average developer salaries by 2028.
The natural response is rationing usage caps, seat limits, and approvals before developers launch agents. But blanket limits can restrict the workflows delivering value. They also optimize the wrong number. Cost per token measures consumption, not results. Some spending reflects waste, including retries and runaway loops. Some represents the work of shipping software. A meter cannot distinguish them, and neither can a spending cap.
Measure the software that ships
A better measure is cost per merged pull request: total AI-assisted development cost divided by the number of changes that pass review and are merged. Track rework and defects alongside it so cheaper changes do not conceal lower quality.
If that cost falls as AI usage rises, without compromising quality, developers are converting more consumption into useful software. The question is not how many tokens they use, but how much finished work the investment produces.
Improving that equation requires two changes: reserve expensive inference for tasks that need it, and lower the cost of routine work.
Match the model to the task
Agentic coding does not require the most powerful model at every step. Use a frontier model, or an on-premises flagship when policy requires it, for difficult planning and novel reasoning. Route suitable work, including code generation, test creation, and repeated refactoring, to open-weight models you operate yourself.
A gateway can route requests according to task complexity, data sensitivity, cost, and latency. This reserves premium inference for the moments that justify it rather than applying premium pricing to an entire workflow. Meter the exception, not the workload.
Open-weight models make this division increasingly practical. Software-engineering benchmarks show that leading open-weight models can approach frontier performance on some tasks. Power, operations, maintenance, and depreciation all must be considered. The number that matters is the fully loaded cost per merged pull request.
Owned capacity also delivers a type of value that never appears on an invoice: control over sensitive code. When code generation and testing run on-premises, proprietary code stays inside the enterprise. Only approved planning prompts and governed exceptions go to external models, through a gateway the organization controls. That opens the sensitive repositories where security usually stalls adoption, and where the biggest gains are waiting.

At HPE, a hybrid AI platform routes routine workloads from more than 150 internal applications to open-weight models running on premises, including on HPE Private Cloud AI. The result: token costs down 30 to 50%.
That is the point of hybrid. With HPE Private Cloud AI, owning your inference does not mean giving up frontier models. Run the volume on capacity you own and let a gateway send the hardest work.

Owned capacity is not for everyone. Low or unpredictable usage favors APIs, with no capital tied up in idle infrastructure. Ownership pays off when sustained demand keeps it busy. Most enterprises will run hybrid: frontier APIs for demanding or intermittent work, owned capacity for repeatable volume. As developers lean harder on coding agents, usage will keep rising. The real choice is whether that growth shows up as a bigger variable-cost bill or as more software shipped on capacity you own. To illustrate what this might look like, Berners-Lee and his colleagues told a story about a pair of siblings who use their agents to automatically research and book physical therapy appointments for their mother, making sure they would be covered by insurance and fit their busy calendars.
At the turn of the millennium, this vision seemed far-fetched: Google had only been online for a couple of years, and most people were still on dial-up connections. But a quarter-century on, the dream of autonomous software agents that use the internet and carry out tasks for us has finally been realized. New tools such as Meta’s blockbuster Muse agent, OpenAI’s Dots, and Anthropic’s Claude Duet are being given access to people’s email inboxes and bank accounts, Meanwhile, in a series of worrying incidents, agents created by OpenAI broke free of their sandboxes and caused havoc online.
