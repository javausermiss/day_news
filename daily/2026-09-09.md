MarkItDown is a lightweight Python utility for converting various files to Markdown for use with LLMs and related text analysis pipelines. To this end, it is most comparable to textract, but with a focus on preserving important document structure and content as Markdown (including: headings, lists, tables, links, etc.) While the output is often reasonably presentable and human-friendly, it is meant to be consumed by text analysis tools -- and may not be the best option for high-fidelity document conversions for human consumption.
MarkItDown currently supports the conversion from:
- PowerPoint
- Word
- Excel
- Images (EXIF metadata and OCR)
- Audio (EXIF metadata and speech transcription)
- HTML
- Text-based formats (CSV, JSON, XML)
- ZIP files (iterates over contents)
- YouTube URLs
- EPubs
- ... and more!
Markdown is extremely close to plain text, with minimal markup or formatting, but still provides a way to represent important document structure. Mainstream LLMs, such as OpenAI's GPT-4o, natively "speak" Markdown, and often incorporate Markdown into their responses unprompted. This suggests that they have been trained on vast amounts of Markdown-formatted text, and understand it well. As a side benefit, Markdown conventions are also highly token-efficient.

The other half of the context problem.
Every MCP tool call dumps raw data into your context window. A Playwright snapshot costs 56 KB. Twenty GitHub issues cost 59 KB. One access log — 45 KB. After 30 minutes, 40% of your context is gone. And when the agent compacts the conversation to free space, it forgets which files it was editing, what tasks are in progress, and what you last asked for. On top of that, the agent wastes output tokens on filler, pleasantries, and verbose explanations — burning context from both sides.
Context Mode is an MCP server that solves all four sides of this problem:
- 
Context Saving — Sandbox tools keep raw data out of the context window. 315 KB becomes 5.4 KB. 98% reduction.
- 
Session Continuity — Every file edit, git operation, task, error, and user decision is tracked in SQLite. When the conversation compacts, context-mode doesn't dump this data back into context — it indexes events into FTS5 and retrieves only what's relevant via BM25 search. The model picks up exactly where you left off. If you don't --continue , previous session data is deleted immediately — a fresh session means a clean slate.
- 
Think in Code — The LLM should program the analysis, not compute it. Instead of reading 50 files into context to count functions, the agent writes a script that does the counting and console.log() s only the result. One script replaces ten tool calls and saves 100x context. This is a mandatory paradigm across all 17 supported clients, plus the OpenClaw gateway integration: stop treating the LLM as a data processor, treat it as a code generator.// Before: 47 × Read() = 700 KB. After: 1 × ctx_execute() = 3.6 KB. ctx_execute("javascript", ` const files = fs.readdirSync('src').filter(f => f.endsWith('.ts')); files.forEach(f => console.log(f + ': ' + fs.readFileSync('src/'+f,'utf8').split('\\n').length + ' lines')); `);
- 
No prose-style enforcement — context-mode keeps raw data out of context but never dictates how the model writes its final answer. Brevity, completeness, formatting — your model's call (or yours via your own CLAUDE.md /AGENTS.md ). The drawing is made of strokes, not pixels. How to build a f**king printer
I was planning to build an e-ink display when I came across the Xteink X3 online. Somewhere in the fine print, it said the thing was fully programmable.
I was sold.

Yuck.
While looking for a nicer way to send things to it, a thought struck me. If it looks like paper, it should act like paper.
I should be able to print on it.
What makes a printer a printer?
I wanted to open something on my MacBook, press Print, and pick the Xteink. That meant finding out what my computer expected to find at the other end.
I ended up in the Internet Printing Protocol, or IPP. It lets a computer ask a printer what it supports, submit a document, and ask what happened to the job. The messages travel over HTTP. An operation such as Get-Printer-Attributes asks about capabilities; Print-Job sends the work.
I advertised monochrome output, 300 dpi, one copy, and one-sided printing. For document formats, I accepted Apple raster and PWG raster. That meant the Mac had to turn the document into pixels before sending it. penguin would shrink the result to fit its screen.
I declared A5 and Letter paper, media type stationery, and an output bin called face-up.
I called it penguin. It had the right color scheme.
I used Bonjour to announce an _ipp._tcp service under that name. The advertisement included the formats I accepted and the address where print jobs should go.
To get driverless discovery on macOS, I also had to add the _universal subtype. That meant calling ESP-IDF’s mDNS API directly, because the Arduino wrapper didn’t expose it.
Getting the computer to send a page was only part of the job. I still had to receive it on this thing.
Where do I put the page?
A Letter page at 300 dpi is 2,550 × 3,300 pixels. At one byte per grayscale pixel, that’s about 8.4 MB uncompressed.
The X3 has 400 KB of RAM, with 16 KB reserved for cache. I needed to run Wi-Fi, run a printer server, and somehow receive an entire fucking page.
With Wi-Fi running and the printer’s page image allocated, I had 6.8 KB of heap left.
I remembered mmap on Linux. Could I do something like that with the SD card and pretend I had more RAM? The C3’s memory-mapping support was for flash, not files on the SD card.
But wait. Could I make the display my storage?
What if I passed the incoming page through a transformation pipeline and wrote the result straight to the display? Decode the pixels, shrink them to fit, dither them into black and white. As soon as a row was ready, put it in its place on the display and reuse the working space. Keep going until I have a page.
The display already had RAM reserved for its screen image. I could build the page right there as it arrived. Until then, I had been assembling a whole second image just to copy it over.
My decoder already worked row by row. I changed the scaler to hand over finished rows too and wired those into the display’s screen image. At first, I let the page appear in bands, like paper feeding out of a printer. Each intermediate refresh took roughly half a second, so I switched to showing the finished page all at once.
I saved the finished page as a BMP on the SD card using the existing screenshot writer.
That gave the network stack room for its socket buffers.
There was a penguin in Preview
I had a sample manga image from Mushoku Tensei on my MacBook for some reason. I opened it in Preview and went to print it.
There was penguin in the printer list.
Holy shit.
I selected it and printed. The manga page looked really good on the Xteink. From memory, it took about a second to appear. It’s still there.
I spent an evening getting to that first print.
The printer server runs on the reader itself. I can have it join a Wi-Fi network or start its own hotspot, literate-penguin.
My penguin can read now.
The code is in my CrossPoint fork, including the printer implementation.
Saved printouts stay on the SD card, and I can browse them on the reader. My printer has an output tray after all. It’s a folder.

Ultimately, she thinks, this approach could help make data centers (and our laptops and phones) much more energy efficient.
When conventional computer chips perform calculations, they erase the information they no longer need along the way, dissipating energy as heat in the process. Earley compares the approach to racing through a city only to pump the brakes at every intersection: The car loses momentum and must burn more fuel to accelerate again. Reversible computing aims to keep the momentum going—instead of erasing information from the intermediate steps in a calculation, the circuit retains it, making it possible to run the computation backward and recover some of the energy.
While the idea was first proposed more than 50 years ago, it proved impractical to implement with existing transistors and circuits. 什么是随航？
或许有些读者对随航还不太熟悉。简单来说，随航（Sidecar）就是通过无线或有线传输的方式，将你的 iPad 作为 Mac 的扩展显示屏。不需要复杂的 App 连接、也不需要数据线，只需打开 Mac 和 iPad 进行配对，Mac 便拥有了第二块屏幕。
你可以在 macOS 菜单栏中点击「控制中心 > 屏幕镜像」，然后在「镜像或扩展至」一栏中选择对应的 iPad 来开启随航。Mac 会通过蓝牙查找 iPad，然后以点对点 Wi-Fi 的形式传输画面。
你也可以前往「系统设置 > 显示器」中，在底部选择「镜像或扩展至 iPad」，然后从列表中选择一部 iPad。
连接完成后，iPad 会像普通外接显示器一样出现在 macOS 的显示器设置中，你可以调整它的位置、分辨率以及镜像或扩展方式。这里就不再赘言了。
除此之外，随航也针对 iPad 的特性进行了一些扩展，前文提到的「触控」特性便是其中之一。另外随航从推出之初便支持 Apple Pencil，你可以直接在 iPad 屏幕上使用 Apple Pencil 操作 Mac 应用；在兼容的应用中，压感、倾斜等笔触信息也能得到保留。从某种程度上说，开启随航的 iPad 可以当作一块带屏幕的数位板使用。

在「随航」成为官方功能之前
从功能和体验层面来说，随航可以说是相当完善，但「让 iPad 变成 Mac 副屏」其实并不是 Apple 首创的想法——事实上，在第一代 iPad 正式发售的当天这一概念便已落地，并以一款 iPad「首发 App」的形式登陆 App Store。
它叫 iDisplay，由 SHAPE Services 开发。
iDisplay 会在 Mac 中安装一套扩展驱动，创建一块系统能够识别的虚拟显示器，再通过 Wi-Fi 将画面发送到 iPad。用户可以像使用普通副屏一样排列两块屏幕，把 Mac 窗口拖到 iPad 上；甚至在遥远的 2010 年，iDisplay 就能「十分先进」地将 iPad 的触摸及键入操作反向传回 Mac。
只是这款诞生于 iPad 发售之初的软件远远谈不上「流畅」，甚至有着堪称灾难的使用体验：无论是繁琐的前期设置、极不稳定的连接，还是动辄数秒的延迟，都表明它更像是一次对新技术的探索，而非成熟的解决方案。
所以同年，Avatron Software 推出了 Air Display。它采用了与 iDisplay 相似的思路，进行了一部分的优化，不过仍称不上「好用」，动态画面仍有不小的延迟。此后几年，围绕「iPad 作为扩展副屏」的解决方案不断涌现，但总体而言，彼时「将 iPad 作为扩展副屏」这个点子在大多数人看来还是一种新奇的功能玩法，或是应急需求，没有人真正将它视作生产力的一部分。
读到这相信你也在想：既然「无线」带来了那么多问题，那加上一根线不就行了？巧了，正有一群和你抱有同样想法的前 Apple 工程师。于是 Duet Display 来了。
与上述使用过 Wi-Fi 传输的产品不同，Duet Display 须使用 Lightning 或 30 Pin 数据线连接 Mac 与 iPad。得益于有线这一较为稳定的传输方式，Duet Display 打出了「Retina、60 fps、No Lag」的宣传旗号。
但需要注意的是，这里的「有线连接」有别于普通的显示器连接，它并不能直接将 iPad 扩展为一块普通的显示器 —— 因为iPad 不能通过它直接接收 Mac 输出的视频信号，本质上，它只是将数据传输方式从无线改为有线；画面的生成与显示过程仍与先前的软件类似，需要先在 Mac 中创建一块虚拟显示器，再将画面处理后传送至 iPad。
因此 Duet 也并没有像宣传的那么美好：其 Retina 与 60 fps 模式会占用大量 CPU，部分旧款 Mac 仍会出现光标延迟、画面伪影与系统卡顿。所以再后来，市面上又出现了针对将 iPad 扩展为数位板的 Astropad、以及借助 DisplayPort 硬件适配器、让 Mac 将 iPad 识别为「真实外接显示器」的 Luna Display 等产品......

一帧画面的旅程
简单来说，一帧画面要显示在作为 Mac 副屏的 iPad 上，主要需要经过以下几个环节：
- 虚拟屏幕渲染
- 画面编码
- 数据传输
- 解码显示
前文中提到的 iDisplay、Air Display 等第三方软件，其实已经用上了「虚拟屏幕渲染」的思路。简单来说，它们会先在系统中创建一块虚拟的显示器，并像对待实体显示器一样，为其正常分配桌面空间和分辨率等。此时应用仍然按照正常方式绘制窗口，再由 macOS 中负责管理和合成屏幕画面的 WindowServer 组合成虚拟显示器上的完整画面。
不过这些画面最终不会被送往真正的物理显示接口，而是由系统或第三方软件读取，再进入后续的编码与传输流程。
相比之下，接下来的几个环节的精密协同，才是随航真正与第三方方案拉开差距的地方，也是其能够做到如此流畅的关键。
画面编码
为什么 WindowServer 合成出的画面还不能直接交给 iPad？
传统外接显示器的逻辑其实很简单，GPU 完成一帧画面的渲染与合成后，只需要按照显示器规格生成显示信号，再通过 HDMI、DisplayPort 或 Thunderbolt 等接口送往显示器即可。
但一块高分辨率屏幕每秒产生的数据量远比想象中庞大。做一个并不严谨的计算：以 2388 × 1668 分辨率的画面为例（2018—2022 款 11 英寸 iPad Pro，也是笔者所用的型号），假设每个像素使用 4 字节（RGBA）表示，那么每帧图像所占用的空间大约为 2388 × 1668 × 4 ÷ 1000² ≈ 15.9 MB。如果设备的刷新率为默认的 60Hz，一秒钟产生的原始画面数据便已经接近 1 GB。
对于上述针对外接显示器的有线传输来说，这样的数据量并不是什么大问题。HDMI 2.0 的最高传输带宽可以达到 18 Gbps，而 DisplayPort 1.2 则可以达到 21.6 Gbps，足以承载 4K 60Hz 级别的显示信号。但对于无线传输的随航来说，想要稳定传输如此庞大的原始画面数据显然并不现实。因此在画面离开 Mac 之前，还需要先经过一道关键步骤——编码。
本质上，随航所传输的其实是一条实时视频流，因此它对屏幕画面的压缩也沿用了现代视频 HEVC 编码的基本思路。
HEVC
HEVC 是 High Efficiency Video Coding （高效率视频编码）的缩写，你或许对它的另一个名字更熟悉——H.265。它由 ITU-T 与 MPEG 共同制定，可以看作 H.264／AVC 的继任者。HEVC 的核心精髓便是「猜」，用尽可能少的原始画面，推算出接下来的视频内容，从而节省海量的空间。
那上述的「海量」究竟如何量化？简单做个演示，我们可以借助 FFmpeg 对系统 UI 进行无损录屏。在系统「终端」中输入以下指令，查看 FFmpeg 可以调用的视频设备：

为了理解这 98% 的数据究竟去了哪里，我们需要先简单了解 HEVC 的编码原理，也就是笔者前文所说的「猜」的过程。
分块
在预测开始前，HEVC 会先将画面划分为一个个编码树单元，也就是 CTU（Coding Tree Unit）。在 HEVC 中，一个 CTU 最多覆盖 64 × 64 个亮度像素，并可以继续通过四叉树结构划分为尺寸更小的编码单元 CU（Coding Unit）。
这种划分并不是固定的。天空、墙面等颜色和纹理较为平缓的区域，可以保留尺寸较大的 CU；车辆、树木和建筑边缘等细节密集的区域，则往往需要继续向下划分。编码器由此能够根据不同区域的复杂程度，选择更合适的处理粒度。在 StreamEye 中2，这一结构可以被直接观察到。
比如选中画面右侧较为平坦的白墙时，一个 CTU 内只有少量尺寸较大的 CU；切换到细节复杂的塔楼后，分块会明显变得更加密集。
确定 CU 的大小后，编码器还会为其选择预测方式，并根据需要将其划分为一个或多个预测单元，也就是 PU（Prediction Unit）。接下来，编码器会针对这些区域寻找尽可能接近原始画面的预测结果。而用于预测的信息主要有两个来源：一种来自当前画面中已经得到的相邻区域，另一种则来自视频中的其他参考画面。根据参考信源的不同，HEVC 中的预测也就可以分为两大类——「帧内预测」与「帧间预测」。
帧内预测
「帧内预测」（Intra Prediction），顾名思义，即不依赖视频中其它帧，而是利用当前帧中已经得到的相邻画面信息，来预测当前单元中的内容。
这里的「相邻区域」通常位于编码块的上方与左侧。由于画面会按照一定顺序逐块处理，当编码器来到当前块时，这些区域已经完成了编码与重建，因此编码器和解码器都能够获得同一组参考像素。
HEVC 共提供了 35 种亮度帧内预测模式，其中包括 33 种角度模式，以及 Planar（平面）模式与 DC 模式。Planar 模式更适合颜色缓慢变化的区域，它会综合块上方与左侧的参考像素，在块内生成较为平滑的渐变。DC 模式则会根据周围参考像素计算一个平均值，再用这个近似的颜色填充整个块。

（进行后续的操作前，请先注意备份。）
在注册表的 计算机\HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\AccountPicture\Users\ 路径下，存储着各种尺寸、用于 Windows 各种界面的头像注册表值。
如果我们按照传统方法运行 regedit、找到键值、编辑保存，就会发现这些数值无法直接修改：
要修改用户头像相关的注册表数值，我们必须以 system 身份来运行注册表，这里我们选择 Windows 知识库中提到的 PsExec 工具，下载并解压得到 PsTools 文件夹，然后在开始菜单上右键，选择「系统」，然后在打开的设置界面中找到并进入「高级系统设置」。
然后在「环境变量」设置中参考下图操作流程，将 PsTools 路径添加至环境变量。
随后我们以管理员身份启动终端或 PowerShell，运行命令：
psexec -i -s regedit.exe
如果你好学看过上面的文档，应该就知道这里的 -i 代表启动可交互界面，-s 则是我们需要的以 system 身份启动。
启动后注册表编辑器页面弹出，我们就可以前往 计算机\HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\AccountPicture\Users\ 路径，将所有头像的键值更改为事先准备好的 GIF 动图路径了。

写在前面
盛夏的夜晚总是很长。
那天晚上和朋友聊起旅行，话题从九州一路往南，最后停在了手机地图上的一片海。朋友指着鹿儿岛以南那座狭长的岛，说了一句：「奄美大岛，好像还没去过。」
关于奄美大岛，我知道得并不算多。印象中，它夹在九州与冲绳之间，四周都是海，岛上似乎有大片亚热带森林，也有红树林和漫长的海岸线。地图上的距离看起来和九州本岛不远，但似乎一直没找到合适的机会专程去一趟。
朋友说，要不就趁着过阵子的假期出发吧。
于是事情变得简单，查机票、看住宿、租台车。像往常一样，没有任何关于旅行地的具体归化，也没有什么特别的朝圣理由。
我也想看看，这座我们一直没有去过的岛，究竟是什么样子。
九州「穴场」
日语里有一个词叫「穴場」，大概是指那些名气不大，却值得专程去一趟的地方。
在探寻奄美的日子到来之前，我索性提前来到九州，暂住在朋友家。看着距和朋友汇合的日子尚有几天，于是我想干脆趁这几天空档，去找一找九州地图上的那些「穴場」。
锅瀑布
一直以来，我很喜欢在日本自驾离开城市的感觉：当城市的道路一点点退出视野，随着导航，一头扎进进阿苏北部的山里。窗外的房子和电线越来越少，取而代之的是一片片绿色，偶尔还能经过几片田地和安静的村落，这种感觉非常奇妙。
所以第一站，我来到了位于群山之中的锅瀑布，相传这是一个由大约9万年前造成阿苏火山口的一次巨大火山喷发所形成的瀑布。从入口沿着林间小路往下走，不过几分钟，先听见的是水声。再往前，树木之间突然露出一整片白色的水帘。
锅瀑布并不高，只有约十米，却足足展开了二十米。水从岩壁上均匀地落下来，没有想象中瀑布那种轰鸣和压迫感，更像是一张很大的帘子，安静地挂在森林深处。
大概是工作日的原因，在我抵达的时候，这里的游客并不算多。我可以很容易地找到绝佳的摄影位置，用慢门的方式给这座瀑布拍几张标准的游客照。
即使是在盛夏，当我站在水边拍照的时候，还是能感受到山风带着潮湿的凉意。阳光从树叶的缝隙落下来，水雾偶尔飘到脸上。
我想，这大概就是我想找的「穴場」吧。没有拥挤的人群，也不需要提前计划什么详尽的攻略；我只需要抵达这里，听着瀑布的声音，看阳光和水雾慢慢变化，就已经足够了。
高森殿の杉
锅瀑布周围其实还散落着不少可以顺路去看看的地方，有些甚至很难称得上正式的景点，只是在地图上留下一个小小的名字。
反正时间还早，我便继续沿着小国町的山路往前开，去看看附近一棵据说已有四百多年树龄的杉树。车开出去没多久，路过阿苏火山时，路边的景色却先让我停了下来。
山坡一层一层向远处铺开，草地被夏日染成深浅不同的绿色。有那么几头牛散在山坡上，悠然自得。更远处的杉林沿着山势向上生长，山顶被低低的云雾遮住，只留下模糊的轮廓。
我在路边站了一会儿，顺手拍了一张照片。我大概已经来过阿苏火山四五次了，但每次经过都会有不同的一些发现，即使眼前只有草地、牛群、森林，还有从山间慢慢飘下来的雾。
继续向目标地前进，从停车的地方穿过一片牧草地，再沿着小路往树林深处走一段，才终于看到据说树龄已经有 400 年的两颗巨大杉树，这就是「高森殿の杉」。
也许是图片无法完全展现出两颗百年杉树的面貌，也许是我很少近距离接触如此高大的树木，在我站在树底下，和它们面对面的时候，总会觉得有些渺小。
抬头望向这两棵树，枝叶几乎占满了头顶的天空。粗壮的树干从低处开始分岔，一根根巨大的枝条向四周伸出去，有的向上生长，有的弯曲着横在半空，还有一些彼此交错，像是在漫长的岁月里逐渐纠缠在了一起。
「高森殿」这个名字背后还有一段发生在战国时代的故事。1586 年，高森城主高森伊予守惟居在与萨摩岛津军交战之后，据说最终与家老三森兵库能因一同在这片杉树下挥手自刃。从那以后，这两株古杉也就得名「高森殿の杉」。
虽然四百多年已经过去，城池和战事早已消失在时间里，但是树还保留完好地留在这里。游走于阿苏的山里，似乎无法抓住流逝的时间。
出发，天空鸟居！
次日，朋友正好休假，于是提议去附近的天空鸟居转转。所谓的「天空鸟居」并非特指一个地点，而是几乎所有建立在高处的鸟居都可以称之为「天空鸟居」。
而我们这次准备拜访的「天空鸟居」位于熊本的天草市，本名叫做「倉岳神社」。顾名思义，它位于天草诸岛最高峰「倉岳」山顶，海拔约 682 米。
开车上山的过程并不轻松。山路非常狭窄，随着山势不断向上，越接近山顶，相互错车的频率也就更高。好在随着海拔的上升，一路上也可以看到几撇不错的风光。
当我们好不容易开到山顶之山，看到石制的鸟居立在山顶边缘，一眼往下去只有海的景象之时，会有一种眼前一亮的感觉。
越过鸟居望出去，视线几乎没有任何遮挡。八代海在脚下铺开，一座座岛屿散落在蓝色的海面上，远处的山与天空已经淡成了浅浅的轮廓。山下的房屋和道路缩得很小，偶尔还能看到船只在海面划出一道白色的痕迹。
站在这里，其实也很容易理解日本人为啥总是沉迷于「天空鸟居」这个概念了。倉岳神社原本是当地人为祈求渔业与航海平安而建，把石制的鸟居建立于山峰之上，不仅与周围的环境融为一体，还可以一直望海守护，表达人们美好的祈愿。
原尻瀑布
在告别「天空鸟居」之后，我和朋友分开，继续一个人在九州寻找「穴場」。
从熊本西行，我来到了大分县丰后大野市的「原尻の滝」，和之前看到的锅瀑布相比，原尻瀑布完全是另一副模样。
这座瀑布出现在一片平缓的田野之间。周围有农田、村落和远山，沿着河边走着走着，地面却像突然被切开了一道巨大的缺口，河水从宽阔的岩壁上一齐落下。
原尻瀑布宽约 120 米、落差约 20 米。而瀑布所在的岩壁，据说是大约9万年前阿苏山火山爆发时的碎熔岩流凝固后，经历漫长岁月的水流侵蚀所形成。因为这里的瀑布呈弧形展开，从正面望过去颇有几分尼亚加拉瀑布的感觉，也因此有一个「东方尼亚加拉」的别称。
在我抵达到时候，虽然水流并没有网上的图片那么夸张，但靠近瀑布的时候还是会感受到扑面而来的水雾。水从岩壁顶端倾泻而下，撞进深绿色的水潭，阳光好的时候，飞散的水雾里还能隐约看见一道彩虹。我在这里找一块不错的位置架好相机，用慢门把水流拉成白色的丝绸，拍下了一张照片。
如果用相机镜头的广角视野来看，这座瀑布并不是在群山之中，而是回到了田园里。远处是层层叠叠的山，近处是农田和树木，身在还可以在河岸边看到一座高鸟居。很难想象，就在这样平静的乡间风景下面，藏着一道横跨百米的瀑布。
西石佛和东石佛
看完原尻瀑布以后，我又顺着地图的指引，顺便拜访了附近的「緒方宮迫東石仏」和「緒方宮迫西石仏」。
两处石佛藏在丰后大野安静的山林里，相距只有几百米。沿着乡间小路走进去，周围很快便只剩下树木和山坡。很难想象，在这样不起眼的地方，会保存着一组已经存在了数百年的磨崖佛。
先看到的是東石仏。几尊佛像直接从岩壁中雕刻出来，中央是一尊巨大的如来坐像，两侧依次可见不动明王、持国天与阿吽金刚力士像。当地传说，这组石佛与平安时代末期活跃于丰后的武将緒方惟栄有关，如今已经被指定为日本国家史迹。
虽然看起来是石佛历经沧桑，但佛像身上还可以明显看到红、黄、黑等色彩依然附着在岩壁和衣纹之间。在好奇心的驱使下，我也查询了一番资料，发现眼前这些依然鲜明的色彩，距离最近一次已知的大规模补彩也已经过去了约一个世纪。
从東石仏继续走不远，便是「緒方宮迫西石仏」。
这里的岩壁上并排坐着三尊佛像，从面对石佛的方向看，右侧是阿弥陀如来，中央是释迦如来，左侧则是药师如来。三尊佛像都接近一人高，身后的光背、衣服甚至头发上，还能看到朱红、黄色与群青等色彩。
当地的解释中，释迦如来对应过去，药师如来寄托着对现世的祈愿，而阿弥陀如来则指向来世。过去、现在与未来，就这样被并排刻进了一整面岩壁里。
虽然数百年的时间过去，曾经雕刻它们的人也许早已无从寻找，周围的村落和道路也不知道改变了多少次，石佛却还留在原来的山里。
从原尻瀑布走到这里并没有多远，看到的东西却从自然风景一下跨越到了数百年前，或许这也是在九州寻找「穴場」有意思的地方。
真玉海岸
离开原尻瀑布的时候，已经是下午了。距离我需要在天黑之前赶很久的路（大约 112 公里，2 小时），才能抵达今天最后一个目标：真玉海岸。
紧赶慢赶，终于从丰后大野一路开到丰后高田。当我抵达海边时，太阳已经快接近海平面，好在还没有错过日落的最佳时刻。
真玉海岸最有名的就是这里的夕阳。由于海岸十分平缓，退潮以后，大片干潟会从海水中露出来。沙洲与残留的水道交错在一起，在海面上形成一道又一道弯曲的纹路。今天的运气非常好，因为只有当干潮与日落的时间恰好重合时，才能看到这里最完整的模样。
当太阳一点点向海面靠近，原本泛蓝的天空逐渐被染成橙红色。退潮后的沙地变成深色的剪影，而留在沟壑里的海水，则把天空的颜色重新映了一遍。
海面上有了很奇妙的层次：一道是黑色的沙洲，一道是橙色的水面，再往前，又是一道黑色的沙洲。夕阳就在这些明暗交错的纹路尽头缓慢下沉，最后只剩下一条很长的金色倒影。
刚才还是金黄色的海面，过一会儿便染成橙红；远处的岛影渐渐变黑，沙洲的轮廓却越来越清楚。很多人已经架好了三脚架，安静地等着属于今天的那一刻。
我也找了个地方坐下来，把相机放在身边，就这样看着太阳一点点落下去，看着最后的光留在潮汐带的水面上，直到海边完全暗下来。
八角隧道
本日是去奄美大岛的前一日。原计划是下午从熊本出发，抵达鹿儿岛机场附近，然后第二天达成飞机抵达奄美大岛，和朋友汇合。
临出发前，我又习惯性地打开地图，在熊本周围随便翻了翻。就在准备关掉的时候，一个藏在美里町山里的一个叫八角隧道的地方引起了我的注意。
从地图上看，几段八角形的混凝土结构孤零零地留在森林里，曾经的铁轨早已消失，照片看起来甚至有些不像现实中的地方。
查了一下也不算太远，于是趁着上午的时间开车到这里看看。这里实际上是已经废止的熊延铁道留下的遗迹，早在1964 年铁路停运以后，铁轨与列车逐渐从这里消失，只有这些当年为了保护铁路而修建的混凝土结构留了下来。
如今这里已经听不到列车的声音。铁轨消失了，枕木也不见了，原来的路基铺满落叶和碎石，青苔顺着混凝土一点点向上生长。只有这些水泥筑成的结构还保持着当年的方向，一直延伸向森林深处。
从八角隧道出来以后，我又顺路去了不远处的「二俣橋」。这里其实是两座石拱桥，由「二俣渡」与「二俣福良渡」组成。
这两座桥在我到来时平平无奇，但之后我才知道，原来每年11月至次年3月，上午11点至12点之间，阳光会在桥下投射出一个心形图案，这一景象蔚为壮观，也因此被列为「情侣圣地」，并被命名为「心之石桥」。
我在桥附近转了一圈，时间也差不多了。回到车上，将导航重新设定为鹿儿岛。接下来不再寻找新的目的地，一路向南，去机场附近住上一晚。
九州这几天临时起意的「穴場」探索，也到这里暂时告一段落。明天，奄美大岛见。
抵达，奄美大岛！
飞机离开鹿儿岛以后，窗外很快只剩下大片的海。飞行时间并不算长，等到陆地再次出现在视野里时，奄美大岛也终于到了。
和朋友汇合、取好车以后，我们没有在机场附近停留太久，直接去了这趟奄美旅行的第一站——「Heart Rock」。
这是奄美大岛北部龙乡町海岸上一处天然形成的心形潮池。退潮以后，海水会留在岩石的凹陷中，从特定角度看过去，刚好形成一颗心，因此有了「Heart Rock」这个名字。
我们本来是挺期待能找到照片里的那颗「心」的，只是到了海边才听旁边的游客说起，由于Heart Rock 本身位于潮间带，需要赶上合适的退潮时间和海况，岩石间的心形轮廓才会完整露出来。最近一段时间，这里经常受到海浪和沙子的影响，因此心形会被沙子直接掩埋。
虽然我们还是不甘心地在海边找了一圈，但是确实没有看到心形，作为抵达奄美大岛后的第一站，多少有些遗憾。
不过第一次站在奄美的海边，眼前的海景也足够漂亮。阳光很强，海水从近岸的浅绿色一点点变成远处的深蓝色，浪不断拍上礁石。刚刚还坐在飞机上俯瞰这座岛，现在已经真正站在了它的海岸边。
虽然有些遗憾，但我还是一边感受着奄美大岛的海滩，一边提醒自己奄美大岛的旅行，才刚刚开始。
在大滨海滩看海
之后，我们又来到了附近的大浜海浜公園，这里的奄美海又换了一种颜色。
从空中俯瞰，沙滩几乎是一整片干净的浅白色。海水从岸边开始，由透明的浅蓝慢慢过渡到青绿色，再向外变成更深的蓝。藏在水下的礁石和珊瑚礁清晰可见，一道并不算大的浪沿着礁盘边缘推向岸边，在沙滩上留下一条细细的白线。
这里海水呈现一种少有的果冻蓝，无论是近看亦或是远观都有一种通透感。借助无人机的上帝视角，当阳光穿过浅海，水下深浅不同的纹理全部显露出来，礁石的阴影、海底的沙纹，甚至浪经过浅滩时改变的颜色，都能从俯视角度看得很清楚。
虽说日本本身作为岛国，我也在日本全国旅行的途中看过了不少的海，但大浜海浜依然能让我在这里停留很久。
这里鲜有游客，大片沙滩上只有零星的脚印，身旁就是一整片从浅蓝延伸到深蓝的海。没有太多复杂的景物，只剩下沙滩、礁石和不断变化的海水。
宫古崎
奄美大岛有无数种海。
沿着奄美大岛西海岸继续前进，我们来到了「宫古崎」。这里并不是一个把车停下就能看到的景点。从宫古崎的停车场出发，大约还需要二十分钟才能走到海边。最开始的路藏在树林里，两旁都是茂密的亚热带植物，偶尔才能从树木的缝隙里看到远处的海。
当树林逐渐变得稀疏，山坡上的高大树木也逐渐消失，取而代之的是大片齐腰高的「リュウキュウチク」，也就是琉球竹。它们沿着起伏的山脊一直铺向岬角，只有一条很窄的土路从草丛中央穿过。
沿着这条路继续走，海也一点点出现在两侧。
从无人机视角的高处望下去，宮古崎像一条覆盖着绿色草原的巨大岬角伸进东海，一座岬角，把两种完全不同的海分在了左右。
一侧侧直接面对开阔的大海，海浪不断撞击岬角下方的岩壁，留下大片白色浪花；另一侧则是相对平静的海湾，海水从岸边的浅蓝逐渐过渡到更深的蓝色。
听说当地喜欢用用一句「地球は丸い」来形容这里，也就是说在这里，可以感受到地球是圆的。
当你真正站在岬角上，视野从远处的海平线可以延伸到无限远，没有建筑，也没有岛屿挡在前面，就好像天然的裸眼3D，恍惚间，有一种强烈的失真感。
