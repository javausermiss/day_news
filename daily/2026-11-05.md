Computer use for AI agents: see and operate desktop apps on macOS, Windows, and Linux through the OS accessibility tree.
agent-desktop gives an AI agent computer use without screenshots or pixel matching. It reads the accessibility tree of a desktop app and returns it as JSON, with a ref for every element the agent can act on. The agent clicks or types on a ref, reads the UI again to check the result, and repeats. The loop lives in your agent; agent-desktop has no model inside. It ships as a CLI and a C library.
Snapshots, clipboard reads, screenshots, command output, and debug artifacts can contain private desktop content. Keep them out of public logs and uploads.
npm install -g agent-desktop
agent-desktop status                # platform, permissions, supported surfaces
agent-desktop permissions --guide   # macOS: walks you through the Accessibility grant
Bun, Yarn and pnpm can install the same package. It includes native binaries and platform helpers for x64 and ARM64. For direct execution without a JavaScript launcher, download the matching native archive from GitHub Releases and keep its helper beside the executable.
On macOS and Linux, Homebrew also works: brew install agent-desktop. There is no official Scoop package yet.
The repository no longer maintains a custom Homebrew tap or Scoop bucket.
Release archives and building from source are covered in Installation.
agent-desktop snapshot --app Finder -i      # interactive elements, each with a ref
agent-desktop click @s8f3k2p9:e8            # act on a ref from that snapshot
agent-desktop snapshot --app Finder -i      # observe again to verify
Each command prints one JSON envelope. A trimmed snapshot:

  "version": "2.6",
  "ok": true,
  "command": "snapshot",
  "data": {
    "app": "Finder",

    "ref_count": 59,
    "complete": true,
    "tree": {
      "role": "window",
      "name": "Downloads",
      "children": [
        { "role": "treeitem", "name": "Documents", "ref_id": "@s8f3k2p9:e8", "available_actions": ["Click"] }
      ]
    }
  }
}
- Refs carry their snapshot id. A bare @e8 fails with INVALID_ARGS.
- If the UI changed, an action returns STALE_REF or AMBIGUOUS_TARGET. Take a new snapshot and use its refs.
- Actions are headless by default: no pointer movement, no focus change. Pass --headed for physical input.
- type, set-value, and clipboard-set accept --stdin for piped text, keeping it out of process arguments. Run secret steps as separate commands; batch JSON text appears in process arguments.
- In PowerShell, quote every ref ('@s8f3k2p9:e8'), because a bare @token is the splatting operator.
The full walkthrough is in the quick start.
Your agent calls the CLI, or the C library in process. Both run the same core, which reaches the OS only through PlatformAdapter. Each binary is built for one OS and talks to that OS's accessibility API.
The binary carries guides that match its version:

Retry a failed command only when error.disposition.retry is safe. See JSON output for the envelope, error codes, and exit codes.
agent-desktop mcp serves every command as an MCP tool over stdio. A tool is named after its command (desktop_snapshot, desktop_click, desktop_session_start), takes that command's arguments, and returns its JSON envelope:
{ "mcpServers": { "agent-desktop": { "command": "agent-desktop", "args": ["mcp"] } } }
Global flags given to mcp, such as --session, --headed or --trace, apply to every call.
agent-desktop has 60 command names, 56 operational commands. The other four (key-down, key-up, mouse-down, mouse-up) refuse to run until a daemon can release a held key or button. Commands documents each one.
Each platform page lists what works headless, what needs --headed, and what refuses.

A mixture-of-experts model is huge on disk and small per token. GLM-5.2 has 744B parameters, uses about 40B for each token, and only about 11 GB of those change from one token to the next: the routed experts.
So the model does not have to fit in fast memory; it has to be placed. The dense part (attention, shared experts, embeddings) stays in RAM. The routed experts stay on the disk and are read when the router asks for them, through a cache that learns which experts your work uses. A GPU, when there is one, holds the hottest experts and the dense layers. Where a weight sits changes how fast the answer comes, not which weights or which router decisions produce it.
Why: to run models of this size on hardware people already own, to watch them work (the dashboard shows every expert as it fires), and to keep the engine small enough that anyone can measure it and make it faster. colibri is also an open research platform: an optimisation earns its place with a reproducible end-to-end measurement, and the default policy never silently changes model precision or router semantics. Less fast memory may cost speed; it must not quietly redefine the model. How it works has the details.

In 2024 the BBC wrote about Why insects are drawn to artificial light at night:
Flying insects use moonlight to navigate. Since the moon is always above them, they orient themselves so that the light shines on their backs. That’s how they stay upright in flight.
Moonlight contains ultraviolet (UV) and infrared wavelengths because it is merely reflected sunlight. Insects cue on UV, believing it to be the moon. When artificial lights transmit UV they look like moonlight so insects orient their backs to it. Consequently they circle the light and even flip upside down when the artificial light is pointing up to the sky!
Incandescent lights transmit UV but LEDs do not. Insects are far less attracted to LED.
In 2016 scientists at the University of Bristol, UK ran experiments to compare insect attraction to four types of light: Incandescent (tungsten filament), Compact fluorescent, “Cool-white” LED and “Warm-white” LED.
We conducted field experiments to compare the relative attractiveness of four commercially available “domestic” lights, one traditional (tungsten filament incandescent) and three modern (compact fluorescent, “cool white” LED and “warm white” LED), to aerial insects, particularly Diptera. We found that LEDs attracted significantly fewer insects than other light sources, but found no significant difference in attraction between the “cool” and “warm white” LEDs. Fewer flies were attracted to LEDs than alternate light sources, including fewer Culicoides midges (Diptera: Ceratopogonidae). Use of LEDs has the potential to mitigate disturbances to wildlife and occurrences of insect?borne diseases relative to competing lighting technologies.

Typically LEDs do not emit UV light and are more energy efficient than traditional technologies. Electrical energy is converted almost entirely into electromagnetic (EM) radiation within the range of the visible light spectrum (400–700 nm) and therefore not wasted on producing wavelengths of light invisible to the human eye, that is, UV and infrared (IR). - [你不知道的客户端开发：AI 时代下的选型、原生与借力](https://sspai.com/post/117713) <sub>11-04 20:25</sub>

<details>
<summary>📄 展开阅读全文（6000 字）</summary>

发现不少小伙伴很好奇我是怎么用 Mac 来开发 Windows 软件的，以及 Windows 软件现在一般用什么技术栈来实现，刚好我这段时间也在做类似的事情，来和大伙随便聊聊关于多端技术选择的思考。
Web、跨端还是原生
做过前端客户端的小伙伴应该都知道，这些年端的开发一般是这三条路。
第一种最简单方便的是，直接写 Web 代码，塞到浏览器就能跑，包括早年的 PhoneGap、Cordova 就是把网页塞进一个原生壳里，然后提供一些 bridge 的能力让 JS 可以调用到一些原生的能力，比如唤起手机摄像头这类的 Web 不好做的事情。
第二种是跨端开发，也就是早年大家常听到的一码多端。当时移动端有 React Native、Weex 这一类技术，主要是为了解决 Web 性能差的问题，一份代码同时打包 iOS 和 Android。国内大厂当时重度用跨端还有一个非常大的原因，就是动态化和热更新，讲得土一点就是可以绕过商店审核直接下发新页面，这也是国内跨端在移动互联网高速发展时特别流行的重要原因。
桌面端大家熟悉的就是 Electron，现在不少 AI 桌面端、VS Code、Slack 是用这个做的，代价是相当于每个应用都自带一份 Chromium 和 Node.js，安装包 100 多 MB，内存也占得多。但好处是在 Chromium 渲染引擎的统一下能够很好地保持多端的展示一致性，加上里面写的代码非常好写，后续不少桌面的速成就会用这个技术。
跨端后面也慢慢延伸出更多有趣的解决方案，类似 Flutter 自己实现一套渲染引擎，早期靠 Skia，现在换成了自研的 Impeller 渲染引擎来保障多端一致和性能效率的均衡，包括桌面端上老牌的 Qt，和 Flutter 一样自己画界面。
这两年桌面跨端也出现了用 Rust 写的 Tauri、Go 写的 Wails，它们和 Electron 不一样的地方就是，没有塞一个 Chromium 进去，而是使用系统自带的 WebView，包会小非常多，但是整体还是基于 Web 这一套研发思路和对应实现语言去进行桥接交互，但是由于系统 WebView 每个平台不一样，Windows 上是 WebView2，Mac 上是 WKWebView，Linux 上是 WebKitGTK，所以多端显示的一致性反而不如 Electron，还是要写兼容代码。所以这种情况下，即使 Electron 很大内存占用也不低，还是会被选择更多。
第三种是原生开发，也是没有 AI 之前大家觉得难度最大的一种方式。早年苹果系的 Objective-C、Android Java、Windows C++ 和 C#，都需要花很多时间去学习、看书、手编代码，深入研究系统底层原理，才能写出性能更好、更稳定的代码，属于前期投入大、后期用户很享受的技术。我 17 年那会儿刚工作不久，职业发展比较爽的一个很大原因，是抽了半年时间学习 Objective-C 和 iOS 研发，让本职是前端的工作提前往跨端方向走了，刚好可以解决一些只懂前端或只懂客户端都搞不定的难题，那也是我做一线开发非常快乐有趣的一段时间。
等到后面 Swift + SwiftUI、Kotlin + Jetpack Compose、C# + WinUI 3 慢慢出来成熟后，这些原生端语言的写法也慢慢向前端的声明式写法靠齐，也更易写了，声明式代码更短、更好读了。但是在国内，原生完全被 React Native、Flutter、Electron 的广泛使用盖过去了，开发者不多，生态发展完全靠官方推动，这也是为什么很多 App 出活很快，但大家普遍觉得用久了卡卡的，而且这类 App 还占了大头。想迁移到原生的话，假如之前架构实现得不好，大概率只能重写，完全不能复用，实现得好，比如你早就把业务逻辑抽出来了，类似 Kotlin Multiplatform 这类方案把业务逻辑共享、界面各写各的原生，算是第四条路，也是最近几年的趋势。
聊到这里大家应该大概明白了，这里也有一个不可能三角，就是研发效率、体验、性能这三者，选择 Web 是多效率少性能，选原生是多性能体验少效率，选跨端刚好是在这三者取一个中间，做得好容易都占，做得不好，容易没有一边占到好处的尴尬局面。
那么在现在 AI 写代码不是大问题的情况下，该怎么选呢？很多时候还是看场景。如果是重内容的浏览、阅读这类轻应用，直接用 Web 技术最省心；但如果是需要深度调用系统底层能力，或者追求更低内存和更顺手交互的应用，我依然更推荐原生技术，可以第一时间享受到系统官方本身的众多调优。有了 AI 之后，一个人写两套原生的成本其实大幅下来了，效率那一边被补上了不少，调试和体验验证反而成了人最需要花心思的地方。
当然假如实在技术选型不那么重要，工作量非常之大，以及业务效果远大于技术体验选择，选择跨端技术也是可以的，这样快，迭代发布也快，能以最快速度把新功能推给用户。
Windows 版为什么还是选了 C# 和 WinUI 3
技术栈上，Mac 版本的 Mole 使用的也是原生的 Swift + SwiftUI，能够让我很好调用系统能力，并且有着非常好的性能体验，想着不将就，所以在 Windows 上我也是想着直接用本身写 Windows 软件最直接的语言，C# 加 WinUI 3，跑在 .NET 10 上，过程虽然难搞，但是相比十年前我了解朋友谈的 Windows 开发要简单好理解一些了。
Windows 上的原生界面框架其实挺多的，包括很多年前了解过的 Win32、WinForms、WPF、UWP 这一波，WPF 是 2006 年出的，到现在还在维护，但控件和设计语言不是很好看，非常上一代的感觉，然后 UWP 又被沙盒和应用商店给绑定住，现在微软主推的是 Windows App SDK 里的 WinUI 3，界面框架从系统里面拆出来单独发版，这样就有一个好处，普通的 Win32 程序也能用，基础组件就是 Windows 11 自己的 Fluent 风格，我还挺喜欢，高分屏缩放和 ARM64 都是原生支持。
然后这里 .NET 10 是去年 11 月发的长期支持版本，打包时我把运行时一起打进去，用户不需要另外装 .NET，x64 和 ARM64 这里各出了一个原生安装包，骁龙的 Windows 笔记本就不要走转译了，相当于尽量让用户使用简单不折腾。这里安装和更新用的是开源的 Velopack 框架，可以很方便做增量更新，也很好用。
工程师开始写代码时候肯定会想到能复用尽量复用，所以我开始写的时候也非常想复用 Mac 的 Swift 代码，后面让 AI 分析了一下，十几万行 Swift 代码可以脱离 AppKit、SwiftUI 这些系统框架使用的 20% 都没有，处理的逻辑也是 ~/Library 这类 macOS 自己的路径规则，基本用不上，所以 Windows 版几乎是从零开始写的。
代码各写各的，两边怎么保持一致
两边的关系其实非常简单，外观和交互我尽量完全一致，尽可能让大家意识里面认为的 Windows 软件不那么精致美观的感觉在这里也保持我认为好的水平，然后底层代码各写各的，关于视觉的一致性还原有了 AI 以后很简单，我把原本的 Mac 版写在 Swift 里的颜色、字号、间距、圆角这些设计 token，直接写了一个脚本生成为 Windows 里面 XAML 资源，文案也是从 Mac 的多语言文件转成 Windows 的格式，11 种语言一起转过来，甚至大家看到的菜单栏里面的那个 runner 动画也是用的同一个脚本同步来的。
虽说同步，可能大家会觉得很简单，其实这里需要花点精力防止 AI 直接给你跑偏了，每次同步其实我会记录对应的是 Mac 的哪一个提交，这样两边就不会走偏去，然后功能上会有一份 SYNC.md 当作对账表，Mac 每加一个功能、修一个安全问题，Windows 这边都会标清楚哪些是已经实现、哪些是刻意不同还是不适用，以及为什么这样判断。
通过这两个机制，我可以很好地让两边的底层完全各写各的，但是又能很好地保持功能对齐，完全不需要刻意去硬写一层兼容去磨平，反而会变复杂，这里能复用的反而是设计、文案以及踩坑后定下来的各种规则，反而这些是 AI 非常喜欢的「能力抽象层」，也就是说随着时代发展，慢慢所谓的代码抽象没有那么重要了，反而是规则抽象更重要。
签名比 Mac 麻烦不少
另外 Windows 开发还有一块比 Mac 要麻烦不少，就是证书签名，没有签名的，一打开会出现「Windows 已保护你的电脑」，甚至 Windows 11 的智能应用控制会直接不让运行，国内不少安全软件也会把没签名的程序当成可疑报毒，这和 Mac 上没签名、没公证的软件提示「已损坏」差不多，平时 Mac 上大家还可以跑一条命令解掉，Windows 上想正规分发，这一步没有啥好办法，就是需要签名。
调研下来微软的签名生态的确比苹果差太多了，微软有自己的 Azure Artifact Signing，一个月 9.99 美元最省事，居然个人只开放给美国和加拿大的开发者，没办法使用，很奇葩的规定，然后行业还规定从 2023 年起签名私钥必须放在硬件或者云端 HSM 里，不能再是电脑上的一个文件，今年起单张证书最长只能用 460 天，差不多一年多就得换一次证书。
最后我买的是 Certum 的云端 OV 证书，3 年 300 多美元，签名时登录电脑上的 SimplySign，再用手机上的 App 给一个动态码，SmartScreen 的信誉也跟着证书上审核过的名字慢慢积累。刚开始一段时间的签名包在 ThinkPad 上也会一样被 SmartScreen 拦了下来，后来我每次发版都把安装包提交到微软的恶意软件分析门户，让信誉慢慢积累起来，而且 SimplySign 的登录会话闲置几个小时就会断开，需要再次输入动态码才能继续签名，所以这里其实很难做成云端自动打包。
怎么用 Mac 开发 Windows 软件
证书搞定后，就是开发环境的事情了，我的研发要求是代码和 AI 的上下文必须全留在 Mac 上，Mac 用习惯了，真的很难使用 Windows 去研发，这里 Windows 只负责编译和验证效果和各种测试，所以我在 Mac 上装了 Parallels Desktop，大概 3 百多块一年，之前也听不少小伙伴吐槽过这个软件，不过在我的 M5 Pro 上跑 Windows 11 还挺顺滑，让我感觉这个钱花得很值。
它最好用的一点是我的 Claude 能很顺手地操作它，仓库直接作为 Parallels 的共享文件夹挂进虚拟机，变成一个 X 盘，Mac 上改完代码，虚拟机里直接编译，不需要来回 copy 文件，只是两边的编译产物要分到不同的目录，对于编译、启动、看日志的工作都被我写成了脚本，通过 Parallels 自带的 prlctl exec 直接在虚拟机里执行，程序启动就崩的时候 Windows 只给一个 0xc000027b，Mole 会把真正的异常写进日志，脚本跑完顺手打印出来，Claude 直接就能读到。相当于写代码还是在 Mac 上的 Claude Code 里，调试和运行都在虚拟机里，脚本不能解决的地方，直接用 Codex 的 computer use 去点，只有少部分那种系统确定弹框点不了，我在这里就是这个职责，点点系统弹框确定，哈哈。
说到这里，可以和大伙分享一下 Mole Windows 的架构分层，一共四层，最底下的 Core 只依赖 .NET，不碰任何 Windows 接口，清理规则、路径安全检查、卸载残留的判断都放到这里，测试用的是一个按 Windows 路径规则模拟出来的内存文件系统，这样在 Mac 上也可以很好地跑；往上是 Platform 层，注册表、文件系统、Win32 调用这些真正的系统接口都放在这一层，打开 EnableWindowsTargeting 以后，Mac 上也能编译通过；再往上就是写过应用同学非常熟悉的界面状态的 ViewModel 层，这里和 Mac 版本会一一对应，这样也能够在 Mac 上测，只有最上面这一层的 WinUI 界面必须去 Windows 里编译。
这也是让我一个月时间可以写 8 万多行 Windows 代码、4000 多个测试，但是几乎大部分可以在 Mac 上完成的一个很方便的地方，也是架构设计的巧妙处，当然这里我只提供之前做架构时候的想法建议，大部分是 Opus 5.5 去帮我整的，很牛逼。

Matrix 首页推荐
Matrix 是少数派的写作社区，我们主张分享真实的产品体验，有实用价值的经验与思考。我们会不定期挑选 Matrix 最优质的文章，展示来自用户的最真实的体验和观点。

故事要从十年前说起。
2015 年 1 月，我做了一个小 App，叫「微诗」，上线时在 V2EX 发帖和大家分享过。那时候它支持 iOS 8，内置了全唐诗和全宋词的数据库，可以离线搜索。功能谈不上多，界面也朴素，但那是我第一次把自己的爱好，做成一件可以拿出来和别人分享的东西。
十年过去了。这中间它被搁置了很多年，我也几乎以为它会就这样留在旧硬盘里。今年我从零开始把它重写了一遍，用的是 SwiftUI 和 WidgetKit，身边多了几个 AI 编程助手。
这篇文章想和大家聊聊微诗的过去和现在。
把一本诗集装进手机
毕业以后，我去了北京一家大型互联网公司做移动端开发。工作几年手上攒了些经验，心里也慢慢冒出一个念头：我一直喜欢古诗词，能不能把这个爱好，做成一个有用的小工具，分享给同样喜欢它的人？
于是有了第一版，它把全唐诗、全宋词装进手机里，不联网也能搜。在那个流量还很金贵的年代，想读的时候随手就能翻开算得上是个亮点。上线以后，我陆续收到不少用户的反馈，印象最深的有两类：一类希望加上注释和赏析，读到生僻的典故时能有个依靠；另一类希望加上拼音，因为很多字认得出形，却不敢确定读音。
后来微诗慢慢有了更多用户，最多的时候有近 10 万人在用它。这对一个业余做的小 App 来说已经远远超出了我的预期。所以在工作之余我依然保持断断续续地更新，前后做了 6 个大版本。这些用户的建议我也一直记着。
可一个人在业余时间里能做的总是有限，很多想法在待办清单里一放就是很多年。
2016 年底，我离开公司出去创业。创业公司里能分给一个业余项目的时间和精力少之又少，我的工作重心也从客户端开发，转向了服务端和公司的技术管理。到 2017 年前后，微诗最终停了下来，就此被搁置。
之后的几年创业失败，我回到了大公司，也经历了一次职业上的转型。生活推着人往前走，那本装在手机里的诗集，离我越来越远。可我心里一直没有真正放下它。
那些曾经用过它的人，那些没来得及做完的想法，时不时还会冒出来提醒我：这件事，还没有做完。
推倒重来
让我重新拾起这个爱好的，是今年 AI 能力的大幅提升。离开客户端开发这么多年，如果要我一个人、只靠业余时间，把一款 App 从头做到自己满意的程度，过去我是不敢想的。
而今年，和 AI agent 一起工作，这件事第一次变得可行了。
十年间，iOS 和 Swift 本身都已经变了太多，与其在旧代码上修修补补，不如重新开始。我最后的决定是从零开始，一行旧代码都不留。技术栈也很快就定了下来：界面全部用 SwiftUI，小组件用 WidgetKit。小组件本来就只能用 SwiftUI 写，主 App 和小组件共用一套视图和数据层。对一个人维护的项目来说，这样的组合是最省心的选择。
新的微诗，我给定下了三个词：美观、简洁、诗意。我希望它是「装在手机里的一本诗集」，是一本你愿意偶尔翻开、翻开之后不会被打扰的书，在微诗里，诗不只是用来默读的——它可以被朗读，可以被吟唱，也可以化作一幅画。
新版微诗
打开微诗，首页是当天的一首诗。这首诗的选择会跟着二十四节气走。
我很喜欢这种安排。节气本身就是古人写给时间的诗，立春、清明、白露、霜降……用诗来标记日子，比一个冷冰冰的日期更像生活本来的样子。
放在锁屏上的「诗笺」小组件是我自己用得最多的功能。每天拿起手机看时间的那一下，顺便看到一两句诗，不需要打开 App、不需要做任何事，它就在那里。
锁屏小组件的空间非常小，而且系统会以单色方式渲染，能用的只有字形、字号和留白。在这么小的一方地方里，让一两句诗读起来仍然舒服，是我反复琢磨过的事。
新版微诗里还有一组动态壁纸：山水是一笔一笔画出来的。我想要的效果是像看一个人在纸上作画，而不是看一段特效，速度太快就没了意境，太慢又让人失去耐心，分寸全在一点点调出来的节奏里。
古人的诗，很多本来也是用来吟、用来唱的。只用眼睛读，总觉得少了点什么。所以这一版的微诗中，诗不只可以默读，你可以听它被朗读出来（TTS），也可以听它被唱出来——这些曲子是我用 Suno 一首一首做出来的。
第一次听到一首熟悉的诗被唱成歌的时候我发现，字还是那些字，却好像换了一种方式走进了心里。
诗中有画是老话，但这一次我想让诗真的「入画」。每一首诗都可以化作一幅画，让那些读过很多遍的句子，有一个可以看见的样子。
至于当年用户最常提的注释和拼音，这一次都做进去了，每首诗都可以看注释、赏析，也可以显示拼音。做完这个功能的那天我也想起了那些早年的用户，这些功能虽然晚到了十年，但总算没有缺席。
新版微诗界面的每一处，我都尽我自己的审美，做到了力所能及范围内的最好看。它未必合每个人的口味，但每一个字号、每一处留白都是我认真选过的。
最后，微诗依然是免费的。它从十年前开始就是如此，这一次也一样。
和 AI 一起写代码
这次重写是在业余时间里和 AI agent 一起完成的。网上关于 AI 编程的讨论很多，这里也说说我的体会。
- AI 搭骨架很快。 从零开始建一个 SwiftUI 工程、把数据层、主 App、小组件扩展之间的关系理顺，这些「知道该怎么做、但做起来很繁琐」的活，AI 完成得又快又稳。
- 补上我不熟的部分。 2016 年底之后，我的工作重心就转向了服务端和技术管理，中间错过了很多 iOS API 的变化。WidgetKit 的时间线（Timeline）怎么规划、锁屏小组件有哪些尺寸和限制，AI 能很快给出一个可以运行的起点，我再在此基础上读文档、改细节。
- 打磨细节。 很多技术细节，靠我一个人在业余时间里慢慢啃，可能要很久，甚至会半途放弃。AI 在这些地方给了我巨大的帮助，让我可以把力气花在真正在意的地方。
当然，这些帮助都不是免费的，实际流程也不是一帆风顺。回头看真正难的地方和我原先以为的不太一样：让 AI 把一个东西做出来，其实并不难。一个界面、一个功能、一种效果，说清楚了，很快就能看到一个能跑起来的版本——难的是让它合乎审美，难的是决定哪些功能留下、哪些砍掉。说到底，是品味和取舍。
这两件事都没有标准答案，也没法一次说清。一版做出来，看着不对，推翻；再做一版，好了一点，还是不对，再改。一个功能做好了，用上几天，觉得它打扰了读诗，又拿掉。大量的反复和消耗，就藏在这一来一回之间。开头说的近 2 万美元的 token，大多是花在了这里。
品味，还是得自己来。
写到这里，我最想说的是：AI 可以帮你把东西做出来，但做成什么样得自己决定。一首诗在屏幕上该用多大的字、行距留多少、标点要不要显示、页面上该有几个按钮——这些问题 AI 都能给出「合理」的答案，但「合理」和「好看」之间，往往还隔着很多次推翻重来。哪一版才对，只能自己一遍遍看、一遍遍改，直到心里那点别扭消失为止。
还有一类决定是关于「不做什么」的。AI 很乐于帮你加功能，每一个都不难实现。但我给微诗定的是「美观、简洁、诗意」，很多功能我最后都没有加。
我的感受是，AI 让「做出来」这件事变便宜了，于是「做成什么样」反而变得更重要。十年前我卡在实现上，十年后我更多时间是在想「这一页配得上这首诗吗」。
写在最后
十年前，我在大公司做移动端开发，业余写下了微诗的第一行代码；十年后，我依然是在业余时间里，和 AI 一起把它从头重写了一遍。中间隔着一次创业、一次失败、一次转型，和很多年的搁置。
近 2 万美元的 token，换算成任何一种回报，大概都不太划算。但如果要我再选一次，我还是会这么做。人这一辈子，总该为自己喜欢的东西，认真地花一次力气。
微诗现在仍是一个人做的小 App，一定还有很多不够好的地方。如果你愿意试一试，非常希望听到你的反馈和建议。

- [国行 Apple 智能上手：这些功能已经准备好](https://sspai.com/post/118404) <sub>11-04 10:41</sub>

<summary>📄 展开阅读全文（6000 字）</summary>

2024 年 9 月 10 日，随着 iPhone 16 系列发布，Apple 中国官网打出了「为 Apple 智能预备好」的宣传语。谁能想到，这一「预备」就是整整 785 天。如今，姗姗来迟的国行 Apple 智能，终于在今天和大家见面了。
按照 Apple 公布的安排，首批核心功能将从今天起在最新的 iOS 27.3 开发者预览版中开放测试，并计划于 12 月随 iOS 27.3 正式版推出。首批功能会先在 iPhone 上启用，包括写作工具、照片消除和实时翻译等。同时，Siri 也将正式接入千问和百度，带来更强大的回答能力。
不过，这次通过审批的仍是采用「跑马灯」Siri 界面的初版 Apple 智能。WWDC 2026 上亮相的灵动岛液态玻璃玻璃界面，以及下一代 Apple 智能和 Siri AI 功能，都不在本次测试范围内。
但不管怎样，漫长的等待总算有了结果。因此我们也在第一时间更新了 iOS 27.3 测试版，看看它们用起来究竟怎么样。
哪些设备能用？
这次 Apple 智能测试版仅在 iPhone 上开放，支持的机型包括 iPhone 15 Pro、iPhone 15 Pro Max，以及 iPhone 16 及之后推出的所有 iPhone，iPhone 16e 和 iPhone 17e 也在其中。至于 iPhone 15 和 iPhone 15 Plus，由于只配备了 6 GB 内存，这次依然无缘。而 iPad、Mac 等其他设备则暂不支持，还需要等待对应的审批。
符合机型要求的 iPhone 想要开启国行版 Apple 智能，只需要满足以下任一条件：
- 使用国行设备，也就是在「设置 > 通用 > 关于本机」中，「型号」末尾三个字符为「CH/A」的设备；
- 使用海外版设备，登录的 Apple 账户国家或地区为中国大陆，也就是俗称的「国区 ID」；
- 使用海外版设备，未登录 Apple 账户，且设备定位位于中国大陆。
满足上述条件并更新到 iOS 27.3 开发者预览版后，设置中原来的「Siri」就会变成「Apple 智能与 Siri」。进入后，点击下方的「打开 Apple 智能」，就能看到获取 Apple 智能的按钮了。
根据 Apple 的介绍，最多需要下载 7GB 的 Apple 智能支持内容，下载完成后也需要等待 Siri 升级和启用，所需时间不固定。好在这次没有等待名单，不用先排队等候开放资格。
根据我的 iPhone Air 为例，更新前 iOS 和系统数据分别占用了 17.01 GB 和 27.14 GB，更新到 iOS 27.3 测试版并开启 Apple 智能后，两者分别变成了 22.69 GB 和 31.59 GB，其中， Apple 智能占用了 5.92 GB。
Siri 跑马灯与第三方模型接入
这次 Apple 智能最直观的变化，莫过于呼出 Siri 时的「跑马灯」效果。不过，除了长按侧边按键用语音和 Siri 交互外，你也可以双击屏幕底部导航条的位置，直接打字与它对话。
模型方面，国行 Apple 智能只有本地模型，用于基础的 Siri 功能、照片消除和实时翻译等任务。至于更复杂、端侧模型无法处理的请求，则会将问题与上下文发送至阿里的千问模型进行处理。
不过，千问扩展并不会默认开启，需要手动启用。你可以前往「设置 > Apple 智能与 Siri」，在下方的「扩展」中点击「千问」，再点击「使用千问」，按照弹出页面的提示完成账户登录来启用。除了用手机号登录已有的千问账户外，你还可以选择「通过 Apple 登录」隐藏邮箱。
启用后，借助 Apple 智能对屏幕内容的识别能力，你可以直接通过 Siri 对屏幕上显示的照片、PDF 或演示文稿向千问提问，并持续进行对话。
通过 Siri 与千问对话的历史记录，也可以在登录了同一账户的千问 App 中查看。此外，千问还会出现在后面要介绍的视觉智能和写作工具中，用于理解画面、回答问题，以及创作图文。
至于数据何时会发给千问，Apple 表示，每次发送请求前都需要征得用户同意。在我的测试中，Siri 每次需要调用千问回答时，也确实都会先询问是否允许，得到同意后才会发送数据。Apple 还表示，通过 Siri 发给千问的数据不会被用于模型训练、营销广告或用户跟踪。
除了千问以外，国行 Apple 智能也和百度进行了合作，不过目前仅限于识图搜索，并不负责 Siri 的问答。
总之，随着大模型的加入，Siri 终于不再是那个动不动就和你说「我在网上找到以下信息」的呆萌机器人，语言理解也有了不小改善。它能更好地理解说话时的停顿和改口，也能结合上下文处理连续提问。比如，一句话说着说着发现自己把时间说错了，就可以直接纠正，不用像以前一样取消对话再从头说一遍。
写作工具
日常生活中，我们总免不了和文字打交道。给老板写报告、给不同的人回复消息，或者看着一大段材料不想从头读起，都能通过写作工具来处理。
只要 App 使用的是 iOS 系统自带的文字选择菜单，包括第三方 App 和网站，在选中文字后，点击弹出的菜单里的 Apple 智能图标，即可使用写作工具。不过，像「小而美」这种自行重写了菜单的 App，暂时就用不了了。
对于无法选中的文字内容，你也可以通过截图 OCR 的方式来选择屏幕内的文字，再进行调用。
写作工具最基础的功能是「校对」。它会检查句子的用词、语法或错别字，并标出建议修改的地方。例如困扰了无数人的「的」「地」「得」，就可以通过它一键校对。
修改之后，你也可以查看改了哪里，以及为什么会被修改。当然，AI 使用的是更标准正式的语法，对于一些俏皮、玩梗的写法，它可能也会觉得你出错了。因此。如果你不满意 AI 改写的结果，也可以保留原来的写法。
想把同样的意思换种说法，就可以用「改写」功能。怎么说呢，这个功能像极了我初中英语考试里的重点题型「解释句子」，也就是同义句转换。（如果你也曾是 2010 年前后的深圳初中生，应该对它印象深刻。）改写时，Apple 智能会理解原句的意思，再换一种表达方式写出来。
此外，你还可以选择「友好」「正式」和「简洁」三种语气，根据使用场合调整措辞。例如，你给甲方和乙方要传递的信息可能一样，但措辞可能就得多加斟酌 —— 发给甲方的文案可以发给乙方，但发给乙方的文案，可就不一定能直接发给甲方了。
如果前面这些改写都不符合你的需求，或是你需要从零开始写一段新内容，还可以用「创作」功能。将写作工具面板向上滑，点击「创作」即可进入自由创作模式。在输入里输入你的创作要求，Apple 智能就会调用千问，根据你的要求创作。
此外，写作工具还提供了摘要功能，将长内容浓缩总结为摘要、要点、列表和表格四种形式。遇到一些太啰嗦的内容（比如老板开会时画的大饼），就可以先让它整理一遍，一眼 get 到重点，或者发现没有重点。
总的来说，Apple 智能的写作工具由于使用的大都是端侧模型，虽然能力有限，但简单处理日常的小需求，还是比使用第三方 AI 应用要方便不少。
视觉智能
视觉智能也是本次 Apple 智能的核心功能之一。对于配备相机控制按钮的 iPhone，只需长按该按钮即可启动视觉智能；如果使用的是没有相机控制按钮的 iPhone 15 Pro 系列，则需要先在控制中心添加「视觉智能」按钮，再通过控制中心进入。
启动视觉智能后，将镜头对准想要识别的物体，按下相机控制按钮或屏幕上的拍摄键，即可定格当前画面，并选择「询问」或「搜索」。
点击左侧的「询问」，系统会将图片发送给千问，由千问结合画面内容和你的问题生成回答。此外，你还可以在获得回答后继续追问。在我看来，这个功能在出国旅行时尤其好用，例如在博物馆看到了自己喜欢的展品介绍，只需将镜头对准它，就能识别其中的文字，并进一步询问具体内容。
右侧的「搜索」则会将定格的画面发送至百度识图，根据图片内容查找相关结果。如果画面中有多个物体，也可以通过圈选指定想要搜索的对象。
除了识别物体，视觉智能还能直接处理画面中的文字。例如，当画面中出现大段文本时，视觉智能可以识别其中的内容，并直接生成摘要，省去手动复制、粘贴的步骤。
图片处理
相信很多人都有过这样的经历：手机里存了上万张照片，想找其中某一张时，却怎么都找不到。明明记得照片里的画面，却想不起具体是什么时候拍的，只能在图库里一张张翻找。
随着此次 Apple 智能的到来，我们终于可以在 iOS 的照片 App 中使用自然语言搜索了。
不过，实际体验下来，这项功能的准确程度还没有达到我的预期。例如，我直接搜索「海边日出的照片」，系统确实能根据描述找到对应的图片，但面对更复杂的描述时，搜索结果就不那么理想了，有时会出现不相关的照片，有时明明有符合条件的照片，却没有出现在结果中。
考虑到目前我的照片图库仍处于分析阶段，或许还需要等系统完成分析，才能进一步判断这项功能的实际表现。
除了搜索照片，Apple 智能也让照片 App 中的「回忆」有了自定义的能力。过去，回忆影片主要由系统自动生成，用户能决定的内容比较有限。现在，只需输入一段自然语言描述，系统就会根据主题，从图库中挑选符合条件的照片和视频，并将这些素材编排成一段具有叙事感的回忆影片。
而在这些功能之外，我最期待的还是照片中的「消除」。
这项功能由设备端模型驱动，即使没有网络也能使用。开启 Apple 智能后，进入照片的编辑界面，等待下载完成，就能看到「消除」选项。只需轻点、涂抹或圈选，就能移除画面中不想保留的物体。
不过，期待归期待，实际效果就见仁见智了。
在我的体验中，如果照片背景比较干净、画面信息相对简单或消除区域较小，消除后的效果通常还算自然，不仔细看很难发现明显的处理痕迹。
但如果背景包含大量复杂纹理，或者需要移除的物体遮挡了较大面积的画面，填补出来的内容就很容易露馅，甚至出现明显的错误。
最后，Apple 智能还带来了一个更偏向趣味性和个性化表达的功能 —— 智绘表情。
在信息 App 中打开任意对话，点击左侧的「+」号，就能找到智绘表情的入口。你可以选择系统提供的建议，也可以直接用自然语言描述想要的表情。甚至还能以照片图库中的亲朋好友为原型，搭配不同的发型、表情和造型，为日常聊天增添一些个性化的表达。
具体生成的效果在我看来较为一般，但好在 Apple 会提供几个选择，你可以多进行尝试。
实时翻译
实时翻译可能是此次 Apple 智能更新中最重磅的功能之一。与照片中的「消除」一样，它同样由 Apple 的设备端模型驱动，提前下载所需的模型和语言后，即使没有网络也能使用。
虽然此次 Apple 智能的设备与 Siri 语言支持范围包括简体中文和英文，但实时翻译支持的语言更加丰富，除了中文和英文，还涵盖了法语、日语、德语、西班牙语等多种语言。实时翻译支持信息、电话、FaceTime，以及通过 AirPods 进行的面对面交流。
在信息 App 中，用户可以直接翻译对话内容；使用 FaceTime 视频通话时，翻译结果会以字幕的形式出现在屏幕上；在普通电话中，系统则会通过语音播放翻译后的内容，让使用不同语言的双方也能顺畅交流。如果是面对面交流，实时翻译还能直接把对方说的话翻译成自己的语言，并通过 AirPods 播放出来，不必再通过手机查看译文。
目前，面对面的 AirPods 实时翻译支持搭载了最新固件的 AirPods 5、AirPods 4（主动降噪）、AirPods Pro 2 及后续机型以及 AirPods Max 2。如果你是这些 AirPods 用户，当它们和一台开启了 Apple 智能的 iPhone 配对后，就能在翻译 App 中看到「实时」的页面入口了。
至于实际效果，在我的体验中，实时翻译已经能够正确理解并翻译大部分对话内容，基本的信息传达不成问题。但译文有时还是显得比较生硬，尤其是在一些更口语化的表达中，能够明显感受到机器翻译的痕迹。
虽然距离自然流畅的跨语言交流还有一定差距，但对于日常沟通来说，已经具有相当不错的实用价值。
摘要与注意力
相比实时翻译和照片消除，Apple 智能在通知、邮件等日常功能上的变化或许没有那么显眼，但它们同样实用，能够减少我们处理信息所花费的时间，让注意力不那么容易被打断，对我这种 AuDHD 患者来说确实是十分友好。
通知方面，Apple 智能会分析 iPhone 收到的所有通知，并将需要优先关注的内容以「首要通知」的形式显示在通知列表顶部。同时，对于同一个 App 发来的多条通知，系统也能自动提炼其中的重点，生成简短的摘要，不必再逐条查看。
不过，「生成通知摘要」这项功能也不是默认打开的，需要到设置 > 通知 > 生成通知摘要页面下手动开启并设定。
与此同时，「减少干扰」专注模式也随着 Apple 智能的到来正式上线。与传统专注模式主要依靠预设规则过滤通知不同，有 Apple 智能加持的「减少干扰」模式能够判断通知内容是否重要，优先显示可能需要及时处理的信息，同时将不那么紧急的通知暂时静音，尽量减少不必要的打扰。
邮件 App 也迎来了类似的变化。面对一封篇幅很长的邮件，或者一连串来回往复的邮件对话，Apple 智能可以直接提炼其中的主要内容，帮助我们快速了解重点。而「优先邮件」则会将具有时效性、需要尽快关注的邮件置于收件箱顶部，避免重要信息被淹没在大量邮件中。
此外，备忘录中的录音，以及电话 App 中的通话录音转录，也都支持通过 Apple 智能生成内容摘要，省去重新听完整段录音或阅读大段文字的麻烦。
尾巴
不难看出，这次 Apple 智能的到来，并没有带来太多惊喜。对于国内用户来说，漫长的等待早已将期待消磨殆尽。在等待期间，海外用户对初版 Apple 智能的普遍负面评价，也让我们对它的实际表现有了心理预期。
毕竟，当各家的 AI 都在向 Agent 进化，我自己的工作流也已经因为 Agent 的加入大幅提速时，再回过头体验这些以信息总结、图片处理和简单交互为主的功能，难免会有一种黄花菜都凉了的感觉。
只能说，这次国行 Apple 智能的到来，更多是补上了 Apple 设备「没有 AI」的缺口。它距离足够好用、实用，甚至是新 Apple 智能液态玻璃效果的 Siri UI 那样让人眼前一亮的「好看」，都还有很长一段路要走。
当然，如果你还是忍不住想要尝鲜，还得提醒的是，目前推送的仍是测试版本，尝鲜有风险，更新前记得做好备份。

Texas was the new epicenter of the AI data center buildout. That might be kaput.
Some of the largest AI infrastructure projects in the world are underway in Texas. A dramatic political shift could slow their construction—and deepen concerns about the economics of the AI boom.
Texas is the fastest-growing data center market in the US and ground zero for Big Tech's largest AI buildouts. But the blue wave that swept the Lone Star State may jeopardize that position.
Democrat James Talarico won the US Senate seat against Ken Paxton. Gina Hinojosa won the race for governor against the Republican incumbent, Greg Abbott. At the state level, Democrats will take control of the Texas House for the first time in 24 years. Talarico and Hinojosa made data centers a central issue, discussing them constantly on the campaign trail.
Even before the polls closed, insiders in the data center industry noticed that the times were changing. At the industry's DCD conference in Ashburn, Virginia, on Tuesday, panelists lamented that Texas had been the easiest place to build for years—until September. That's when Abbott, perhaps seeing the increasingly bipartisan distaste for these facilities, began changing course himself.
Developers said the governor’s office had stopped responding to their emails. On September 21, Abbott directed a key state regulator to halt data center permits. Many panelists at the conference were expecting this to mean that existing projects might be slowed and new ones could be halted altogether.
The governor-elect indeed seems eager to do that. Hinojosa supported tax breaks for data centers in 2023 as a way to boost construction jobs, but during her campaign she began pushing for a full-fledged moratorium.

            Abstract:Language models can follow a directive when they believe they are monitored and abandon it when they believe they are not, a pattern termed Alignment Faking. Prior work establishes this for harmful-content objectives and a handful of moral-foundations values, leaving open how it distributes across a wider value space. We argue it is value-dependent: whether compliance survives a change in perceived oversight is a property of the model--value pairing, not of the model alone. Our framework profiles Alignment Faking per value, scoring each model-value pair under three conditions: bare (no system prompt), unmonitored, and monitored.
