Note: This repository contains Anthropic's implementation of skills for Claude. For information about the Agent Skills standard, see agentskills.io.
Skills are folders of instructions, scripts, and resources that Claude loads dynamically to improve performance on specialized tasks. Skills teach Claude how to complete specific tasks in a repeatable way, whether that's creating documents with your company's brand guidelines, analyzing data using your organization's specific workflows, or automating personal tasks.
For more information, check out:
- What are skills?
- Using skills in Claude
- How to create custom skills
- Equipping agents for the real world with Agent Skills
This repository contains skills that demonstrate what's possible with Claude's skills system. These skills range from creative applications (art, music, design) to technical tasks (testing web apps, MCP server generation) to enterprise workflows (communications, branding, etc.).
Each skill is self-contained in its own folder with a SKILL.md file containing the instructions and metadata that Claude uses. Browse through these skills to get inspiration for your own skills or to understand different patterns and approaches.
Many skills in this repo are open source (Apache 2.0). We've also included the document creation & editing skills that power Claude's document capabilities under the hood in the skills/docx, skills/pdf, skills/pptx, and skills/xlsx subfolders. These are also open source (Apache 2.0), and we wanted to share them with developers as a reference for more complex skills that are actively used in a production AI application.
These skills are provided for demonstration and educational purposes only. While some of these capabilities may be available in Claude, the implementations and behaviors you receive from Claude may differ from what is shown in these skills. These skills are meant to illustrate patterns and possibilities. Always test skills thoroughly in your own environment before relying on them for critical tasks.
- ./skills: Skill examples for Creative & Design, Development & Technical, Enterprise & Communication, and Document Skills
- ./spec: The Agent Skills specification
- ./template: Skill template
You can register this repository as a Claude Code Plugin marketplace by running the following command in Claude Code:
/plugin marketplace add anthropics/skills
Then, to install a specific set of skills:
- Select Browse and install plugins
- Select anthropic-agent-skills
- Select document-skills or example-skills
- Select Install now
Alternatively, directly install either Plugin via:
/plugin install document-skills@anthropic-agent-skills
/plugin install example-skills@anthropic-agent-skills
After installing the plugin, you can use the skill by just mentioning it. For instance, if you install the document-skills plugin from the marketplace, you can ask Claude Code to do something like: "Use the PDF skill to extract the form fields from path/to/some-file.pdf"
These example skills are all already available to paid plans in Claude.ai.
To use any skill from this repository or upload custom skills, follow the instructions in Using skills in Claude.
You can use Anthropic's pre-built skills, and upload custom skills, via the Claude API. See the Skills API Quickstart for more.
Skills are simple to create - just a folder with a SKILL.md file containing YAML frontmatter and instructions. You can use the template-skill in this repository as a starting point:

- name - A unique identifier for your skill (lowercase, hyphens for spaces)

An open source design system that's fully customizable and built for how we build now: 
by people and the agents working alongside them.
Currently in Beta · Built on React 19+ and StyleX
Docs · Storybook · Sandbox · Contributing · Discord
Astryx is an open source design system that grew inside Meta over the last eight years, where it became the most-used and largest design system in the company — powering 13,000+ apps and shaped by the engineers, designers, and product teams who depend on it every day.
It ships 150+ accessible components, brand-level theming, dark mode, ready-to-ship templates, and a CLI as one cohesive system. You import pre-built CSS and use typed React components — no build plugin, no styling library to adopt — and both people and AI assistants build with the same tooling.
What makes Astryx different:
- Open internals. Components are built to be composed at any level, not locked behind a closed top-level API. The building blocks you'd reach for are exported directly, and when you need to go deeper, swizzle ejects a component's full source into your project to own.
- No styling lock-in. Astryx authors its styles with StyleX, but that's invisible to consumers. Override with className using Tailwind, CSS modules, or plain CSS — whatever your project already uses.
- Customize without wrapping. A theme is a set of CSS custom property overrides, so a designer can make Astryx unmistakably theirs without forking or wrapping component source.
- Built for people and agents. The API, docs, and CLI are designed together so a person and an AI assistant build the same way, from the same reference.
Astryx requires React 19 or later (react and react-dom are peer dependencies of @astryxdesign/core).
Install Astryx, a theme, and its peer dependencies:
# npm
npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
npm install -D @astryxdesign/cli
# pnpm
pnpm add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
pnpm add -D @astryxdesign/cli
# yarn
yarn add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
yarn add -D @astryxdesign/cli
You can also install the CLI once for your computer, so astryx works in any folder and every coding agent knows Astryx; in a project, it still runs that project's own version:
npm i -g @astryxdesign/cli
Project install, global install, or both? astryx docs global/project-global-or-both compares them (both is recommended), and astryx docs global explains how global mode works.
The simplest setup is a few CSS imports plus a theme provider — no build plugin, no PostCSS or Babel config. See the @astryxdesign/core README for the full guide (Next.js, Tailwind, Vite, and CDN).
For reliable CLI access, add a script to your package.json:
"scripts": {
  "astryx": "node node_modules/@astryxdesign/cli/clients/cli/bin/astryx.mjs"
}
Then use it as npm run astryx -- component --list. This avoids path errors when AI assistants or new developers invoke the CLI directly.
@astryxdesign/lab (experimental components) is used internally for Storybook and the sandbox and is not published to npm. @astryxdesign/vega (Vega/Vega-Lite chart wrapper) and @astryxdesign/charts (chart components) are published to npm only under the @canary dist-tag — there is no stable release yet.
These are the promises Astryx makes to the people building on it.
- Guidance over enforcement. Components give you capability rather than guardrails that fight you. Design opinions live in docs and examples — if you pass a value, the component renders it.
- Strong, documented conventions. Every component follows the same naming, prop, and composition rules, and every one is thoroughly documented — so once you've learned a few, the rest feel familiar, and both people and AI can predict how an unfamiliar component behaves.
- One system for humans and AI. The API, conventions, docs, and CLI are designed together so people and AI assistants build the same way. Every change that made Astryx easier for AI made it easier for people too.
- Earned by measurement. We test conventions rather than assert them, hold the results loosely, and revisit them when a new situation proves them wrong.

MuJoCo stands for Multi-Joint dynamics with Contact. It is a general purpose physics engine that aims to facilitate research and development in robotics, biomechanics, graphics and animation, machine learning, and other areas which demand fast and accurate simulation of articulated structures interacting with their environment.
This repository is maintained by Google DeepMind.
MuJoCo has a C API and is intended for researchers and developers. The runtime simulation module is tuned to maximize performance and operates on low-level data structures that are preallocated by the built-in XML compiler. The library includes interactive visualization in native desktop windows and web browsers. MuJoCo further exposes a large number of utility functions for computing physics-related quantities.
We also provide Python bindings and a plug-in for the Unity game engine.

我家客厅一边是玻璃阳台门，另一边连着餐厅，左右并不对称。刚通电时，我在 Sonos App 里做了一遍 Trueplay 调音，举着手机绕客厅走了一圈。调完之后，阳台玻璃那边原本有些散的低频，听起来确实收敛了不少。
最近我在追 HBO Max 上的「Lanterns」，里面有不少压低嗓子说话的戏份，正好是以前用漫步者听着最费劲的部分。Beam Ultra 的 AI 人声增强有四档，我开到第二档，压低声音说话的角色也能听清楚了。背景声没有被完全压掉，听起来不至于只剩下一层干巴巴的人声。
接口上也有一点可惜。Beam Ultra 背面只有一个 HDMI eARC，没有额外的 HDMI 输入，也不支持 HDMI 直通。游戏机和机顶盒都得接到电视上，再通过 eARC 把声音传给回音壁，外接设备多的话，还得看看电视上的接口够不够用。另外，它支持杜比全景声、TrueHD 和 DTS Digital Surround，但不支持原生 DTS:X。
拿它听歌，和屋里的 HomePod 也有些不同。HomePod 在客厅不同位置听起来都比较接近，Beam Ultra 则有更明确的正面感。坐在沙发上听，更容易分清乐器在左边还是右边。
在耳机和音箱之间切歌
收到设备的那天夜里，我就想试试把回音壁正在放的音乐切进耳机，结果第一回就没成功。
Sonos 27 新增的这项功能叫 Headphone linking（关联到系统）。我先在 Sonos App 里按提示完成了关联设置，然后照着平时的习惯，在 Apple Music 里用 AirPlay 把歌投到回音壁。接着戴上耳机，长按右耳罩上的 Content Key。耳机响了一声提示音，回音壁还在自己唱自己的，声音并没有切过来。
我翻了一圈设置才发现，问题出在音源上。Headphone linking 并不是所有播放方式都能用。直接在 Sonos App 里点播的流媒体、本地曲库，以及接入系统的线路输入都可以切换；但通过 AirPlay、蓝牙，或者部分音乐服务 App 的直接控制功能发起的播放，就不能这样转过去。
这就得稍微改一下平时听歌的习惯，把常用的 Apple Music 账号绑进 Sonos App，从里面开始放歌。之后切换设备就不用再拿手机了，想在客厅外放，或者把声音收回耳机，长按 Content Key，听到切换提示音后松开就行。
当然，它也不是一套完全独立的无线播放系统。家里仍然得有至少一台兼容的 Sonos 设备保持通电在线，Ace Ultra 本身还不能脱离 Sonos 系统单独播放 Wi-Fi 音乐。
另外，音乐关联目前还在 Early Access 阶段，传输的是有损压缩立体声，不支持无损和空间音频。切换也得等一会儿，长按 Content Key 后大概要过三四秒，声音才会切过去。
还有个挺有意思的细节：把回音壁的声音切进耳机，我在客厅哪个角落长按都能用；反过来切回音箱，坐在远处的餐桌旁就没反应，得走到音箱一臂以内。
Sonos 在官方社区的说明里提到，这样设计是为了避免意外外放，吓到旁人或吵醒孩子。家里刚好有两个小孩，我倒觉得这个限制挺合理。毕竟有时候只是想把耳机摘下来，并不意味着希望客厅突然响起音乐。
两个小孩睡着以后

那晚企鹅说有点困，想在沙发另一头就着落地灯看会儿书。我拿起茶几上的 Ace Ultra 戴好，长按右耳罩上的 Content Key。
这次用的是 TV Audio Swap（电视音频切换），和前面切音乐相比，速度快了不少。客厅里的引擎声停下，耳机里接着响起声音，电视画面一直往下走，没有明显的中断。
刚切过来的时候，我还以为回音壁没有停，下意识把右耳罩掀开了一点。电影里的声音听着仍然来自正前方的电视，赛车从左边开到右边，维修站里的广播和混响也没有一下全挤到脑袋中间。掀开耳罩，才发现客厅已经安静了，只剩下企鹅翻书的声音。

转头去茶几拿水杯，或者看一眼旁边的企鹅，对白和引擎声还是从电视的方向传过来，不会跟着我的脑袋一起转。看踩离合、挂挡的特写和人物说话，也没察觉明显的音画延迟。整个过程不用去电视设置里重新找耳机，也不用等配对，切过来就能接着看。
那晚客厅只亮着落地灯和电视。企鹅在旁边看完了几章书，后来先回房睡了。我戴着耳机，把音量开到平时白天看片的大小，听着引擎声冲过终点线，把剩下的电影看完了。
睡前靠在床头
不看电影的晚上，我也会靠在床头，用手机蓝牙连上 Ace Ultra，再听两首歌。Daft Punk 的「Random Access Memories」已经听过无数遍了，我还是喜欢直接跳到「Giorgio by Moroder」，从开头的独白，听到后面合成器贝斯和真鼓进来。乐器之间拉得开，低频也干净、有弹性。

两个星期下来
用了两个多星期，Beam Ultra 已经接替了家里原来的电视音箱，小音量下也能听清对白。Ace Ultra 白天戴着写代码，晚上则接着用它看电视里没看完的电影。两台设备连起来以后，倒是省去了不少来回切换的麻烦，不用每次都重新找设备、调整播放方式。

前言：不只是几个红色和白色的盒子
看到标题，你或许已经意识到本文的研究对象：无处不在而丑到爆的烟雾报警器。表面上它们是一个个独立的单元，但实际上其背后是无数个探测器、警报器、输入输出模块和主机所构建的巨大消防网络。你可能从未注意到它们，也从未需要关注它们，毕竟（也幸好）火灾并不经常发生。那我们究竟为何需要为一个如此小概率事件设计安装一套如此复杂的系统？这个系统又如何工作来保护我们的安全？
从一场模拟的火灾说起
假设你在一个高层写字楼的办公室里。由于线路过载，本楼层的配电箱起火了。此时你所在的楼层甚至整个地上部分都毫无异样。
假设这个建筑没有现代的防火设计。烟气从配电箱周围的缝隙和未封堵的管线穿墙孔洞中逸出，逐渐进入走廊，沿着电梯井、楼梯和管道井飘向其他楼层。此时空气中有股淡淡的焦糊味，但你没有看见很浓的烟气，别的人也没有任何要动的迹象，于是你索性忽略这些奇怪的迹象，继续工作。但烟雾越来越浓，你终于意识到不对劲，决定出去看一看发生了什么情况。但当你推开办公室门时，一股热浪与浓烟扑面而来，走廊里已经看不清前方，远处隐约闪着火光。
所幸事实不会如此。配电箱故障会导致所在区域供电中断，办公室内顿时一片漆黑。但没过几秒，几盏灯自动亮起。墙上的红色盒子发出「呜——哇——」的响声。包括你在内的所有人都僵住了，不知所措。但广播随即传来「请注意，楼内发生紧急情况，请沿疏散通道有序撤离」的语音，你这才反应过来，立即跟随其他人离开办公室，沿着闪烁的绿色疏散指示灯的方向撤离了大楼。
这两种截然不同的结果，差别并不在于火灾是否发生，而在于建筑能否及时发现危险、向人们发出警告，并尽可能控制火灾和烟气的蔓延。一套火灾自动报警系统，以及与之配合的防火分隔、防烟排烟、应急照明和自动灭火等设施，其意义便是在这场与时间的赛跑中，为人员识别危险、采取行动并最终安全撤离争取宝贵的时间。
一场火灾，是如何被发现的？
这就不得不提到开篇那个熟悉的白盒子了，它就是早期探测中的重要一环。不过，我们需要先规范一下术语：商用建筑里那种中央控制的、连接的「烟雾报警器」，实际上叫「点型光电感烟探测器」。点型，指的是它能在一个固定点位探测火灾迹象，而区别于监测一段长条区域的线型探测器；光电，指的是它采用光电原理来判断是否有烟雾（此外还有离子感烟探测器，采用电离室原理，不过如今在普通商业建筑中相对少见）。
让系统能感知到火灾的，就是这些火灾探测器。常见探测器可以分为感烟、感温和火焰，以及图像型、气体和复合式等相对较为少见的类别。感烟包括刚刚提到的点型感烟、线型光束感烟和吸气式感烟。
前两者的基本原理很简单：点型主要靠光的散射，正常时传感器几乎「看不见」发射LED的光，但是有烟会使得部分光散射到了传感器，达到一定阈值就报警；线型光束则是发射红外光经过反射又再接收（也有对射型，一边发射另一边接收），如果有烟会使得接收光强过小而报警。吸气式则较为特殊，通过一系列管道持续抽取空气，通过高灵敏度的光学传感器分析其中的烟雾粒子，由于较为复杂，不再赘述。
不过，不是所有的火都会产生浓烟，也不是所有的区域都适合安装烟感（比如别往厨房里装，别问我怎么知道的……）。因此便有了其他探测方式。感温探测器更为直观，就是探测环境温度及其变化，不过具体探测方式有所不同。值得一提的是，感温探测器不只是达到一定温度就报警，还可以使用差温探测——在短时间内温度升高过快时触发警报。
而火焰探测器也一样直接，就是通过检测火焰发出的紫外光或者红外光来探测火灾。不过，这也意味着它需要监测区域内出现明火才能有效工作，因此不适合作为可能发生阴燃火灾场所的唯一探测手段。此外，探测器还需要有合适的视野，安装位置受到一定限制，成本也通常较高。
当然还有最传统的手动火灾报警按钮，就是那种灯开关大小、写着按下报警的红色盒子（后文简称「手报」）。如果有人员看到了火灾需要立刻上报，就可以按下。顺便辟个谣，第一它不会喷墨水；第二它通常不会直接启动喷淋！（特殊的雨淋等系统另当别论）
探测器报警了，然后呢？
五官集齐了，似乎还缺一个脑子来控制。它便是控制主机。这里的主机包括两台，其一是火灾报警控制器，它汇集并处理所有探测器的信息；其二是消防联动控制器，负责指挥现场模块和声光警报器、应急广播等警报设备。不过，现在主流的设计已经将其合二为一，形成了火灾报警控制器（联动型），下文简称「主机」。那探测设备是如何给主机报警的呢？
一个简单的解法，便是非编址型设备。别看名字唬人，实际原理很简单：一堆探测器连接在一个区域回路，如果报警了就增大电流消耗或者拉低电压，主机监测到这一电压或者电流的变化就报警。
十分简单对不？但其实有个很大的Bug：要么你要用特别多回路连接到主机，要么你就可能不清楚一个回路上哪个设备在报警，只有一个很粗略的「分区1 火警」。小的建筑没啥问题，但是机场、高铁站这种地方……还是算了吧。
于是便诞生了编址型设备。这些设备里面都有相对复杂的控制器，每一个设备都有自己的地址。以常见的轮询方式为例，探测器不再是主动上报报警情况，而是主机像点名一样问：「一号烟感请回复！」然后探测器通过特殊协议回复状态。主机持续循环查询、保持对设备状态的监视。这样，主机能精准定位到报警的设备，方便相关人员。这样的通信方式还有几个好处：一是更方便故障定位和排查；二是它使得复杂数据传输成为可能，因而部分主机能接受探测器的实时模拟量读数，结合变化趋势和特定算法，更细致地判断火灾迹象，减少某些环境干扰造成的误报，也方便进行探测器状态监测和维护。
主机收到了报警，然后呢？
首先，当然不能一有探测器报警，就直接启动全楼的声光警报器和所有消防设备。姑且不谈有多烦人，如果误报频繁，人员很容易产生报警疲劳——说人话就是「狼来了」效应，久而久之，即使真正发生紧急情况，也可能不再及时响应。因此，系统需要根据火灾信号和预设逻辑，区分初始报警、火灾确认以及后续的消防联动。
下面以我国现行规范为例。GB 55036-2022规定，火灾确认后，系统应启动建筑内所有火灾声光警报器。而对于需要自动联动控制的消防设备，其联动触发信号则应采用两个独立报警触发装置报警信号的「与」逻辑组合。具体采用哪些设备、怎样组合，还要根据受控设备的类型和相应规范确定。例如，常开式防火门的关闭联动，可以采用所在防火分区内两只独立火灾探测器的报警信号，也可以采用一只火灾探测器与一只手动火灾报警按钮的报警信号。
另外，消防控制室通常还设有消防联动控制器的手动控制盘。不过，它并不是一个可以无差别启动所有设备的总开关。对于消防水泵、防烟和排烟风机等关键设备，规范还要求设置手动直接控制装置，即常说的多线控制盘，以便在自动联动未能正常工作的情况下，由值班人员直接操作。
那什么是联动输出？它就是主机的「四肢」，是通过实际工作来保护人员安全的一系列具体动作。
有哪些联动输出？
首先，楼内人员必须知道发生了火灾，因此最直接的输出就是报警设备。常见的有声光警报器（顾名思义，就是同时发出声音和闪光警报的设备；声音在国内常见的是「呜——哇——」的变调音，偶尔也有「嘀——嘀——」的类型）、传统警铃，以及消防应急广播。应急广播通过楼内扬声器，以语音形式告知火灾情况和疏散指令。如果建筑同时设置了声警报器和应急广播，两者通常会交替播放，避免警报声和广播内容相互干扰。毕竟，光知道发生了火灾还不够，楼内人员还得知道接下来该怎么办。
其次，还得保障人员疏散路径的安全。火灾中，烟气往往比火焰更早威胁人员生命，甚至可能在火焰蔓延到之前，就已经让逃生通道变得难以通行。因此，建筑需要一套防排烟系统。
先说排烟系统。简单来说，就是通过自然排烟窗或者机械排烟系统，将火灾产生的烟气排出建筑，尽可能减少烟气在室内积聚，为人员疏散和消防救援争取时间。而防烟则是尽可能阻止烟气进入疏散楼梯、前室、避难层等受保护区域。它可以通过自然通风实现，也可以通过机械正压送风：风机将室外空气送入受保护空间，使其内部压力高于相邻区域。这样，在门开启时，空气便倾向于从受保护空间流向外部，减少烟气倒灌的可能。
联动控制器在满足预设条件后，便会启动相关的正压送风机、排烟风机，并控制相应的风口和阀门。不过，这里又有一个 Bug：要是楼梯间的压力过高，而防火门又比较难推开怎么办？毕竟，门打不开，逃生通道再安全也没用。于是便有了余压监测与泄压装置。通过传感器监测受保护区域与相邻区域之间的压差，在余压过大时控制泄压阀打开，避免防火门因压差过大而难以开启。具体原理就不再赘述。
再次，还得控制火灾蔓延，尽可能将火灾限制在相应的防火分区内。这便依赖于防火门与防火卷帘。防火门的动作相对简单：常闭式防火门平时依靠闭门器保持关闭；常开式防火门则保持开启，发生火灾并满足联动条件后，联动闭门器或电磁释放器动作，防火门自动关闭。
而防火卷帘有所不同。对于设置在疏散通道上的防火卷帘，通常采用两步降落的方式：当所在防火分区内任意两只独立的感烟探测器，或一只专门用于联动防火卷帘的感烟探测器报警后，卷帘先下降至距地面1.8m的位置，既能在一定程度上阻止烟气扩散，又为人员通过保留空间；当专用感温探测器报警后，卷帘便完全下降至地面，形成完整的防火分隔。而对于设置在非疏散通道上的防火卷帘，则按相应联动条件直接下降到底。过程看似复杂，但还是很有逻辑的：先尽量保障人员通行，随后再完成防火分隔。
最后，还得保证人员逃生时看得清、找得到路。这便是消防应急照明和疏散指示系统的作用。传统建筑中常见的是非集中控制型灯具，也就是每盏灯具独立运行，没有中央控制。不过，近年来集中控制型系统也越来越常见。顾名思义，这种系统设有专门的应急照明控制器（注意不是火灾报警控制器哦），能够集中监控和控制各处灯具的应急工作状态。
你可能会想：不就是亮起来就行了吗，有什么可控制的？答案是，现在的疏散指示灯已经不只是亮灭那么简单了。在一些需要多种疏散方案的场所，智能型疏散指示灯可以根据火灾情况动态改变箭头方向，关闭不适宜通行的出口指示，并引导人员选择其他疏散路径。换句话说，火情在变，疏散路线也可以随之调整。
那这又是怎么工作的呢？这就不得不提到上文的编址型设备了。通过火灾自动报警系统，控制器能够获得火灾报警区域等信息，并将相应的联动信号发送给应急照明控制器。后者根据预先设定的疏散指示方案，控制相应的方向标志灯切换箭头指示方向，必要时还会将不适宜通行的出口标志切换为「禁止入内」。这样，系统便能根据火灾发生的位置和预设的疏散策略，引导人员避开受火灾影响的区域。不过，这并不是控制器临时从零开始计算一条新路线，而是在设计阶段就已经制定好的多套疏散方案之间进行选择。
最后还有一些其他的联动功能。例如电梯迫降，就是通过消防联动控制使相关电梯返回首层或指定转换层，停靠后退出正常乘客服务，以便轿厢内人员离开。消防电梯则有专门的消防运行模式，不能简单地与普通乘客电梯一并视为停用。非消防电源切除，则是在确认火灾后，根据建筑消防设计切断火灾区域及相关区域内不需要继续运行的非消防电源，以减少电气设备带来的次生风险。不过，这并不意味着整栋楼的照明都要立即切断，保持足够的照明对人员疏散同样重要。
此外，门禁系统控制的疏散通道门和停车场出入口挡杆，也可以在火灾时按预设逻辑自动开启或释放，避免人员被困，同时方便消防救援人员进入。至于自动喷水灭火、消火栓和气体灭火等系统，它们也与火灾自动报警及消防联动系统有着密切联系，不过各自的工作原理和控制逻辑相当复杂，这里就不再展开了。顺便辟个谣：普通闭式自动喷水灭火系统的喷头是靠自身的感温元件动作的，并不是报警主机一报警，所有喷头就会集体喷水。
写在最后
读到这里，你应该已经对商用建筑中的火灾自动报警系统，以及与之联动的部分消防设施有了一个大致的认识。
那回到开篇的问题：天花板上那个不起眼的白色盒子，究竟是怎样保护我们的安全的？
它本身并不能扑灭火灾，也不能保证所有人都能安全撤离。它所做的，是尽可能早地发现火灾，将信息传递给控制主机，再通过一系列预先设计好的联动逻辑，协调报警、广播、防排烟、防火分隔和疏散指引等设施，共同应对火灾。
从一个小小的探测器，到整栋建筑的消防系统，看似各自独立的设备实际上构成了一张紧密协作的安全网络。它们的最终目的并不是让火灾不再发生，而是在火灾发生后，尽可能控制危险的发展，为建筑内的人员争取更多反应和逃生的时间。
毕竟，消防系统真正守护的，从来都不是设备本身，而是生活在建筑里的人。
谨以此文向奋战在一线的消防救援人员，以及长期从事消防设计、施工、维护和安全管理的工作者致以敬意。也希望通过这篇小小的科普，让更多人认识到那些平日里并不起眼、却在关键时刻守护生命的设施。

The backlash about data centers might really just be about electricity
Big Tech sees a culture war over progress. But the real fault line is electricity: drawing it from the grid and generating it onsite provoke different kinds of backlash, neither easily solved by public relations.
This story originally appeared in The Algorithm, our weekly newsletter on AI. To get stories like this in your inbox first, sign up here.
As voters went to the polls across the US last week, I was in Ashburn, Virginia, part of what’s known as Data Center Alley—the world’s largest data center hub. It’s also where the backlash now sweeping the country arguably first began taking shape.
Driving through it is surreal. Concrete monolithic buildings loom along every major road, with names like Skybox and CloudHQ.
It’s accepted wisdom in Big Tech that the war against data centers must be about something bigger than just data centers themselves. Two days after the midterms, OpenAI’s chief global affairs officer, Chris Lehane, wrote that data centers “have become a proxy for public unease about affordability, corporate power, and people losing control over their futures.” It’s a culture war, in other words.
But spending a few days in Data Center Alley left me wondering if it’s really the proxy that Lehane describes. I came away convinced that the data center backlash is more about electricity than Big Tech admits. The industry can improve its image, but it can’t escape the physical consequences of its enormous appetite for electricity.
Here’s why. There are two ways to power the sort of data center that AI companies want: connecting to the grid, or generating electricity onsite. In Virginia’s Loudoun County, where data centers are ubiquitous but have been built at a steadier pace than the breakneck expansion now underway elsewhere in the country, most are connected to the existing grid.
One facility I went inside, operated by Equinix, has massive diesel generators onsite for backup but gets its power from the local utility, Dominion Energy. Much of Dominion’s electricity is generated by natural gas (which is cleaner than coal or oil, but worse than renewables).
The average data center operating in this part of Virginia today has a power capacity of 54 megawatts. That’s more than the power draw of the Denver International Airport.
Elena Schlossberg, a prominent activist against data centers in Virginia, told me she’s “always banging my head against the wall” when the industry paints the fight as a culture war. “It was always about power,” she says—that is, electricity.
Some Virginia protesters appear more animated by a broader anti-tech populism than Schlossberg, to be fair. But it’s the particular consequences of drawing so much power from the grid that have done the most to shape how the backlash has played out.
Recent protests have led to new rules from the state that data centers must pay fully for the cost of new transmission lines to the grid and make sure they’re not spread among everyone else. Data center developers told me they’re preparing for new rules that would cut them off from grid power during peak demand. Schlossberg also worries about the downstream effects of a strained grid—for example, that data centers will run more diesel generators or that Dominion Energy will expand fossil fuel inputs rather than renewables to meet demand.
The overwhelming majority of AI data centers being built elsewhere in the country are not designed this way. The scale desired is so massive that companies are setting up in rural areas where there is virtually no grid infrastructure to connect to. Building there means bringing your own power (so-called “behind the meter” power), in the form of natural-gas-powered turbines. Companies also build diesel generators for backup. Anthropic, for example, has reportedly agreed to pay $3.4 billion for gas turbines in what’s described as the largest power generation purchase by an AI company.
Even if grids were nearby, they’d be unlikely to serve the amount of power demanded. The smallest data centers attractive for AI training are 300 megawatts. It’s a lot of power for one industrial site, but not unprecedented: One data center developer told me he’s eyeing a former steel mill already equipped to draw that much electricity from the grid.
But the ideal facilities are more like 6,000 megawatts. That’s the estimated draw of the city of Chicago, which is powered by more than 20 power plants within the city alone (and dozens farther out).
The notion of data center companies’ bringing their own power might seem attractive at first, because they wouldn’t be straining the grid. But generating electricity at this scale inevitably affects surrounding communities, and when public utilities build infrastructure of this magnitude, communities have traditionally expected a say in where it goes. Now, private companies are undertaking projects on a similar scale.
Natural-gas turbines of any scale release air pollutants. When diesel generators are used, it’s even worse. And in the unprecedented rush to get these facilities operating, companies have become horrible neighbors (recall that Elon Musk violated air quality laws when he set up dozens of turbines to power a data center in Memphis, according to the Environmental Protection Agency).
Big Tech’s tendency to chalk the backlash up to a culture war obfuscates one simple fact: There’s only so pleasant you can make a small city of computers to live around. El Niño is part of a cycle in Earth’s climate that is linked to warmer than usual waters in the Pacific Ocean. Every few years, it brings droughts or floods to different regions. This year, sea surface temperatures in the eastern Pacific have already exceeded those of the four other recorded very strong El Niño events that have occurred in the past 50 years. Countries such as Panama and Indonesia are now experiencing low rainfall, and Brazil is bracing itself for wildfires. Such events have also historically had long-lived effects on economies and health. For example, the 1982–83 El Niño event resulted in a global income loss of US$4.1 trillion; for the 1997–98 one, the figure was $5.7 trillion1. And life expectancy at birth in ten (relatively wealthy) Pacific Rim countries was lowered by 0.54 years during the earlier event and by 0.37 years during the later one, relative to what would otherwise have been expected2. El Niño exposure has also been linked to childhood undernutrition, with measurable effects on height and weight3.
The latest El Niño’s effects on different places will thus depend not just on the regions’ resilience to extreme weather, but on the resilience of their food, agriculture and health systems. The World Health Organization (WHO)4 and other global organizations are aware of these risks. However, climate change, food insecurity and infectious diseases are often considered separately, despite being interdependent5.
We argue that the risk of catastrophe does not lie solely with the strength of this El Niño, but rather with how it interacts with other crises and local institutions. Comparatively little attention has been given to what happens when El Niño disrupts food supplies, affects what people eat and potentially changes their exposure to infectious disease.
And the latest El Niño is occurring at a time when global food systems are under pressure. Ongoing wars in Ukraine and Iran have disrupted agricultural production and trade, and fertilizers are in short supply. In isolation, many countries could withstand a major El Niño, but the combined effect of several shocks could overwhelm that resilience.
These interactions might also create health risks that are less obvious. Food shortages and changes in relative prices can alter what people eat and where they obtain their food from, potentially increasing contact with animals carrying zoonotic diseases. We argue that understanding how climate, food insecurity and infectious-disease risks interact is essential to anticipating the wider health consequences of the coming El Niño.
Interaction of risks
The WHO rightly describes El Niño as ‘a risk modifier’: its health effects depend not just on the climatic shock, but also on the vulnerabilities of the populations and systems that it affects. Yet, public-health discussions have so far centred on the direct consequences of extreme weather.
The Climate Impact Lab at the University of Chicago in Illinois projects 451,000 extra heat-related deaths — mainly in low- and middle-income countries (LMICs), particularly the Sahel region of Africa — associated with this El Niño6. The World Meteorological Organization also warns of the health risks associated with extreme heat, as well as increased spread of infectious diseases linked to changes in weather patterns. A WHO assessment identifies very high risks from malnutrition; cholera due to water contamination and heat stress; and high risks from malaria, arthropod-borne viral diseases and zoonotic diseases associated with greater exposure to vectors and movement of animals in changing conditions.
These risks can be substantial. The 2022 Pakistan floods demonstrated how extreme weather can generate several public-health crises. There were considerable agricultural losses, and flooding contributed to outbreaks of malaria and waterborne diseases. This was compounded by damage to health-care infrastructure that disrupted access to essential medicines7.
But another pathway to health has garnered less attention: what happens when extreme weather disrupts food supplies?
Earlier this year, the UN Food and Agriculture Organization (FAO) and World Food Programme warned that the current El Niño could compound already high levels of food insecurity across parts of Africa, Asia, Latin America and the Caribbean8. The two agencies proposed providing anticipatory assistance to 8.8 million people. The countries they highlighted were already experiencing severe food insecurity: an estimated 57% of Somalia’s population and 51% of Haiti’s were undernourished, and 63% of South Sudan’s population was experiencing severe food insecurity.
Lower agricultural production is a concern — particularly of maize (corn) in South Africa, where output was around 40% lower than normal during the 2015–16 El Niño and about 20% lower during the 2023–24 one. More concerning is that the current El Niño is arriving alongside other shocks that will push up the cost of food9. Low-income countries have experienced the brunt of food price inflation since 2020, linked to disruptions due to COVID-19 and wars. At the height of food price inflation, 65% of low-income countries and 61% of LMICs experienced levels greater than 10%.

Neither 1997–98 nor 2015–16 coincided with a global food-price shock comparable to those the world has experienced since 2020 (see ‘Food price spikes’).
