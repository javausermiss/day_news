Open Code Review is an AI-powered code review CLI tool. It originated as Alibaba Group's internal official AI code review assistant — over the past two years, it has served tens of thousands of developers and identified millions of code defects. After thorough validation at massive scale, we incubated it into an open source project for the community. Simply configure a model endpoint to get started.
It reads Git diffs, sends changed files to a configurable LLM via an agent with tool-use capabilities, and generates structured review comments with line-level precision. The agent can read full file contents, search the codebase, inspect other changed files for context, and produce deep reviews — not just surface-level diff feedback. Beyond diff review, ocr scan reviews entire files for auditing unfamiliar codebases or directories that have no meaningful diff.
Visit the official website for more details.
Compared to general-purpose agents (Claude Code), Open Code Review achieves significantly higher Precision and F1 with the same underlying model, while consuming only ~1/9 of the tokens and completing reviews faster. Note that its Recall is lower than general-purpose agents — a deliberate trade-off favoring precision over noise.
A real-world code review benchmark built from 50 popular open-source repositories, 200 real Pull Requests, and 10 programming languages — cross-validated by 80+ senior engineers (1,505 annotated ground-truth issues).
Explore the AACR-Bench dataset on Hugging Face.
If you've used general-purpose agents like Claude Code with Skills for code review, you've likely encountered these pain points:
- Incomplete coverage — On larger changesets, agents tend to "cut corners," selectively reviewing only some files and missing others.
- Position drift — Reported issues frequently don't match the actual code location, with line numbers or file references drifting off target.
- Unstable quality — Natural-language-driven Skills are hard to debug, and review quality fluctuates significantly with minor prompt variations.
The root cause: a purely language-driven architecture lacks hard constraints on the review process.
Open Code Review's core philosophy is to combine deterministic engineering with an agent, each handling what it does best.
Deterministic Engineering — Hard Constraints
For review steps that must not go wrong, engineering logic — not the language model — guarantees correctness:
- Precise file selection — Determines exactly which files need review and which should be filtered, ensuring no important change is missed.
- Smart file bundling — Groups related files into a single review unit (e.g., message_en.properties andmessage_zh.properties are bundled together). Each bundle runs as a sub-agent with isolated context — a divide-and-conquer strategy that stays stable on very large changesets and naturally supports concurrent review.
- Fine-grained rule matching — Matches review rules to each file's characteristics, keeping the model's attention sharply focused and eliminating information noise at the source. Compared to purely language-driven rule guidance, template-engine-based rule matching is more stable and predictable.
- External positioning and reflection modules — Independent comment-positioning and comment-reflection modules systematically improve both the location accuracy and content accuracy of AI feedback.
Agent — Dynamic Decision-Making
The agent's strengths are concentrated where they matter most — dynamic decisions and dynamic context retrieval:
- Scenario-tuned prompts — Prompt templates deeply optimized for code review, improving effectiveness while reducing token consumption.
- Scenario-tuned toolset — Distilled from deep analysis of tool-call traces in large-scale production data — including call frequency distributions, per-tool repetition rates, and the impact of new tools on the overall call chain — resulting in a purpose-built toolset that is more stable and predictable for code review than a generic agent toolkit.

A coding-agent skill that turns your agent into a security auditor. It orchestrates isolated agents through reconnaissance, coverage-led hunting, candidate validation, structured output, independent record verification, and target-neutral reporting.
This is the skill that seeded Cloudflare's vulnerability discovery harness, described in Build your own vulnerability harness. The harness grew into a multi-stage, fleet-wide system; this skill is the single-repo starting point it evolved from.
The skill runs a structured audit in six phases:
- Reconnaissance -- map architecture, trust boundaries, input surfaces, prior evidence, and deterministic coverage in architecture.md andcoverage-ledger.json .
- Coverage-led hunting -- assign isolated hunters from ledger units, record their checks, and use coverage critics to find gaps.
- Candidate validation -- give every unique candidate to a fresh verifier that tries to disprove it.
- Structured output -- write confirmed ,needs_validation , andrejected records tofindings.json and validate them againstreport-schema.json .
- Independent record verification -- fresh agents verify final source claims. Material replacements receive another independent verifier.
- Target-neutral reporting -- derive REPORT.md ,FINDINGS-DETAIL.md , andNEEDS-VALIDATION.md from the verified records and coverage ledger.
The parent runs validate-coverage-ledger.cjs after creating the ledger and after each later ledger update. It runs validate-findings.cjs in Phase 4 and again after every Phase 5 replacement.
The verdicts are distinct: confirmed has a complete source trace and bounded observed result, needs_validation has an exact unresolved fact and no severity, and rejected records a disproved candidate.
Multiple runs against the same repo are additive. The skill uses prior ledgers and findings to target gaps, revalidate changed source, and carry forward current-source evidence without treating stale or unresolved work as covered.
Install the skill with the Skills CLI:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
Use --global for a user-level installation:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit \
  --global
Run npx skills --help for agent-selection and non-interactive options.
Start your coding agent in (or pointed at) the codebase you want to audit, then ask it to do a security audit:
security audit this codebase
find security vulnerabilities in ./src
do a security review, output to ~/audits/my-project
The skill activates automatically when the request matches its trigger (security audit, find vulnerabilities, pen-test the code, etc.). A direct codebase audit or pen-test request uses full audit mode. Security questions and focused vulnerability work use guidance mode unless you request report artifacts. In full audit mode, an unspecified output directory defaults to ~/security-audit-skill/<repo-name>/run-<N>. The workflow writes inside the target repository only when you explicitly select a directory that version control ignores.
- A coding agent with a model that supports tool use and parallel sub-agents
- Node.js for the zero-dependency findings and coverage-ledger validators
- An OS-enforced sandbox for target-controlled builds, tests, processes, browsers, emulators, fuzzers, and fixtures. It must disable external networking, use a sanitized allowlisted environment, enforce resource limits, and allow writes only to assigned scratch paths. Without these controls, the workflow keeps the lead as needs_validation instead of executing target code.
- Only confirm established boundary failures. Keep a source-grounded blocked lead as needs_validation with its exact unresolved fact.
- Adversarial validation. The agent that checks a finding is never the agent that found it.
- Severity requires impact. Likelihood x impact, not deviation from a checklist.
- Defense-in-depth gaps are not vulnerabilities. If Layer A prevents the attack, the absence of Layer B is a hardening note.
- Multiple runs improve coverage. In our test runs, a single run found roughly half of the vulnerabilities that repeated runs found in total.

Readers can detect LLM words in the parts per trillion. However much work you put into scuffing up and humanizing it, an LLM paragraph will register to much of your audience not as writing but as output. So, first the bad news: you have to write for yourself.
But LLMs are still extraordinarily useful. It’s just you need to use them like a copyeditor rather than a ghostwriter. So, step one of my method: write your piece. Then, step two: feed it to a good model to find flaws.
But before we talk about how that works, there are two rules you need to understand. They’ll ward off LLM-creep that will knock you into the uncanny valley between expression and output and knock you out of your reader’s attention.
Rule Number One: You may not use a single word an LLM suggests to you.
Breaking this rule is what’s going to get you into trouble. Reason being: frontier models are supernaturally good at selecting pleasing turns of phrase. It’s sort of their whole thing. The problems with what models suggest are subtle. Think of it this way: frontier models are wedged in a mode where everything they write is a magazine headline. Introduction
Retry storms historically impact business operations and brand trust. While retry configuration tuning and retry budgets provide meaningful mitigation at the service level, they’re manually configured and lack visibility into cross-service amplification caused by deep dependency chains and fan-out patterns. As a result, it can be difficult to shield infrastructure against the domino effect triggered by a single service outage deeper in the stack.
A key reason is that retry behavior today isn’t context-aware. While we can control how many retries occur, we can’t precisely control when they occur. This stems from the challenge of reliably distinguishing between errors generated by a service and those merely propagated through it.
As a result, retries are applied uniformly rather than conditionally.
This approach works for transient or low-rate failures. However, during moderate or severe degradation, it becomes counterproductive. Aggressively retrying against an already struggling service increases load, accelerates failure, and amplifies retry traffic across upstream dependencies. The effort to mix the brain tissues of distant species is being reported today in the journal Nature by a team at Stanford University, led by neuroscientist Sergiu Pașca.
Pașca’s group previously showed that human brain “organoids”—small blobs of neural tissue—could survive, and even function, after being injected into the heads of baby rodents.
Now, Pașca has taken things a step further by genetically modifying mice so their brains don’t fully develop in the first place. These modified mice are missing most cells of both the cortex and the hippocampus, two key brain areas.
That creates much more room for the human cells to take hold, he says. “Human cells that are placed in these animals will divide, will grow, and within a few weeks to a few months they will take most of that space,” he says. Pașca says one surprising discovery is that the mice lacking brain tissue seemed fairly normal—they walked around and squeaked. But they did have memory problems. In a maze test, they couldn’t remember what parts they’d explored.
The mice with the added human cells, by contrast, performed better on the maze test. That means the human tissue is playing some role in the animals’ cognition.
Pașca believes what he is calling “xenocortical mice” could be useful in studying brain injuries. However, the report is also a dramatic demonstration of “the combined power of genetic engineering and stem-cell technology to reshape biology,” says Carsten Charlesworth, a scientist who works in a different Stanford lab and was not involved in the research.
Already, brain organoids are being tested in labs to see if they can be connected to computers to play video games. Other scientists have proposed using them like replacement parts to treat stroke victims.
“What’s most remarkable to me is the extent to which human neural tissue introduced after birth grew and connected with the mouse nervous system across a species barrier,” says Charlesworth. “As these technologies advance, they’ll increasingly force us to challenge our traditional assumptions.”
Last year, Pașca convened a group of ethics experts to study the implications of neural organoid technology, including the odds that an animal could develop human consciousness and the risk that “organoid therapy clinics” might offer scam treatments to desperate patients.
For now, he says, he’s not concerned that the rodents have any type of human cognitive capacities. That is because their brains are relatively tiny and the evolutionary distance between man and mouse is so great.
But that’s also why Pașca says this type of experiment should not be carried out on higher species: They could end up with large volumes of functioning human brain tissue, potentially blurring the cognitive boundaries between people and animals.
Pașca specifically cautioned against adding human brain organoids to a monkey engineered to lack a cortex.
“One of the things that I see as a very clear red line is doing this experiment in a primate,” he says. “I don’t think that is justified at this point in any way.”

前方来到远遥码头。也得亏是大风浪停航，我们才能看到驻留港内的渔船集群。
金海滩，又一个度假沙滩，照片里狭长的山是威海市区最长的半岛，尖端有个高尔夫度假村。这里距离最大的国际海水浴场已经不远了，海滩上几乎没人。
金海岸栈桥，是国际海水浴场东端一个五星级酒店的内部景点，对外开放。
横跨整个国际海水浴场，包车最后一站，火炬八街。这是条倾斜的道路，尽头直指大海。打卡游客非常多，几个拍照点甚至排起了长队。
整条街不长，符合网红景点的所有特征：易出片，地方小，有奶茶，不费脚。
第 5 天：军舰与海滩
很遗憾，刘公岛继续停航。这天的行程基本属于即兴发挥了。
大连号驱逐舰
先来到刘公岛码头。岛上去不了，定远号复原舰看不到，但码头有现代驱逐舰可看。
这是大连号驱逐舰，能力全面：130mm 口径主炮，30 多公里的对海射程，几乎可以达到海上肉眼视野极限。主炮后面的副炮，可对付反舰导弹，每分钟射速达 800 发，仰角最高可达 45 度。主炮前方两侧有反潜水雷火箭，新闻里的海军演习画面，经常拍这玩意发射。
这是舰长室，就在驾驶舱后面。隔壁还有个政委室。一组年长游客走到这，其中一人很激动指着政委室说，你看这是我的屋。
那香海
打车往荣成方向，到达那香海。
这一带沿岸风机林立，说明风力资源丰富且稳定。远处是鸡鸣岛，荣成的招牌度假离岛。
有的风机甚至立在人行道上，第一次这么近距离观察风力发电机。
今天天气仍然很糟糕，风浪巨大。海滩反复广播，说景点已经关闭，岸上游客注意安全，切勿下海。
这个画面就很像《马达加斯加的企鹅》，几小只费老大劲来到南极，呆立在风雪中，十几秒后憋出一句：Well, this sucks.
我们也是快被这风吹傻了。陪女儿在沙滩堆了 1 小时沙堡，火速撤离，退到滨海公路对面的那香海小镇里。
许多城市都有这样的旅游城：开发商拿下某景点附近一大片地，建成集旅游和本地生活于一体的街区。温泉、游乐场、商业中心、度假酒店、本地居民楼混合在一起。
小镇路边有这种电动边三轮可以租，全家尝个鲜。第一次开起来感觉非常奇怪，反正我很难对它的重心位置和左右拐弯半径产生正确的认识。
只要有本地小区，对女儿来说就够了。这个海盗船主题的淘气堡她玩了 1 个半小时。
第 6 天：环翠楼
返程日，下午的飞机，只能酒店周边逛逛。
刚好环翠楼公园就在附近，一个本地免费公园。登楼可欣赏威海市区全景，我们时间不够没进去。
公园里载歌载舞，细听发现广场舞跳的是新疆音乐。真有几个戴新疆帽的大叔和阿姨，转着圈跳起民族舞蹈。也有些汉族长相的市民加入进去，看起来笨手笨脚的，但也同样欢乐，很好区分。新疆大叔教他们跳，演示怎么拍手、抬腿。
沿着台阶往上爬一小段，半道又听到一组专业的老年合唱团练习革命歌曲。那声部分工、发声方式，一听就是练家子。
从台阶上下来，环翠楼脚下的广场中央。邓世昌铜像拄着长剑，目光穿过笔直的现代马路，凝视刘公岛和曾经的北洋水师军港。他脚下的石墩其实是船头造型，这个角度看不明显，想必是他的致远号。
回想这几日的海滩、海鲜、渔港、军舰，还有威海市内常见的军事管理区，在全城的民用设施与建筑当中，不经意转个弯就会遇到。很少有一座城，能让你感受生活美好的同时，也能想起背后的那份守护力量。
地理历史
威海是胶东半岛最东端的地级市，三面环海，是渤海湾的门户。这样的地理位置给威海赋予了特殊的命运。
大多数城市都是由聚落人口增长逐渐扩张形成的，威海一诞生就是一座军事要塞。明朝为应对倭寇袭扰，沿海岸线设立了大量海防要塞，称作“卫”。威海卫是现代威海的前身，取威震海疆之意。甲午战争北洋水师的覆灭，给威海蒙上了一层悲壮色彩。关于甲午战争和近现代海战的演变，有兴趣可以看我这篇，游记里就不展开讲了。
甲午战争后，列强纷纷在清朝沿海占据租界口岸。那时南边有德租界青岛，北边有俄租界大连。英国人很着急，从清政府强租了威海，以抗衡俄国在远东的影响力。德国与沙俄就地发展工业基础，英国人则把威海打造成海军疗养胜地。
威海今天的部分民宅、商场，仍能看到英国文艺复兴建筑的影子。
经过民国政府和民间运动的长期努力，1930 年，英国和平归还威海卫。威海成了中国首个和平回归的租界。
摆脱沉重历史，现代威海展现出它精彩的一面，这远不止旅游业。它的优势产业包括医药与医疗器械、复合材料、特种船舶、钓具。还有非常重要的：渔业，荣成与乳山是威海远洋捕捞与沿岸大规模养殖的核心地带。
威海还有一处鲜为人知的硬核王牌，石岛湾核电站，世界首个投入使用的第四代核电机组。每颗核燃料都被包裹在直径 0.5mm 的石墨颗粒中，这种稀疏程度，即使所有外部降温措施都失效，堆芯自由反应也无法达到 1600 度融化石墨外壳，从物理上确保了安全。此前切尔诺贝利和福岛核事故，都有堆芯温度过高、一路烧穿外层容器的过程。第四代核电另一项突破是高温气冷堆，采用氦气代替水来作为冷却剂。氦气能大幅提高堆芯出口温度，发电效率提升 30% 以上。
除了英国的影响，你在威海能感受到一股更强的文化力量：韩国文化的影响。
国际海水浴场也打出这样的标牌。虽然我很想较个真，从地图上看，你这海的对岸其实是大连啊。
为啥呢？威海是离韩国直线距离最近的城市。在中韩正式建交前，民间早有往来。当时威海到仁川的客运航线，使威海成为对韩贸易的前哨站。双方大量人员往来流动，也支撑起了威海本地的对韩服务业。
我们此行就在酒店电梯遇到 3 位韩国游客。我大学时学了点韩语皮毛，听出来她们在夸我女儿漂亮。
当地生活
气候
威海夏秋季很凉爽，虽然沿海，空气并不算潮湿。9 月初的威海，气温 22-27 度范围上下，非常舒适。此时的海水刚触碰会感觉凉，正午和午后会暖和起来，下海游泳没有问题。当然，这是指没有台风的时候。
威海冬季非常冷，比东北纯粹的干冷更让人难受。威海市区北边是渤海，毫无遮拦，迎面受着西伯利亚来的强劲冷空气。本地司机师傅说，冬天里你不全副武装，根本受不了。
威海绝大多数房屋都是这种红色尖顶。问了当地人才知道，这是方便除雪。威海冬季的积雪最深可以到小腿肚子，北方人可能习以为常了，南方是从没见过。想象一下，一场雪过后，马路和人行道都除雪除干净了，旁边草坪的雪还堆到小腿肚这么高。
酒店
来威海玩，住宿选择主要在 4 个区域，从左上到右下依次是：
- 国际海水浴场沿岸：多日连续玩海滩的话优先住这，周边餐饮商业非常成熟，自成一片。
- 威海市区：老城和本地生活体验最丰富，兼顾威海市区各处景点。
- 威海站片区：离火车站和机场都最近，附近有韩乐坊和几个海滨公园，商业也很成熟。
- 荣成方向：荣成方向景点最近的也 40 多分钟车程，只有主玩荣成方向才会考虑住这边。
交通
威海没有地铁或轻轨，而且是丘陵地形，上下陡坡很多，几乎见不到自行车和共享单车。这里可选的交通方案不多，打车、包车、租车自驾、租电瓶车。
打车是最首选的方案，因为整个市区游玩设施比较集中，距离都没多远。而且威海的网约车价格真的低，市中心出发，20 以内几乎可以到老城区任何地方，折算下来每公里单价大约只有杭州的一半。
美食
威海 9 月 1 日开渔，近海小船有个两三天就能有收获返港了，9 月上旬来能吃上第一波新鲜海鲜。
既然是美食度假之旅，吃饭肯定是重头戏。此行探出 2 家品质非常高的餐馆，每家都各去吃了 2 次，这比什么都能说明问题了吧？
幸福门附近，环海路旁有一家映像威海·威海宴，本地家宴类型的餐馆，包厢多，大厅小。
渔港路沿线，有家龙城饭店。那一带附近没有景点，店面一副本地老牌餐馆模样，店里本地食客比游客多。
海肠的口感很脆，我在另一家店还吃到过炒韭菜的做法，也非常棒。这种动物活着的时候就像一条大肉虫，也确实形似肠子，图就不放了，感兴趣可以自己搜。

Apple 于 9 月 15 日凌晨正式发布 iOS 27、iPadOS 27、macOS 27 Golden Gate 和 watchOS 27 等系统的正式版。其中，macOS 27 Golden Gate 也同样改进了界面设计和性能表现，此外 macOS 27 Golden Gate 还带来了一些细节方面的改进。
少数派为你整理了新版系统中值得关注的新功能和新特性。不管你是升级后，想了解新系统有哪些新功能，或者还在观望是否需要升级，这篇文章都能帮助到你。当然，升级新版系统之前，别忘了通过时间机器对你当前的 Mac 中的数据进行备份。
抛弃 x86 架构
在正式聊新特性之前，我想先说一下硬件支持。
其实 Apple 去年在 WWDC25 上就已经提前说明，macOS 26 会是最后一个支持 Intel Mac 的大版本。到了今年的 macOS 27 Golden Gate，这个过渡终于正式完成：新系统已经完全放弃 Intel 处理器架构，硬件支持范围也收缩到了 Apple Silicon Mac。
也就是说，从 macOS 27 开始，能够升级到新系统的 Mac 都必须搭载 Apple 自研芯片。具体支持机型包括：
- 配备 Apple 芯片的 MacBook Air（2020 年及后续机型）
- 配备 Apple 芯片的 MacBook Pro（2020 年及后续机型）
- 配备 Apple 芯片的 iMac（2021 年及后续机型）
- 配备 Apple 芯片的 Mac mini（2020 年及后续机型）
- 配备 Apple 芯片的 Mac Studio（2022 年及后续机型）
- 配备 Apple 芯片的 Mac Pro（2023 年及后续机型）
- MacBook Neo（2026年）
与此对应，Rosetta 2 的完整支持也进入了倒计时。按照 Apple 去年在 WWDC25 公布的时间表，macOS 27 将是最后一个完整支持 Rosetta 2 全部功能的大版本；到了 macOS 28，Rosetta 2 只会保留用于兼容 Intel 架构游戏的功能。所以，对于那些到现在还没有提供 Apple Silicon 原生版本的厂商来说，macOS 27 就是最后的缓冲期。
如果你的 Mac 上还有通过 Rosetta 2 运行的软件，那么在 macOS 27 上你可以通过点击相关通知或「设置-通用-关于本机」，找到这些还没有 Apple Silicon 的软件。
在实际上手后，macOS 27 确实如发布会上所言，对底层做了相当多的优化。不管是动画，还是软件的响应速度都比 macOS 26 灵敏不少，像极了当年的 Snow Leopard。
重新打磨设计系统
Apple 在 macOS 26 中引入了新的视觉语言 Liquid Glass。它带来的透明玻璃质感确实很抓眼，但在 macOS 上也暴露出清晰度、对比度和可读性的问题，有点像当年 Mac OS X 10.10 Yosemite 那样。
到了 macOS 27，Apple 也和其他系统一样，重新梳理了 Liquid Glass 在 macOS 上的呈现方式，让整体观感更统一，也解决了不少之前暴露出来的问题。具体而言：
Apple 把 Liquid Glass 的控制权交给了用户，在「设置」-「外观」里多了一个专门调节玻璃透明效果的滑块，从左边透明度更高的玻璃模式到右边更不透明的毛玻璃效果，Apple 相信总有一种符合用户喜好的效果。
类似的调整也能在窗口和界面元素中看到。macOS 27 的窗口圆角弧度收敛了一些，没有 macOS 26 那么夸张。侧边栏也从 macOS 26 采用的是浮动式侧边栏，变为了 macOS Sequoia 和之前版本那样的重新紧贴窗口边缘的设计。虽然我个人还是比较喜欢 macOS 26 中的浮动式侧边栏的设计，但重新紧贴窗口边缘也确实让界面干净了不少。

defaults write -g NSSplitViewItemSidebarDefaultsToFloatingAppearance -bool Yes
# 还原 macOS 侧边栏的默认值，即显示。输入完以后回车，并重启 Mac 电脑

另一个界面上的变化就是侧边栏图标着色。macOS 26 中由于缺少侧边栏图标着色，我们很难第一眼就分辨是否激活了某个窗口；而 macOS 27 中侧边栏图标着色也回来了，一个窗口没有用激活一眼就能看出来。
macOS 26 的菜单栏还有一个问题：过度使用图标，且效果并不理想。一方面，这些图标并没有覆盖所有菜单项，放在一起看显得不太统一；另一方面，部分图标本身的含义也不够清晰，我们也未必能通过图标更快地找到想要的功能。
macOS 27 对菜单栏中的图标重新做了调整，移除了大量有歧义、或者表述不清的图标，只保留了少数和系统既有功能强相关的图标，整体观感清晰很多。
