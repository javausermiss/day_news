Univer is an Office SDK for building Office applications inside your own product. It provides Office editing, calculation, collaboration, and file processing for people and existing agents, using your data and permissions. The product family covers spreadsheets, documents, presentations, relational tables, canvases, and PDFs.
Univer Office SDK has three parts:
- Web SDK is the foundation: content models, editing, rendering, formula calculation, and Facade APIs (application-facing APIs). Compose its plugins into an embedded editor or your own Office application, and reuse the content models, commands, and calculation for Headless processing without an interactive editor.
- Server SDK adds backend services for real-time collaboration, edit history, and Office file import and export.
- AI SDK connects Office capabilities to existing agents and workflows, with content tools, execution, and review integrations.
This repository provides the Web SDK's core architecture and engine implementations under Apache-2.0: content models and snapshot formats, plugin and dependency management, the command system, formula and rendering engines, Facade APIs, UI foundation, and Sheets and Docs editing capabilities. Commercial Web SDK plugins, Server SDK, and commercial AI SDK extensions are distributed and licensed separately.
Agents can use the same open-source APIs; your application supplies the model and tool orchestration. The quotation example demonstrates editing, calculation, and saving without an AI SDK dependency.
Features are composed through plugins and presets; the quick start uses only the Sheets Core preset. Images use the corresponding drawing plugins. See the feature comparison for detailed open-source and commercial coverage.

AG-UI is an open, lightweight, event-based protocol that standardizes how AI agents connect to user-facing applications.
Agents don't fit the request/response model. They stream tokens, call tools mid-response, update shared state, pause for a human, and spawn subagents, and every framework does it differently. AG-UI replaces that custom wiring with one bi-directional event stream: the agent emits typed events, and any client can render them, no matter which framework built the agent. The same agent can power a web app, a mobile app, a terminal, or Slack.
Important
AG-UI 1.0 is here. The protocol now has a stable, frozen specification backed by a JSON Schema, and the TypeScript, Python, and .NET SDKs are generated from it. 1.0 is backwards compatible in both directions: 0.x agents work with 1.0 clients and vice versa. What changed → · Migration guide →
Start a new app. The CLI scaffolds a frontend (CopilotKit on Next.js, or a terminal client) wired to the agent framework you pick:
npx create-ag-ui-app@latest
Then follow the printed next steps. The generated templates call OpenAI, so set your key before npm run dev:
export OPENAI_API_KEY="sk-..."
Or speak the protocol directly: a 30-line agent server and client
An AG-UI agent is any HTTP endpoint that accepts a RunAgentInput and streams events back. No API keys needed for this one.
1. The agent (Python). Requires Python 3.9+.
pip install ag-ui-protocol fastapi uvicorn# server.py
import uuid
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from ag_ui.core import (
    PROTOCOL_VERSION,
    RunAgentInput,
    RunStartedEvent,
    RunFinishedEvent,
    TextMessageStartEvent,
    TextMessageContentEvent,
    TextMessageEndEvent,
)
from ag_ui.encoder import EventEncoder
app = FastAPI()
@app.post("/")
async def run_agent(input_data: RunAgentInput, request: Request):
    encoder = EventEncoder(accept=request.headers.get("accept"))
    async def events():
        yield encoder.encode(RunStartedEvent(
            thread_id=input_data.thread_id,
            run_id=input_data.run_id,
            protocol_version=PROTOCOL_VERSION,
        ))
        message_id = str(uuid.uuid4())
        yield encoder.encode(TextMessageStartEvent(message_id=message_id, role="assistant"))
        for chunk in ["Hello ", "from ", "AG-UI!"]:
            yield encoder.encode(TextMessageContentEvent(message_id=message_id, delta=chunk))
        yield encoder.encode(TextMessageEndEvent(message_id=message_id))
        yield encoder.encode(RunFinishedEvent(thread_id=input_data.thread_id, run_id=input_data.run_id))
    return StreamingResponse(events(), media_type=encoder.get_content_type())uvicorn server:app --port 8000

AG-UI is one of three open, complementary agentic protocols. MCP gives agents tools and context, A2A lets agents work with other agents, and AG-UI brings agents to users. A single agent often uses all three, and AG-UI can front agents that speak MCP or A2A. Read more →

Your app starts a run by sending the agent a single RunAgentInput: the conversation, the tools the frontend offers, shared state, and context. The agent answers with a stream of typed events from eight families: run lifecycle, text messages, tool calls, state, reasoning, activity, subagents, and custom events (full list). 选择下一个发行版
在不太愉快而且最终失败的配置之后，我短暂回到了 Windows，打算寻找下一个发行版。我稍微梳理了一下各个发行版的专长和短板之后，我决定试试 Bazzite。
Bazzite 是一款将流畅运行 Windows 游戏作为目标的 Linux 发行版；同时，它具有「默认沙盒」的特性，通过内置改版 RPM 安装的二进制默认会进入沙盒环境中。但更重要的是，它的安装程序默认会携带显卡驱动安装包。虽然我这么多年使用 Linux 还暂时没遇到显卡驱动问题（也有可能我没有太多「开源软件洁癖」，直接点「允许闭源驱动」一把梭），但至少它能内置也能省下不少事。
（顺便提一嘴，虽然很不想这么说，但是感谢 AI 大浪潮逼着老黄为 Nvidia 显卡推出了开源驱动，这在某种程度上也省了不少事。）
对独显、游戏等场景做专门优化，对我而言也有一点额外的好处：我希望在 Linux 上使用 DaVinci Resolve 剪辑视频，对于独显的优化那自然是多多益善。社区还有一个专门的 davincibox 项目，让 DaVinci Resolve 在 Bazzite 上能够十分流畅地运行。（也有一些尚可接受的妥协……之后我会提到。）
说干就干，直接下载 ISO，拷贝到已经安装好 MultiOS-USB 的优盘上，然后直接从优盘启动即可。说句实话，多数 Linux 发行版的安装已经不像多年以前「蛋糕要自己烤」这样麻烦，Live CD 中已经内置了一个十分优雅而且简洁的安装向导。做好一些初始化设置之后，离线安装（离线是为了避免它又在没有额外设置的前提下访问包管理器镜像）就行。
即使是离线安装 Bazzite，安装流程中也会卡在「软件安装」这个步骤很长时间。如果你也遇到了一样的情况，请坐和放宽，耐心等待安装完成。
进系统之后的第一件事就是配置代理，以及 1Password 等基础软件（没这玩意我连登帐户我都登不上去）。这些安装好之后，就可以让 LLM 来帮我代劳很多东西了。
面向 LLM 的 Linux 配置方案
作为一个「text in, text out」为底层逻辑的操作系统，Linux 天生很适合让 LLM 来做很多设置工作。无论是什么指令，只要 LLM 可以读写终端输入，它就能帮你做大多数配置。也就是说，只要我把代理设置做好了（嘘……），我就可以请 ChatGPT 这类 LLM 来帮我解决绝大部分问题——只需要时常输入一下 sudo 密码即可。
说来，我在很久之前就提到过，以后的电脑，有可能是一种「面向 LLM」的。即，你只需要在电脑上输入要干嘛，然后 LLM 获得授权之后直接帮你改就万事大吉。这对于 Linux 这种操作系统而言可能是一种重大利好，毕竟，多数人对 Linux 敬而远之的重要原因，就是 TUI 实在是太晦涩了。
扯远了。总之，在整个设置过程中，LLM 的确帮了不少的忙。例如，帮我将浏览器和 1Password 安装到沙盒之外——多数 Linux 中的沙盒实现都是完全禁止应用程序之间互相沟通的，这让像 1Password app 和浏览器内的密码填充扩展之间通信成了问题。解决方案只有一种，那就是让它们脱离沙盒环境、独立安装在系统环境内。
由于 Bazzite 默认是一个沙盒式的操作系统，所以你必须依靠一些特殊手段，将浏览器和 1Password app 安装到沙盒以外，它们才能正常工作。好在这对于 LLM 来说是轻车熟路、信手拈来。
另外，内置的包管理器前端 Bazzar 似乎没办法搜索到 DaVinci Resolve 和它的兼容沙盒 davincibox。没关系，这时候 LLM 会出手：给它一个指令，它就会自动帮你从零配置好 davincibox，让 DaVinci Resolve 顺利地在 Bazzite 上启动。
当然，非要说让 LLM 代劳这些有什么缺点，可能「没办法亲自动手」这一点算一个。虽然听上去稍微有点「凡尔赛」或是有悖于「吃水不忘挖井人」的想法，但自己没有亲自动手也意味着一旦这个配置出现问题，大概率还是得请 LLM 来帮忙修，但毕竟现在的大模型还是得依靠云端大公司才能调用，要是 LLM 调用掉了链子那还是得出大问题。不过，鉴于我也并非完全没有 Linux 运维经验，加上我的目的是把这套 setup 设置到我可以正常使用的状态、而非出于兴趣去折腾，再加上 Bazzite 也算是一个对 average user 相对友好的操作系统，我目前倒也不会太担心这个事情。
一些小问题
主动选择 niche 的解决方案，自然得面对一些 niche 的问题。首先遇到的问题是，Linux 上的 DaVinci Resolve（免费版）对 H.264 和 H.265 的支持较弱，没办法在软件里直接预览。
ChatGPT 给我推荐的方案是，将素材转换为 DNxHR HQX 格式。格式转换不是问题，问题是，DNxHR HQX 的体积实在是太大了。我现有的新工程的素材在 H.265 下的体积大概是 20 GB 左右，但在 DNxHR HQX 格式下，占用空间直接干到了 500 GB。好在，我在十年前升级内存的时候同时升级了固态硬盘，所以我的电脑有 2 TB 大容量固态可供使用，至少剪辑一期节目问题不大。唯一的问题是，转换后的文件似乎没办法和原素材形成代理，不过我觉得这应该是换个封装就能解决的问题，之后我会再研究一下。
另外一个很重要的问题是，国服《最终幻想 XIV》没法启动：中国区代理方盛趣游戏在它的启动器里大量使用 IE 和 32 位 COM 等组件，这导致它在 Linux 上无法正常使用。社区多数玩家会推荐在 Linux 上使用第三方的启动器，但毕竟因为各种各样的原因，导致它经常和「外挂」有关。
我把国服 FF14 启动器安装包下载回来，尝试让 ChatGPT 试试能不能解决这个问题。它花了大概 40 分钟，最终真的成功把它启动。当我在 Linux 上看到国服启动器的登录对话框，再看到 ChatGPT 对这个问题的诊断和修复，一时之间有点语塞：看着 Windows 给开发者「擦屁股」致使催生出的这种用二十年前的组件组装出来的奇怪「产物」，很难说这到底是好事还是坏事。
结语
在写这篇流水帐的过程中，我看到一篇报道称 Steam 中 Linux 用户占比很大程度上取决于简体中文用户的数量：当某月的简中用户提升，那么 Linux 占比就会下降；反之亦然。
虽然直接下「简中用户不爱用 Linux」的结论非常武断——我这里有个很直接的反例，例如不知道为什么 Linux 下的 Steam 程序不会跟随 Steam 或者系统设置的语言，只会 fallback 到英语；我猜测这可能是致使统计数据中 Linux 用户普遍不使用简体中文的缘故——但这个判断但其中确实有一定道理。
最重要的一点是，中国和美国的游戏玩家的画像并不一致：中国平均水平玩家更多使用电脑游玩游戏，致使更多技术水平一般的用户更愿意使用更友好的 Windows 而非 Linux；美国或其他国家的一般水平游戏玩家更倾向于购买游戏主机：更便宜，更开箱即用，大部分情况下也无需纠结 Windows 还是 Linux；真正「硬核」玩家才会使用 PC 游玩游戏，而对他们而言 Linux 运维并不成问题，在 Linux 上玩游戏就成了很自然的选择。
倒也不是在说「中国玩家很 low」或是「外国玩家真有钱」这种论断，只是在说，客观而言的现阶段，无论在什么地区，Linux 依然还停留在「小众」的层面。好在，事情已经开始在发生变化。目前多数 Linux 发行版的安装和设置，已经要比十年前纯 TUI 那样要对普通用户友好很多了。至少，一个普通的用户只需要了解计算机基本原理、并稍微学习如何修改引导启动设置，就能独自完成 Linux 的安装。
更大的问题还是在于一些阻碍。除了之前提到过的设置代理问题，真正的「阻碍」其实还是在人的内心。当外部的限制开始逐渐渗透、内化到每个人的内心，另一种真正的「可能性」在现今尤为珍贵。Linux 也许就是这样的「另一种可能性」。

Dalibre：让 AI Agent 帮你管理电子书

Dalibre 最直接的优势是轻量化。传统电子书管理软件 Calibre 功能丰富，但安装包和运行环境相对庞大。Dalibre 则将重点放在日常书库管理上，macOS 版本安装包仅约 10 MB，安装后的应用体积约 32 MB。更重要的是，它兼容 Calibre 的书库结构，在首次打开 Dalibre 时，应用会自动检测电脑已有的 Calibre 书库，无需重新导入或迁移数据。我们可以在两款软件之间切换使用，在 Dalibre 中修改的书名、作者、封面和标签等元数据，也会同步保存到原有书库中。

Apple 在 Mac 电脑的发展历程中经历过数次架构转换。其中最广为人知的，当属 2005 年从 PowerPC 转向 Intel x86 架构，以及从 2020 年启动、由 Intel x86 转向 ARM64 架构的 Apple Silicon 迁移。
有趣的是，在这两次关键转折中，承担核心过渡任务的技术均被命名为 Rosetta，名字灵感正来源于帮助考古学家破解古埃及象形文字的「罗塞塔石碑」（Rosetta Stone）。我觉得 Apple 也想借此隐喻，在架构转换的过程里，代码转译工具扮演着非常重要的角色。
正如初代 Rosetta 在使命达成后功成身退，自 2020 年拉开序幕的 Mac 向 Apple 芯片迁移如今也已步入尾声。
在 2025 年 6 月 9 日的 WWDC25 上，Apple 宣布 macOS Tahoe 将是最后一个支持 Intel Mac 的系统版本；而在随后的 WWDC26 上，Apple 也宣布 macOS Golden Gate 将是最后一代内置完整 Rosetta 2 的 macOS。
换言之，预计于 2027 年登场的 macOS 28 中，Rosetta 2 或许仅用于维持极少数依赖 Intel 架构的停更老游戏运行。
Rosetta 2 退役了，但是应用准备好了么？
截至本文发稿，距离 Rosetta 2 全面退役已不足一年。然而，我们日常频繁使用的那些 Mac 应用，是否都已经原生适配了 Apple Silicon？
带着这个疑问，我用到了 macOS 软件架构检测工具 Silicon。这款在初代 M1 芯片 Mac 面世时推出的实用工具，能快速扫描本地所有已安装应用的支持架构。从扫描结果来看，相较于 6 年前满屏都是 x86-64 架构的景象，如今绝大多数 Mac 应用要么提供通用二进制（Universal），要么已彻底转向 Apple Silicon 原生（标记为 Apple），纯 x86-64 架构的旧应用已所剩无几。
即便这类应用已经在我的电脑里屈指可数，但真到了 macOS 27 它们就会完全停摆。失去 Rosetta 2 之后，我们又该如何留住这些老工具呢？
三个方法助力后 Rosetta 2 时代
经过一番探索与实践，我摸索出了 3 种解决思路，顺利替换掉了手头仅剩的几个 x86-64 老应用。
寻找开源、第三方替代
其实我们使用软件，本质上消费的是其背后的核心服务。如今不少服务商都开放了 API 接口，允许第三方开发者围绕平台生态展开二次开发。
以我日常频繁使用的 Sonos 为例：此前官方将开发资源完全倾斜在移动端，长达六年时间从未推出适配 Apple Silicon 架构的 Mac 客户端1，只能使用相对简陋的网页版。好在 Sonos 的开放 API 生态足够健全，我很快便找到了一款基于官方 API 构建的开源第三方 Mac 客户端：Choragus。
在交互逻辑上，Choragus 与官方客户端十分相似：二者都采用了经典的三段式界面，不仅能快速接入本地的 Sonos 设备，也可以自由添加流媒体服务。当然，由于各家 API 开放程度不一，不同音乐服务的支持程度参差不齐。好在 Choragus 会以蓝点标出完美兼容的服务，比如：Sonos Radio、Suno.ai、Spotify；黄点则代表未经验证，比如「网易云音乐」，虽然能正常同步并播放个人歌单，但搜索功能完全不用。
当然，相较于官方客户端，Choragus 能调用系统级 MusicKit 框架，可以无缝接入本地 Apple Music，支持搜索、查看推荐、浏览资料库等等操作。如果你平日重度依赖 Apple Music，那么借助 Choragus 来控制全屋 Sonos 音响，那么体验会更好些。
不过，第三方工具终究有其局限。Choragus 的定位仅仅是「播放控制器」，不支持设备管理等功能。所以像是，是给音响配网、添加新设备或升级固件这类底层操作，依然得用手机上的官方 App 处理。

在办公套件方面，我一直主力使用微软的 Microsoft 365 套件；但因团队协作需要，日常难免要高频查阅同事分享的 WPS 在线文档。为兼顾轻量与便捷，我并未安装庞大的完整版 WPS，而是单独下载了金山文档客户端。

在此我推荐 Setapp 订阅中包含的 Web 封装工具 Unite Pro。启动 Unite Pro 点击新建应用，在网址栏中填入金山文档地址，点击创建即可。
随后在属性设置面板中做简单微调：将应用名称设为「金山文档」，图标可按需保留默认；将显示模式设为 Normal；最关键的一步是开启「启用标签页」开关，确保支持多文档并行查看。其余高级项保持默认，点击底部的「Create 应用程序」，最后等待打包完成即可。
自己打包的 PWA 版本「金山文档」视觉和交互体验和官方客户端几乎无异。新建打开文档也都能以独立标签页的方式打开，顶多就是多标签控件在设计细节上稍逊于原版客户端。
不过，网页打包方案也有自己的问题。Unite Pro 本身属于商业付费软件，存在一定的获取门槛；其次，封装后的 Web 应用缺少官方客户端里的企业高级功能。但倘若像我一样只需要撰写和协作，这种轻量级替代方案已经能胜任了。
使用腾讯应用宝 Mac 版
不过，并非所有工具都有 API 或网页版。像「万兴脑图」，其 Mac 端不仅常年止步于 x86-64 架构2，版本迭代也严重滞后，时不时就会遇到跨平台打开文件报错的问题。面对这种官方半弃坑的应用，最省心的办法反而是在 Mac 上直接运行它的 Windows 版本。
与传统动辄需要部署虚拟机（如 Parallels Desktop）的繁琐方案不同，如今我们可以借助更加轻量的转译工具直接运行 Windows 应用，例如腾讯应用宝 Mac 版。腾讯应用宝 Mac 版底层使用的是开源的兼容层项目 Wine，所以其实你可以考虑直接通过 Wine 或者 Wine 的衍生项目来在 macOS 上运行 Windows 软件。
启动腾讯应用宝 Mac 版，在侧边栏切换至「应用」页并点击右上角的「本地安装」；随后选择提前准备好万兴脑图 Windows 版安装程序，等待安装完成即可。
从实际运行体验来看，虽然界面和 Windows 版一模一样，但不管是添加节点、还是调整分支都很流畅。加上没有传统虚拟机那套完整的虚拟化组件，所以整体的 CPU 和内存开销都低的。
不过，这套方案多少带点「套娃」：腾讯应用宝底层依赖的是 Wine，而目前绝大多数成熟的 Wine 构建版本，自身依然要依赖 Rosetta 2 才能在 Mac 上运行。虽然官方开发版已经开始逐步优化，并尝试探索针对 Apple Silicon 的原生 ARM64 Wine 引擎，但整体仍处于实验阶段。
此外，转译机制也带来了一些体验上的小瑕疵，比如部分 Windows 软件的中文字体渲染不够细腻甚至偶有发虚，窗口拉伸缩放也不够自由等。

就在撰写本文期间，那些过去六年多迟迟未做原生适配的厂商，竟在 2026 年 9 月前后扎堆推出了通用二进制更新。不仅前文提及的 Sonos 与万兴脑图终于适配了，我常年使用的阿里无影云桌面也发布了 Apple Silicon 版本。再加上上述三种解决方案的处理，至此我 Mac 上已经没有 x86-64 Mac 应用了。

If an app asks for Full Disk Access or System & App Protection Override on your Mac
Starting in macOS 27.3, when some apps ask for Full Disk Access or System & App Protection Override, you have the option to choose only specific protected folders or apps for the app to access. This puts you in control of what data is accessible to the app.
Why apps ask for these permissions
Apps that might ask for Full Disk Access or System & App Protection Override include backup apps, disk cleaners, file indexers, security apps, and others. While some of these apps operate best when granted broader access, others may ask for the same level of access even when they don't need it. It's important to understand the risks of granting broad access to any app, so you can make informed decisions about your own data and privacy.
When you give an app Full Disk Access instead of choosing only specific protected folders for it to access, it can bypass system protections and access all of the files on your Mac, including your messages, emails, photos and videos, data from other user accounts, and more. It can read, change, delete, and export this data without asking.
When you give an app System & App Protection Override, you can choose specific apps for it to control. If you allow it to bypass system protections instead, it can fully control your Mac and apps, which allows it to access all of your data. It can also see every window and app, including ones in the background, and capture every keystroke.
What you can do
An app might ask you to give it access to all of the files on your Mac, or to let it control your Mac. When you turn on access for the app in Privacy & Security settings, depending on the app, your Mac prompts you to:
- Allow or not allow the app to have access. This option appears for some apps, such as backup apps that ask for Full Disk Access, and screen readers and voice control tools that ask for Accessibility.
- Choose specific protected folders or apps for the app to access instead. This option appears for other apps that ask for Full Disk Access or System & App Protection Override. It allows the app to access only what you choose, while system protections stay in place for the rest of your data.
If your Mac prompts you to choose specific protected folders or apps
To keep more of your data protected, choose specific protected folders or apps for the app to access instead of bypassing system protections.
Choose specific protected folders or apps
When your Mac prompts you, click Choose Folder or Choose Apps, then:
- Check the app's setup instructions for information about which protected folders or apps it needs.
- Choose only the protected folders or apps that it needs.
- For System & App Protection Override, choose whether the app needs to ask for your permission before it controls each app. Use the menu next to each app to choose Ask First or At Any Time.
- If you're not sure which protected folders or apps to choose, contact the app developer. To stay protected, wait until you're sure which folders or apps that the app needs before giving access.
You can change which protected folders or apps that the app can access at any time.
If you're certain that an app needs Full Disk Access or System & App Protection Override
Bypassing system protections might expose your personal information to an app that doesn't behave as you expect. An app with Full Disk Access can read, change, delete, and export all of the files on your Mac, and an app with System & App Protection Override can fully control your Mac and apps.
If you're certain that the app is from a trustworthy source and needs this level of access, you can give it Full Disk Access or System & App Protection Override permissions by clicking Bypass System Protections:
- Confirm each action that the app will be able to take: 
  - Full Disk Access: Read, Change, Delete, and Export All Your Data; View Hidden and Recently Deleted Photos; and Browse As You on Websites.
  - System & App Protection Override: Read, Change, Delete, and Export All Your Data; View Hidden and Recently Deleted Photos; Browse As You on Websites; Control Your Mac, Apps, and Settings; and Monitor Everything You Do.
- If you're absolutely sure that you want to give the app Full Disk Access or System & App Protection Override, click Turn On Full Disk Access or Allow System & App Protection Override, then enter your password and click Modify Settings.
Change or remove an app's access
You can review app permissions in Privacy & Security settings, and change or remove them at any time.
- From the Apple menu, choose System Settings.
- Click Privacy & Security in the sidebar, then click Files & Folders, Full Disk Access, or System & App Protection Override.
- Change an app's access: 
  - Remove an app's access: Select the app, then click the Remove button (−). If asked, enter your password, then click Modify Settings.
  - Change which protected folders or apps an app can access: In Files & Folders or System & App Protection Override, click the Info button (i) next to the app, make your changes, then click Done.
  - Limit an app with Full Disk Access or System & App Protection Override to specific protected folders or apps: Remove the app's access, then click the Add button (+) to add the app again. If your Mac prompts you, choose specific folders or apps.
If you remove an app's access, the app might not work as expected.

I usually have a few going at once: Claude Code working in one repo, Codex reviewing a branch in another, and something long-running in the background. I often have them review each other's work too. herdr #
herdr is a terminal multiplexer built for coding agents. You get the usual workspaces, tabs, and panes, and it also knows which agent is running in each pane and what it's doing. The sidebar shows whether each agent is working, waiting on me, or done, so I can tell at a glance which one needs attention.

Ovis #
Ovis is a browser and phone client for herdr. It shows each agent's transcript as a chat, with the live terminal a tap away. When an agent asks for approval or has a question, Ovis turns it into a card I can answer and sends me a push notification. The credential problem #
Agents on a VM still need to act as me. I use them to monitor CI with gh, call APIs with tokens from 1Password, and SSH into other hosts. There are two usual ways to make that work, and I don't love either of them.
The first is copying credentials onto the VM. A token in ~/.config/gh/hosts.yml can be read by every process on that machine, including the agent and anything it runs, for as long as the token is valid.
The second is forwarding my SSH agent with ssh -A. The private keys stay on my laptop, but the VM can use every key in the agent without asking and without any record of what it signed. It also only covers SSH keys.
What I wanted was for the credentials to stay on the laptop and for the commands that need them to run there too. The agent asks to run something, I approve it with Touch ID, and the agent gets the output back.
lend #
That's where lend comes in. lend is a proxy that sits in front of your existing SSH agent, and you forward its socket in place of the real one. SSH and Git keep working like normal, and lend adds a way to run commands through an SSH agent extension.
When an agent on the VM asks to run gh, the request goes over the socket and gh runs on my laptop with my login. The token never leaves the laptop, so the agent never has it. Every request, whether it's a signature or a command, is checked against a policy on the laptop and needs my approval before anything happens.
1Remote: lend exec -- command args
2                  |
3          forwarded SSH agent socket
4                  |
5Laptop: lend agent -> policy + local approval -> local command
6                                           -> original SSH agent (signing)
The policy lives on the laptop and lists what the VM is allowed to ask for. Everything else is denied. Mine is pretty short:
 1{
 2  "default": "deny",
 3  "commands": [
 4    {"executable": "/opt/homebrew/bin/gh", "approval": "biometric:inline"}
 5  ],
 6  "ssh": {
 7    "default": "deny",
 8    "keys": [
 9      {"fingerprint": "SHA256:...", "approval": "biometric:inline"}
10    ]
11  }
12}
A rule can also take an args_prefix like ["pr", "view"] if you only want to allow some subcommands. biometric:inline puts Touch ID right in the request dialog, so I read the request and touch once to approve it. Plain biometric asks for Touch ID in a second prompt after I click Allow.
To connect, I run lend ssh from the laptop. It starts a proxy for that one connection and stops it when SSH exits:
1lend ssh --config ./policy.json -- agent-vm

1{
2  "mcpServers": {
3    "laptop": {"command": "lend", "args": ["mcp"]}

5}

Both NeXT and 3DFX tried to “do the right thing” with color spaces, and it wound up generally making them look worse than competing options. I didn’t really understand it properly until years later.
It is natural to think that a pixel with a value of 1.0 is emitting twice the photons as a pixel with a value of 0.5, so you can do the obvious linear math to calculate partial pixel coverage, blending a foreground over a background, or interpolating between colors in a texture.
If displays are “linear”, that is correct. NeXT and 3DFX were much closer to linear than other contemporary displays. NeXT had crossover from the deep graphics understanding at Pixar, and 3DFX had the SGI heritage. They did this intentionally.
If you have 10+ bits per channel like the professional rendering systems, linear displays are The Right Thing.
Unfortunately, NeXTStation Colors were 4 bits per channel and 3DFX was 5 or 6 bits per channel, and there… it was not the right thing.
Human eyes aren’t linear intensity sensors. We mostly register relative changes in intensity, so we can tell the difference between 0.01 and 0.02 as a huge doubling, while 0.99 to 1.00 is almost imperceptible.
This distribution of intensities is often referred to as the “gamma” of the display system, but the actual curves like sRGB are a bit more complicated.
If you only have a small number of discrete pixel values, you definitely don’t want to spread them evenly from 0 to 1! If you do, you will have good precision in the brights, but very stark “intensity bands” in the dark colors.
If everything was authored specifically for 3DFX, you would still have the fundamental problem with the dark bands, but more accurate blending and filtering. The problem was that artists made all of their textures in paint programs on conventional non-linear displays, so when they were drawn by 3DFX cards, they got the characteristic “washed out color” look.
You can mathematically correct textures for differences in display gamma, but I didn’t really understand the issue back in the glQuake days, and we were so enthralled by the absolute performance of 3DFX that the color fidelity didn’t get as much attention as it should have.
Even today, tons of games don’t properly handle gamma across their textures and render targets. High resolutions and 24 bit color masks most of it, but you still see it in some slight shimmerings in high contrast textures and edges.
Does anybody know why 3DfX 1 cards had such a washed out color output? In my research, circa '97 I found many people complaining about the colors. Is it gamma? 16-bit color? What can it be?

For a century, we have built trust in technology on predictability: predefined inputs, predictable outputs, and layers of protection. Consider how a breaker trips at a set current or an aircraft component is tested against known (i.e., predictable) stresses.

With temperatures in the Pacific Ocean at record-high levels and forecasts of an extreme El Niño climate event, intense marine heatwaves are expected around the world in the coming year1,2. Scientists must prepare to study these extreme conditions now, so that managers of marine resources and decision makers can develop and implement response strategies and communities can plan for a hotter future.
El Niño is part of a recurring natural cycle in Earth’s climate in which warmer waters in the central and eastern Pacific alter ocean and atmospheric circulation, affecting weather worldwide. Marine heatwaves associated with El Niño provide opportunities to study ecosystems under real-world stress conditions and on scales that cannot be replicated in a laboratory.
Marine heatwaves can be forecast weeks or months ahead, giving researchers time to design field studies, deploy instruments and collect baseline data. Investigations can be designed to test theories and improve our understanding of ecological processes, thresholds and recovery mechanisms in a rapidly warming ocean.
Such knowledge can inform decisions about how to manage marine resources, such as whether to close fisheries. Much has been learnt about marine heatwaves since the last El Niño, in 2023–24 (see ‘Hot water’). But these lessons need to be consolidated and scaled up into consistent, long-term preparedness plans.
Fortunately, effective approaches established in one place can be extended to others. Australia is a leader in developing early-warning systems and response plans for adaptation to a more extreme ocean climate. Other nations (including the United Kingdom, the United States, New Zealand and Peru) have improved their awareness of these events and put in place observation systems, forecasts and briefings, policy mechanisms and (in a few cases) adaptation measures.
But further action is needed, particularly in locations that have previously been unaffected by severe marine heatwaves. Here, we highlight seven priorities in increasing marine heatwave preparedness.
Forecast and early-warning systems
Seasonal forecasts with lead times of several months are now being delivered in various regions, including the United States3 and Australia4, and such systems are being developed in the United Kingdom and New Zealand5 and for the Mediterranean Sea6.
Forecasting relies on physical and statistical models to predict probable ocean temperatures7. Data from sustained surface and below-surface observations are essential for initializing models and verifying predictions, building users’ confidence in forecasts.
But managers want to know more precisely what the duration and intensity of a marine heatwave is expected to be. Forecasts become less accurate the further ahead they look and at fine spatial scales, such as along coasts. Improved ocean monitoring, a better understanding of the drivers of marine heatwaves and continued refinements of model physics are needed to improve forecast accuracy7.
Advances in machine learning are expected to be transformative. Next-generation models that incorporate ocean physics might be able to predict unprecedented marine heatwaves more accurately than current technologies can. Downscaling global climate models to inshore regions using machine-learning techniques could also increase the usefulness of forecasts in places where most marine-resource users operate.
Coordinated briefings
Planning for and communication about impending marine heatwaves are also improving1. In 2023, engagement was piecemeal and often only in response to events that were already in progress. Activities are now more proactive and structured.
Coordinated briefings that translate forecasts into action provide ways of engaging with affected groups and planning ahead. Such communication strategies should be implemented around the world4,8. National briefings provide a broad overview of marine heatwave risks and impacts. Regional and industry specialists can provide further local advice.
For example, Australia’s national marine climate briefing series4 has been running since 2023. Similar meetings (led or contributed to by some of us) have taken place for the western Pacific Ocean (G.S.) and in the United Kingdom (C.R.), Brazil (K.E.S.), Singapore (C.M.S.) and New Zealand (C.M.S.).
