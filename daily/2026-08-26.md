Follow me on X: https://x.com/jiayuan_jy
A single CLAUDE.md file to improve Claude Code behavior, derived from Andrej Karpathy's observations on LLM coding pitfalls.
English | 简体中文
From Andrej's post:
"The models make wrong assumptions on your behalf and just run along with them without checking. They don't manage their confusion, don't seek clarifications, don't surface inconsistencies, don't present tradeoffs, don't push back when they should."
"They really like to overcomplicate code and APIs, bloat abstractions, don't clean up dead code... implement a bloated construction over 1000 lines when 100 would do."
"They still sometimes change/remove comments and code they don't sufficiently understand as side effects, even if orthogonal to the task."
Four principles in one file that directly address these issues:
Don't assume. Don't hide confusion. Surface tradeoffs.
LLMs often pick an interpretation silently and run with it. This principle forces explicit reasoning:
- State assumptions explicitly — If uncertain, ask rather than guess
- Present multiple interpretations — Don't pick silently when ambiguity exists
- Push back when warranted — If a simpler approach exists, say so
- Stop when confused — Name what's unclear and ask for clarification
Minimum code that solves the problem. Nothing speculative.
Combat the tendency toward overengineering:
- No features beyond what was asked
- No abstractions for single-use code
- No "flexibility" or "configurability" that wasn't requested
- No error handling for impossible scenarios
- If 200 lines could be 50, rewrite it
The test: Would a senior engineer say this is overcomplicated? If yes, simplify.
Touch only what you must. Clean up only your own mess.
When editing existing code:
- Don't "improve" adjacent code, comments, or formatting
- Don't refactor things that aren't broken
- Match existing style, even if you'd do it differently
- If you notice unrelated dead code, mention it — don't delete it
When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused
- Don't remove pre-existing dead code unless asked
The test: Every changed line should trace directly to the user's request.
Define success criteria. Loop until verified.
Transform imperative tasks into verifiable goals:
For multi-step tasks, state a brief plan:
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
Strong success criteria let the LLM loop independently. Weak criteria ("make it work") require constant clarification.

This repository includes a committed Cursor project rule (.cursor/rules/karpathy-guidelines.mdc) so the same guidelines apply when you open the project in Cursor. See CURSOR.md for setup, using the rule in other projects, and how this relates to Claude Code.
From Andrej:
"LLMs are exceptionally good at looping until they meet specific goals... Don't tell it what to do, give it success criteria and watch it go."
The "Goal-Driven Execution" principle captures this: transform imperative instructions into declarative goals with verification loops.
These guidelines are working if you see:
- Fewer unnecessary changes in diffs — Only requested changes appear
- Fewer rewrites due to overcomplication — Code is simple the first time
- Clarifying questions come before implementation — Not after mistakes
- Clean, minimal PRs — No drive-by refactoring or "improvements"
These guidelines are designed to be merged with project-specific instructions. Add them to your existing CLAUDE.md or create a new one.
For project-specific rules, add sections like:
## Project-Specific Guidelines
- Use TypeScript strict mode
- All API endpoints must have tests
- Follow the existing error handling patterns in `src/utils/errors.ts`
These guidelines bias toward caution over speed. For trivial tasks (simple typo fixes, obvious one-liners), use judgment — not every change needs the full rigor.
The goal is reducing costly mistakes on non-trivial work, not slowing down simple tasks.

python has 6 pre-declared "constants": True, False, None, __debug__, Ellipsis (or equivalently ...), and NotImplemented. but they all behave slightly differently, for some reason.
        
True, False, and None
        True, False, and None are keywords. they aren't identifiers, they're just straight up their own lexical tokens. which is really weird; nothing else is like this in python. usually stuff is resolved during regular name resolution, not in the lexer itself.
        
an interesting side effect of this is that expressions like x.True raise a SyntaxError. i'm curious as to what the rationale was for this decision (if there was one).
        
there's some more interesting stuff with these constants, but i'll get to it later, since it ties in with the other constants.
__debug__
        __debug__ is a boolean constant: it's normally True, but when running with -O, it's False. the idea is similar to how assert is disabled in non-debug builds: you can wrap code in if __debug__ if the check would be too expensive in an "optimized" build, or something.
        
__debug__ is really interesting though, because although it's a normal identifier (unlike True, False, and None), it's the only identifier in the language which can't be assigned to:
        
>>> __debug__ = 67
  File "", line 1 SyntaxError: cannot assign to __debug__ 
you can't even assign to it as an attribute:
>>> x.__debug__ = 67
  File "", line 1 SyntaxError: cannot assign to __debug__ 
again, no other identifier behaves like this. this is a true special case.
but because it's not a keyword, it behaves slightly differently to True, False, and None:
        x.__debug__ raises AttributeError (rather than SyntaxError), since it's syntactically valid; it's just looking up an attribute which doesn't exist.
        
interestingly, there's also a special error message for attempting to delete __debug__ (despite the fact that this would raise a NameError anyway if not for the special case), but this doesn't apply for deleting an attribute named __debug__:
        
>>> del __debug__
  File "", line 1 SyntaxError: cannot delete __debug__ >>> del x.__debug__ Traceback (most recent call last): File " ", line 1, in NameError: name 'x' is not defined 
if x were defined, an AttributeError would be raised instead. in either case, it's not a SyntaxError (unlike assignment), for some reason.
        
tangent: SyntaxError is a lie
        speaking of errors: assigning to __debug__ is one of only a few cases i'm aware of where a SyntaxError is raised despite something not actually being invalid syntax. here, you can confirm it yourself:
        
>>> assert (__debug__ := 67)
running that assert in a debug build raises a SyntaxError, but with -O, the assertion is never compiled, and so no exception is raised.
        
two other instances of this are using yield or await outside of a function:
        
>>> assert (yield)
>>> assert (await 67)
Ellipsis and NotImplemented
        Ellipsis and NotImplemented are documented in the "constants" section of the reference, but unlike the other 4 constants, they aren't "real" constants. they're just normal builtins, so they can be shadowed by globals:
        
>>> NotImplemented = 67
>>> NotImplemented
67
again, i'm curious about the rationale here. why is it that these aren't special, but the other constants are?
overwriting constants
here's something interesting: despite being lexical tokens, True, False, and None also exist as normal builtins:
        
>>> import builtins
>>> getattr(builtins, 'True')
True
>>> getattr(builtins, 'False')
False
>>> getattr(builtins, 'None') is None
True
there's no way to directly access these without using getattr.
        
but here's where things get really interesting: setattr also works!
        
>>> setattr(builtins, 'True', 67)
>>> getattr(builtins, 'True')
67
however, this doesn't change the value when accessed with the lexical token:
>>> True
True
but __debug__ has the same behavior!
        
>>> setattr(builtins, '__debug__', 67)
>>> builtins.__debug__
67
>>> __debug__
True
so __debug__ can sorta be assigned to, but despite not being a lexical token, it's special cased just like True, False, and None: its value is unaffected by changes to the builtins module. so it really is a constant!
        
Ellipsis and NotImplemented are, once again, not actually constants:
        
>>> setattr(builtins, 'Ellipsis', 67)
>>> Ellipsis
67
this doesn't change the value of ... though:
        
>>> ...
Ellipsis
so in some sense, ... is a real constant, but Ellipsis isn't. weird, right?

Some internet standards only support ASCII characters, but the world uses much more than the Latin alphabet. Thus, a mapping from Unicode to ASCII for use in domain names is required.
NamePrep was part of that solution, defined in RFC 3491 as a profile of StringPrep, and is crucially a component of Internationalizing Domain Names in Applications (IDNA), also known as “IDNA 2003”. The StringPrep algorithm is defined in RFC 3454. IDNA 2003 has been obsoleted by IDNA 2008 defined in RFC 5890, 5891, 5892, and 5893.
Python supports IDNA 2003 through the idna codec (str.encode('idna')) and
IDNA 2008 is supported by the idna package on the Python package Index. 
Python's implementation of StringPrep is implemented in the stringprep module
in the standard library. In general, you should be using the idna package (IDNA 2008)
and not .encode("idna") (IDNA 2003), but sometimes you
do need the older behavior.
StringPrep defines the “case folding” step (case folding is approximately “how to lowercase/uppercase a codepoint”) in Section 3.2, enabling case-insensitive
comparisons of strings, by mapping all characters through mapping tables B.2 and B.3.
B.2 is effectively str.lower(), lowercasing all characters according to
Unicode rules and B.3 contains the exceptions. The Python code implementing
this (and assuming B.3 table is captured correctly) is the following code below:
def map_table_b3(code):
    r = b3_exceptions.get(ord(code))
    if r is not None: return r
    return code.lower()
And that might seem fine... and the title probably gave it away already.
The str.lower() call in this function is a vulnerability!
Why? Because str uses whatever Unicode data that the particular Python
interpreter is shipped with, you can figure out what Unicode version your
Python interpreter uses by accessing unicodedata.unidata_version:
>>> import unicodedata
>>> unicodedata.unidata_version
'17.0.0'
There's also a database of Unicode 3.2.0 data available on every version
of Python (unicodedata.ucd_3_2_0) specifically for the StringPrep and IDNA algorithms:
$ grep -I "ucd_3_2_0" -R Lib/
Lib/stringprep.py:from unicodedata import ucd_3_2_0 as unicodedata
Lib/encodings/idna.py:from unicodedata import ucd_3_2_0 as unicodedata
This is important! StringPrep depends on this specific version of Unicode
to operate consistently, the B.2 and B.3 tables in RFC 3454 are essentially
Unicode 3.2.0 case-folding rules encoded into
a table. So we need to use Unicode 3.2.0 case-folding rules, not newer
Unicode case-folding rules. This is why calling str.lower() represents
a difference in the implementation and the specification,
and therefore a vulnerability:
# RFC 3454 compliant value ('Ꭰ' is U+13A0)
>>> "ᎠᎠ".encode("idna")
'xn--58da'
# Value if using Unicode 17.0.0 case-folding
>>> "ᎠᎠ".encode("idna")
'xn--kz9aa'
The fix was to create new exceptions so that str.lower() would behave
as if it was using Unicode 3.2.0 for only particular function. So, we
go through each Unicode codepoint and record when the behavior of
str.lower() is different when comparing the Unicode version shipped with Python and Unicode 3.2.0.
And that's all, now IDNA 2003 is consistent with the specification.

            Abstract:It is widely repeated in the popular literature and elsewhere that the singularity at the center of a black hole is a point. It is not true. Two observers who free-fall into a spherical black hole along two different angular trajectories at the same time $t$ do not encounter each other at the central singularity; rather, they lose causal contact with each other already well away from the singularity. Counterintuitively, in general relativity two points can be spatially close yet causally distant. The singularity is a surface, not a point. The story for rotating black holes is more complicated, but the same conclusion holds. For a rotating black hole, the singular surface almost certainly resides at its inner horizon, where even the tiniest classical or quantum perturbations ignite the exponential mass inflation instability, precipitating collapse to a spacelike singular surface. There are implications for quantum gravity. We argue that, whatever the ultimate theory of quantum gravity may be, the quantum states of a black hole probably reside at its effectively 2-dimensional singular surface, which coevolves unitarily with, and in thermodynamic equilibrium with, the hot atmosphere of trapped Hawking radiation that the black hole generates within its event horizon.

Why the Riemann hypothesis matters
The primes 2, 3, 5, 7, 11, 13, … are the atoms of arithmetic: every whole number factors into primes in exactly one way, so facts about primes become facts about all numbers. Individually they are irregular — no known rule produces the next prime from the ones before it. Counted in bulk, they obey a law: the number of primes up to x stays close to a single smooth curve (the prime number theorem, proved in 1896). The open question is the size of the error — how far the true count can stray from the curve. That error term is what the Riemann hypothesis governs, and it is why RH matters: sharpen the error term and you sharpen hundreds of results in number theory that depend on it.
In 1859 Bernhard Riemann explained where that hidden order comes from. He took Euler's identity, which connects the primes to a single function of one complex variable,
extended it to the whole complex plane, and discovered that the wobble of the prime count around its smooth curve is governed — exactly, via an explicit formula — by the locations of the zeros of this function. Each zero contributes one wave to the error; the zero's height sets the wave's frequency and, crucially, its horizontal position sets the wave's amplitude. Riemann observed that every zero he could examine sat on one vertical line, Re s = ½, now called the critical line — the position giving the smallest possible amplitude — and remarked it was “very probable” all of them do. That remark is the Riemann hypothesis. Its concrete content: the prime-count error up to x never exceeds roughly √x, the same size as the wobble of a fair coin flipped x times. The primes are allowed to look random; RH says they are never allowed to drift with a bias.

前言
2024 年，我曾三次来到台湾，但都不是独自旅行。当身边有熟悉的人时，旅行是一件很自然的事：一起制定行程，讨论下一站要去哪里。即使到了陌生的地方，因为有人陪伴，我也不太需要单独面对「陌生」。
2026 年的这次旅行却有些不同。这是我第二次来淡水，也是我第一次尝试以写游记换宿的方式，在一个地方短暂生活。与其说这是一趟普通的旅行，不如说它更像是一段被借来的日常：我以写作换取在台北 Yes 民宿生活一周的机会，认识一些原本不会相遇的人，按照自己的步调散步、吃饭、看海，感受一个个地图上的目的地慢慢变成由许多具体记忆组成的地方。
出发前，我对这趟旅行一直很期待，可是当我真正拖着行李走出淡水捷运站往民宿方向走时，才发现期待里也混着紧张。越接近民宿门口，我的心跳得越厉害。第一眼看到民宿时，我站在门外拍了一张照片。那一刻，它对我来说还是一个全然陌生的地方：里面有我不认识的房间、不认识的人，也有接下来一周尚未展开的生活。
进门后，我先看到五六个人坐在大厅的桌边聊天。大概是因为太紧张，我不好意思主动打招呼，只是拖着行李匆匆躲进自己的房间。直到房门关上，行李放下，心跳才慢慢平静下来。这就是我抵达淡水的第一刻：不是浪漫的，也不是从容的，是「我真的一个人来到了这里」的恍惚感。
接下来的一周里，我沿着几条不同的线认识淡水：白天用步行阅读这座河港的历史，傍晚坐在岸边等待日落，到了晚上则去餐厅和酒吧。淡水就在这些重复的散步、偶然的推荐和短暂的相处里，一点点改变了我与它之间的距离。
白天：沿着「沪尾」的历史散步
第二天早上，我很早就醒了。那天在很热的夏天里走了一万五千多步，沿着淡水慢慢散步。因为以前来过，老街、河岸和几个主要景点对我而言都不算陌生。但这一次，我不太想再按照「抵达景点、拍照、离开」的方式重游，而是提前了解了一些淡水的历史，想看看自己能否从熟悉的街道里，读到过去没有留意的东西。
淡水是一座很适合步行的城市。从捷运站出发，沿着老街与河岸慢慢前行，再往山坡上的古迹前进，城市的样子会一层一层展开。河岸平缓而热闹，往里走则是弯曲的街道和不断起伏的坡道。在烈日下不停爬坡时，我才切身体会到，淡水不只是一座河港，也是一座依着山势生长起来的城市。
一座城市为什么会在这里出现
今日的淡水旧称「沪尾」，过去「淡水」原本是一个更宽泛的称呼，可以指淡水河流域乃至北台湾一带；沪尾才是位于淡水河口的聚落名称。关于「沪尾」这个名字的由来，有两种说法：一种认为它是凯达格兰族语的音译；另一种说法则认为，过去淡水一带有许多捕鱼的石沪，位于石沪尾端的村庄因而得名「沪尾」。
淡水河在这里流入台湾海峡，背后又有大屯山系作为屏障。这种扼守河口的位置，使它很早就成为外来船只进入北台湾的重要门户。如果沿着时间往前看，会发现淡水的历史，几乎就是一部不同的人从河口进入北台湾的历史。
十七世纪，西班牙人与荷兰人先后来到淡水，在河口附近建立据点。到了十九世纪，天津条约签订后，淡水成为国际通商口岸；1862 年，沪尾洋关正式开关征税。茶叶、樟脑、硫磺和煤等物产从这里被运往海外，各国商人、海关人员、传教士与船员也沿着港口来到淡水。商船带来了贸易，领事与洋行带来了新的建筑和生活方式，传教士则将宗教、医疗与教育带入当地。1884年清法战争期间，法国舰队进攻沪尾；战争结束后，清政府又在河口高处修建新式礮台，加强北台湾的海防。
这些历史如今分别留在淡水的不同位置。因为民宿就在捷运站附近，我从这里出发，先经过老街与河岸，再沿着山坡前往红毛城、前清英国领事官邸和真理大学，最后走到位置更高、也更安静的沪尾礮台。这不仅是一条连接景点的步行路线，也像是一条从今日逐渐走入过去的时间线。
淡水老街与河岸
从民宿往外走，最先遇见的是淡水老街。老街上挤满游客，店铺的招牌彼此相连，空气里混着食物的香气。再往河岸走，则能看到渡船、街头表演和坐在岸边休息的人。
我以前来淡水时，更多是把老街视为一条「有很多东西可以吃」的街道。直到这一次了解淡水的港口历史，我才开始尝试想象：眼前这条挤满游客和纪念品店的街道，曾经与商船、洋行和货物运输紧密相连；从北台湾各地汇集而来的茶叶与樟脑，也曾沿着淡水河来到港口，再从这里被送往海外。
城市的功能已经改变，但热闹没有完全消失。过去的繁荣来自货物的流动，今天的繁荣则来自旅行者的到来。两种人潮相隔百年，却都因为同一条河汇集在这里。
红毛城与英国领事官邸
穿过淡水老街，沿着山坡往上漫步，我来到红毛城与前清英国领事官邸。
红毛城的历史可以追溯至十七世纪。西班牙人曾在淡水建立圣多明哥城，后来荷兰人驱逐西班牙人，并于 1644 年重新修筑安东尼堡，也就是今日所见的红毛城主堡。到了十九世纪，淡水开港通商，英国在 1860 年代租借红毛城作为领事馆使用。随着贸易增加，又在主堡东侧兴建领事官邸。
站在两座建筑之间，可以很直接地感受到历史的交叠。一边是墙体厚重、空间封闭，以军事防御为目的的城堡；另一边则是由红砖、拱廊与斜屋顶构成的二层洋楼。领事官邸由英国人设计、中国工匠施工，墙壁使用中国红砖，屋顶则铺着闽南式红瓦。它看起来很「西洋」，细看之后却会发现，建筑本身也像淡水一样，由不同文化共同完成。
真理大学
从红毛城继续沿着真理街前行，很快便能走到真理大学。
1872年，加拿大传教士马偕抵达沪尾，并以淡水作为传教、医疗与教育工作的据点。1882年，他在今日真理大学校址创办理学堂大书院，英文名为 Oxford College，后人也称其为牛津学堂。
来到这里之前，我对马偕的认识更多停留在名字和医院上。走进校园后才发现，他在淡水留下的不只是一段传教史，也包括医疗和近代教育的发展。红毛城与领事官邸呈现的是外国势力通过港口进入淡水；理学堂大书院所留下的，则是一些外来的知识和制度如何在这里落地，并继续影响当地社会。
沪尾礮台
离开真理大学后，我继续走向沪尾礮台。1884 年清法战争期间，法国舰队曾进攻沪尾。战事结束后，刘铭传意识到台湾海防的重要，于是在淡水河口高处兴建新式礮台，并亲自题写「北门锁钥」四字。不过，今日保存下来的沪尾礮台是在战争结束后才兴建的，并没有真正参与 1884 年的战斗。
走进礮台时，发现我是唯一的旅客，工作人员坐在入口处乘凉，看到我笑笑地说一句「今日好热呢」。想一想也是，在三十多度的夏天里，这个需要走过不少坡道才能抵达的地方，或许并不是多数游客的第一选择。
礮台里的展品不算丰富，一处原本设置火炮的位置如今只留下说明牌，现场可以看到的导览和历史介绍也不算多，因此我只停留了一会便离开了。
傍晚：每天把一场日落看完
白天，我尝试通过建筑理解淡水；到了傍晚，我认识这座城市的方式却变得简单——只是在河岸坐下来，看天色慢慢暗下去。在淡水的每一天，我都会去看日落。码头旁坐着许多和我一样等待夕阳的人，大家不一定说话，只是面向同一片水面，等待天空一点点改变颜色。
我喜欢欣赏日落，也喜欢看别人欣赏日落的样子：有人举起手机拍照，有人和身边的人小声说话，也有人只是静静地站着，任由夕阳把自己的背影也照成风景的一部分。最初，我也习惯把注意力放在太阳接近地平线的那几分钟，等待天空变成最鲜艳的橙红色，仿佛那才是整场日落最值得记录的时刻。
但连续看了几天以后，我渐渐发现，日落并不是太阳沉下去的一个瞬间，而是一段缓慢发生的过程。有时候，太阳落下后的余晖甚至比落日时更加令人惊喜。
那时候想到的是，我们好像习惯追逐最明亮和所谓最适合记录的时刻，旅行时急着拍下抵达的景点，看日落时等待太阳碰触地平线的绚烂瞬间，仿佛只有这些清晰的瞬间才值得被记住。但有时候慢慢地去感受，不刻意追赶某个时刻，而是放松安静地去观察所有流动的变化，也有会不一样的体验。
看着身边不断举起手机的人，我偶尔也会想：他们拍下这一刻，或许是想留给自己，或许是想发给某个心爱的人。日落本来只是自然中再寻常不过的事情，却因为我们想要记录、分享，想把眼前的美好传递给另一个人，而变得格外温暖。
这让我想起《旅行之木》里的一段话：如果独自看见了美得让人落泪的夕阳，要怎样把这份感动传达给心爱的人？拍照、画下来，还是亲口讲述？书中的回答是「我会用自己的变化告诉他」。我很喜欢这个答案，被一场夕阳打动，并因此一点点改变，或许就是传递这份心情最好的方式。
夜晚：让刚刚遇见的人决定下一站
历史让我明白淡水为什么会成为今天的样子，而生活在这里的人，则带我看见了这座城市更加私人的一面。这次旅行里，我很喜欢的一件事，是透过人与人之间的连接探索淡水。每一次推荐都像是一根细细的线，从一个地方牵到另一个地方，也从一个人牵到另一个人。
最先开始的，是 Henry 和店长。住在民宿时，他们带我去吃了好吃的蛋饼，然后 Henry 跟我推荐了名厨铁板烧。我来过台湾几次，却一直没有特别去吃过这边的铁板烧。出发前，我原本跟自己说，这次来淡水，每一餐都要尽量吃不一样的东西，没想到这个计划很快就被名厨铁板烧打破了。我连续三天吃了三顿，因为真的觉得好好吃。
旅行时，我曾觉得好像应该把有限的餐数分给更多店家，才算充分体验一座城市。但当我第三次走进同一家店时，反而产生了一种很微妙的熟悉感。第一次是来尝试，第二次是因为喜欢，第三次则已经有点像回到食堂的感觉。
另一条线，则是从一本书开始的。
我去了一间叫「多崎作」的酒吧。这个名字很容易让人想到村上春树的《没有色彩的多崎作和他的巡礼之年》。很巧的是，这本书是我在少数派认识的台湾笔友 @Jason 去英国找我玩时带的礼物。因为这个缘由，我对这间酒吧多了一些好奇，于是在看完日落后走了进去。
刚到店里时，里面只有我和另一位客人。对方看起来是一位熟客，坐在吧台前看书，我便和老板闲聊起来，问他店名是否与村上春树有关。他告诉我，自己确实是村上的书迷，然后与我分享了许多和书有关的内容。我也偶然得知，有不少旅客和我一样，因为店名走进来，再问他是不是村上春树的读者。
酒过两杯，我看着时间差不多回民宿，就问起老板附近有什么其他酒吧推荐，他和我推荐了 Bar Qvevri 自然酒吧。很少喝葡萄酒的我问起什么是自然酒，老板就拿出来几瓶酒，向我解释如何分辨，也让我第一次认识这种尽量减少人工干预、希望保留原始风土的酿造方式。
可惜 Bar Qvevri 只有周四才开门。那天还是周一，于是我把这个推荐记在心里，一直等到周四，才和 Jason 一起前往。没想到那天喝到的自然酒意外地好喝，使得我第二天晚上又独自去了一次。
后来，Bar Qvevri 的老板又向我推荐了再再咖啡，我隔天去了，发现那是一间很漂亮、也很舒服的咖啡店。
这种感觉很奇妙。我不是通过一篇完整的攻略认识淡水，而是因为一本书走进一间酒吧，再因为一场谈话去了另一间酒吧，最后被带到一家咖啡店。这些地方原本只是城市里分散的点，却因为一个人对另一个地方的喜欢，慢慢连成了一张只属于这趟旅行的地图。地图告诉我一个地方在哪里，人却告诉我为什么值得去。
回到民宿：让收到的善意继续往前走
在旅行开始时，Yes 民宿对我而言只是一个未知的借宿地点。我站在门外拍下第一张照片，不知道推开门以后会遇见什么人；看到大家坐在桌边聊天时，我甚至紧张得匆匆躲回房间。但一周以后，民宿不再只是一个睡觉的地方。它成为我每天出发与回来的起点，也是这一连串推荐最初发生的地方。
后来和民宿老板 Henry 聊天时，我才知道，他以前在大理旅行时，也曾经以类似的方式打工换宿。正是因为那段经历，他后来把这种方式延续了下来，希望更多人也有机会通过交换，来到一个地方短暂生活。知道这件事时，我觉得非常神奇：曾经发生在大理的一段旅行经验，在多年之后为淡水的一名陌生旅客打开了一扇门，而我恰好成为了走进这扇门的人。
刚来到淡水时，我只知道民宿在捷运站附近，知道老街和河岸是这里最著名的景点。离开时，我已经认得从民宿走向河边的路，知道太阳落下以后还可以再坐二十分钟，知道哪间店值得连续吃三次，也知道周四晚上可以去哪里喝一杯自然酒。淡水没有因此变成一座完全不同的城市，改变的是我与它之间的距离。原本陌生的门、重复走过的路、一次次吃过的饭和从别人那里收到的推荐，共同组成了我在这里生活过一周的证据～
最后简单说明一下这次前往台湾的方式：由于我目前在澳门读书，持有当地的居留证明，因此可以以旅居港澳的大陆居民身份在线申请入台证。获批后便能自行前往台湾，每次最多停留 15 天。

Matrix 首页推荐
Matrix 是少数派的写作社区，我们主张分享真实的产品体验，有实用价值的经验与思考。我们会不定期挑选 Matrix 最优质的文章，展示来自用户的最真实的体验和观点。
文章代表作者个人观点，少数派仅对标题和排版略作修改。
大家好，我是 Ark。一晃来少数派已经 11 年多了，这也是我第一次在这里发文。
过去两个月，利用工作之外的时间，一个人借助 Codex 和 Claude Code，完成了 ArkFlow 长流 app 的设计、开发和上架。上线 7 天后，它获得了 1000 次下载。
不过，这篇文章并不主要想讨论 AI 如何帮我写代码。
我更想分享一件出乎我意料的事：我原本花了最多时间，设计了一套关于资产和人生自由度的系统；产品上线后，几乎没有人讨论它，大家反而更喜欢滑银行卡。
这也让我重新认识了自己做出来的产品。
我目前大约有 50+ 需要管理的账户。
其中包括 10 多张储蓄卡、20 多张信用卡、几张海外银行卡，以及股票、基金、电子钱包等账户。
账户多了以后，真正麻烦的并不是计算总资产。
麻烦的是，我经常记不清某张信用卡的还款日，不确定一张很少使用的卡是否还要收年费；临时需要某个账户时，还要在不同银行 App 之间反复寻找。至于股票、基金和外币账户，则散落在另外几个不同的券商平台里。
我试过用记账软件，也试过用表格整理。
但传统记账软件更关心「今天花了多少钱」，表格则需要持续维护。它们都很实用，只是解决的并不是我最想解决的问题：
我不想记录每一杯咖啡，我只是想知道自己有哪些账户、钱放在哪里，以及接下来有哪些事情不能忘。
于是，我开始做 ArkFlow。
最开始，我以为它会是一款比较常规的资产管理 App。直到产品上线后，我才发现，用户真正感兴趣的东西，和我最初设想的完全不同。
银行卡不只是一串余额
整理银行卡时，我发现一个很奇怪的现象。
有些卡其实已经很久没有使用了，我却一直舍不得删除。
第一张工资卡、刚工作时办理的信用卡、出国时申请的 VISA 和运通银行卡，以及某个阶段为了积分、权益或者卡面专门办理的卡。它们的实际用途可能已经消失，但看到卡面的那一刻，我还是能够想起当时的生活。
我们习惯收藏照片、车票、电影票和旧手机，却很少把银行卡看成一种值得保存的东西。
但对很多人来说，银行卡其实也在记录人生。
一张卡可能对应第一份工作，一张卡可能是第一次独自旅行，还有一张卡可能只是因为卡面很好看，明明用不上，却一直没有舍得注销。
这也是为什么，在设计 ArkFlow 时，我没有把账户简单做成传统的表格列表，而是希望它首先看起来像一个真正的卡包。
每一个账户都可以使用银行 Logo，也可以上传自己喜欢的真实卡面。银行卡按照接近真实卡片的比例展示，可以堆叠、滑动、展开，也可以整理成一面卡墙。
金额和账户信息仍然存在，但卡本身不再只是数据的容器。
它也可以是一件值得把玩的东西。
我原本以为，用户最需要的是资产分析
ArkFlow 最初的定位是一个「人生自由度资产系统」。
我不只想告诉用户「现在有多少钱」，还想回答一个更难的问题：
这些资产，究竟能为一个人带来多大的生活选择权？
同样是一笔存款，对一个没有负债、生活成本很低的人，和一个承担房贷、家庭支出的人，意义可能完全不同。相比单独展示资产数字，我更希望用户能看见，自己的财务状态正在怎样改变生活。
因此，我专门设计了一套「自由度画像」系统。
它会综合资产、负债、收入、支出和目标完成情况，计算用户当前的自由度阶段。为了不让结果只是一条冰冷的进度条，我又设计了 60 个成长阶段，并为男性和女性分别制作了一套人物形象。
从被账单和工作推着走，到逐渐拥有缓冲空间；从可以暂时停下来休息，到真正拥有重新选择工作和生活方式的能力。
我在这套系统上花了很多时间。
除了测算逻辑，还需要反复调整分数变化、阶段划分、人物状态和对应文案。我既不希望它变成简单的财富排名，也不希望用户因为资产不够多而感到被评判。
在产品上线前，我一直认为，这会是 ArkFlow 最重要、也最容易引起讨论的功能。
结果上线之后，几乎没有人讨论它。
很少有人问自由度分数是怎么计算的，也几乎没有人分享自己到达了哪个人物阶段。
用户反馈最多的反而是：
- 能不能上传自己的真实卡面？
- 卡片可不可以增加更多堆叠方式？
- 能不能把首页和分析页隐藏，只留下卡包？
- 能不能做一面墙，专门展示收藏的银行卡？
- 卡片抽出来以后，返回时能不能飞回原来的位置？
有用户甚至直接告诉我，他根本不在意资产分析，只想用它收藏卡面。
这对我来说是一个很强烈的信号。
开发者很容易认为，自己花费时间最多、逻辑最复杂的功能，也应该是用户最在意的功能。
但用户不会按照开发成本评价产品。
自由度画像需要用户先理解一套概念，而银行卡卡包几乎不需要解释。用户看到自己的银行卡在屏幕里堆叠、滑动和展开，立刻就能判断自己喜不喜欢。
对 ArkFlow 来说，用户最先记住的并不是「它可以计算资产自由度」，而是：
银行卡原来还可以这样玩。
于是，我开始重新调整产品。
资产管理依然是底层能力，自由度画像也没有被删除，但卡包逐渐成为产品最重要的入口。用户不是先看到一堆数字，再进入账户列表；而是先看到自己的卡，再从卡片进入余额、额度、还款日和账户详情。
我依然相信，资产最终应该服务于人的选择自由。
但我也开始明白，一个宏大的产品理念，不一定适合作为用户进入产品的第一步。
这不仅是视觉顺序的变化，也是我对产品定位的一次重新理解。
为了让滑动「有感觉」，我做了三种卡片堆叠
卡片交互看起来并不复杂：上下滑动、点击展开、长按排序。
但真正实现后，我发现，卡片「能滑」和「滑起来舒服」完全是两件事。
如果所有卡片平均排列，账户一多，屏幕会显得非常拥挤；如果堆叠得太紧，用户又无法判断下面还有多少张卡。卡片抽出时如果速度太快，会显得生硬；返回时如果直接消失，又会破坏卡片原本存在于卡包中的感觉。
我陆续尝试了三种排列方式。
第一种是比较传统的层叠方式，每张卡露出一部分，可以快速浏览多个账户。并且精心设计了卡片之间重叠区域上下露出的间距和字段，确保用户在各种场景下可以一眼看清每个卡片的账户名称和金额：这个卡是哪个银行，欠款或者余额具体是多少。
第二种会把当前卡片作为视觉焦点，其他卡片在后方收拢，更适合慢慢查看卡面，也更规整和有序。
第三种则更接近 Apple Wallet 的体验。卡片平时紧凑地堆在一起，点击后展开，选中的卡片从堆叠中抽出，关闭详情时再返回原位。这个也是几乎按照Apple的效果进行的还原，我原本不想做这个效果，但是用户反馈的需要的人特别多，都希望加上，并且我的创新的交互也要我1:1去还原Apple，大家都说的是，习惯了Apple的交互，懒得修改了。于是我被迫走上了」抄袭「，也算一种对Apple的致敬。
为了让卡片返回时看起来更自然，我反复调整了遮罩、位移、缩放和动画触发的顺序。
有时候只是几十毫秒的差异，最终的感受却会完全不同。
动画太快，像界面跳转；太慢，又会阻碍操作。卡片移动距离太小，没有被真正「抽出」的感觉；移动距离太大，又像从另一个页面飞进来。
这可能是整个开发过程中，最不符合投入产出比的一部分。
它没有增加新的资产类别，也没有让计算结果更加精确。但很多用户第一次看到 ArkFlow 时，恰恰会因为这段滑动停下来。
我后来逐渐接受了一件事：
对工具类产品来说，愉悦感本身也可以是一种功能。
它不会替用户完成任务，却会决定用户是否愿意再次打开这个工具。
好看之后，它仍然需要解决实际问题
当然，我并不希望 ArkFlow 最终只是一个银行卡展示架。
当账户数量超过十几个以后，管理问题仍然真实存在。
因此，每张卡片背后都可以记录余额、信用额度、账单日、还款日、年费信息、币种和备注。股票、基金、现金和其他类型的账户，也可以放进同一个系统中。
我没有把它做成一款需要记录每笔消费的记账软件。
ArkFlow 更关心的是「现在」。
现在一共有多少资产和负债，分别放在哪些账户；信用卡还有多少额度，哪几张即将还款；不同币种的资产换算后大约是多少；哪些账户正在使用，哪些只是暂时保留。
这种模式不一定适合所有人。
如果只有一两张银行卡，打开银行 App 可能已经足够。只有当账户逐渐增多，或者开始同时管理信用卡、投资和外币资产时，把它们集中起来才会产生明显价值。
这也是 ArkFlow 比较明确的目标用户：拥有多个账户，同时在意隐私、效率和视觉体验的人。
财务 App 最重要的能力，可能是「不知道你有多少钱」
在制作 ArkFlow 时，我一直不太愿意接入银行账户。
自动同步听起来很方便，但也意味着用户需要交出更多敏感信息。对于一个个人开发者产品来说，我不认为自己应该要求用户承担这种信任成本。
因此，ArkFlow 目前更接近一个由用户主动维护的私人资产卡包。
账户和资产数据保存在用户自己的设备中，并可以通过个人 iCloud 在设备之间同步。它不要求注册一个 ArkFlow 账户，也不需要提供网银账号，更不会读取银行流水。
用户可以使用 Face ID 保护 App，也可以在切换到后台时自动隐藏金额。数据还能通过本地备份导出，避免把恢复能力完全依赖于某一个在线服务。
这种选择当然有代价。
没有银行直连，余额不会凭空自动更新；没有完整流水，也无法提供特别复杂的消费分析。
但它让我能够清楚地回答一个问题：
作为开发者，我并不知道用户具体有多少钱。
对于一款管理财务信息的 App，我认为「不知道」反而是一种重要的产品能力。
用 AI 一个月做出 App，真正困难的仍然不是写代码
ArkFlow 也是我第一次如此深入地使用 AI 辅助完成一个完整的 iOS 产品。
我主要使用 SwiftUI 开发，并让 Codex 和 Claude Code 参与代码编写、界面实现、问题排查和回归检查。
这套工作方式确实大幅缩短了从想法到上线的距离。
过去，一个复杂动画可能需要先阅读大量资料，再反复尝试不同实现；现在我可以先描述想要的效果，让 AI 给出基础方案，然后直接在真机上判断，再继续修改。
但实际做下来，我并不认为 AI 已经把独立开发变成了一件容易的事。
AI 很擅长实现一个明确的要求，却不擅长替产品做最终判断。
它可以帮我快速增加十个功能，却不会主动告诉我，其中八个可能根本不应该出现；它可以生成一套看起来完整的资产看板，却无法通过代码判断，用户真正喜欢的其实是那几张可以滑动的银行卡。
在制作卡片动画时，AI 可以给出弹簧参数和位移逻辑，但「这个动作看起来是否舒服」，仍然需要一遍遍在手机上操作。
我也遇到过不少典型问题：
代码表面上可以运行，但修改一个动画后破坏了另一个交互；不同功能分别完成，组合起来却出现状态冲突；AI 为了解决局部问题，引入了不必要的复杂结构。
后来，我开始把不同任务拆到独立的 Git 分支和 worktree 中，让不同模型分别负责实现、审查和回归，再由我决定是否合并。
AI 提供的是生产速度。
但产品方向、功能取舍、交互审美和发布责任，仍然需要开发者自己承担。
如果没有这些判断，更快的开发速度只会让产品更快地变得臃肿。
上线以后，我才开始真正理解这个产品
ArkFlow 上线后的第一个月，我几乎每天都在根据反馈修改产品。
一开始，我会认真向用户介绍资产分析、自由度目标和多币种管理。后来我发现，很多人只是看到一段卡片滑动的视频，便主动询问这是什么 App。
也有人下载后觉得它没有必要。
这其实很正常。对于账户很少、也不在意卡面的人来说，ArkFlow 很可能就是一个过度设计的账户列表。
但另一部分用户会花很长时间寻找银行卡卡面，调整卡片顺序，把已经停用的卡重新添加回来。他们关心的不只是账户余额，还会讨论一张卡应该使用哪个年份的设计、是否应该保留旧版卡面，以及卡片在屏幕里怎样排列才更好看。
这让我意识到，ArkFlow 可能没有必要成为一个覆盖所有财务场景的「大而全」产品。
市场上并不缺少专业记账软件、投资工具和资产管理平台。一个个人开发者也很难在每个领域都做到最好。
但我可以把一个很窄的问题做得更认真：
当一个人拥有很多账户时，能不能让管理它们这件事不再像整理表格，而更像整理自己的收藏？
这也是我现在更愿意继续探索的方向。
AI 降低了开发门槛，但并不意味着零成本
在开始开发后，我也专门统计了一下 ArkFlow 到目前为止产生的现金开销。
其中，Codex、Claude 等 AI 工具的订阅和调用费用两个月约为 900 美元；Apple Developer 会员约为 100 美元；域名、备案和服务器等支出约为 50 美元。合计大约 1050 美元。
这里没有计算我原本已经拥有的 Mac、iPhone 等设备，也没有计算自己的时间成本。部分 AI 订阅同时用于日常工作，因此这也不是一份特别严格的项目财务报表。
但它至少说明了一件事：AI 确实让一个人完成产品设计、开发和上架成为可能，却没有让开发变成一件免费的事。
更大的成本依然是时间。
过去两个月里，我大量的晚上和周末都用在功能设计、真机测试、审核修改、用户反馈和版本迭代上。AI 可以显著缩短写代码的时间，但代码完成以后，还有大量工作无法被自动完成。开玩笑的说，随着继续迭代，回本的预期只会越来越低，因为当前的收入模型是不足以支持每个月450美元的Codex和Claude的订阅费用的。
最后
制作 ArkFlow 之前，我认为自己是在解决一个资产管理问题。
制作一个月后，我发现它同时也是一个关于收藏、记忆和数字物品的问题。
银行卡正在逐渐变成手机里的数字凭证，实体卡的使用频率越来越低。但越是如此，那些曾经陪伴过我们的卡面，反而越容易从生活里消失。
我不知道未来大家是否还会保留这么多实体银行卡。
但至少现在，我希望可以给它们留下一面墙。
ArkFlow 目前已经在 App Store 上架，支持 iPhone 和 iPad，以及 ARM 版本的 Mac 和 Vision Pro。目前也覆盖了简体中文、繁体中文、英语、日语、韩语、德语等语言。
它还有很多不完整的地方。卡片交互仍然在继续调整，资产管理能力也需要慢慢补充。
如果你也拥有很多银行卡，或者曾经有一张已经不用、却舍不得删除的卡，我很想知道：
你会把它当成一个金融账户，还是一件属于自己人生的收藏品？

Work on this harness sensitivity reports it as aggregate score variance, leaving unexamined which items the variance falls on and whether they are the items that separate one model from the next. We treat the evaluation harness of large language models (LLMs) as an independent variable and resolve its effect to single items. We introduce the \textit{fragility grid}: 12 open-weight instruction-tuned LLMs from 4 families answer the same 3{,}679 items from 4 benchmarks (ARC, HellaSwag, MMLU, TruthfulQA) under 26 equally defensible harness configurations, recording one correctness bit for every model, item, and configuration. Under the grid a model's score is a band rather than a point: gemma4-31b scores between 31 and 89 percent depending only on the harness. Three results follow. On the items that two adjacent models both answer stably the pair is tied, and config-fragile items carry 95.7 percent of a pair's gap on average. Four of the 12 models reach rank one under some configuration, so the harness selects the winner. Item discrimination, the property that benchmark-compression methods maximize, correlates with fragility at 0.28 (95 percent CI 0.25 to 0.30), so compression keeps the fragile items rather than removing them. The scoring choice, not the option order that protocols usually fix, is the load-bearing axis. We release the per-item records and the analysis script, from which every number regenerates on a CPU in seconds, and we position the fragility grid as a check a leaderboard can run before it reports an order.

This Addendum provides the configuration details for the geoid models used in the methodology underlying the coastal exposure meta-analysis in the original article1. It expands upon the description in the original publication to ensure full reproducibility of our results. The specific configuration details are outlined below and in Extended Data Tables 1–5.
Geoid model information was obtained from the openly accessible calculation service of the International Centre for Global Earth Models from GFZ Helmholtz Centre for Geosciences (ICGEM)2. Point data on geoid height anomaly to the WGS84 ellipsoid (in m) was obtained for the entire globe at a resolution of 0.085° for the EGM96 (ref. 3), EGM2008 (ref. 4) and GOCO06s (ref. 5) geoid models, respectively6 (data downloaded on 22/08/2023 for EGM96 and EGM2008 and on 10/01/2024 for GOCO06s) (Extended Data Tables 1–3). Specifically, the output grid from ICGEM documents the maximum latitudes of 90.000 °N and 89.945 °S (2118 latitude parallels), and the maximum longitudes of 180 °W and 179.975 °E (4236 longitude parallels). In total, 8,971,848 points were downloaded for each geoid model. We included the zero-degree term as given by ICGEM into the geoid model configuration7 and for each geoid model refer to a tide-free system configuration6. The reference ellipsoid WGS84 underlying these geoid models is defined by the geocentric gravitational constant GM = 3.98600441800 × 1014 m3/s2, a radius of a = 6378137.00 m, a flattening of f = 1/298.25722356300, an angular velocity of ω = 7.292115 × 10–5 s–1 and a normal potential of U0 = 6.263685171456948 × 107 m2/s2. We did not apply any filters in the configuration6. Consequently, the geoid model data we obtained from the ICGEM calculation service include the EGM96 (with a maximum used degree of 360) characterized by a weighted mean of –7.1416531 × 10–3 m, a maximum of 8.5891824 × 101 m, a minimum of –1.0651816 × 102 m and a weighted root mean square of 3.0566520 × 101 m (Extended Data Table 1); EGM2008 (with a maximum used degree of 2190) characterized by a weighted mean of –8.2435599 × 10–3 m, a maximum of 8.6064395 × 101 m, a minimum of –1.0648962 × 102 m and a weighted root mean square of 3.0570532 × 101 m (Extended Data Table 2); and GOCO06s (with a maximum used degree of 300) characterized by a weighted mean of –7.1516965 × 10–3 m, a maximum of 8.5419839 × 101 m, a minimum of –1.0651832 × 102 m and a weighted root mean square of 3.0569639 × 101 m (Extended Data Table 3).
For each geoid model, the height anomaly points were interpolated into a global raster by using multiquadric radial basis functions, which gave the most accurate interpolation results and is also used by gravitational field modelling studies8,9. The interpolations were conducted using the geostatistical wizard in ArcGIS Pro (version 3.1.3). For each interpolation, the kernel parameter was optimized. The standard neighbourhood type was automatically set with a minimum of 10 and a maximum of 15 neighbours. A sector type of one sector was used.
