A coding-agent skill that turns your agent into a security auditor. It orchestrates isolated agents through reconnaissance, coverage-led hunting, candidate validation, structured output, independent record verification, and target-neutral reporting.
This is the skill that seeded Cloudflare's vulnerability discovery harness, described in Build your own vulnerability harness. The harness grew into a multi-stage, fleet-wide system; this skill is the single-repo starting point it evolved from.
The skill runs a structured audit in six phases:
- Reconnaissance -- map architecture, trust boundaries, input surfaces, prior evidence, and deterministic coverage in architecture.md and coverage-ledger.json.
- Coverage-led hunting -- assign isolated hunters from ledger units, record their checks, and use coverage critics to find gaps.
- Candidate validation -- give every unique candidate to a fresh verifier that tries to disprove it.
- Structured output -- write confirmed, needs_validation, and rejected records to findings.json and validate them against report-schema.json.
- Independent record verification -- fresh agents verify final source claims. Material replacements receive another independent verifier.
- Target-neutral reporting -- derive REPORT.md, FINDINGS-DETAIL.md, and NEEDS-VALIDATION.md from the verified records and coverage ledger.
The parent runs validate-coverage-ledger.cjs after creating the ledger and after each later ledger update. It runs validate-findings.cjs in Phase 4 and again after every Phase 5 replacement.
The verdicts are distinct: confirmed has a complete source trace and bounded observed result, needs_validation has an exact unresolved fact and no severity, and rejected records a disproved candidate.
Multiple runs against the same repo are additive. The skill uses prior ledgers and findings to target gaps, revalidate changed source, and carry forward current-source evidence without treating stale or unresolved work as covered.
Install the skill with the Skills CLI:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
Use --global for a user-level installation:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit \
  --global
Run npx skills --help for agent-selection and non-interactive options.
Start your coding agent in (or pointed at) the codebase you want to audit, then ask it to do a security audit:
security audit this codebase
find security vulnerabilities in ./src
do a security review, output to ~/audits/my-project
The skill activates automatically when the request matches its trigger (security audit, find vulnerabilities, pen-test the code, etc.). A direct codebase audit or pen-test request uses full audit mode. Security questions and focused vulnerability work use guidance mode unless you request report artifacts. In full audit mode, an unspecified output directory defaults to ~/security-audit-skill/<repo-name>/run-<N>. The workflow writes inside the target repository only when you explicitly select a directory that version control ignores.
- A coding agent with a model that supports tool use and parallel sub-agents
- Node.js for the zero-dependency findings and coverage-ledger validators
- An OS-enforced sandbox for target-controlled builds, tests, processes, browsers, emulators, fuzzers, and fixtures. It must disable external networking, use a sanitized allowlisted environment, enforce resource limits, and allow writes only to assigned scratch paths. Without these controls, the workflow keeps the lead as needs_validation instead of executing target code.
- Only confirm established boundary failures. Keep a source-grounded blocked lead as needs_validation with its exact unresolved fact.
- Adversarial validation. The agent that checks a finding is never the agent that found it.
- Severity requires impact. Likelihood x impact, not deviation from a checklist.
- Defense-in-depth gaps are not vulnerabilities. If Layer A prevents the attack, the absence of Layer B is a hardening note.
- Multiple runs improve coverage. In our test runs, a single run found roughly half of the vulnerabilities that repeated runs found in total.
Questions, feedback, or comparing notes on AI-driven security tooling: security-ai-research@cloudflare.com

- Agent wrap — headroom wrap claude|codex|grok|copilot|cursor|aider|opencode|cline|continue|goose|openhands|openclaw|vibe|omp|zcode in one command; undo with headroom unwrap <tool>.
- MCP server — headroom_compress, headroom_retrieve, headroom_stats for any MCP client.
- Cross-agent memory — one shared store across Claude, Codex, Gemini and Grok, with automatic dedup.
- headroom learn — mines failed sessions and writes corrections to CLAUDE.local.md (default, gitignored), CLAUDE.md, AGENTS.md, GEMINI.md or GROK.md.
- Output token reduction — trims what the model writes back, not only what you send. See below.

Most software is riddled with bugs, which AI can now easily find and exploit. The standard defenses against cyberattacks are no longer sufficient: we need ways to prove that code is free of bugs. Formal software verification could provide this guarantee, but it has historically required years of expert effort, making it impractical for most real-world projects. In a collaboration with Theorem, however, we show this is no longer the case: LLMs can now produce formal proofs at large scale, enabling new software development workflows that include proven security guarantees. Introduction
Even mature, heavily tested software contains bugs, and LLMs are increasingly adept at finding them. The Linux kernel—one of the most well-tested pieces of software today, deployed on billions of devices worldwide—recently had over 1,000 vulnerabilities disclosed. With frontier models becoming more capable of chaining seemingly benign bugs into critical exploits, we need techniques that can detect and fix these bugs before they can be exploited in the wild.
Ideally, such techniques could find and patch all bugs, and then provide some proof that there are no more to be found. Formal verification is one way to do this. In formal verification, developers translate their code into a mathematical model, then try to prove that it always follows some defined set of security rules. If they fail to prove this, that means there could be a bug in the code that would violate a rule, and the nature of the failure implies what the bug might be. Repeating this process (after eliminating the cause of failure each time) will ultimately yield proof that the code is devoid of any bug that would violate those rules.
However, formal verification isn’t easy. Proofs can be many times larger than the original code, and writing them requires significant effort and a niche, highly specialized skill set. For instance, it took two person-years to implement the seL4 operating system kernel, but 20 person-years to formally verify it. Accordingly, formal verification has been practical only in truly mission-critical applications, such as Airbus’s avionics code.
But LLMs are making it far easier. Frontier models can now produce correctness proofs for real-world software fully autonomously. To demonstrate this, we asked Claude to prove useful security properties across 123 open-source libraries, including showing that some of their executable artifacts can never crash under certain conditions. Specifically, Claude proved that these programs will always exit normally without triggering memory-safety errors or failing assertions, for every input less than 64 MB and every modeled Linux operating system (OS) response and memory layout, under certain assumptions (namely that the program runs as a single-threaded static binary with a fixed memory budget on a RISC-V1 CPU using Linux OS). This is still far away from fixing all possible bugs, but it does get us much closer than before and provides a roadmap toward that end.
We’re publishing a subset of these proofs so that anyone can verify and reuse them, along with the RISC-V and OS semantics. Theorem, our collaborator on this project, is also offering to run the same pipeline for other open-source projects, and is publishing a Claude skill to help developers get started with verifying their own code.
Formal verification is a broad field with many methodologies. Below, we also describe our initial explorations using other formal verification methods to accelerate other security or software development tasks, such as assessing the security of the zlib compression algorithm, proving behavioral equivalence of a Python interpreter written in Rust, and rooting out long-standing bugs in critical software.
The road ahead for formal verification is promising. The cost of writing proofs is falling as models become more intelligent. Moreover, as more code is formalized and methods of achieving security guarantees become more standardized, the ability to reuse or modify proofs across codebases will amortize the cost. We encourage all developers to explore formal verification with LLMs—especially those who previously tried it with less capable models and found it didn’t work.

The engineering system surrounding an AI model increasingly determines whether its intelligence can be delivered reliably, economically, and at scale.
Provided byEXL
The next competitive advantage in enterprise AI has less to do with which model you choose than with what you build around it.
That’s an important shift. For the past several years, much of the AI conversation has centered on model capability: bigger models, better reasoning, larger context windows, higher benchmark scores. Those advances have been extraordinary. But as AI moves from experimentation to production, the question facing enterprise leaders has changed—it’s no longer, “what can the model do?”—it’s now, “Can we deliver that intelligence reliably, economically, and at scale?”
Increasingly, the answer depends on the serving harness—the engineering system surrounding the model, including the architecture, memory management, scheduling, and optimization decisions that determine how efficiently model intelligence becomes a production capability.
For technical executives, that changes where AI investment should go—and what they should demand from the architecture supporting it.
Start with the workload, not the model
There is no universally “best” model or AI architecture. There is only the right solution for the business problem.
A customer-facing assistant optimized for fast responses has fundamentally different requirements from a document-processing pipeline that can run overnight. An internal knowledge application and a high-volume customer service platform may use the same foundation model but require very different serving architectures.
The workload defines the constraints. The constraints should determine the architecture.
That sounds simple, but it runs counter to the way many organizations have approached early AI deployments. During a proof of concept, model accuracy naturally dominates the discussion. Production introduces constraints that are much easier to ignore when only a handful of users are involved: latency, concurrency, memory pressure, GPU utilization, infrastructure cost, and unpredictable traffic.
A model that produces marginally better answers is not necessarily the better production choice if it doubles inference costs or cannot meet the application's latency requirements. Not every workload needs a Ferrari. Sometimes the smarter engineering decision is the model that delivers exactly the performance the business needs without paying for capability it doesn't.
The objective should be to deploy the right intelligence at the right cost for the workload. That makes serving architecture more than an engineering concern. It becomes an investment decision: where to spend on compute, where to optimize, and where additional model capability simply isn't worth the cost.
Engineer the system, not the model
Once AI reaches production, seemingly isolated engineering decisions begin affecting one another. Serving architecture influences memory utilization. Memory management affects concurrency. Concurrency shapes batching and scheduling, and scheduling affects GPU utilization and latency.
Only then can techniques such as quantization, speculative decoding, or optimized attention mechanisms deliver their full value. This interdependence matters because organizations can spend considerably more on infrastructure without solving the constraint limiting performance.
GPU memory is a good example. During inference, the model's weights remain fixed, but the key-value (KV) cache grows with active requests and context length. As concurrency increases, a system can run short of usable GPU memory even when compute capacity is still available. Adding more compute without understanding that bottleneck may simply make an inefficient system more expensive.
The lesson for technology leaders is broader than memory management: Measure before you optimize. Identify the dominant constraint. Address it. Measure the result. Then determine if another bottleneck emerged. Repeat.
Don't think of optimization techniques as Pokémon cards: The goal isn't to collect them all. The goal is to apply the technique that removes the highest-impact constraint while preserving the application's business requirements.
For technology leaders, that demands a different governance question. Instead of asking which AI capabilities the organization can deploy, ask which constraints stand between a proven capability and sustainable business value.
Build for change, not today's benchmark
Perhaps the most important reason to invest in the serving harness is that today's leading model will probably not be tomorrow’s. Models will improve. Hardware will evolve. New optimization techniques will emerge. The architecture surrounding them should make those changes easier to absorb, not force the enterprise to rebuild its AI platform every time technology advances.
That makes adaptability an increasingly important outcome of AI strategy.
Organizations that build serving systems around workload requirements, clear service-level objectives, and measurable production economics gain the ability to evaluate new models and infrastructure against what the business actually needs. A model change can become an evaluation and configuration decision rather than an architectural reset.

The model provides the intelligence. The harness determines whether the enterprise can deliver outcomes reliably, economically, and at scale.

Three things you should know about permafrost
A primer on this crucial and frankly mysterious piece of climate science.
How much do you know about permafrost?
Maybe, like me, you’ve been aware that this layer of frozen soil is thawing, that it’s important in the global puzzle of climate change … and that’s about the extent of it.
The great news for both of us is that my colleague James Temple just published two in-depth stories about permafrost. His reporting took him to the boreal forests of Alaska, where he helicoptered into the wilderness to learn more about how this material could affect our climate both now and in the future.
I’d recommend you give both of James’s stories a read. There’s this feature about efforts to tackle the intensifying fires that are threatening permafrost, as well as this look at how researchers are trying to understand the complicated tangle of potential climate effects. Here are three things I took away.
Permafrost is a massive blind spot for climate change
Permafrost is the frozen layer of soil that’s under about 15% of land around the Northern Hemisphere. While technically material needs to be frozen for only two consecutive years to count as permafrost, most of our current permafrost formed during the last ice age.
That means there’s organic material that’s been frozen, and essentially locked away, for thousands of years. But as global temperatures tick up and this layer thaws, microbes are able to break down that organic matter, releasing carbon dioxide and methane—powerful greenhouse gases that drive climate change. Those emissions form a feedback loop, accelerating warming further.
The steady rise in global temperatures has already shrunk the footprint of the Arctic permafrost by about 12% since 1850, and the pace has been picking up in the last 50 years.
The wild thing is, only a minority of the models that have been used in UN climate reports actually take into account the gradual loss of permafrost. And none of them include the abrupt thaw and collapse that can happen after events like heat waves and fires (more on those fires in a moment). There are efforts to make sure future UN reports reflect the growing science, but for now, all this means that we’re probably underestimating how much and how fast the planet is going to warm.
Wildfires can speed up permafrost loss
Fire is a natural part of boreal forests’ life cycle, but they’re getting more intense because of climate change. And crucially, fires can accelerate the thawing of permafrost. By the end of the century, this effect could release the equivalent of 80 billion metric tons of carbon dioxide.
Today, the policy across remote parts of Canada and Alaska is generally to let wildfires burn as long as they’re not threatening human habitats. But some researchers say we should explore fighting these fires to save the carbon trapped in the forests and the permafrost beneath them.
Researchers at the Woodwell Climate Research Center are developing a map of burn risk and carbon vulnerability across Alaska, essentially highlighting areas where fires are most likely to spread and which areas are home to certain types of permafrost that would release the most emissions. (Yes, apparently there are different types of permafrost. Yedoma is a particularly deep, carbon-dense form from the late Pleistocene era.)
That’s all just the beginning—once we figure out potential targets, the question is what to do about it. Some suggest setting more prescribed fires, something Indigenous groups have done for thousands of years, partly to reduce the danger of massive blazes. Or resources could go to early detection and efforts to put out fires before they grow.
The carbon cycle of permafrost is incredibly complicated
There’s about 1.5 trillion tons of carbon locked away in permafrost, about twice the amount in the atmosphere. We know that permafrost thawing can release greenhouse-gas emissions and drive climate change. But there are complications.
One particularly big wrinkle: Other effects from permafrost thawing and fire recovery might counteract the carbon lost from those events. For example, as temperatures warm, plants can gradually move north and take hold where they couldn’t have before. Those plants soak up carbon from the atmosphere as they grow, at least partly locking away what was emitted.
Researchers are working to better understand this ecosystem. And the more we learn, the more complicated the picture looks. How much carbon is lost from permafrost, and how much a given area will recover its carbon, depend on a huge array of factors. How severe are the fires that have accelerated local thawing? What’s the local climate and environment? And what kind of permafrost is at stake?
The higher we push the planet’s temperature, the more we mess with complicated natural phenomena that we’re only beginning to understand.

            Abstract:This study proposes a sketch-to-simulation system to solve handwritten circuit diagrams. The system converts raw images into a Simulation Program with Integrated Circuit Emphasis (SPICE)-compatible netlist and automatically calculates the circuit's nodal voltages and currents. Another objective is to propose a holistic framework that benefits students and educators by enhancing the teaching and learning experience of electric circuits and expediting engineering design reviews. This article presents a multistage pipeline that converts raw photographs of handwritten electric circuits into executable SPICE-like netlists, providing a solution. A dataset of 1,000 hand-drawn Resistor-Inductor-Capacitor (RLC) circuits was curated and annotated for components, text regions, and character recognition. The proposed system decomposes a circuit diagram into three stages: (i) dual You Only Look Once (YOLO)-based detectors for components and text regions, (ii) a Convolutional Recurrent Neural Network (CRNN) with Connectionist Temporal Classification (CTC) and Optical Character Recognition (OCR)-based domain-aware symbol value extraction, and (iii) image processing with thresholding, skeletonization, and Density-Based Spatial Clustering of Applications with Noise (DBSCAN) to automatically identify nodes and map them with corresponding components. The proposed system produces the netlist and solves the circuit. The qualitative and quantitative ablation studies on modular stages, as well as end-to-end tests, demonstrate robust performance across various handwriting styles, lighting conditions, and this http URL study serves as an interactive learning aid and practical tool for professionals, providing a comprehensive user interface (UI), enabling rapid digitization of circuit sketches for study, design, prototyping, or troubleshooting.

Title:Speedrunning Relational Foundation Model Pretraining
View PDF HTML (experimental)
            Abstract:Progress on foundation model pretraining is gated by who can afford a trial, and relational pretraining is no exception. Recipes are developed inside individual labs, reported under private protocols, and do not accumulate. Speedrun leaderboards remove that barrier by decentralizing the search rather than the training run. The problem is fixed, the stack is open, entries are ranked by wall-clock time to a quality target, and one GPU is enough to hold the record. We introduce modded-nanoRT, the first such leaderboard for Relational Transformers. Which database to hold out decides whether the benchmark can resolve improvements at all, so we fix it by calibration, ranking six candidates by how sharply a 45-minute learning curve separates improvement from seed noise. We open the leaderboard with typed trilinear attention, a relational operator that conditions attention scores and values on the foreign key traversed, together with Muon and SIGReg. The recipe reaches the target in 305.63 seconds on one NVIDIA H200, 8.11x faster than the reference implementation, and wins 13 of 15 pairs outside the development database. We will release the benchmark, its frozen artifacts, and the record runs. Our code is available at this https URL.

A powerful gene-editing technique has been used to edit DNA directly in a person’s body — the first known instance of such a treatment.
The milestone treatment is part of a clinical trial of prime editing, a technique that can alter DNA with more precision than standard CRISPR–Cas9 methods can. In this case, prime editing was used to treat a condition called Wilson disease by rewriting DNA in liver cells, to erase a mutation that prevents them from eliminating excess copper.
Prime Medicine, a biotechnology company in Cambridge, Massachusetts, announced that it had treated the first person in its trial earlier this month. It expects to announce the first results from the study next year.
“I never dreamed that in my lifetime I would see this applied to my rare disease,” says Rhonda Rowland, president of the Wilson Disease Association in Atlanta, Georgia. “It’s going to be a really exciting year.”
In launching the trial, Prime Medicine joins a host of companies aiming to engineer cells directly in the body, rather than using the standard method of extracting a person’s cells, editing their DNA in a laboratory and then reinjecting the altered cells. Rewriting DNA in the body, or in vivo, is appealing because manufacturing and administering the treatment might be much cheaper and faster than making a bespoke therapy for each person from their own cells.
But in vivo approaches have their own challenges, says Krishanu Saha, a biomedical engineer at the University of Wisconsin–Madison. “It depends on what types of risks you’re willing to accept,” he says.
Prime time
Wilson disease is caused by mutations in a gene called ATP7B, which encodes a protein that transports excess copper out of the liver. If left untreated, the resulting build-up of copper can cause liver and nerve damage, as well as neurological disorders.
People with Wilson disease are eager for a one-and-done treatment for their condition, says Rowland, rather than the current, complicated regimen of copper-clearing molecules and other medicines. And gene editing could, in theory, provide a lasting solution by correcting the faulty ATP7B gene.
So far, the US Food and Drug Administration (FDA) has approved only one gene-editing therapy, called Casgevy, which is used to treat two inherited blood disorders. Casgevy relies on CRISPR–Cas9 gene editing, which is often used to disable genes rather than to rewrite their sequences.
Another form of gene editing, called base editing, can rewrite individual DNA letters, but cannot make the particular corrections needed to fix the most common ATP7B mutations. That left prime editing, a more complex and versatile system that can insert, delete and rewrite segments of DNA. In another clinical trial, Prime Medicine used the technique to treat two people with a rare immune disorder, by rewriting DNA in each participant’s blood stem cells outside of the body and then injecting them back in.
So far, no gene-editing therapies have been approved for use in vivo. But the FDA is expected to issue a decision early next year about an in vivo CRISPR–Cas9 therapy for a condition called hereditary angioedema, which causes severe swelling.
