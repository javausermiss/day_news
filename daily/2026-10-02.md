New in OpenShell 0.1.x: a stable release cadence, new isolation primitives, an expanded extension surface, and new APIs. Read the 0.1.0 upgrade guide.
OpenShell is the safe, private runtime for fleets of autonomous AI agents. Agents are most useful when they can read files, install packages, call APIs, and use credentials. OpenShell gives them that capability without giving them unrestricted access to your data, secrets, or network. You declare what each agent can touch in a policy, and OpenShell enforces it.
OpenShell governs what agents can do in two ways: it instruments the kernel to enforce policy on every file access, system call, and network connection at runtime, and it uses formal verification to check what a policy change would allow before it is applied.
- Kernel-level enforcement. Each agent runs in an isolated sandbox. Kernel controls confine which files it can access and which system calls it can make, and every network connection passes through a policy check before it leaves the sandbox. Agents never see real credentials; OpenShell adds them only to requests bound for approved endpoints.
- Formally verified policy changes. Before a policy change is approved, OpenShell uses formal verification to flag risky new access it would grant, such as reaching a new host with credentials or calling a new API method, so those changes wait for human review.
See Architecture for how the gateway, supervisor, and sandbox fit together.
You need Linux, macOS on Apple Silicon, or Windows with WSL 2 (experimental), plus Docker, Podman, or host virtualization. See the Support Matrix for details.

The other half of the context problem.
Every MCP tool call dumps raw data into your context window. A Playwright snapshot costs 56 KB. Twenty GitHub issues cost 59 KB. One access log — 45 KB. After 30 minutes, 40% of your context is gone. And when the agent compacts the conversation to free space, it forgets which files it was editing, what tasks are in progress, and what you last asked for. On top of that, the agent wastes output tokens on filler, pleasantries, and verbose explanations — burning context from both sides.
Context Mode is an MCP server that solves all four sides of this problem:
- 
Context Saving — Sandbox tools keep raw data out of the context window. 315 KB becomes 5.4 KB. 98% reduction.
- 
Session Continuity — Every file edit, git operation, task, error, and user decision is tracked in SQLite. When the conversation compacts, context-mode doesn't dump this data back into context — it indexes events into FTS5 and retrieves only what's relevant via BM25 search. The model picks up exactly where you left off. If you don't --continue , previous session data is deleted immediately — a fresh session means a clean slate.
- 
Think in Code — The LLM should program the analysis, not compute it. Instead of reading 50 files into context to count functions, the agent writes a script that does the counting and console.log() s only the result. One script replaces ten tool calls and saves 100x context. This is a mandatory paradigm across all 17 supported clients, plus the OpenClaw gateway integration: stop treating the LLM as a data processor, treat it as a code generator.// Before: 47 × Read() = 700 KB. After: 1 × ctx_execute() = 3.6 KB. ctx_execute("javascript", ` const files = fs.readdirSync('src').filter(f => f.endsWith('.ts')); files.forEach(f => console.log(f + ': ' + fs.readFileSync('src/'+f,'utf8').split('\\n').length + ' lines')); `);
- 
No prose-style enforcement — context-mode keeps raw data out of context but never dictates how the model writes its final answer. Brevity, completeness, formatting — your model's call (or yours via your own CLAUDE.md /AGENTS.md ). Aggressive brevity prompts have been shown to degrade coding/reasoning benchmarks (Moonshot AI onkimi-k2.5 ) — the routing block stays focused on where data goes, not on how the model talks.

The rule was never "fewest tokens." It is: write only what the task needs, and never cut validation, error handling, security, or accessibility. Lower cost and latency are a side effect on the models that follow the ladder; a terse reasoning model that spends thinking tokens deliberating the rungs can go the other way (on GPT-5.5 it does).
Before writing code, the agent stops at the first rung that holds:
1. Does this need to exist?   → no: skip it (YAGNI)
2. Already in this codebase?  → reuse it, don't rewrite
3. Stdlib does it?            → use it
4. Native platform feature?   → use it
5. Installed dependency?      → use it
6. One line?                  → one line
7. Only then: the minimum that works
The ladder runs after it understands the problem, not instead of it: it reads the code the change touches and traces the real flow before picking a rung. Lazy about the solution, never about reading.
Lazy, not negligent: trust-boundary validation, data-loss handling, security, and accessibility are never on the chopping block.

Wed 30 Sep 26
A bird attacking a butterfly will often find its beak snapping at thin air.
According to new research, that split-second miss isn't just bad luck. It's caused by a visual illusion from the butterfly's wings.
The new study – published in the journal Nature, by the University of Exeter and the University of Essex – provides the first evidence that a butterfly's flight and wing pattern work together to create powerful visual illusions that scramble a predator's sense of speed and direction, making them misdirect attacks.
It helps solve a long-standing puzzle - butterflies have striking patterns that make them stand out, yet remarkably few predators specialise in catching them mid-flight.
Moths, by contrast, are hunted by a wide range of visually guided aerial predators.
"The stripes and spots on many butterflies’ wings interfere with the way visual systems try to guess the direction and speed of moving things, boosting false motion cues while hiding the butterfly's true heading," said Dr George Hancock, from the University of Exeter's Centre for Ecology and Conservation on the Penryn Campus in Cornwall.
"The illusions interfere with the predator’s most basic visual targeting system and disrupt the final ‘ballistic attack’ in the tens of milliseconds when it commits to grabbing its prey, with no time to change course.
"As a result, birds and other predators will often simply miss."
Dr Anna Hughes, from the Department of Psychology, at the University of Essex added: "Butterflies’ beautiful wings are not just for show, they are vital for survival.
"Our brains – and those of other animals - don’t always interpret visual information perfectly, leading to illusions.
"We show this might have important consequences in the natural world, and in particular for butterflies, their striking patterns may have evolved to create confusing motion signals when in flight, making it difficult for predators to make accurate attacks."
The underlying mechanism works much like the 'barber-pole illusion' – the red-and-white striped pole outside barber shops, where the stripes appear to travel upward even though the pole is only spinning in place.
"Butterfly wings deform as they fly – clapping together on the upstroke and peeling apart on the downstroke – so their stripes shift angle and point in different directions as they flap," said Dr Jolyon Troscianko, also from the University of Exeter.
"Combined with their unpredictable flight paths, this patterning creates misleading motion illusions just like the barber-pole, causing a predator to miss entirely, or to strike a less vulnerable part of the wing, such as the hindwing or tail.
“The first slow-motion video of a butterfly I put through our bird-vision computer model was glowing with downwards motion even though the butterfly was moving up.
“First I checked this wasn’t a coding error, that I’d swapped up and down somehow, but then it dawned on me that this would be a perfect way to confuse attacking predators.”
The team combined multiple lines of evidence. They used a high-speed camera to film real butterflies taking off at over 1,000 frames per second to capture how their patterns behave in flight, as seen through the eyes of a bird.
They then looked at the patterns of around 400 European butterflies and found that motion illusion patterns are widespread.
To test how patterns affected real attacks, 100 volunteers acted as “predators”, trying to catch virtual butterflies on a touchscreen.
Finally, they used a computer simulation to “evolve” over 50,000 wing patterns from random starting points, selecting for patterns that created the most motion confusion.
Patterns converged on designs strikingly similar to those found in nature, suggesting that this illusion is a major force shaping butterfly wing evolution.
"It might seem strange that a butterfly would evolve to be so visible, especially as very few European species are toxic or unpalatable," Dr Hancock said.
"But our study reveals the wide variety of different patterns butterflies can use to create illusions that confuse predators."
Butterflies and moths are also well known for using camouflage while resting, but movement breaks camouflage.
This study shows how, once airborne, highly visible butterflies evolved their colours for a completely different line of defence to solve that problem.
"The dazzling stripes on zebras and snakes have long been suspected of confusing predators' motion perception, but firm evidence has been hard to come by," said Dr Troscianko.
"Our study gives us a genuinely new way to analyse motion vision, and we think motion confusion is likely to be far more widespread in nature than previously realised, from the flapping wings of birds to the flicking tails of lizards and fish. It opens up an exciting new research avenue."
The study was funded by the Biotechnology and Biological Sciences Research Council.

Peeking into the brain
Neuroscientists have been working for years on ways to use functional magnetic resonance imaging (fMRI) to reconstruct what people see and what’s going on in their minds. The first attempts produced images that were blurry and hard to make sense of. Advances in technology—both in the fMRI scans themselves and in the tools used to make sense of the results—have led to improvements over the years.
Irani and her colleagues started by analyzing publicly available brain-scan data. Other researchers had already collected scans from volunteers who were shown hundreds of images while they lay in fMRI scanners.
fMRI uses a giant magnet to track the flow of oxygenated blood through the brain. Brain areas that “light up” on the scans are thought to be those that are particularly active at any given moment. The results are not especially specific—in typical fMRI scanners, each highlighted “voxel” of activity covers around three cubic millimeters, containing around 16,000 neurons.
But Irani and her colleagues used newer datasets collected using scanners with a higher resolution—each voxel covered around one cubic millimeter of neurons, she says. Those datasets showed what the brain activity of volunteers looked like when they viewed various images.
Other teams have done this too, and several other tools have been used to re-create images from brain-scan data. But they’re not good enough, says Irani. Say a person saw a banana. These models can generate an image of a banana, but it would look different, she says. “It wouldn’t have the same structure, the same position.”

The researchers wanted to more closely re-create the images that had been seen. The first step was to train an AI model on already available data from eight people who each had been shown around 9,000 images while in a high-resolution fMRI scanner.

But to improve the models they needed more data—far more than was actually available.

Bungie 就是在这个时候开窍的。随着《遗落之族》拓展包内不断有新内容产出，Bungie 逐渐明白了作为开发者该怎么处理一款持续运营的、服务型游戏的内容，《遗落之族》结合了《D1》中那些广受好评的游戏模式，同时加入了充实的主线战役内容和限时的活动内容，最大的不同是，《遗落之族》在发布后仍会有接连不断的小内容更新，这些小型更新填补了在下一个大型资料片到来之前玩家游玩的空档期，不至于在主要大型更新发布后出现留存不住玩家的状况。
很多在这个时候推出的游戏模式，后来也成为了奠定《D2》活动内容的基础，这种短小而快速的更新使得更多玩家回流。《D2》的开发者们也意识到了一件事：更新的速度很大程度上决定了一款服务型游戏留存玩家的多少，玩家游玩内容的速度永远是比预计的速度要快的，因此游戏内要么有足够深度的内容，要么就源源不断地推出新内容来满足玩家的新鲜感。《遗落之族》在当时都做到了。
这便是「火车站理论」的核心，Bungie 从一个提供盒装产品的游戏工作室变成了一个线上服务团队。如果把《D1》的开发比作制造一辆火车，那么自《遗落之族》后，Bungie 的工作就更像是在维护一个火车站。以单机游戏的思维来看，我们需要出厂前把每一辆火车都制作得好，给他们用上最好的引擎、涂上最好的车漆、配上最华丽的装潢，然后擦亮每一个可以看见的部位，以便让它在开出去后可以行驶得更久一点。但如果以火车站的思维去思考问题，会发现一辆装配精良但有可能延期发出的火车，其实也会打乱整个火车站的时刻表，甚至与其他车辆相撞。
为了火车站的良好运行，必须先把准时发车放在第一位。车辆出发比车辆本身质量要重要。停掉整个火车站去修好一辆故障的火车的行为只会让情况更加雪上加霜。而 Bungie 宁愿让玩法趋于无聊甚至崩坏，也要让赛季和资料片按时发出。据 Justin 所言，依靠这种「让带有风险的火车驶出车站」的策略，游戏吸引了越来越多的玩家，也让当时的《D2》走到了第 16 赛季。
事实上，一直到第七个资料片《终焉之形》结束，Bungie 都是这么做的。是的，在公司报表和商业创新上，这个概念算得上是空前成功，可 Bungie 越来越忽视了一款游戏首先需要经过玩家的检验，而非董事会的老爷们的睥睨。
恶魔谎言
一个不起眼的东西，但在运用得恰到好处时，造成的损害能让你瞠目结舌。

Matrix 首页推荐
Matrix 是少数派的写作社区，我们主张分享真实的产品体验，有实用价值的经验与思考。我们会不定期挑选 Matrix 最优质的文章，展示来自用户的最真实的体验和观点。
文章代表作者个人观点，少数派仅对标题和排版略作修改。
2Do 于今年 8 月推出了全新版本，新版本的 2Do 并没有抛弃之前版本高自由度这个特点，甚至自由度更高了；同时还彻底换上了现代化的界面设计，并加入了诸多顺应时代潮流的实用功能。
在经历了一个多月的深度使用后，我想借这篇文章，与大家聊聊现代重构后的 2Do。本文将以 macOS 版本为主，并简单提及部分 iOS、iPadOS 上的特色功能，希望可以带大家了解我心目中最佳的任务管理工具。
不只 UI 升级，2Do 交互里还有这些新变化
作为一款诞生已有十余年的老牌 macOS 原生效率工具，2Do 在重构之前带有非常明显的拟物和早期扁平时代的设计风格。尽管旧版本在功能上已经非常丰富了，但密集的控件排布、偏灰暗的配色以及逼仄的空间间距，让它在近年来的 macOS 系统中显得格外陈旧。
新版最大的改变，就是通过大幅加入留白、清晰的模块分割，让 2Do 的整个界面现代了起来。在整体架构上，2Do 还是比较经典的三栏式布局：左侧为列表与智能筛选器、中间为任务主列表、右侧则是标签和地理信息面板。
更加自由的显示逻辑
在 UI 更新的同时，2Do 还加入了大量可调节的视图选项。
左侧边栏支持折叠，这样当我在「今天」或特定列表的时候，可以收起侧栏，来最大程度减少视觉干扰。
新版支持为浅色与深色模式独立配置不同主题，并开放了字体大小、行间距与内容密度等比较细节的 UI 调整。当然，老版本里我最喜欢「友好相对日期」「逾期任务标红高亮」等经典开关也依旧存在，可以根据喜好自由调整。
如果你习惯结合日历来规划时间，新版引入的日程负担可视化（Busy Days）功能也非常实用。它可以在日期选择器、迷你日历和日历栏中，根据已有日程的密集程度显示忙碌热力图，让我在为任务设定日期时就能提前判断当日的精力情况，提前避开排期冲突。
对于喜欢极简界面的用户，你还可以在设置中关闭「始终显示标签」，此时任务列表中的标签会被折叠为一个小图标；当你需要临时确认任务的标签属性时，只需长按键盘上的 Option ，所有隐藏的标签就会实时显示出来。
桌面平台不可或缺的独立多窗口
此前在使用 Apple 自带的「提醒事项」时，最让我困扰的一点就是，普通列表支持在独立新窗口里打开，但智能列表不行，导致多场景筛选任务的时候必须在不同视图间反复来回跳转。在过去，老版本的 2Do Mac 端同样受限于单窗口逻辑。
在这次重构中，2Do 带来了原生的多窗口支持。
通过快捷键 Control-Option-Command-N，我可以随时从当前视图快速新建出一个独立窗口。不仅在编辑时跨项目、跨列表的任务时，能更容易比对；还能让我在一个窗口中固定「今天」、一个窗口显示其他的智能过滤视图，另一个窗口依然可以进一步拆解项目中的子任务，来加速完善 GTD 的后续流程。
得益于多窗口，2Do 也引入了拖拽交互。现在我可以在不同窗口之间自由拖拽任务，直观批量地管理任务。
又比如，我可以把任务直接拖入侧边的日历栏，批量重新分配任务的到期日。我还可以把任务拖向顶部工具栏的相应按钮，实现推迟、复制、分享或是删除任务。整个体验和经典的 OS X 上的 Finder 几乎一模一样。
移动平台：保留经典手势，补齐现代功能
在移动端，新版 2Do 在翻新 UI 的同时，依旧采用了其标志性的三栏滑动交互。只需简单的左右轻扫，就能在「完整列表」「半列表+任务视图」「纯任务列表」和抽屉式的全局标签、地理位置过滤与日历视图之间切换，符合直觉的同时，切换视图也不依赖反复点击。
当然我之前很喜欢的「双指捏合调节视图密度」功能在新版里也在，在屏幕上双指捏合缩放，就可以在「紧凑」「标准」与「详细」三个显示密度之间切换，实时调整标题行数、是否显示标签、备注摘要和所属列表等任务信息的丰富程度。
这次重构后的移动端也基本适配了现代 iOS、iPadOS 上的锁屏小组件、控制中心快捷入口和多尺寸桌面交互小组件，这样 2Do 在应用外的体验也变得更完整了。
灵活可靠的使用方式
一直以来，2Do 就以高度自由的组织维度和极为详尽的任务元数据著称。它从不强制用户遵从某种使用流程，无论是标准 GTD、时间块还是最简单的清单，每个人都能在 2Do 中搭建出一套最适合自己的任务系统。
正因其系统的庞大与灵活，即便在全面重构后，也很难完整梳理它全部的能力。接下来，我将借由经典的 GTD 工作流脉络，为大家梳理新版 2Do 中最值得关注的新功能。
更自然的收集流程
在 GTD 理念中，一切高效流转的前提是「无阻力地收集任务」。
虽然过去 2Do 任务的属性非常丰富，但如果每次新建任务都要停下来逐项点击选择列表、时间、标签，还是很麻烦的，而且也容易在设置属性的过程中漏掉一闪而过的念头。
新版 2Do 终于支持了自然语言识别。虽然理论上我们只需像日常打字一样直接输入完整的句子，2Do 就能在标题栏中实时高亮并解析出关键信息，不过实际使用中还得用一点标记来帮助 2Do 解析：
- 时间与日期：支持「今天」「下周五」「3 天后」等相对日期，支持识别如 15:30 的具体时间点，也支持10 月 20 到 22 日 这样的时间跨度；对于周期性事项，直接输入「每周」「每隔两周」就可自动转换为重复任务；
- 任务预估时长：用方括号包裹时间，如 [2h] 或[30m] 即可设定预计用时；
- 提醒设置：输入 alert 30m 即可配置提前提醒（但中文版 2Do 似乎不能正常识别）；
- 优先级与星标：输入 ! （或!! 、!!! ）标记优先级（我个人是拿来标记任务需要消耗的精力的），输入* 设为星标；
- 维度：通过 /工作 指定列表，#写作 添加标签，@办公室 设定地理位置。
如果你在任务标题中确实需要包含某些关键词，只需用双引号将其包裹（例如输入读 《“明天”》），2Do 就不会把明天误解析成时间。
在碎片化任务录入上，2Do 也做了打磨。一个是快速连续录入，在 iOS 上长按右下角「+」即可进入连续输入模式；在 macOS 端，通过shift-cmd-2打开「快速录入」面板，设置完毕后再次按下快捷键，2Do 会立即保存当前任务并清空输入框，等待下一条输入。这非常适合在会议结束或头脑风暴后，批量记录待办的情况。
另一个就是，新版 2Do 彻底重写了邮件收集机制，放弃了老版本依赖本地客户端收信转待办的旧方式，改为了云端邮件转待办。开启后，2Do 会为每个客户端分配一个专属的私有转发邮箱地址。
这样就能在不支持 2Do 的设备上，通过邮件将必要信息转发至该地址，2Do 便会自动在后台生成待办任务。
其中，邮件主题作为任务标题，正文自动转为详细备注。邮件主题中还支持通过 due(tomorrow)、list(Work) 等括号语法直接指定属性，也可以在正文使用数字序号直接生成子任务清单。
更完善的过滤机制和任务组织逻辑
在我看来 2Do 最独特的地方，就是它的元数据组织能力。重构后的 2Do 进一步强化了过滤与搜索逻辑，让复杂任务的筛选与呈现变得更自由了。
在以往，OR（或）逻辑只能在同一个维度内部生效（例如 tags: 手机 OR 电脑、locations: 家 OR 公司），而不同维度之间只能进行 AND（与）找交集，其实极大地限制了构建高级智能列表的能力。
而在新版中，2Do 终于支持了全维度的括号嵌套与跨维度 OR。你可以轻松写出诸如：
lists: Work AND (type: overdue OR type: starred OR type: hiprio)
这样的高级规则，将工作列表中所有「已逾期」「带星标」或「高优先级」的要紧事一并提炼出来，把针对工作上的急事或者要事提前筛选出来。
新版 2Do 也新增了针对列表和标签组的范围限定语法。过去我们只能在「单选特定列表」或「全局所有列表」中进行搜索，现在可以自由组合多个指定列表（如 lists: (工作, 个人项目)），在跨项目协作或特定阶段的复盘中尤其好用。
在检索时，我们也可以根据需要开启或关闭「搜索继承」。关闭后，即便子任务符合筛选条件，也会默认显示其所属的父项目。结合 2Do 经典的「标签暂停」功能，临时屏蔽某些特定情境下的非紧急标签，灵活地根据当下的精力状态、所在地点或项目周期，动态切换视图。
新版 2Do 对任务内部的笔记编辑器进行了不少升级。支持完整的 Markdown 语法排版。当任务在收集初期背景复杂、材料琐碎时，我可以毫无顾虑地把背景、信息、列表等长篇信息一起保存到笔记里，用于后续的拆解。
笔记编辑器也支持在笔记中通过 @{任务名称} 语法实现跨任务的双向关联。比如在整理菜谱或家务清单时，遇到缺少的耗材，可以直接双向关联到购物列表中的具体采购项，建立清晰的上下文。只不过我有点不理解，为什么 2Do 没有选择相对更通用的 Wiki-style link 语法 [[另一个任务]] ，@{…} 还是有点反肌肉记忆的。
当任务笔记中包含大量参考资料、网页链接，或是指向其他本地 App 的 URL Scheme（如 DEVONthink、Obsidian 等）时，2Do 会在侧边自动生成一个提取面板，所有外链一目了然，点击即可直接跳转，无需在长篇笔记中反复翻找。
为了提升日常查看与切换的效率，2Do 也引入几个新功能。首先是新增了一个「快速打开」面板，Shift-Cmd-O或者在 iOS 上点击任务列表顶部的当前列表名称，就会弹出一个类似 Spotlight 的窗口。默认情况下，会显示最近修改的任务以及最近访问的列表，输入字符即可搜索任务和列表，点击即可跳转。
此外，在 macOS 上，还可以用快捷键 J展开 List Jump Bar，会在列表面板底部出现一个搜索栏，输入列表名时不会弹出独立窗口，而是直接在侧边栏中高亮匹配项；折叠的列表组也会临时展开，用上下方向键可以在结果之间移动，回车直接切换过去。除了匹配列表和智能列表， List Jump Bar 还会匹配展开在列表下面的项目和清单。
最后，在 macOS 和 iPadOS 上的 2Do 还支持用 Cmd-0~5 快捷键在收件箱、全部、今天、星标和已完成这几个内置列表里快速切换。
全面重构的同步引擎
新版 2Do 依然选择了完全开放的后端策略，用户可以根据自己的喜好选择最适合自己的同步方式。
老版本 2Do 所谓的 iCloud 同步本质上基于旧式的 iCloud CalDAV 协议，不仅需要用户前往 Apple 账户手动生成复杂的 App 专用密码，而且受限于 CalDAV 协议本身的结构，根本无法同步智能列表、列表组、标签组以及任务附件等核心元数据；想要获得完整的全功能同步，老用户当年唯一的选择只有 Dropbox。
得益于从底层完全重写的同步引擎，带来原生的 iCloud 同步与 Apple 提醒事项双向同步功能，并预告了基于 WebDAV 的完全同步。
对大多数 Apple 生态用户来说，新版最省心的无疑是原生的 iCloud 同步。可以直接使用 OS 内置的 Apple 登录，不仅彻底免去了手动配置专用密码的繁琐，还能完整无损地同步智能列表、标签组以及各类附件。
如果你想在 2Do 不支持的平台同步提醒事项的话，Apple「提醒事项」双向同步和新版的 Todoist 也是值得考虑的选择，它们能帮你轻松把任务同步到 Windows、Android 或者网页端。
比如借助 Apple「提醒事项」同步，你还可以在 iPhone、Apple Watch、HomePod 甚至车载 CarPlay 上直接用 Siri 随手记任务；而通过 Todoist，则能在更多平台上查看和勾选待办。
不过因为这些第三方平台本身不支持 2Do 那么复杂的数据结构，所以像标签组、附件这类高级元数据是无法直接同步过去的。2Do 的解决办法是把部分不支持的属性以明文的形式直接写入到任务备注里，保证数据能够正常同步。但不同的第三方同步可以保留的数据不一样，还是得酌情使用。
此外，2Do 依然可以用经典的 Dropbox 同步，并预告了后续会支持 WebDAV。
如果你只是想和家人或同事进行小范围协作，甚至可以直接通过局域网把特定的列表共享给同一 Wi-Fi 下的其他人。
平台特性

Matrix 是少数派的写作社区，我们主张分享真实的产品体验，有实用价值的经验与思考。我们会不定期挑选 Matrix 最优质的文章，展示来自用户的最真实的体验和观点。

我是典型的 J 人，出行前不做攻略，心里就没底。说走就走听着潇洒，放到国庆这种大日子，往往会变成灾难：酒店价格临时翻倍，热门演出早就无票，博物馆根本约不上号……除非你愿意用金钱为这份潇洒买单，我可是舍不得。
往年做攻略最烦两件事。一是信息太乱，十几个标签页开着来回切，同一个地方不同笔记的说法对不上，营业时间、门票政策各说各的，只能一条条点进去核对，遇到说法矛盾的时候尤其耗费心力。二是我一直用 Notion 记行程，重要节点没有问题，但细节的呈现始终不够理想。
今年国庆，一家四口从山西自驾去河南，往返七天，带着两位老人，开着新能源车。这次做攻略，查资料、对信息这些体力活都交给了 Agent，很快攻略就成型了；过程中还用上了小红书自带的 AI 助手「点点」，帮我发现不少有用的信息。文末附上融合了我个人理念的提示词，复制就能开聊，着急的同学可以直接拉到最后（但希望你不着急）。
这篇文章，想和大家完整拆解我的具体做法与实操思路。文章很长，可以收藏再看。
理念
做攻略，本质上是一项高密度的信息处理工作：从海量的笔记、攻略和官方政策里，准确筛选出真正能够辅助决策的那一小部分。
不少人使用 AI 做攻略，习惯一句话丢过去：「从X出发，去Y玩Z天，帮我做份攻略。」Agent当然能交出一版像模像样的行程，但如果你直接照单全收，效果往往不尽如人意。这种一键生成的短板非常明显：
- 忽略人的生理极限：计划往往从早排到晚，毫无喘息空间；
- 时空计算脱离实际：对假期的路况、景区的实际排队时间以及城际车程算得极不准确；
- 极度缺乏深度落地的能力：尤其在酒店与餐饮推荐上，它一般只能定位到模糊的大区域，一旦涉及到具体房型、真实性价比和特色菜品，它就无能为力了。
我的做法恰恰相反：先由我自己把大致的主线规划摸清楚，再让 Agent 在这份底稿上进行精准的微调与细化。
在这个过程中，我总结了四条核心原则：
第一条，从噪音里识别信号。攻略信息的特点是又多又杂、甚至互相矛盾，这些都是噪音。能够直接支持你做出具体决定（如今晚住哪、几点抢票、这家店去不去）的信息，才是真正的信号。凡是无法转化为具体行动的信息，扫一眼即可，切忌带进行程。
第二条，一手信息优于二手转述。景区的官方购票说明是一手信息，各类达人的攻略笔记是二手转述。转述每经过一道手，就会产生一层信息折损。营业时间记错、优惠政策记串，大半出在二手环节。凡是涉及时间、门票、预约等关键节点，必须回到官方原文进行核对。
第三条，信任具体的人，胜过信任算法。平台推送什么给使用者，很大程度上是由流量逻辑决定的。一个真实到访者在笔记评论区留下的碎碎念，往往比精心修图的爆款笔记可靠得多。评论区的真实性虽然也需要相对判断，但总体而言，评论区里普通人的声音，远比营销笔记本身可信。
第四条，输入质量决定输出质量。攻略的最终质量，取决于原始信息的成色，更取决于你对信息的加工能力。提给 Agent 的参考信息越明确、成色越高，最终生成的落稿就越扎实。这一关把好了，后面的行程安排才有可靠的根基。
形式
讲完原则，再来看看攻略的呈现载体。
在整个交互流程中，与 Agent 对话产生的原始文本一般都是 Markdown。但在最终定稿阶段，我选择将它转化为 HTML。
为什么选择 HTML？优势非常直观：
- 体积小巧，跨终端无缝调阅：单文件形态，直接发到微信里，手机浏览器就能一键打开。发进家庭群后，家人下载保存即为本地文档，哪怕在景区遇到信号不好的情况，也能随时调出，完全不受网络波动影响。
- 高自定义度，交互体验极佳：我可以让 Agent 帮我设计「总览页」与「每日分页」。总览页一眼掌握七天全局，点击对应的日期，就能无缝切换到当天的详细规划。到了现场需要核对安排，掏出手机点一下，直观又高效。
- 视觉美观，查阅心情更愉悦：你可以随心所欲地调校页面样式，甚至加入简单的交互逻辑，让旅行过程中的信息检索变得非常丝滑。
当然，HTML 只是我个人偏好的载体。如果你不喜欢网页，完全可以要求 Agent 输出其他格式——保留 Markdown 结构、生成单日行程的长图存入相册，甚至让 Agent 生成一些插画示意图。
核心在于：你需要清晰地知道自己想要怎样的调性与呈现，然后把需求下达给 Agent 协同完成。
工具
我的整体实操链路，可以归纳为这样一条单向演进的流水线：
确定旅行目标（选定主题）→ 确定时间与目标城市 → 挑选核心景点 → 制定推演路线（提前抢票）→ 倒推敲定酒店 → 沿线匹配餈饮 → 执行与动态调整
上一步的产出，就是下一步的输入。
不先定目标，就挑不准景点；不定好路线，酒店和饭店就无从谈起；不确定具体哪天去哪里，就没法预订爆火的门票；而没预订到门票，就可能留点遗憾回去。
不过换个角度想……遗憾有时候也是一种美。节假日出行，必须具备这种豁达的心态。
在工具的选择上，我们需要两套基础设施相互配合：小红书自有 AI、任意 Agent。
第一阶段：信息挖掘与多方校对
「点点」是小红书推出的 AI 搜索助手（拥有独立 App 与微信小程序）。它的核心优势在于背靠整个小红书社区的真实笔记库。
点点在回答问题时会附上出处，点击即可直接溯源到原帖，答案大部分来自真实用户的亲友体验。旅游、美食这类生活化攻略，恰好是它最擅长的领域。
很多人觉得小红书上面全是广告，容易干扰判断。但借助「点点」的 AI 搜索能力，当你提问「洛阳景点推荐」时，它会将多篇笔记进行综合提炼，自动梳理出一份图文并茂的景点推荐与行程初稿。AI 相当于替你完成了一轮多方校对，这比单看某一篇孤立的笔记要可靠得多。
利用点点拿到底稿后，你还可以进一步顺藤摸瓜，去翻阅那些极具活人感的帖子里面的评论区，将零散而真实的细节手记保存下来。
Why？因为要进入第二阶段了！
第二阶段：整理、推演和改写文件
将第一阶段收集到的规划底稿、景点清单、帖子文本以及评论细节，一股脑输入给本地的 Agent 工具（如ZCode、Claude Code、Workbuddy 等）。
之所以强烈建议选择本地 Agent 而不是网页版对话框，是因为本地 Agent 具备直接读写本地文件的能力，在修改、调整以及输出大文件时体验更加稳定。
此外，如今不少模型都具备出色的视觉能力（例如智谱的 GLM-5.3-Flash）。景区门口实拍的最新票价牌、达人笔记里的路线示意图，直接截屏发给 Agent，它就能自动识别图像内容并提取关键信息。
第三阶段：循环融合
在筛选阶段，先用人脑过滤掉那些明显的低质量营销信息，然后将有价值的干货抛给 Agent 进行融合，生成第一版完整规载。
后续只要刷到新的动态、查到官方最新的放票政策，随时贴给 Agent 补充，让它进行一轮又一轮的迭代。但最终的取舍权与定稿权，必须牢牢掌握在你自己手里。
这时我们又回到了第一阶段、第二阶段……没错，这是一个反馈和循环。
再额外介绍一个工具：高德地图。在做自驾路线规划时，高德地图的「地图小程序」是一个出色的辅助工具。你可以建立专属的行程标记点，将景点、美食、酒店等备选地点全部标注在地图上，一键生成路线。通过直观观察各个地点的空间位置关系，删减不顺路的节点会高效很多。
攻略实操全流程拆解
接下来，我将结合这次国庆河南七天自驾的真实经历，完整呈现从零到一的实操过程。
目标与景点：如何做减法？
做攻略的第一步，要有「以终为始」的态度：先确定这次出门，到底想做什么。
归纳起来，出行的目标大致可以分为三类：
- 景点打卡式：见什么都新鲜，想把当地的名胜古迹挨个看一遍。这类模式其实完全不需要自驾，选定一座城市，公共交通加网约车即可轻松搞定；如果要跨多座城市连轴转，就需要预留大量天数，体力消耗极大。若要游玩山山水水而交通不便，可以在当地报个一日游旅行团；不喜欢报团，建议租车而非打车（打车返程可能有困难）。
- 度假式：以纯粹的休息为导向，去哪是次要的，节奏放慢才是核心。不必太计较花费，喜欢就花，吃住玩都以舒适为先，景点反而不要排太多，免得舟车劳顿。适合选一个江浙水乡或海岛小镇，把时间交给酒店与漫步。
- 主题式：先确定一个明确的主题，再去匹配承载它的城市与景点。主题可以是人文古建（如河西走廊、山西古建、中原文化）、可以是看海（如山东、大连、海南、福建、深圳、珠海和浙江等沿海地区）、可以是乐园狂欢（如迪士尼、环球影城、方特等），也可以是博物馆之旅或美食寻味。主题式的优势在于玩得很有脉络，哪怕同一座城市去很多回，每趟也都知道自己在看什么。
打卡式和度假式往往一座城市就能装下。一旦像我这次这样长行程自驾，串联起多座城市时，城市之间就有了衔接问题，主题的分量就更重了：它决定每一站看什么，也决定哪些要舍弃。归根结底是一句：你想做什么，就去挑什么样的城市、什么样的景点，做什么样的事。
行程长短不同，规划的重心也不一样。如果是三天的小长假，比如中秋，你可以采用同样的思路计划，也可以之间坐车去到一个地方舒舒服服玩三天。如果是中秋国庆连休十三天这种长假期，规划就要重得多：长行程看的是连贯性和接续，还得认真考虑驾驶员的整体状态。可以先判断开车的他是「夜行者」还是「日行者」：喜欢晚上开车、夜里精神足但早起困难的，就安排晚上出发，夜间路上车也少；是能早上五点多起床的晨型人，就按实际情况安排早起赶路。不开车的人，最好顺着驾驶员的作息走，互相迁就。毕竟一路下来，最累的永远是握方向盘的那个人。
另外，目标制定必须深度考量同行人的生理与心理需求。一个人出行，你可以随心所欲；和朋友、伴侣或者父母一起，就得按大家共同的需求来。像我们这次出行：驾驶员只有我老公一人，太远太累的路线直接排除；我爸妈想看演出、吃美食，不想爬山；而我也有自己的偏好。求同存异，删繁就简，最终我们将本次出行的主题定为：演出多多 + 美食作伴。
在省份的选择上，可以采用「圆规排除法」： 以山西为圆心，设定自驾单程约 500 公里的半径，可选的省份有内蒙、宁夏、河北、山东、河南。接下来开始排除，我和我老公去过宁夏，而且宁夏距离有 700 公里，太远；今年端午刚带爸妈去过内蒙；河北离山西太近，周末随时能玩。这下，就剩下山东和河南了，其实自驾距离上相差无几，主要看你想玩什么。最终让河南胜出的，正是我们的「演出 + 美食」主题。河南的剧场实景演出与中原饮食体系，对长辈的吸引力显然更大。
敲定河南！接着看城市组合。考虑到自驾环线的顺畅度，我们挑选了位于河南北部的三座相邻城市：洛阳、登封、开封。
选市看的是距离和景点的平衡。考虑到环线比较方便，我们此次选择在河南北部三座城市游玩，洛阳、登封、开封。恰好，这也是河南非常热门的城市。
在这个过程中，我们做了非常果断的舍弃：
- 南阳：玉石文化出名，但位于河南最南端，强行跨越会导致行驶里程暴涨，放弃；
- 许昌：想去胖东来逛逛，但路线偏离主干动线，绕路，放弃；
- 郑州：原本打算作为中转站去河南博物院和「只有河南·戏剧幻城」。但权衡再三后选择完全不入郑州。原因有三：时间有限；爸妈和老公对博物院兴趣不大；《只有河南》属于高强度的户外戏剧观演，国庆期间人潮汹涌，体验感会大打折扣。与其浅尝辄止，不如干脆不进。
城市敲定后，接下来就是往这三座城市里填入具体景点。候选的收集还是Agent和小红书一起用：让Agent按我的要求列一份候选，再去翻小红书的攻略笔记对照；点点也能直接问「七天怎么玩」。两边对照，攻略很快初具雏形。
先说洛阳。白马寺是早就定好的，上午看古刹，中午回住处歇脚，下午进龙门石窟，一直待到傍晚，看亮灯后的卢舍那大佛。规划快收尾的时候，我在抖音刷到神州牡丹园秋牡丹的推广，一查就在白马寺对面，十月温室里也能看牡丹，顺路就加上了。
再说登封。都去河南了，怎能不去嵩山少林寺？一查发现少林寺在登封，寺里有武术表演，可以排在白天；晚上嵩山脚下还有《禅宗少林·音乐大典》实景演出，完美契合「演出」主题，一并锁定。
开封这边，主要是在万岁山和清明上河园里选一个。两个都是热门景区，风格不一样。万岁山是沉浸式武侠体验，满城NPC互动和武侠打斗，但要放得开、化上妆造，NPC才会跟你互动，爸妈这种年纪多半只能站在旁边看。清明上河园按《清明上河图》复原了一个宋朝市井园子，面积更大，运营也更成熟，白天有民俗演出和情景剧，晚上有打铁花和《大宋·东京梦华》实景演出。我们想看演出，还带着老人，就选了清明上河园，白天逛园子，晚上看表演，岂不美哉？
吃饭上也碰到过类似问题。河南有不少边吃边看表演的宴席，开封的宋宴、洛阳的宫宴，还送清明上河园的门票，一开始我想着尝尝鲜，后来查了下评价不算好，而且这种宴席要做足妆造才有意思，否则等于花大钱吃个氛围，最后就放弃了，专心看《东京梦华》。
路线与门票：拆解冲突
确定好景点后，就可以与 Agent 协同生成初稿。这个阶段的核心目的只有三个：找出时间上的隐性冲突、理顺每天的行驶动线、倒推必须提前锁定的门票。
在交互时，千万不要期望一句「帮我做份攻略」就能直接拿到可用的结果，多半你会得到辞藻漂亮的流水账。你需要带着批判性视角，重点关注以下两类问题：
第一，景区规则与时间的隐性冲突。这不光是体力分配的问题，更多是景区内部的安排冲突。拿清明上河园举例，晚间多场演出的时间非常紧凑，且国庆期间的票务规则与平时完全不同：平时普通门票凭票可在三天内反复入园，但国庆期间实行单日一次性入园制度，出园即失效。唯有购买《大宋·东京梦华》的演出票，才能凭票换取三天的无限次入园权益。

这种隐藏在票面细则里的规则冲突极易遗漏，必须随时让 Agent 检索：行程中是否存在时间冲突或不合理的规则限制？
