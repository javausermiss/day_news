Open Code Review is an AI-powered code review CLI tool. It originated as Alibaba Group's internal official AI code review assistant — over the past two years, it has served tens of thousands of developers and identified millions of code defects. After thorough validation at massive scale, we incubated it into an open source project for the community. Simply configure a model endpoint to get started.
It reads Git diffs, sends changed files to a configurable LLM via an agent with tool-use capabilities, and generates structured review comments with line-level precision. The agent can read full file contents, search the codebase, inspect other changed files for context, and produce deep reviews — not just surface-level diff feedback. Beyond diff review, ocr scan reviews entire files for auditing unfamiliar codebases or directories that have no meaningful diff.
Visit the official website for more details.
Compared to general-purpose agents (Claude Code), Open Code Review achieves significantly higher Precision and F1 with the same underlying model, while consuming only ~1/9 of the tokens and completing reviews faster. Note that its Recall is lower than general-purpose agents — a deliberate trade-off favoring precision over noise.
A real-world code review benchmark built from 50 popular open-source repositories, 200 real Pull Requests, and 10 programming languages — cross-validated by 80+ senior engineers (1,505 annotated ground-truth issues).
Explore the AACR-Bench dataset on Hugging Face.
If you've used general-purpose agents like Claude Code with Skills for code review, you've likely encountered these pain points:
- Incomplete coverage — On larger changesets, agents tend to "cut corners," selectively reviewing only some files and missing others.
- Position drift — Reported issues frequently don't match the actual code location, with line numbers or file references drifting off target.
- Unstable quality — Natural-language-driven Skills are hard to debug, and review quality fluctuates significantly with minor prompt variations.
The root cause: a purely language-driven architecture lacks hard constraints on the review process.
Open Code Review's core philosophy is to combine deterministic engineering with an agent, each handling what it does best.
Deterministic Engineering — Hard Constraints
For review steps that must not go wrong, engineering logic — not the language model — guarantees correctness:
- Precise file selection — Determines exactly which files need review and which should be filtered, ensuring no important change is missed.
- Smart file bundling — Groups related files into a single review unit (e.g., message_en.properties and message_zh.properties are bundled together). Each bundle runs as a sub-agent with isolated context — a divide-and-conquer strategy that stays stable on very large changesets and naturally supports concurrent review.
- Fine-grained rule matching — Matches review rules to each file's characteristics, keeping the model's attention sharply focused and eliminating information noise at the source. Compared to purely language-driven rule guidance, template-engine-based rule matching is more stable and predictable.
- External positioning and reflection modules — Independent comment-positioning and comment-reflection modules systematically improve both the location accuracy and content accuracy of AI feedback.
Agent — Dynamic Decision-Making
The agent's strengths are concentrated where they matter most — dynamic decisions and dynamic context retrieval:
- Scenario-tuned prompts — Prompt templates deeply optimized for code review, improving effectiveness while reducing token consumption.
- Scenario-tuned toolset — Distilled from deep analysis of tool-call traces in large-scale production data — including call frequency distributions, per-tool repetition rates, and the impact of new tools on the overall call chain — resulting in a purpose-built toolset that is more stable and predictable for code review than a generic agent toolkit.
- Git >= 2.41 — Open Code Review relies on Git for diff generation, code search, and repository operations.

Coding agents often default to older patterns because LLM training data contains vast amounts of legacy code. This often leads them to generate bloated JavaScript for tasks that now have native, high-performance web platform solutions.
Even if a model knows an API exists, it often lacks the density of real-world, modern implementation patterns required for production-ready code.
Modern Web Guidance bridges this gap. Our skill's CLI returns targeted, expert-curated guidelines directly into your agent's context window, focusing on:
- Modern Browser APIs: Helping models correctly structure APIs they frequently misuse.
- Performance & Accessibility: Preferring platform-level APIs that can be optimized by the browser and include built-in accessibility affordances.
- Responsible Fallbacks: Guiding models to use sensible, lightweight fallbacks instead of heavy polyfills or legacy libraries.
We cover the past several years of the web platform's new features, all the way up to the cutting edge. The guides are designed to be token-efficient; we run evals enabling us to prune lowest-common-denominator content that models already know.

For a few years I was ‘Head of DevOps’. Before I got that job title I’d done much the same work under other names, and since then I’ve watched the same work get called SRE, and then it seemed to morph towards platform engineering. If you’ve been in this industry for any length of time you’ll have seen titles come and go like this, and you might have wondered where they all came from.
So I (with the help of Mr Claude) built this family tree of software job titles, from the 1940s to now.
It’s here: ianmiell.github.io/sw-job-title-family-tree
What It Is
There are 104 titles, from ‘Computer’ (a person, not a machine) at the top to ‘AI Agent / Context Engineer’ at the bottom.
Time runs from top to bottom, in five-year rows. The titles sit in seven coloured columns by family:
- Development
- Analysis, architecture and leadership
- Operations and infrastructure
- Networks and security
- Data and AI
- Quality and test
- Support and customer-facing
A solid arrow means the title grew out of its parent. A dashed arrow means influence, or a common career move. Landmark titles are in bold.
On the site you can click a family to see just that column (here’s Data & AI), or click a title to get its history, background and connections (here’s SRE).
The whole thing is one Graphviz file and one JSON file of descriptions. Each title is one line in the .dot file, and the picture is rendered with:
$ dot -Tsvg job_title_family_tree.dot -o job_title_family_tree.svg
Adding a title is three small edits: a node in its family’s column, an entry in the row for its five-year period, and its parent arrows.
A word on the dates. They’re roughly when a title became common, not its first recorded use, and they’re my best estimates, not sourced citations. Some are well known (SRE at Google in 2003, ‘DevOps’ coined in 2009, ‘Data Scientist’ in 2008). Plenty are a ‘c.’ and a shrug.
Six Things I Noticed
Drawing it out made a few patterns hard to miss.
1) Coding Started Out as the Clerical Bit
In 1947, Goldstine and von Neumann’s ‘Planning and Coding of Problems’ split the work of using a computer in two: mathematicians planned the problem, and coders translated the plan into machine instructions. Coding was treated as lower-status clerical work, and much of it was done by women.
It turned out that coding eventually became the hard, creative part, and the coder merged into the programmer.
Go back further and it’s stranger still. Several of the first ENIAC programmers were recruited from the Army’s human computers, people whose job was to compute by hand. So the job gave its name to the machine, and its people to programming.
2) Titles Break Apart, Then Join Back Up
The webmaster turned up around 1993, and was often a single person who wrote the HTML, ran the webserver (often a box under a desk), answered the email, and kept the site up (sometimes by kicking it, more often by plugging it back in after kicking it).
By the mid-2000s the title had all but gone, as it was unfashionably ancient. The code went to web developers, the servers to sysadmins, and the content to editors and designers.
Then the web developer split into front-end and back-end around 2005, and the two joined back up again as ‘full-stack’ around 2008.
This is the centralisation/distribution see-saw I’ve written about before, playing out in job titles.
3) Some Titles Don’t Last
The prompt engineer made headlines in 2023 with a few eye-wateringly well-paid job listings. As the models got better, the skill became part of other jobs, and on the tree it gets absorbed into the AI engineer almost as soon as it appears.
The scrum master is a slower version of the same story: demand peaked in the 2010s, and many organisations have since folded it back into engineering management or delivery roles.
The newest title on the tree is the ‘AI Agent / Context Engineer’ (c. 2025). The description for it currently says “time will tell whether it stays a separate title”. I’m not taking bets.
4) Names Get Recycled
‘Systems Engineer’ is two different jobs on the tree. At IBM in the 1960s it was a pre-sales role, working with customers to design installations and get them running. In the 1990s, thanks largely to Microsoft’s MCSE certification, it meant a more senior, design-oriented sysadmin. Same title, different branch, no relation.
‘Configuration management’ started as a 1960s US defence discipline for tracking hardware changes, became software version control in the 1970s, and then came back decades later as the name for tools like Puppet and Chef.
5) The New Thing Is Often an Old Thing
The ‘forward deployed engineer’ (FDE) is one of the hottest titles of 2025, as OpenAI, Anthropic and plenty of AI startups hire FDEs to get AI working inside their customers’ organisations.
Palantir built its business around them from about 2010: software engineers embedded with a customer, often on site, building whatever is needed to make the product work for that customer’s problem.
Which sounds a lot like IBM’s systems engineers of the 1960s, who worked with customers before and after the sale, designing installations and getting systems running. (It also sounds a lot like old-style consulting, but I would say that.)
6) The DevOps Debate Is There
Ben Treynor Sloss defined SRE as “what happens when you ask a software engineer to design an operations team”. DevOps was meant as a culture of developers and operations working together, but by about 2011 ‘DevOps Engineer’ had become a job title, usually for whoever did the automation. On the tree, the arrow between SRE and DevOps points both ways. Platform engineering has both of them as parents, and was sold around 2022 as ‘the successor to DevOps’.
The Dev/Ops divide has never been resolved. It just keeps getting new names.
Why Bother?
When I’m asked what the difference is between a DevOps engineer, an SRE and a platform engineer, the honest answer is always a little history lesson. This is the shortest version of that lesson I’ve managed so far.

In July, we announced a series of planned updates to the PyPI user interface. Shaped by user research with members of the Python community, the updates aim to improve how we surface security signals and display package details.
We're pleased to share that this work is now complete and live on PyPI.
Context¶
With the rapid growth of the Python ecosystem, PyPI has become an increasingly attractive target for malicious actors. In response, the PyPI team has delivered many security features while taking a more active role in helping PyPI users assess and understand package security.
Digital attestations, introduced in 2024, are an example of this effort, providing a verifiable record of a release file's provenance (where it came from). However, provenance and attestations are still unfamiliar concepts for many PyPI users, and PyPI's interface did little to communicate their meaning, importance, or limitations.
To address this, PyPI partnered with Kabu Creative to bring clearer security signals to the PyPI UI, implementing the recommendations developed in the OpenSSF Attestations Style Guide.
Here's a look at what's changed, what it means for you, and what actions you can take.
The New Security Tab¶
The new security tab communicates release provenance states and displays per-file attestations, giving you a dedicated place to verify where the release files came from.

Full Provenance¶

No Provenance¶
"No provenance" simply means that no file in the release has an attestation. This is typical for older releases or projects that have not yet configured Trusted Publishing. This means that some files carry attestations while others do not (e.g., wheels were published via Trusted Publishing, but the source tarball was uploaded using an API token).
Exercise caution if you see this warning. Check release notes for build issues or ask in the project's issue tracker before installing.
Inconsistent Provenance¶
This warning indicates that files within the same release originate from different build systems or source repositories.
Check the attestation metadata to confirm whether all files came from sources controlled by the maintainers.
Change of Provenance¶
This warning tells you that the release files originated from a different repository or workflow than a previous release. While often legitimate (such as an organization name change or repository migration), it can also indicate a compromised pipeline or account takeover.
If you see this warning, check the project release notes or official channels to confirm that an infrastructure migration was planned.
Loss of Provenance¶
This means that a project that previously published with attestations has changed to uploading release files without them.
Check whether the maintainers intentionally changed their publishing process, for example by switching back to API tokens, or by changing their publishing configuration so that it no longer generates attestations. If this is unexpected, treat the release with skepticism until verified.

Introduction #
Commercial phone unlocking tools are not magic. They exploit the same classes of vulnerabilities that security researchers publish about at conferences and in academic papers. What makes them distinctive is not the novelty of the techniques, but the systematic commercialization of exploitation: acquiring or developing exploits for each hardware and software combination, and reaching a certain degree of stability, packaging them into automated workflows that require minimal operator expertise.

The attack vectors available to a forensic examiner with physical access to a device are constrained by well-understood boundaries: the boot chain, the trusted execution environment, the secure element (when present), and the kernel’s peripheral driver stack. This post mostly details Android internals, however iOS equivalent concepts are technically similar.

Hardware security architecture #
Before examining attack vectors, it is necessary to understand the hardware security architecture of modern Android devices. The following sections describe the components that forensic tools must eventually hack or bypass.
The System-on-Chip: Normal World and Secure World #
Modern ARM-based mobile processors implement TrustZone, a hardware security extension that partitions the processor into two execution environments: the Normal World and the Secure World. The Normal World runs the Android operating system, user applications, and the Linux kernel. The Secure World runs a separate, minimal operating system, the Trusted OS, along with small, specialized applications known as Trusted Applications (TAs).
The two worlds share the same physical processor cores but are hardware-isolated: the Normal World cannot directly read or write Secure World memory. Communication between the two happens through a monitor, a piece of code running at the highest privilege level (EL3 on ARMv8), which handles context switches triggered by Secure Monitor Call (SMC) instructions. Each physical processor core effectively provides two virtual cores, with the Non-Secure bit in the Secure Configuration Register determining which world is active at any given time.
The Trusted OS hosts critical security services. Two are directly relevant to device unlocking:
- Gatekeeper: responsible for verifying user credentials (PIN, password, pattern). It implements rate-limiting to throttle brute-force attempts and, upon successful authentication, issues a signed authentication token.
- Keymaster: the key management service that stores and operates on cryptographic keys. Some keys are authentication-bound, meaning they can only be used after Gatekeeper has issued a valid token.
Different SoC vendors ship different TrustZone implementations. Google (and AOSP in general) uses TrustyOS; Qualcomm uses QSEE; Samsung uses TEEGRIS (on both Exynos and MediaTek SoCs in Samsung devices); Huawei uses TrustedCore; Trustonic’s Kinibi is also often found on MediaTek and Exynos SoCs. The security properties vary between implementations.
The Secure Element #
A Secure Element (SE) is a physically separate, tamper-resistant hardware chip that provides an additional layer of security beyond the TEE. Unlike the Secure World, which runs on the same SoC as the Normal World, a Secure Element is an independent processor with its own boot chain, its own firmware, and its own cryptographic key storage.
In the Android ecosystem, the Secure Element is exposed through the StrongBox API (introduced in Android 9). Google’s Pixel phones, starting with the Pixel 3, include the Titan M chip as their Secure Element, that was later upgraded with the Titan M2 from Pixel 6 onward. On Apple devices, the equivalent is the Secure Enclave Processor (SEP).
The Secure Element’s role in device encryption is to hold key-encryption keys and enforce rate-limiting for credential verification in hardware that the main SoC cannot tamper with, even if fully compromised. This is an important distinction: on a device without a Secure Element, compromising the TEE is sufficient to extract or bypass credential-derived keys. On a device with a Secure Element, the attacker must additionally compromise a separate, hardened chip.
Unfortunately, only flagship devices typically include a Secure Element. Most mid-range and budget devices rely solely on the TEE for credential protection. 外观
拿到这台机器，第一眼就能看出 NX 系列定位高端旗舰——最亮眼的莫过于镁合金材质的银色外壳，放在掌中分量十足。
将设备打开就能发现，NX70V 采用翻盖式设计，上半部分是 3.8 英寸彩色触控屏，下半部分为 QWERTY 键盘和快捷键。
转轴位置还有一颗约 31 万像素的内置 CMOS 摄像头，支持 260 度旋转，可以拍摄静止图像和带音频的 MPEG-4 格式视频。
仔细观察不难发现，NX70V 除了翻盖，屏幕还支持 180 度旋转，并且可以将屏幕反盖在键盘上；这个时候就可以使用触控屏操作设备。
这个充满动感的比喻，旨在强调该设计带来的自由度和多种使用形态。但这种翻盖加旋转的设计在索尼 CLIE 上并不算新鲜——更早的 NR 系列上第一次出现了这种设计，官方称其为：「Wing Design」（ウイングデザイン）。在当时的发布会上，索尼高管进一步阐释了这一命名的灵感来源：「大空を羽ばたく鳥をイメージした‘Wing スタイル’」（令人联想到在广阔天空中展翅飞翔的鸟的「Wing Style」）。
配置
除了让人眼前一亮的设计，NX70V 的配置放在当时一众 Palm 设备当中也十分亮眼：
- 操作系统：Palm OS 5 ，兼容 Palm OS 4 应用，并原生支持无线通信。
- 处理器：Intel PXA250 (200MHz)，从上一代 Dragonball 处理器大幅升级而来。
- 显示屏：3.8 英寸折叠式纵向宽屏彩色 TFT 液晶，分辨率 320×480，支持 65536 色显示。
- 摄像头：内置约 31 万像素 CMOS 传感器的 260 度旋转式相机，支持拍摄静止图像和带音频的 MPEG-4 格式视频。
- 扩展与连接：内置 CF Type II 卡槽（可用于 PHS 通信卡或无线 LAN 卡），并配备 USB、红外线端口及耳机接口。
首批发布的 NX 系列当中，除了我手中这台 NX70V 还有无内置摄像头的 NX60。这种功能上的取舍在 NR 系列上也有所体现，比如 NR70 无内置摄像头，NR70V 内置了 10 万像素摄像头。
在查资料的时候，我在网上看到了一篇 2003 年的文章，内容是国内媒体第一时间对索尼最新发布的 CLIE PEG-NX70V 的测评。当时的媒体给出的评价是：旧瓶新酒，缺乏创新的造型。
但我认为，在真实体验过 NX70V 之后这个评价还有可以商榷的地方。的确，第一眼看过去 NX70V 和之前的 NR 系列同样采用「Wing Design」，并且机身都为银色。不过 NX70V 外观上最明显的变化在于机器背面新增的 CF 扩展卡槽，相比 NR 系列只能使用索尼自家 Memory Stick 而言，NX 系列还支持 CF 卡扩展。
虽然支持的范围很有限，根据我所查到的资料，NX 系列的 CF 扩展卡槽有一个「白名单」，白名单外的 CF 卡，无论是存储卡还是扩展设备，都无法被机器正常识别。但后期经过软件方面的破解可以正常识别一些 CF 存储卡。
此外，内在的升级点我认为是最重要的。NX70V 上搭载的 Palm OS 5 无论是从扩展性、系统外观上都比 Palm OS 4 提升不少。
软件
索尼专门为 Palm OS 5 定制了许多软件，这里我着重分享一下 CLIE 的原创新启动器 CLIE Launcher。
CLIE Launcher 是索尼为自家 CLIE 掌上电脑专门定制的操作界面，也是当时你能看到搭载 Palm OS 5 系统的索尼掌上电脑和其他的 Palm 设备最大的不同点之一。和传统的 Palm OS 5 界面对比，就能看出个中的区别；CLIE Launcher 界面设计更复杂，分为多个功能板块——左上角是功能分区，左下角是常驻软件（可以把平时常用的功能或者软件放在这个地方），右边一长列就是系统内置的软件和安装的第三方软件。
你可能会认为这种复杂的操作界面，对于当时使用电阻式触控屏的掌上电脑来说不太好操控。答案是肯定的，不过索尼 CLIE 掌上电脑还有一个「独家」的操作按键：Jog Dial。你可能对这个按键有所印象，因为在之前的《怀旧手记》当中，我曾为大家分享过 2000 年左右索尼推出的笔记本电脑：VAIO，在当时 VAIO 电脑上也有 Jog Dial。
这个按键有什么用，怎么用？你可以把它理解为鼠标上的滑动按键。在 CLIE 上上下滑动 Jog Dial，就可以选择对应的软件和文件。
一般在 Jog Dial 下方还会有一个 Back 返回键。这个时候再回过头来看看 CLIE Launcher 上面的设计，明摆着就是为了让用户配合 Jog Dial 操作的。
除了内置软件外，Palm OS 5 本身是一个非常成熟的系统，有很多第三方软件、游戏可供选择。
那么在当下，资源要从哪里找？这里我推荐两个网站：PalmDB 和 Internet Archive。前者专门提供 Palm 的各种资源，包括软件和游戏。后者收集了互联网上各种古老稀缺的资源，《怀旧手记》里面的很多设备系统和软件资源都是在这个网站找到的。
想要把软件游戏同步进 Palm 设备也非常简单，你只需要一根数据线（不是充电线），或者一个专门适配 Palm 设备的同步底座。详细步骤参考我这台 NX70V：将设备开机，连上数据线，在机器当中找到 HotSync 选择中间的同步按钮。这时观察电脑，只要事先安装了「Palm Desktop / HotSync Manager」并让它在后台运行，就能够看到电脑上出现同步进度条。
如果是第一次同步，软件会要求你选择或者输入一个账号，接着就会自动同步数据。如果想要安装软件，需要先在电脑上打开 Palm Desktop，选择 Install，把对应的软件添加到列表当中，点完成，然后就可以把 Palm Desktop 关掉，在设备上再选择 HotSync 同步一次。
是不是非常简单？除了可以这样子安装软件以外，如果设备上的 Palm OS 是英文，日文或者外文，还可以通过同步的方法外挂中文系统。像我选择的就是 CJKOS，操作也很简单：在电脑上解压并打开 CJKOS 选择需要同步到设备上的语言（中文）、在同步之前先选择好设备型号，比如我这一台是 Palm OS 5 的 NX70V，就选择对应的型号。
如果型号或系统版本不同，就不太推荐同步了。且不说能不能成功，不同设备的型号、分辨率和系统版本都可能导致软件同步失效，外挂中文系统失败。
我这里安装了几个软件和应用到我的 NX70V 上，简单体验分享一下：
- Bejeweled（宝石迷阵）：Palm 上非常经典的一款休闲小游戏，玩法很有意思，有点像现在的消消乐：在一排排宝石当中选中相邻的同色系宝石，轻点就可以消除。
- Zuma（祖玛）：更为经典的一款游戏，由 PopCap 开发。我在诺基亚塞班、苹果 iOS，甚至 Palm 的 webOS 上都玩过它。一款游戏能跨这么多平台，本身就挺能说明它有多经典。玩法都很基础，不需要费脑子：操控游戏中间的癞蛤蟆吐弹珠，阻止轨道上的球链到达终点骷髅洞。把轨道上的球全部消除即可过关。
NX70V 基本聊完了。它代表的是 CLIE 的高端旗舰；接下来把视线转到产品线的另一头——大众入门的 SJ 系列。
PEG-SJ33
SJ 系列定位大众入门，部分型号是 CLIE 当中最便宜的。这个系列中有彩色屏幕机器，也有单色屏幕机器。
SJ33 则是 SJ 系列最后一款机器，发布于 2003 年 1 月。在 SJ 系列上你能看到，哪怕是索尼定位入门的设备，也有针对其一整套「营销」和「特色亮点」。
索尼对应的新闻稿上是这么介绍 SJ33 的：设计与娱乐。另外，比较有意思的是 SJ33 和 NZ90 其实也是同时期的产物。
而 NZ90 是索尼继 NR、NX 系列之后的产物，区别在于摄像头像素提升（内置氙气闪光灯），外观设计上较前代有轻微变化（不过仍然是「Wing Design」）。
多彩配色
说回 SJ33，因为定位入门，配置放在 2003 年同期的索尼掌上设备当中并不算亮眼，所以这款设备更偏向对外营销上。SJ33 首发版本常规配色只有黑色一种，官方后续又追加了蓝色、橙色两种数量限定配色。
到后期因为蓝色大受欢迎，官方又将蓝色定为和黑色一样的常规配色，同时再次新增一款白色常规配色。
除此之外，SJ33 上有可翻开的透明亚克力保护盖；平常不用的时候可以保护设备屏幕。透明亚克力的设计，还可以看到屏幕上的一些有效信息。
多种配件
在官方的新闻稿当中明确表示「SJ33 透明亚克力保护盖作为周边配件，另提供多种限定配色。」
所以这样一对比就非常清晰了：产品定位入门、售价便宜的时候，索尼会在机器的外观和营销上「大动干戈」，同时推出一系列可选周边配件。
外观
上手看到实物 SJ33 的时候，第一眼我其实并没有觉得廉价。也可能是因为我这一台是当时数量限定的蓝色版本，相比亮黑色，蓝色的版本更亮眼。
设备正面是非常传统的「Palm 布局」；点亮屏幕，可以发现虽然是入门产品，索尼也选择了彩色高分辨率屏幕，只是在看不见的地方进行了一些阉割。
配置
比如 2003 年的设备还在使用 Palm OS 4.1，CPU 也是 Dragonball Super VZ 66MHz，没有实体键盘，也没有摄像头，最大的亮点就是可以插耳机听 mp3 音乐，并且内置了对应的播放器。
因为系统不是 Palm OS 5，所以之前我所分享的那些索尼专门为新系统定制的启动器，还有软件在这台设备上都体验不到了。
与其说 SJ33 是索尼的大众入门掌上电脑，我觉得它更像是索尼对自家 CLIE 的一次「回归本质」。毕竟当时绝大多数 Palm 设备还在拿彩色高分屏做亮点，「效率」和「续航」依旧是主打卖点之一，这些特点在 CLIE SJ33 上你也能够看到。
Palm Zire 71
说到 Palm 设备拿彩色高分屏做亮点，2003 年 Palm 自家的 PDA 也进入了「彩屏时代」，多数定位中端、高端的产品都配备了彩色高分屏。其中我认为最值得谈一谈的是：Palm Zire 71。
原因很简单，当时人们对 Palm 的第一印象是：商务办公人士的主流选择，娱乐性一般。但 Zire 71 打破了这种印象，Palm 为 Zire 71 配备了一颗 30 万像素的摄像头。触发方式也很有趣，将屏幕向上推，机器背面就会露出隐藏的摄像头，此时正面下方多出了一枚单独的拍照按键。
Palm Zire 71 不只是内置摄像头的 PDA，它定位中端，却配备了彩色高分辨率屏幕、内置摄像头、耳机接口、还有 SD 卡扩展以及 Palm OS 5 系统。作为 2003 年的 PDA，这些很「够看」。同时，Palm 自身也在试图用不同亮点区分不同产品线。
从 Zire 71 也能看出，Palm 自身在试图用不同亮点区分不同产品线。再把视线收回索尼 CLIE：2003 年之后，CLIE 的故事并没有结束。索尼仍然推出了很多让人「眼前一亮」的掌上设备。
CLIE 的后续
2004 年前后，索尼发布了 TH55、TJ27 和 TJ37，这些机器往往被认为是索尼面向全球市场最后的机型。
但还有一款特殊的机器同样属于 CLIE，它知名度更低，只在日本本土发售：2004 年 9 月，PEG-VZ90 发布，VZ90 最大的亮点是搭载有机 EL（OLED）显示屏，这在当时的 PDA 中极为罕见。
它的外观设计和以往 CLIE 系列也不太一样，我个人觉得更偏向于当时索尼推出过的「电子相框」。到了 2005 年 2 月，索尼正式宣布终止该系列，并计划在同年 7 月结束所有机型的生产。至此索尼 CLIE——以精巧工业设计让人眼前一亮的 Palm OS PDA，正式消失在大众视野中。
不得不承认，通过这一次的回顾让我认识到，索尼 CLIE 上那些当年让人眼前一亮的想法和设计，在日后也被他人不断汲取打磨早已融入

那么，究竟该如何开始撰写一篇合格、有质量的综述呢？
写综述前的准备：聚焦与文献分级
综述具有较强的「时效性」，主要汇报某一领域近期关于某个「小痛点、小热点」的研究进展与空白（例如：特定物质的联合作用机制或感官品质改良）。因此，写综述选题切忌宽泛，唯有高度聚焦才能把某个小问题讲透。
在文献选取上，虽然我重视近几年的前沿成果，但并不唯年份论。更科学的做法是按功能对文献进行分级管理：
- 经典文献：交代研究背景、基础理论与奠基性方法（引用前需核查是否有后续勘误或结论修正）。
- 代表性研究：说明关键技术或学术观点的演变脉络。
- 前沿研究：反映近 3～5 年的新突破与新应用。
- 争议性研究：横向对比不同团队的结论差异与实验条件局限。
明确了上述原则，下面正式进入主题：如何好好利用 AI 工具，快速撰写一篇综述文章？
Step 1：用「科研指令」确定选题与大纲
动笔写综述前，我们需要先通过阅读同领域的近期综述完成基础积累，摸清行业痛点。在此基础上，与其对着空白文档苦思冥想，不如借助自带联网能力的 AI 工具（如 Gemini、ChatGPT 或国内直连的 Qwen）辅助发散思路。
向 AI 提问需要打磨「科研指令」。以下是我用于确定综述主题、挖掘研究空白的提示词模板（建议使用 Gemini）：
# 角色设定
你是一位【填入学科，如：食品科学与工程】领域的资深科研专家与期刊审稿人，我是一名该领域的研究生，正在筹备一篇学术综述。
# 任务目标
我计划撰写一篇与【填入大方向，如：沙棘果渣高值化利用与面制品品质改良】相关的【中文 / 英文】综述文章。请结合近 5 年（2021–2026 年）国内外研究现状，帮我挖掘目前该方向尚存的研究痛点或综述空白，并提供 5 个具备发表潜力的具体选题。
# 输出要求
每个选题请按以下结构输出：
1. 拟定题目（需具体聚焦，避免宽泛）
2. 核心切入点与综述必要性（解决什么行业/学术痛点）
3. 涵盖的 3～4 个核心讨论维度
# 科研严谨性约束（必须严格遵守）
- 严禁编造论文、作者、期刊、DOI 或具体实验数值。
- 明确区分「学界已证实的共识」与「你基于逻辑做出的推断」。
- 对于缺乏充分证据支撑的判断，必须使用「可能」「提示」「尚不明确」等谨慎学术表述。
- 若涉及存在学界争议的观点，请同时列出正反双方的研究视角及条件差异。
得到了几个选题后，在里面挑选一个自己觉得还不错、能大概理清逻辑的选题，开始下一步：
# 任务目标
我最终选定了《【填入确定好的综述题目】》作为综述题目。请为我设计一份符合主流核心期刊（如《食品科学》或同级 SCI 期刊）规范的详细三级大纲目录。
# 具体要求
1. 逻辑递进：章节之间需体现「背景痛点 -> 核心机制/处理方法对比 -> 品质/应用影响 -> 现存瓶颈与展望」的层层递进关系，拒绝简单的文献罗列。
2. 撰写指引：请在每个二级/三级标题下方，用括号简短注明该小节「应当重点对比哪些研究指标」或「需要回答什么核心科学问题」。
3. 检索词建议：在大纲末尾，提炼出支撑各章节所需的核心中英文检索关键词。
然后按照自己已经有的知识储备，再用多个 AI 工具验证一下，这个目录还有没有可以补充、完善、修改的地方，使得整篇综述文章的逻辑条理更清晰。

Step 2：数据库检索文献
确定选题与大纲后，我不会直接让 AI 替我检索文献，而是先利用它将研究主题拆解为「核心对象、处理技术、应用方向」三个维度，扩展同义词并生成适配不同数据库语法的检索式，然后将这些概念的同义词组合起来，形成可执行的检索策略。
但注意：AI 可以帮助我们扩展关键词，但最终检索结果仍然需要我们回到数据库中检索、筛选。
使用以下指令：
# 任务目标
我准备以《【填入综述题目】》为题撰写综述。请将我的研究主题拆解为「核心研究对象」「关键处理技术/方法」和「研究结果/应用方向」三个维度，为我构建可直接复制到科研数据库的高级检索式。
# 具体要求
1. 关键词扩展：为上述三个维度分别列出中英文核心词、同义词、近义词及常见学术缩写。
2. 中国知网（CNKI）检索式：提供 2～3 组适配知网高级检索语法的检索词组合（区分「主题」「篇名」字段，使用 SU=、TI= 及 AND/OR 逻辑运算符）。
3. Web of Science (WoS) 检索式：提供 2～3 组适配 WoS 核心合集的英文布尔检索式（使用 TS= 主题字段、引号精确匹配及 * 通配符，如 "sea buckthorn pomace" AND ("solid-state fermentation" OR pretreatment)）。
如上操作，会出现与我们主题相关的文献检索结果。我建议大家第一遍收集文献的时候，按照文献标题判断这篇文献是否与自己综述内容有关，有关的就保留到 Zotero 里，无关的就略过。
Step 3：参考资料初筛
以上准备工作做好后，我们来到写综述的重头戏——摘要的提取、筛选与管理。
传统的综述写作，需要批量下载、分类管理，然后大量阅读文献……挺麻烦的，看起来就很复杂、很不想开始，我给大家介绍一个好思路。
以「文献摘要」作为核心输入
撰写综述需要参考海量文献的内容，包括但不限于研究背景、实验方法、核心数据与结论。如果直接将几十篇完整 PDF 扔给 AI，不仅容易超出上下文限制，还会因无关细节过多而引发严重的「AI 幻觉」。实际上，由原作者撰写、高度凝练的「文献摘要」已经囊括了上述核心要素。以摘要替代全文投喂给 AI，既能大幅增加单次对话处理的文献数量，又能显著提升信息提取的准确度与聚焦度。
准备摘要
在知网或 Web of Science 将初筛文献导入 Zotero 后，无需逐篇手动复制摘要，可通过以下 4 步批量导出：：
- 在 Zotero 中选中、全选你要用到的文献。
- 右键点击 -> 选择「由所选条目生成报告 (Generate Report from Items)」；Zotero 会弹出一个窗口，里面整齐地列出了标题、作者、摘要等信息。
- 全选复制 (Cmd + A, Cmd + C) 这个报告的内容。
- 粘贴（Cmd + V）给 AI 工具对话框内。
这是向 AI 投喂摘要前的准备工作，有了这样一份文献摘要文件，我们就可以进行下面的操作。
筛选摘要
获取摘要报告后，不要直接让 AI 生成正文内容。我通常会先将其投喂给 Qwen 进行相关性分级与信息预提取，剔除无关文献：
# 任务目标
请根据我提供的 Zotero 文献导出报告，对这批文献进行初步筛选与核心信息提取。
注意：本次任务仅限于文献初筛与摘要提取，请勿直接撰写综述正文。
# 我的综述主题与大纲方向
【填入你的综述题目或当前章节主题】
# 输出格式要求
请先以 Markdown 表格形式汇总以下 6 项基本信息：
| 原文献编号 | 作者与年份 | 研究对象与核心问题 | 关键研究方法 | 摘要报告的主要结果与结论 | 相关性评级（高/中/低） |
表格下方，请针对「高相关性」文献单独列出：
- 归属章节建议：该文献适合放入我大纲的哪一部分？
- 待核实盲区：摘要中未提供、必须精读全文才能确认的关键实验条件或数据。
# 严谨性红线
1. 必须严格保留原报告中的文献编号，切勿打乱顺序。
2. 严禁根据论文标题脑补实验结果，严禁补充摘要中未出现的数据。
3. 不同研究结论存在差异时需如实分别记录；凡摘要表述含糊之处，统一标注「[需读全文核实]」。
# 待处理的 Zotero 文献报告：
【在此处粘贴 Zotero 生成的报告内容（建议按子章节分批投喂，单次 15～20 篇左右，避免模型因输入过长而漏读细节）】
完成以上步骤后，我们就获得了一份与我们主题非常贴合的摘要报告了，为后面书写正文打好了基础。
Step 4：正文写作
综述写作很忌讳将文献摘要按发表时间或研究对象逐篇改写、简单汇编。更科学的做法是以『研究问题或作用机制』为主线——例如横向对比不同处理方式对同一原料的影响，或剖析相同实验方法下因条件与指标不同而产生的结论差异。
在利用 AI 提炼综述章节的初稿时，我经常使用以下指令：

你现在是一位【填入学科领域】的资深学者。我正在撰写综述论文《【填入综述题目】》，现在需要你根据我提供的文献摘要库，辅助撰写大纲中的指定章节。
# 输入材料
1. 全文大纲背景：
【粘贴完整大纲，帮助 AI 理解上下文边界】
2. 本次需撰写的目标章节：
【填入具体小节标题，如：2.2 超声与过热蒸汽预处理对果渣膳食纤维结构的影响】
3. 支撑该章节的 Zotero 文献摘要报告：
【粘贴筛选后的高度相关文献摘要】
# 写作任务与核心要求
1. 先综后述（拒绝文献堆砌）：请勿按「A 研究了什么、B 研究了什么」的流水账方式逐篇改写摘要。必须以「研究问题或作用机制」为主线，将不同文献的方法、实验条件与结论进行横向对比、归类与串联，指出共性规律与差异原因。
2. 初稿撰写：写出该小节的学术初稿，字数控制在【如：1000】字左右，语言需严谨、客观、平实，符合中文核心期刊学术规范。
3. 溯源标注：文中凡引述观点或数据处，必须在句末严格使用【[原文献编号, 第一作者, 年份]】格式标注来源，方便我后续回溯核验。
4. 事实边界：所有论述必须 100% 来源于我此次提交的文献摘要，严禁调用你自身的外部预训练知识凭空编造数据或结论。如果现有摘要不足以支撑某个论点，请直接在文中用【[此处缺乏文献支撑，需补充检索]】标出。
借助上述指令，大纲的每个子章节只需分批投喂一次摘要即可搭建出初稿（我通常先用 Gemini 和 Qwen 提炼各章节草稿，再交由 ChatGPT 对照核心文献补充润色）。
初稿完成后，我自己会把综述进行多轮核对：
- 把一些语言表述调整得更符合学术文章的风格。
- 带有「数据」的表达，我都会回到参考文献核对，数字是否准确。
- 带有「专有名词」的表述，我会回到参考文献核对称呼是否正确，如何用英文表述。
- 涉及到前处理、固态发酵、产物转化等过程的描述，我会回到文献仔细阅读、做笔记，然后用 AI 工具整理出文献里核心的方法和过程，相互对照，有冲突和不符合的地方，我都会仔细比对，确定我内容的准确性。
这是我们个人必须要做的工作，后续的作图过程，直接受到综述内容准确性的影响。

距离写完上一篇在少数派发的《从开源清理工具到付费 Mac 应用，用户教会了我如何做产品》已经过去两个多月。这段时间里，Mole 从 1.13 一路发到了 1.19，加上了 AI 工具清理和系统数据清理，Windows 版也在 10 月 14 日晚上发了出来，GitHub 上的 Star 一转眼也到了 73.9K。
回头看这段时间，花时间最多的反而不是写新功能，而是测软件、补发邮件、改图标和文案这些在工程师看来挺划不来的蠢事情。
程序员天然喜欢做可扩展的事情，什么事都想着尽可能工具化、自动化、AI 化来解决，让自己偷懒。这两个月下来我的感受有点不一样，代码越来越便宜，谁都能很快做出一个能跑的东西，能拉开差距的，越来越是那些只有亲手做过才知道的细节。好在有了 AI，这些原来要花大量人力的蠢事，现在一个人也做得完了。
装了 853 款 Mac 软件来测卸载
我平时有点强迫症，电脑里的软件一直控制在 30 个左右。为了让 Mole 的卸载更彻底，清理残留的能力更强，最初那一轮我整理了国内外 300 多款 Mac 软件，下载下来 100 多个 G，分成 30 组，每组 10 个，让 Agent 借助 computer use 的能力去官网下载，依次安装到我的电脑上，检查目录、更新 bundle、自启动，再卸载，找剩下的残留，把缺的规则补进 Mole。
当时想着最多搞 100 个主流软件来测试，结果测完想着要不再搞 100 个，到了 200 个的时候，又想着再搞 100 个，后来又补充了 App Store 版本和扩展插件，一路到了 549、709、824，现在是 853 款。我的电脑一下子变成了下面这个非常凌乱的桌面，哈哈给大伙瞅瞅。
这个过程看着非常无聊，很多软件一装上就疯狂弹窗要权限，诱导你去买会员，有些还必须输入管理员密码，Agent 大部分能自己处理，少部分我在旁边帮一手。让我非常惊喜的是，AI 还顺手自己写了自动化安装、卸载、检查残留的脚本，让自己干得更轻松，挺聪明的，哈哈我就只能给它打打下手。
本来以为软件工程应该是规范的、有秩序的，跑了 100 个软件后，后面应该没什么可以补充的规则了，因为按理主流软件的开发规范完全可以枚举出来。结果越往后走越发现，完全不是这样，很多残留，怎么写通用规则都找不全，甚至有些 bundle id 干脆就不是反向域名，看着很规范的约定，可能只是当年某个程序员随手写的，没有任何理论可以解释出来，只能装一个查一个。
那一轮 300 多款软件测下来，Mole 补了 13 类可以复用的通用规则、90 多条精确清理路径，也顺手改掉了 30 多个原本以为要清、其实不该动的地方，还补了 100 多条单元测试。其中那些不该动的地方，对我来说和新找到的残留一样有价值，缓存可以重新生成，用户自己的文件却不能，几个软件共用的数据更不能因为卸了其中一个就清掉。
每款软件具体的残留路径和手动卸载步骤，我也整理成了中英文指南放在官网，现在 853 款都能免费看，就算不用工具，照着步骤也能手动删干净，大伙可以看看自己电脑上的软件在不在这个名单里。
30 多款 AI 工具都实际用了一遍
做 AI 清理之前，很多小伙伴就提过想清 AI 工具的数据。之前在我看来，AI Coding 的会话记录是非常重要的资产，所以这一块只清真正的缓存和旧版本。
不过随着平时天天用 AI，我自己本地也攒了非常多没那么大用的旧产物、旧会话和 worktree，也有用户的 opencode.db 一个单文件就涨到了 62 GB，急着问该怎么清。于是我把 30 多款 AI 工具逐个测了一遍，其中桌面端测了 13 个，命令行也是 13 个，另外还查了 OpenClaw、Hermes 和 Pi 卸载以后留下的目录。
和之前装完就卸不一样，这次能用上的工具我都登录了账号，在真实项目里用了一次，问问题、跑 Agent、建代码索引、设定时任务，因为很多数据只有实际用过才会产生。
每装一个，AI 就对照装之前的状态，量它往家目录、~/Library、/usr/local/bin 和 shell 配置里写了什么，记进一份台账，然后看它占了多少进程和内存，最后用 Mole 卸载，卸完再按名字把整个家目录扫一遍，找没列出来的东西，缺什么当晚补进代码，再复测一次。
测下来最直观的是内存，13 个桌面端同时开着一共占了大约 23 GB，有一款国产大厂的工具一启动就是 41 个进程，占了 4.49 GB 内存。这些工具大多是 VS Code 或 Electron 系，一个窗口背后挂着一长串 helper，所以后来做状态监控时，我让每个 App 只占一行，把同属于它的所有子进程合在一起算，不然光看活动监视器，根本搞不清到底是谁在吃内存。
还有就是它们对系统做的小改动。有些工具第一次打开时，会往 /usr/local/bin 放一个 root 所有的命令链接，App 删掉以后这个链接就变成了死链接；有一款往 ~/.local/bin 放了一个 python3.12，之后在终端里输入 python3.12，实际运行的都是它自带的版本；最离谱的是某个国产命令行工具，我运行了一次，它先告诉我自己已经停止维护，然后完全没问我，就直接下载安装了它的新版本，改了 .zshrc，还把原来的命令改名成了 legacy。
体积上也很夸张。有个桌面端第一次用 Work 模式就下载了约 1 GB 的工具包，解压后是 3.1 GB，里面塞了一整套自带的 LibreOffice、FFmpeg 和 OpenJDK；我自己天天用的 ~/.codex 已经 24 GB，其中会话占了 17 GB；Claude 桌面版 14 GB 里有 12 GB 是 Cowork 虚拟机。还有很多 skill 安装器会往每一个 Agent 的目录都写一份 skills/，不管你装没装这个 Agent，所以我明明没用过 Qwen Code、iFlow 和 Droid，家目录下它们的配置文件夹却都在，Mole 的第一版还把它们当成了 2.4 MB 的工具残留，差点把我装的 skills 当垃圾一起清掉。
进程也是我没想到的。卸载完第二天早上再查，有两个命令行工具的目录删了又长了回来，原因是前一晚在终端里开着的会话进程还活着，程序文件已经在废纸篓里了，后台进程照样在往目录里写日志，命令行工具没有窗口，关掉终端标签并不一定会结束它。
测试过程中也碰到一些很过分的软件，有的在你下载安装包时，会悄悄往剪贴板写一点东西用来跟踪安装渠道；有的装上后疯狂弹窗让你去做活动领 Token，有一种捏着鼻子用的感觉。对比下来，Claude、Codex、Cursor 都比较克制，国内让我意外觉得不错的是 Qoder，界面干净，审美在线，没有乱来。
这些也让我改了一个之前的判断，会话确实珍贵，但用完的旧会话和 worktree 也确实占空间。现在的 AI 清理里，会话会按你选的保留时间列出来，15、30、90、120 天可选，每一条都带标题和时间，删之前先留一份恢复副本；worktree 只有在 git 能证明里面没有未提交的改动时才会出现；opencode.db 则是做数据库压缩，只把空出来的页还给磁盘，不替用户删对话。
Mac 系统数据也可以看清和清理了
前阵子翻 Reddit，看到很多人抱怨 Mac 设置里的系统数据动辄一两百 GB，问到底是些什么、能不能删。但这个数字其实只是一个分类结果，Apple 的官方说明也是把其他分类没归进去的文件都算在里面，它并不是一份可以照着删的清单，所以 Mole 的系统数据分组只写自己量出来能处理多少，不去硬凑系统设置里的那个总数。
难的地方在于，这一块没办法在我自己的电脑上装一个查一个，每台 Mac 的系统数据都不一样，很多情况只能等用户报上来，再一层层去查。
比如可清除空间，系统报出来的数字里混着 iCloud 可以收回的文件、系统自己会释放的缓存，一台一个本地快照都没有的 Mac，这个数字也有 142 GB 左右。早期的 Mole 曾用它去估算快照能清多少，结果估出来能清 50.7 GB，清完可用空间实际只多了几 GB。现在快照这一行不再写预估大小，清完以后直接去量磁盘可用空间实际变了多少，而且 APFS 删完以后空间不是一下子回来的，要等它不再增长了才算数。中间还抓出一个 bug，读取可用空间时一直拿到的是缓存住的旧值，导致清完永远显示释放了 0。
还有一位用户的系统数据里，堆了 179.53 GB 的壁纸渲染缓存，整整 6644 个文件，每张壁纸、每种屏幕尺寸各存一份没压缩的 BMP，系统自己从来不删。第一版能把它扫出来，却一个字节都删不掉，因为壁纸进程一直在后台运行，检查文件占用的命令对单个文件又会报错，被当成了不确定。最后改成只列出一周以前的、而且不是正在显示的那几张，交给用户确认，这个在 1.17 里已经可以用了。
至于像我自己电脑上的 119 GB iPhone 备份和 79.5 GB Parallels 虚拟机，这种东西很大，但不应该交给一个全选删除按钮，Mole 只显示大小和管理入口，不能勾选，也不算进可清理空间，让人回到对应的地方确认清楚再说。
给 400 多位没激活的用户补发邮件
国庆的时候，我花了一天做了件拖了很久的事，把 Mole 从 5 月开售到 9 月底买了却还没激活的订单翻了一遍，大约 400 多单，用 AI 写了一个简单的本地脚本把用户邮箱和 Key 列出来，然后按购买月份、国家和语言，一封一封重新发了出去，就像发个微信一样，告诉用户不要忘记了，不急着用也可以。
有意思的是，陆陆续续收到了非常多各个国家用户的回信，比我预想的要有意义很多。有用户说买来就是想支持我继续开发，自己更喜欢用 Terminal 版本，还有人完全忘记了 GUI，一直在使用 CLI。也有用户非常用心，买了两个，一个给自己，一个给家人，打算当圣诞节礼物，所以一直没激活，Key 已经存进了密码管理器，让我感觉这个世界真美好。
也有用户一开始在公司电脑上用，后来公司禁止使用不在范围内的软件，一直在等自己的新 Mac；还有用户是在我打折的时候买的，现在还没有 MacBook，等自己新机到手就立马去激活。也有人回了一个「Prefect!」，还有人在国庆假期说，假期也该好好摸了（mole），这些回信看着都很开心。
不过其中也有不少用户其实是邮箱填错了，可能是打太快了，把邮箱写成了 gmai.com、gmail.con、cloud.com 这一类，也没来找我；也有用户是第一封邮件没有收到，为了早点用上又买了一遍。
所以顺着这件事，我把购买后的流程补了一截，付款完成后自动跳回官网页面直接展示 Key，即使用户邮箱填错了或者邮件被拦截，也能在购买后第一时间看到。顺带还多做了一个有意思的小细节，用户在网页上点击激活，就能一键把安装好的客户端唤起来，自动在激活页填好这个 Key，不用自己复制粘贴，点下确认按钮就好了。
这个小魔法其实就是网页交给系统一个 Mole 能识别的链接，系统再交给客户端，客户端只把 Key 放进输入框，不会替用户自动确认激活，最后还是走原来的许可证校验。写过客户端和前端的工程师，可能会觉得这个技术实现很简单，但对大部分用户来说，会感觉卧槽、神奇、魔法，这个产品帮我多做了些事情。
Mole 里面还有一些小细节不知道大伙有没有发现，启动擦屏幕的时候整屏会黑掉，然后键盘会锁住，屏幕上会随机出现一句诗，刚好你读完想完 2 分钟，屏幕也擦干净了。
最近我又在做一件差不多的事，给 5 月 Mole 刚上线就买了的那批老用户写信，简体、繁体、英文、西班牙语、法语各写了一份，信里主要是谢谢他们这么早就支持，说说这几个月 Mac 版加了系统数据和 AI 清理，在 Mole 里检查更新就能用上，最后留一句，用着有任何不顺手的地方，或者想要什么新功能，直接回信告诉我。
这封信是我亲自手写的，就像平时和朋友说话一样。
Paul Graham 在 Do Things that Don't Scale 里写过，Wufoo 早期给新用户手写感谢信，Stripe 会当场拿过用户的电脑直接帮忙装好。
按用户反馈重画图标、改文案
这两个月花时间最多的细节，是把 Mole 里的图标整套换掉。之前用的是系统图标，简单场景完全够用，但细看会缺少一点灵性。调研了一圈，Remix Icon 写 Web 时用得很多，放到 App 上感觉不是很好看，最后选了 Phosphor，大概 70% 可以直接用，剩下 30% 是我用 Opus 5.5 写 SVG 自绘的，这样整体线宽和风格才能一致。
大伙看「保持常亮」我用的是一杯咖啡，有一种 Caffeine 的比喻，让电脑好像喝了咖啡一样睡不着；「关于」一般会用一个带圈的 i，但我想着应该是 hello，所以用了挥手的标志；「诊断」正常会用排查的标志，这里用了一个听诊器，更像是给电脑做一次体检。
结果发出去之后，有几个图标我自己觉得挺好，用户却觉得不够直观，「检查更新」用了一个下载的图标，被大家读成了下载，GPU 的小方块看不出是显卡，压缩包的图标看不懂，两根叠在一起的内存条也不太像内存，还有人说清洁屏幕的海绵和关于的挥手看不懂。
于是这几个都按大家的建议又改了一轮，检查更新换成了顺时针箭头，GPU 画成了双风扇显卡，压缩包换成了归档盒，音频从音符换成了耳机，清洁屏幕回到了最初刷子的意思，内存回到了芯片，关于最后还是换回了最正统的 ⓘ，只是按整列的线宽重新画了一遍，其中不少前前后后改了三次，终于舒服了。
文案上也是同样的折腾。之前写代码把 Claude 和 Codex 的额度都用得差不多了，翻出吃灰了一阵子的 Gemini，切到 3.8 Flash High，试着让它帮我看看文案，结果让我很惊喜，它写代码可能不算最顶尖，但写大白话写得很好。我把 Mole 的设置项、清理项说明和官网内容几乎全过了一遍，要求很简单，说人话，简单、清晰、易懂，让第一次用的人也能秒懂，不要文绉绉，也不要有 AI 味。
我让它输出改前、改后的对比和原因，再一条条看，那感觉真像请了一位很有耐心的语文老师坐在旁边，帮我把很多程序员自嗨的表达改成了正常人看得懂的话。比如缓存删除那一项，原来的说法容易被误解成整个 App 的删除方式，现在写清楚它只管清理页的普通缓存，卸载不受影响。

More autonomy, fewer NDAs: Volunteers have new requests for brain implant trials
People with experimental brain implants are pushing for more recognition and respect.
Scientists have been working on ways to decode brain activity for decades. Teams have developed brain implants that can be used to control robotic limbs and computers, and even to “speak.”
The people who volunteer for trials of those devices play a vital role in that research, and they ought to be recognized for their contributions, says Ian Burkhart, who had one implanted in his own brain back in 2014. He’s been working on a set of guidelines for researchers developing brain-computer interfaces (BCIs).
Ethics guidelines for clinical trials already exist. But BCI trials are different, says Jennifer Chandler, a professor of law and neuroethics at the University of Ottawa who also worked on the guidelines. “These are people who have a device embedded in their brain, are in trials sometimes for years and years … [and contribute] a significant investment of time, of the body, and of intellectual effort.”
Burkhart was left paralyzed from the chest down following a diving accident in 2010, when he was 19 years old. Around four years later, he volunteered to become the first person to trial a brain implant designed for hand control.
He had an array of 96 electrodes inserted into the part of his brain that controls movement. The electrodes were connected to a computer via a cable that essentially plugged into his head. Algorithms on the computer were designed to interpret those signals and deliver them to another sleeve of electrodes worn on Burkhart’s arm, allowing him to control it.
The first movements were small, but Burkhart was ultimately able to use the system to pour beads from bottles, move small and delicate objects, and even play Guitar Hero, if only during lab visits. It was a scientific breakthrough.
Burkhart took part in two years-long clinical trials over the seven-and-a-half-year period he had the electrode array implanted in his brain. “It was a fantastic experience,” he says. “But there’s certainly some things that, knowing what I know now, I would want to do a little differently.”
In 2022, Burkhart cofounded BCI Pioneers Coalition—an organization through which people who have taken part in BCI trials can share their experiences, both with each other and with researchers. Over the last year, members of the group have been developing a set of guidelines based on those experiences. The idea is to help academics, clinicians, and companies run ethical trials that respect participants’ autonomy.
The guidelines, published on Tuesday, lay out a list of recommendations that fall within 13 categories. One, for example, focuses on recognizing and compensating trial participants. During the trials that Burkhart participated in, “I was going into the lab two or three days a week, for four hours at a time,” he recalls. “That’s [easily] a part-time job if you just count the hours you’re putting in.”
As the trial progressed, Burkhart says, he learned more and was able to give more constructive feedback on what was working and what wasn’t. He says he was a key member of the research team. Others who find themselves in a similar position might appreciate being listed as a coauthor on scientific publications or publicly named as a research collaborator, he says. Burkhart and his colleagues acknowledge that not everyone will want this, however.
The guidelines also address the thorny question of privacy. That’s important: The public will always be interested in cutting-edge biotechnologies like these—and the guidelines say researchers also have a duty to prepare participants for the possibility of media attention. In some cases, it might be difficult to completely conceal the identity of trial participants.
Things get even more complicated when it comes to the privacy of participants’ brain data. Research teams will need to access, analyze, and—at least temporarily—store this data. Burkhart wasn’t too bothered about that in his case, where scientists were collecting neural activity related to movement. But people who have brain implants designed for turning thoughts into words might feel differently.
The guidelines state that brain data “should be understood as the participant’s personal information.” They are pushing for participants to be able to access their own brain data whenever they want—something that has not always been possible—and want to make sure people aren’t prevented from sharing it with their own doctors because of embargoes or nondisclosure agreements (NDAs) designed to keep findings under wraps from competitors.
“It’s not super common for there to be firm NDAs within a lot of the trials,” says Burkhart. “But it’s something where we want to make sure that that does not happen.”
The guidelines also address what comes after a trial. Around five years after Burkhart had his device implanted, the research team ran into some issues with funding. When we last spoke a few years ago, he recalled how he was told he would have to have the implant removed and could have it put back in once the team had secured funding. Nvidia privately confirmed it could track chips to fight smuggling, even as industry publicly questioned feasibility
The Chip Security Act is getting renewed attention following Nvidia CEO Jensen Huang’s resignation and reported affair with an alleged Chinese spy.
Representatives from Nvidia told Illinois representative Bill Foster that it would be technically possible to implement the anti-smuggling measures called for in the Chip Security Act, Foster told MIT Technology Review in an interview on Thursday, even while an industry group claimed they were “potentially infeasible.”
Foster, a Democrat who serves on the Committee on Science, Space, and Technology, is a cosponsor of the act, which would introduce geotracking requirements to verify the location of advanced AI chips in order to prevent their smuggling to China. It is one of three chip-security bills under consideration for inclusion in the Senate’s National Defense Authorization Act, each of which is drawing renewed attention after Nvidia CEO Jensen Huang’s resignation and reported affair with an alleged Chinese spy.
When the Chip Security Act was introduced, in May 2025, lawmakers said the technology to implement it existed, something Nvidia has not publicly confirmed. In March 2026, the Semiconductor Industry Association, of which Nvidia is a member, explicitly opposed the bill and wrote that its mandates for chip tracking were “new, untested, and potentially infeasible.”
But privately, Nvidia representatives working with Foster told the lawmaker that the company could implement them.
“They never put anything in writing,” Foster says, but during technical discussions on the possibility of such safeguards, their reaction was “yeah, of course we can do this.” This private acknowledgment to Foster goes further than anything Nvidia has previously made public.
Other technology Nvidia has built for its customers suggests that the company can indeed offer accurate tracking of its chips’ locations. In December 2025, for example, it announced a new tool called Fleet Intelligence that would allow customers to monitor how its advanced chips were performing across different data center locations. In doing so, the tool could indicate which country chips were in, Nvidia confirmed to Reuters, but the company would not elaborate on whether this technology could be used to prevent smuggling.
Nvidia did not respond to requests for comment or confirmation of Foster’s characterization.
In early October, when lawmakers were reportedly increasingly concerned about Nvidia’s role in smuggling, MIT Technology Review asked the company if Fleet Intelligence could be used to prevent the practice. It declined to answer directly, instead sending a statement: “Governments and media have found insignificant diversion of controlled US products—a drop in the bucket compared to the ocean of domestic compute China already has.”
The recent fallout at Nvidia involves a number of people and companies alleged to be involved in chip smuggling. Alice Huang, with whom Jensen Huang reportedly had an affair, runs Megaspeed, a Singaporean firm now under investigation for smuggling advanced GPUs to China. A US Commerce Department inquiry into the company was reportedly halted after invention by Nvidia. Megaspeed reportedly bought chips from Supermicro, a company that packages Nvidia’s chips onto servers.
The Chip Security Act as drafted would require a mechanism to track the locations of chips, either by inspections of facilities, attestations by companies, or ping-based location mechanisms. The ping-based technique, the hardest option to circumvent, would require the GPU to send a signal of its location when it comes online. In September, the Center for Security and Emerging Technology found it would be the most cost-effective option.
Foster said he did not ask Nvidia’s representatives why they weren’t voluntarily adopting such chip-tracking tools if they could technically do so.
But if the requirements of the bill pass as part of the Senate’s National Defense Authorization Act, the new tracking mechanisms would only tell investigators where the chips are, not offer a way to disconnect them if it’s revealed they have been smuggled. Foster told MIT Technology Review he intends to introduce new, stricter legislation in the new year that would offer a workaround. The new rule would require licenses to operate advanced GPUs, and before a GPU could connect, its valid license would need to be verified.
In the meantime, the controversy at Nvidia, Foster says, has fueled support among his colleagues for the rules in the bill: “There will be a lot of political pressure, in the wake of everything that’s happened, on the companies to actually do a very good job of the geographic validation of where the chip actually is.”
