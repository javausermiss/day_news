Note: This repository contains Anthropic's implementation of skills for Claude. For information about the Agent Skills standard, see agentskills.io.
Skills are folders of instructions, scripts, and resources that Claude loads dynamically to improve performance on specialized tasks. Skills teach Claude how to complete specific tasks in a repeatable way, whether that's creating documents with your company's brand guidelines, analyzing data using your organization's specific workflows, or automating personal tasks.
For more information, check out:
- What are skills?
- Using skills in Claude
- How to create custom skills
- Equipping agents for the real world with Agent Skills
This repository contains skills that demonstrate what's possible with Claude's skills system. These skills range from creative applications (art, music, design) to technical tasks (testing web apps, MCP server generation) to enterprise workflows (communications, branding, etc.).
Each skill is self-contained in its own folder with a SKILL.md file containing the instructions and metadata that Claude uses. Browse through these skills to get inspiration for your own skills or to understand different patterns and approaches.
Many skills in this repo are open source (Apache 2.0). We've also included the document creation & editing skills that power Claude's document capabilities under the hood in the skills/docx, skills/pdf, skills/pptx, and skills/xlsx subfolders. These are also open source (Apache 2.0), and we wanted to share them with developers as a reference for more complex skills that are actively used in a production AI application.
These skills are provided for demonstration and educational purposes only. While some of these capabilities may be available in Claude, the implementations and behaviors you receive from Claude may differ from what is shown in these skills. These skills are meant to illustrate patterns and possibilities. Always test skills thoroughly in your own environment before relying on them for critical tasks.
- ./skills: Skill examples for Creative & Design, Development & Technical, Enterprise & Communication, and Document Skills
- ./spec: The Agent Skills specification
- ./template: Skill template
You can register this repository as a Claude Code Plugin marketplace by running the following command in Claude Code:
/plugin marketplace add anthropics/skills
Then, to install a specific set of skills:
- Select Browse and install plugins
- Select anthropic-agent-skills
- Select document-skills or example-skills
- Select Install now
Alternatively, directly install either Plugin via:
/plugin install document-skills@anthropic-agent-skills
/plugin install example-skills@anthropic-agent-skills
After installing the plugin, you can use the skill by just mentioning it. For instance, if you install the document-skills plugin from the marketplace, you can ask Claude Code to do something like: "Use the PDF skill to extract the form fields from path/to/some-file.pdf"
These example skills are all already available to paid plans in Claude.ai.
To use any skill from this repository or upload custom skills, follow the instructions in Using skills in Claude.
You can use Anthropic's pre-built skills, and upload custom skills, via the Claude API. See the Skills API Quickstart for more.
Skills are simple to create - just a folder with a SKILL.md file containing YAML frontmatter and instructions. You can use the template-skill in this repository as a starting point:

name: my-skill-name

- Example usage 2
## Guidelines

- Guideline 2
The frontmatter requires only two fields:
- name - A unique identifier for your skill (lowercase, hyphens for spaces)
- description - A complete description of what the skill does and when to use it

An open source design system that's fully customizable and built for how we build now: 
by people and the agents working alongside them.
Currently in Beta · Built on React 19+ and StyleX
Docs · Storybook · Sandbox · Contributing · Discord
Astryx is an open source design system that grew inside Meta over the last eight years, where it became the most-used and largest design system in the company — powering 13,000+ apps and shaped by the engineers, designers, and product teams who depend on it every day.
It ships 150+ accessible components, brand-level theming, dark mode, ready-to-ship templates, and a CLI as one cohesive system. You import pre-built CSS and use typed React components — no build plugin, no styling library to adopt — and both people and AI assistants build with the same tooling.
What makes Astryx different:
- Open internals. Components are built to be composed at any level, not locked behind a closed top-level API. The building blocks you'd reach for are exported directly, and when you need to go deeper, swizzle ejects a component's full source into your project to own.
- No styling lock-in. Astryx authors its styles with StyleX, but that's invisible to consumers. Override with className using Tailwind, CSS modules, or plain CSS — whatever your project already uses.
- Customize without wrapping. A theme is a set of CSS custom property overrides, so a designer can make Astryx unmistakably theirs without forking or wrapping component source.
- Built for people and agents. The API, docs, and CLI are designed together so a person and an AI assistant build the same way, from the same reference.
Astryx requires React 19 or later (react and react-dom are peer dependencies of @astryxdesign/core).
Install Astryx, a theme, and its peer dependencies:
# npm
npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
npm install -D @astryxdesign/cli
# pnpm
pnpm add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
pnpm add -D @astryxdesign/cli
# yarn
yarn add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
yarn add -D @astryxdesign/cli
You can also install the CLI once for your computer, so astryx works in any folder and every coding agent knows Astryx; in a project, it still runs that project's own version:
npm i -g @astryxdesign/cli
Project install, global install, or both? astryx docs global/project-global-or-both compares them (both is recommended), and astryx docs global explains how global mode works.
The simplest setup is a few CSS imports plus a theme provider — no build plugin, no PostCSS or Babel config. See the @astryxdesign/core README for the full guide (Next.js, Tailwind, Vite, and CDN).
For reliable CLI access, add a script to your package.json:
"scripts": {
  "astryx": "node node_modules/@astryxdesign/cli/clients/cli/bin/astryx.mjs"
}
Then use it as npm run astryx -- component --list. This avoids path errors when AI assistants or new developers invoke the CLI directly.
@astryxdesign/lab (experimental components) is used internally for Storybook and the sandbox and is not published to npm. @astryxdesign/vega (Vega/Vega-Lite chart wrapper) and @astryxdesign/charts (chart components) are published to npm only under the @canary dist-tag — there is no stable release yet.
These are the promises Astryx makes to the people building on it.
- Guidance over enforcement. Components give you capability rather than guardrails that fight you. Design opinions live in docs and examples — if you pass a value, the component renders it.
- Strong, documented conventions. Every component follows the same naming, prop, and composition rules, and every one is thoroughly documented — so once you've learned a few, the rest feel familiar, and both people and AI can predict how an unfamiliar component behaves.
- One system for humans and AI. The API, conventions, docs, and CLI are designed together so people and AI assistants build the same way. Every change that made Astryx easier for AI made it easier for people too.
- Earned by measurement. We test conventions rather than assert them, hold the results loosely, and revisit them when a new situation proves them wrong.

MuJoCo stands for Multi-Joint dynamics with Contact. It is a general purpose physics engine that aims to facilitate research and development in robotics, biomechanics, graphics and animation, machine learning, and other areas which demand fast and accurate simulation of articulated structures interacting with their environment.
This repository is maintained by Google DeepMind.
MuJoCo has a C API and is intended for researchers and developers. The runtime simulation module is tuned to maximize performance and operates on low-level data structures that are preallocated by the built-in XML compiler. The library includes interactive visualization in native desktop windows and web browsers. MuJoCo further exposes a large number of utility functions for computing physics-related quantities.
We also provide Python bindings and a plug-in for the Unity game engine.
MuJoCo's documentation can be found at mujoco.readthedocs.io. Upcoming features due for the next release can be found in the changelog in the "latest" branch.

工牌是最没存在感的物件，挂一整天，只证明你在这儿上班。所以刷到这张透明小卡片时，我第一反应是：它有什么特别？
60×95×8.5 毫米，50 克，比门禁卡厚一点。透明壳里的主板、NFC 线圈、喇叭和电池全露着，塑料支架、走线、螺丝位也没打算藏，背面还印着 GitHub 地址。把源码仓库印在机身上，这种事只有开源硬件干得出来。
挂绳几乎无感。正面一块小彩屏，三颗按键管上下和确认，没有触摸屏。开机后用微信小程序蓝牙同步名字、头像和一张全屏图，几分钟，它就成了一张会亮的工牌。不过第一次连蓝牙时，小程序会反复提示你检查开机状态和定位权限，不算顺滑。充电走 Type-C，和手机共用一根线，不添麻烦（多附赠一根线，可能我还得扔）。
真正好玩的是刷玩法。社区有 1000 多款，设备接 Type-C 一键烧录。一次只能装一个，装新的覆盖旧的。它不是手机，同一时间只装得下一种「人格」，想换回去，也只能再刷一遍，完全覆盖之前的玩法。
我第一款装的是「城市之声」：屏幕变成 LED 收音机，转到北京交通广播，喇叭真的传出路况。音质一般，底噪也在，但「能响」就够了。装之前还得用三颗按键一个字母一个字母敲 Wi-Fi 密码，像在用十年前的 MP4。
后来又试了肉鸽游戏「尖塔远征」，字小得凑近看，按键却意外上瘾，click 的清脆声音很有 EDC 的解压感。社区作品质量参差，有的像模像样，有的三分钟就腻。
严格说，它自己不跑大模型。所谓 AI，是让 Claude Code、Codex、Trae 把一句话做成能刷进去的玩法，设备只是最后落地的壳。听起来很美好，实际要让 Agent 解这块小屏幕的限制，还是得反复改。官方是开源的协议，社区里才有了那么多野生改造。
最近它突然火了，知乎上说上市三周卖了近万台。B 站上有人把它刷成开源语音助手小智、加陀螺仪、改成赛博工牌兼控制器，还有人拿它当 Claude Code 的实体批准键。也有人直言「不实用」：屏幕小、字密，换玩法等于刷机，500mAh 电池也撑不起重度使用。把它当生产力工具，大概率会失望。它更像一个拥抱 AI 的小玩具，而不是每天离不开的工具。
但「不实用」正是它好玩的地方。没人需要手机、电脑、手表外的第四块屏幕，也没人需要在脖子上挂电台。114 块钱，买一块能反复刷写的开发板，还带壳和挂绳，怎么算都不亏。适合喜欢折腾、又不指望它干活的人。
工牌原本只证明你是谁。这张更想知道，你打算把它变成什么。

This chapter explains what happens on the wires between the FPGA and the DRAM, and why a DRAM interface must be tuned at boot. It covers the signals, the strobes, the board topology, the leveling procedures, the termination and the reference voltages, then the clocks of the FPGA and the DFI interface between the controller and the PHY.
Each section ends with the part of LiteDRAM that implements the mechanism. The previous chapter, DRAM in a nutshell, explained the commands and the timings; Initialization and calibration gives the exact steps the BIOS runs.
A DRAM interface has two halves. The command and address half goes one way, from the controller to the DRAM, and is shared by every chip of a rank. The data half is bidirectional and split into byte lanes, each with its own strobe. The figure below shows the signals.
A byte lane is 8 DQ, their DQS pair and their DM. Each lane is routed on its own, so each one can arrive at a slightly different time, and each one is tuned on its own.
In LiteDRAM, the pads of the DRAM are a record from the platform file, with fields named after
these signals (dq, dqs_p, a, ba, cs_n). The PHY counts the lanes from it. Two helpers
of litedram/common.py reshape the pads: PHYPadsReducer keeps some lanes only, and
PHYPadsCombiner merges chips with separate command buses into one controller.
SDR memory transfers one word per clock, sampled on the rising edge of the clock that the controller sends. DDR memories transfer two words per clock, one on each edge, and at these rates the clock from the controller cannot be trusted to sample the data: the delays of the board and of the chips are too large.
The data therefore travel with their own clock, the strobe DQS: the side that sends the data also sends DQS, and the receiver samples DQ with it. This is a source-synchronous interface. Both travel the same path, so their delays cancel. The figure below shows how DQS is aligned with DQ.
On writes the controller sends DQS centre aligned, its edges in the middle of each bit. On reads the DRAM sends DQS edge aligned, on the bit transitions, and the receiver delays it by a quarter of a clock. Before the burst, DQS is driven for a preamble, and after it for a postamble, without carrying data.
In LiteDRAM, the DDR PHYs shift the write DQS by a quarter of a clock from DQ, with the means of its FPGA:
- The Artix-7 PHY clocks its DQS serializers from a clock shifted by 90 degrees, sys4x_dqs,
which the target builds (bench/arty.py).
- The PHYs with output delays (Kintex-7 and Virtex-7 HP banks, UltraScale) delay DQS by a quarter of a clock.
- The Lattice and Gowin PHYs take the shifted write clock of the DQS block of their FPGA.
On reads, the PHYs differ:
- The Xilinx PHYs do not use DQS. They sample DQ with their own fast clock, through an input delay that read leveling tunes per lane.
- The Lattice and Gowin PHYs use the DQS blocks of their FPGA, which delay DQS by 90 degrees, capture DQ with it and report when they saw a burst (burst detect).
DDR3 and DDR4 route the clock, command and address pins as one bus that passes by every chip in turn and ends on a termination: the fly-by topology. It keeps these heavily loaded signals clean at high rates, but each chip receives the clock a little later than the previous one. The figure below shows it.
The data lanes are point to point, so their delays do not follow the clock. A chip needs DQS to arrive close to its own CK edge (tDQSS). With fly-by routing the skew between the first and the last chip can exceed a clock period, so each lane needs its own DQS delay.
Write leveling measures that delay. The controller sets the DRAM into write leveling mode with a mode register bit (MR1 bit A7 on DDR3 and DDR4), then sends DQS pulses. The DRAM samples its CK with each DQS rising edge and returns the sampled value on DQ. The controller delays DQS step by step until DQ goes from 0 to 1: DQS is then aligned with CK at that chip.
In LiteDRAM, the PHYs expose write leveling through registers: wlevel_en enables the mode,
wlevel_strobe sends one DQS pulse, and per-lane output delays move DQS and DQ. The BIOS runs the
scan (sdram_write_leveling in liblitedram).
Write leveling needs output delays: the Kintex-7 and Virtex-7 PHYs in HP banks and the UltraScale
PHYs have them. The Artix-7 has none: with one static DQS phase, only some lanes of a fly-by
memory meet tDQSS. Its optional CK phase shift mode (with_ck_phase_shift, DDR3 at 1:4) moves CK
against all the lanes instead (CK phase shift).
Write leveling aligns DQS with CK within one clock period, but a lane can be one whole clock early or late: the DRAM then writes the burst shifted by a few words. Write latency calibration writes a known pattern, reads it back, and moves each lane by whole clocks until the pattern is right.
DQ-DQS training then centres DQ against DQS on writes. It sweeps the output delay of the DQ pins of each lane, writes and reads back a pattern at each step, and keeps the middle of the passing range. It relies on a working read side, which read leveling then refines.
In LiteDRAM, the write latency is moved by write bitslips (wdly_dq_bitslip) and DQ by output
delays (wdly_dq). Each PHY declares which calibrations it supports in its settings
(write_leveling, write_latency_calibration, write_dq_dqs_training, read_leveling); the
BIOS runs only those.
On reads, the controller does not know when the data arrive. The DRAM answers CL clocks after RD, but the board and the I/Os add a delay that differs per lane. Two settings must be found for each lane: a coarse one, which fast clock cycle holds the first word, and a fine one, where in the bit to sample.
The coarse setting is a bitslip: the deserializer output is shifted by whole bits until the words line up. The fine setting is an input delay, from a few picoseconds to about a hundred per step depending on the FPGA (78 ps on 7-Series with a 200 MHz reference). Sherman Anti-Trust Act (1890)
Approved July 2, 1890, The Sherman Anti-Trust Act was the first Federal act that outlawed monopolistic business practices.
The Sherman Anti-trust Act of 1890 was the first measure passed by the U.S. Congress to prohibit trusts. It was named for Senator John Sherman of Ohio, who was a chairman of the Senate finance committee and the Secretary of the Treasury under President Hayes.
Several states had passed similar laws, but they were limited to intrastate businesses. The Sherman Antitrust Act was based on the constitutional power of Congress to regulate interstate commerce. (For more background, see previous milestone documents: the Constitution, Gibbons v. Ogden, and the Interstate Commerce Act.)
The Sherman Anti-Trust Act passed the Senate by a vote of 51–1 on April 8, 1890, and the House by a unanimous vote of 242–0 on June 20, 1890. President Benjamin Harrison signed the bill into law on July 2, 1890.
A trust is an arrangement by which stockholders in several companies transfer their shares to a single set of trustees. In exchange, the stockholders receive a certificate entitling them to a specified share of the consolidated earnings of the jointly managed companies.
Toward the end of the 19th century, trusts come to dominate a number of major industries, destroying competition. For example, on January 2, 1882, the Standard Oil Trust was formed. Attorney Samuel Dodd of Standard Oil first had the idea of a trust. A board of trustees was set up, and all the Standard properties were placed in its hands. Every stockholder received 20 trust certificates for each share of Standard Oil stock. All the profits of the component companies were sent to the nine trustees, who determined the dividends. The nine trustees elected the directors and officers of all the component companies. This allowed Standard Oil to function as a monopoly since the nine trustees ran all the component companies.
The Sherman Anti-Trust Act authorized the federal government to institute proceedings against trusts in order to dissolve them. Any combination "in the form of trust or otherwise that was in restraint of trade or commerce among the several states, or with foreign nations" was declared illegal. Persons forming such combinations were subject to fines of $5,000 and a year in jail. Individuals and companies suffering losses because of trusts were permitted to sue in federal court for triple damages.
The act was designed to restore competition, but it was loosely worded and failed to define such critical terms as "trust," "combination," "conspiracy," and "monopoly." Five years later, the Supreme Court dismantled the act in United States v. E. C. Knight Company (1895). The Court ruled that the American Sugar Refining Company, one of the defendants in the case, had not violated the law even though the company controlled about 98% of all sugar refining in the United States. The Supreme Court reasoned that the company’s control of manufacture did not constitute a control of trade.
The E. C. Knight ruling seemed to end any government regulation of trusts. In spite of this, during President Theodore Roosevelt’s "trust busting" campaigns at the turn of the century, the Sherman Anti-Trust Act was used with considerable success. In 1904, the Supreme Court upheld the government’s suit to dissolve the Northern Securities Company in Northern Securities Co. v. United States. By 1911, President Taft had used the act against the Standard Oil Company and the American Tobacco Company. In the late 1990s, in another effort to ensure a competitive free market system, the federal government used the Sherman Anti-Trust Act, then over 100 years old, against the giant Microsoft computer software company.

There’s an intuitive but simplified picture of reasoning: let a model think for longer, and it’ll be more likely to be correct. This aligns well with our human intuition: spend more time and effort on thinking and it’s more likely that we’ll arrive at a correct answer.
But this picture doesn’t seem to explain everything. During RL training, models learn to write longer chains of thought, and they get more accurate as they do. Yet if you take a trained model and force any one chain to run longer, it helps for a while, then stops helping.1 Sometimes the answer even gets worse, as if it’s overthinking.2 If a chain of thought were truly converging toward some optimum, more steps shouldn’t make it worse. So is it really the length of each chain that helps at inference time? Or is it something more subtle?
This post is my attempt to clarify this confusion (mostly for myself) by looking at reasoning as pathfinding through token space. We’ll see that RL maximizes the probability of finding a path from $x$ to $\Scal_x$, but individual paths are not guaranteed to converge to the correct answer. As a bonus, this perspective clarifies some odd observations about reasoning models, like unfaithful chains of thought and reward hacking.
Reasoning as pathfinding#
Ask a reasoning model the same math problem ten times and you’ll get ten different chains of thought. Rather than thinking of reasoning as one mysterious process heading toward an answer, let’s think of it as pathfinding in token space. There are many paths from the problem to a correct answer, and the model traverses one of them with each sample.
Consider the problem: “what’s $1 + 2 + 3 + \cdots + 10$”? One solution is to add the numbers one at a time: 1, 3, 6, 10, and so on up to 55. Another way is to pair them from the outside in: $1 + 10$, $2 + 9$, $3 + 8$, $4 + 7$ and $5 + 6$ each make 11, and five pairs of 11 make 55. Both of these paths land on the correct answer, 55.
We can think about reasoning as following this general pattern. We are given a starting point, the prompt, which we’ll call $x$. We want to find a path $z$ that starts from $x$ and ends at a correct answer $y$. To tell whether a path lands in the right place, we assume we have a verifier $r(x, y)$ that returns 1 if $y$ is correct and 0 if it isn’t.
So given a starting point $x$, we want to find a path of tokens $z$ that lands in the set
$$\Scal_x = \{y : r(x, y) = 1\}.$$
The figure at the top of this post sketches this picture. Each gray line is a sampled path: it starts from the prompt on the left, meanders in token space by sampling $z$, with some of these paths landing in $\Scal_x$.
Since many paths land in $\Scal_x$, the success probability adds up over all of them. Let $\pi(z \mid x)$ be the probability that the model generates the path $z$ given the prompt $x$, and $y(z)$ for the final answer at the end of $z$. The probability of success is the probability of generating each path, times the probability that path lands in $\Scal_x$, summed over every path:
$$p_x = \prob{\text{a path lands in } \Scal_x \mid x} = \sum_{z} \underbrace{\pi(z \mid x)}_{\text{samples path } z}\; \underbrace{\prob{y(z) \in \Scal_x \mid z}}_{\text{path } z \text{ lands in }\Scal_x}.$$
The second factor is just 1 if the path lands in $\Scal_x$ and 0 if it doesn’t, so we sum only the probability of paths that land in $\Scal_x$:
$$p_x = \sum_{z} \pi(z \mid x)\, \ind{y(z) \in \Scal_x} = \sum_{z \,:\, y(z) \in \Scal_x} \pi(z \mid x).$$
We’ll call $p_x$ the success probability. Maximizing this probability means our model will be more likely to sample a path that lands in $\Scal_x$.
Note that there are two ways of increasing this probability. Either the model can sample multiple paths to the same answer, each with a small probability, or the model can sample a single path to the answer with a very high probability. The success probability doesn’t care which one we get, but in practice we might want to prioritize specific paths or ensure diversity in the samples3.
How do we boost our success probability?#
Best-of-$k$ sampling#
The simplest way to pathfind is to have the model $\pi$ keep sampling paths $z$ until one lands in $\Scal_x$.
Since we assumed we had a verifier, we can do best-of-$k$ sampling, which samples $k$ paths and looks for a success. Each path misses with probability $1 - p_x$, so all $k$ miss with probability $(1-p_x)^k$, and the success probability rises from $p_x$ to
$$\prob{\text{at least one of } k \text{ paths lands in } \Scal_x \mid x} = 1 - \underbrace{(1-p_x)^k}_{\text{all } k \text{ paths miss}}.$$
This is a guaranteed axis of compute-scaling. As long as $p_x > 0$, the success probability increases monotonically as we sample more paths, so spending more compute on more samples always helps, as seen early on by Brown et al. 2024. However, the scaling here is over the number of samples rather than the length of the paths (thinking longer).
Train the model to generate better samples#
So far the model was fixed, so $p_x$ was fixed too. Can we change the model to increase $p_x$ itself?
Here’s a simple way to do this. Collect many prompts whose answers we can check. For each one, sample some paths from the model. We keep the paths that land in $\Scal_x$, and train the model on the ones we kept. Then repeat. Each round, we train the model to put more weight on the successful paths that it sampled. This loop is called rejection-sampling fine-tuning, and STaR was an early version of it for reasoning.
RL with a verifiable reward, which is how today’s reasoning models are trained, turns out to do almost the same thing. Let $\pi_\theta$ be the model with weights $\theta$. Then since $r(x, y(z)) = 1$ exactly when $y(z) \in \Scal_x$:
$$ \begin{aligned} p_x &= \sum_{z \,:\, y(z) \in \Scal_x} \pi_\theta(z \mid x) \\ &= \sum_{z} \pi_\theta(z \mid x)\, \ind{y(z) \in \Scal_x} \\ &= \sum_{z} \pi_\theta(z \mid x)\, r(x, y(z)) \\ &= \ev[z \sim \pi_\theta(\cdot \mid x)]{r(x, y(z))}, \end{aligned} $$

            Abstract:AI sycophancy, the tendency of large language models (LLMs) to flatter users and affirm their beliefs, can undermine accuracy and contribute to misinformation, dependence, and overconfidence. Although prior work has benchmarked sycophancy in released models and proposed mitigations, its origins during training remain poorly understood. Preference alignment methods such as RLHF and DPO are often blamed, but their effects are rarely compared with earlier training stages. We investigate sycophancy across the training pipelines of three model families and three benchmarks. We find that sycophancy is largely established by the end of supervised fine-tuning (SFT), rather than introduced by preference alignment. Across all nine model benchmark combinations, SFT checkpoints attain at least 92% of preference aligned models' sycophancy scores and at least 85% of final models' scores; on average, they are about as sycophantic as final models. Preference alignment increases sycophancy in only four of nine cases, by an average of 4.2 percentage points when it does. To probe the underlying causes, we isolate model representations associated with sycophancy using mechanistic interpretability and measure their activation on training datasets from each stage. SFT datasets show roughly the same average activation as other training data but contribute substantially more examples, and the highest-scoring individual datasets all come from SFT. Our findings suggest that addressing sycophancy requires interventions throughout the training pipeline, particularly in data selection and augmentation for pre-training and SFT.
