Open Code Review is an AI-powered code review CLI tool. It originated as Alibaba Group's internal official AI code review assistant — over the past two years, it has served tens of thousands of developers and identified millions of code defects. After thorough validation at massive scale, we incubated it into an open source project for the community. Simply configure a model endpoint to get started.
It reads Git diffs, sends changed files to a configurable LLM via an agent with tool-use capabilities, and generates structured review comments with line-level precision. The agent can read full file contents, search the codebase, inspect other changed files for context, and produce deep reviews — not just surface-level diff feedback. Beyond diff review, ocr scan reviews entire files for auditing unfamiliar codebases or directories that have no meaningful diff.
Visit the official website for more details.
Compared to general-purpose agents (Claude Code), Open Code Review achieves significantly higher Precision and F1 with the same underlying model, while consuming only ~1/9 of the tokens and completing reviews faster. Note that its Recall is lower than general-purpose agents — a deliberate trade-off favoring precision over noise.
A real-world code review benchmark built from 50 popular open-source repositories, 200 real Pull Requests, and 10 programming languages — cross-validated by 80+ senior engineers (1,505 annotated ground-truth issues).
Explore the AACR-Bench dataset on Hugging Face.
If you've used general-purpose agents like Claude Code with Skills for code review, you've likely encountered these pain points:
- Incomplete coverage — On larger changesets, agents tend to "cut corners," selectively reviewing only some files and missing others.
- Position drift — Reported issues frequently don't match the actual code location, with line numbers or file references drifting off target.
- Unstable quality — Natural-language-driven Skills are hard to debug, and review quality fluctuates significantly with minor prompt variations.
The root cause: a purely language-driven architecture lacks hard constraints on the review process.
Open Code Review's core philosophy is to combine deterministic engineering with an agent, each handling what it does best.
Deterministic Engineering — Hard Constraints
For review steps that must not go wrong, engineering logic — not the language model — guarantees correctness:
- Precise file selection — Determines exactly which files need review and which should be filtered, ensuring no important change is missed.
- Smart file bundling — Groups related files into a single review unit (e.g., message_en.properties andmessage_zh.properties are bundled together). Each bundle runs as a sub-agent with isolated context — a divide-and-conquer strategy that stays stable on very large changesets and naturally supports concurrent review.
- Fine-grained rule matching — Matches review rules to each file's characteristics, keeping the model's attention sharply focused and eliminating information noise at the source. Compared to purely language-driven rule guidance, template-engine-based rule matching is more stable and predictable.
- External positioning and reflection modules — Independent comment-positioning and comment-reflection modules systematically improve both the location accuracy and content accuracy of AI feedback.
Agent — Dynamic Decision-Making
The agent's strengths are concentrated where they matter most — dynamic decisions and dynamic context retrieval:
- Scenario-tuned prompts — Prompt templates deeply optimized for code review, improving effectiveness while reducing token consumption.
- Scenario-tuned toolset — Distilled from deep analysis of tool-call traces in large-scale production data — including call frequency distributions, per-tool repetition rates, and the impact of new tools on the overall call chain — resulting in a purpose-built toolset that is more stable and predictable for code review than a generic agent toolkit.
- Git >= 2.41 — Open Code Review relies on Git for diff generation, code search, and repository operations.

            Abstract:Ternary Large Language Models (LLM) store every weight as one of three symbols $\{-1,0,+1\}$, so the cost of a ternary model is conventionally referenced to the information-theoretic $\log_2 3 \approx 1.585$ bits per weight. The prevailing deployment format packs five ternary weights into one byte (five-trit packing), and due to the power-of-two group sizes used in practice this rounds up to $1.625$ bits per weight. This effective storage bit-width treats the three symbols $\{-1,0,+1\}$ as equiprobable. We measure the actual symbol distribution of 29 ternary LLM models and find that zeros account for up to $51.5\%$ of all weights. Motivated by this finding, we introduce BITCOS, a simple distribution-adaptive layout comprised of a dense presence bitmap plus a compacted sign vector, and costs $2 - z$ bits per weight element given a zero density $z$ in the model's weights. BITCOS stores weights more compactly than the five-trit packing in 26 of the 29 tested models, and reaches $1.485$ bits per weight on the sparsest of them. BITCOS is amenable to efficient unpacking on modern processors and GPUs, and we present optimized unpacking sequences for AVX-512, AVX2 and Intel Xe2 GPUs. Measured against production state-of-the-art ternary matrix-vector multiplication kernels, at the zero densities real-world ternary models exhibit, the realized gain with our proposed layout is up to $1.28\times$. Finally, we illustrate end-to-end LLM inference results on 5 different platforms (client and server CPUs, integrated and discrete Xe2 GPUs) where decode throughput improves by up to $1.18\times$ on CPUs and $1.27\times$ on GPUs.

Backups aren't simple
Aleksandar Filipovski, 2026-09-16
See also: John Salvatier’s excellent blog, Reality has a surprising amount of detail
I read a comment somewhere that stuck with me, that went something like this:
“There are two types of people: those who have suffered a catastrophic loss of data, and those who will.”
Trying to find the source for it for this blog, it turned out that every other sysadmin has his rehashed version of the quote, but the gist of it is the same everywhere. Data loss is something that happens more often than we’d hope, and most of us are woefully unprepared for when it hits us (which is almost always at the worst possible time).
I can confirm that I had a similar experience once. When I was little we had pulled all our family photos from our home laptops and PCs onto an external hard drive, in order to free up some space. This worked beautifully until one day my dad wanted to use the drive as storage for our TV set-top box (one of these old things), and was prompted to format the drive. He went ahead with it, and the disk was reformatted. The index of files was deleted, and we were stuck with a nominally empty drive.
It would be easy to blame him for screwing up, but it takes beginning a career in tech to realise that there is a series of errors that lead to this kind of mistake. Firstly, we had put all of our photos in one place and didn’t bother with backups. Secondly, most consumer-facing software usually has bold disclaimers telling you that formatting a disk means losing data (which the set-top box didn’t, terrible UI). Besides, why would you even expect a non-technical person to even have to know any of this?
Thankfully we were able to get the photos restored, and it turned out to be a cheap lesson in handling data. You never keep important things in one place only. There’s about a million things that can go wrong. Your drive could die, it could be stolen, bits could rot in cold storage (hard drives have magnetic particles which can inexplicably shift, and SSDs are made of NAND transistors which leak electricity and over time, corrupt your data).
So our first principle is to have a backup, i.e. a copy of your files someplace else. So far so good.
This doesn’t cover the headaches of what a plugged in drive could do. Ransomware could encrypt your files, and you could do anything from an honest mistake like deleting the wrong file; up to catastrophic mistakes like running a script that overwrites everything with zeroes.
So our backup should not be a mirror of the first drive, because we also want to be able to go back in time if we mess up. Importantly, this means that mirroring your disk with something like RAID 1 is out. We need some other method that snapshots things.
How often do we want to take snapshots? Maybe in our case with the photos we should have run a backup every week. If we lose 6 days and 23 hours of data, that’s fine and we can live with it. This is what’s called a Recovery Point Objective (RPO) in IT, and in real cases, it ranges from <30 seconds for critical financial institutions which really can’t afford to lose data, to 24 hours or more for some small enterprises (if they even have a disaster recovery strategy).
Taking snapshots means that we have an increasing burden on our storage. With an RPO of 24 hours, you will end up having 7 snapshots per week. 30 per month. 365 per year, if you really don’t go and prune your snapshots. So you need to rotate your backups.
Let’s say I go with the naive approach and decide to keep 14 days’ worth of snapshots. When I take a new snapshot, I delete the oldest one and I add the new one. Pretty simple, but this now forces me to have a watchful eye. Maybe I keep lots of data and can’t be bothered to check if something got corrupted in the past two weeks? But then again, I can’t just store a year’s worth of backups and they’re simply not relevant to me. What happened between day 2 and day 3 of the year has almost no significance when it’s day 364. So the granularity at which we take backups must change. The closer we are to today, the more frequent the snapshots. The further back, the less frequent the snapshots.
So maybe we rotate our daily backups every 14 days, but also take weekly backups that we rotate every 7 weeks, and monthly backups we rotate every 12 months. This should be much more efficient. But again our complexity grows. We now have something called a GFS-rotated, snapshot-based backup. This list of adjectives will continue growing, as we’ll see in a bit.
Maybe then you take a look at how MPEG compresses video, and get fascinated by how a calm scene in a movie, where the protagonist speaks but otherwise doesn’t move against a completely still background can be used for compressing video. You notice that videos are composed of frames that are mostly similar to each other, only changing with a certain movement that can be represented as a vector for a fraction of the storage. Which leads you to the very logical conclusion that your snapshots also follow the same pattern! Today we're sharing open source code that can sort arrays of numbers about ten times as fast as the C++ std::sort, and outperforms state of the art architecture-specific algorithms, while being portable across all modern CPU architectures. Below we discuss how we achieved this.
First, some background. There is a recent trend towards columnar databases that consecutively store all values from a particular column, as opposed to storing all fields of a record or "row" before those of the next record. This can be faster to filter or sort, which are key building blocks for SQL queries; thus we focus on this data layout.
Given that sorting has been heavily studied, how can we possibly find a 10x speedup? The answer lies in SIMD/vector instructions. These carry out operations on multiple independent elements in a single instruction—for example, operating on 16 float32 at once when using the AVX-512 instruction set, or four on Arm NEON:
If you are already familiar with SIMD, you may have heard of it being used in supercomputers, linear algebra for machine learning applications, video processing, or image codecs such as JPEG XL. But if SIMD operations only involve independent elements, how can we sort them, which involves re-arranging adjacent array elements?
Imagine we have some special way to sort, for instance 256 element arrays. Then, the Quicksort algorithm for sorting a larger array consists of partitioning it into two sub-arrays: those less than a "pivot" value (ideally the median), and all others; then recursing until a sub-array is at most 256 elements large, and using our special method for sorting those. Partitioning accounts for most of the CPU time, so if we can speed it up using SIMD, we have a fast sort. 
Happily, modern instruction sets (Arm SVE, RISC-V V, x86 AVX-512) include a special instruction suitable for partitioning. Given a separate input of yes/no values (whether an element is less than the pivot), this "compress-store" instruction stores to consecutive memory only the elements whose corresponding input is "yes". We can then logically negate the yes/no values and apply the instruction again to write the elements to the other partition. This strategy has been used in an AVX-512-specific Quicksort. But what about other instruction sets such as AVX2 that don't have compress-store? Previous work has shown how to emulate this instruction using permute instructions.
We build on these techniques to achieve the first vectorized Quicksort that is portable to six instruction sets across three architectures, and in fact outperforms prior architecture-specific sorts. Our implementation uses Highway's portable SIMD functions, so we do not have to re-implement about 3,000 lines of C++ for each platform. Highway uses compress-store when available and otherwise the equivalent permute instructions. In contrast to the previous state of the art—which was also specific to 32-bit integers—we support a full range of 16-128 bit inputs.
Despite our single portable implementation, we reach record-setting speeds on both AVX2, AVX-512 (Intel Skylake) and Arm NEON (Apple M1). For one million 32/64/128-bit numbers, our code running on Apple M1 can produce sorted output at rates of 499/471/466 MB/s. On a 3 GHz Skylake with AVX-512, the speeds are 1123/1119/1120 MB/s. Interestingly, AVX-512 is 1.4-1.6 times as fast as AVX2 - a worthwhile speedup for zero additional effort (Highway checks what instructions are available on the CPU and uses the best available ones). When running on AVX2, we measure 798 MB/s, whereas the prior state of the art optimized for AVX2 only manages 699 MB/s. By comparison, the standard library reaches 58/128/117 MB/s on the same CPU, so we have managed a 9-19x speedup depending on the type of numbers.
Previously, sorting has been considered expensive. We are interested to see what new applications and capabilities will be unlocked by being able to sort at 1 GB/s on a single CPU core. Almost all generative image and video models are Latent Diffusion Models (LDMs). These have two key components, a Variational Auto Encoder (VAE) for compression and a Diffusion Transformer (DiT) for generation.

因此，我们没有包车逛吴哥窟，而是找到了一家名为「Mr. Tom」的摩托车租赁店铺，还价到了 8 美金一天租了三天摩托。摩托车一早 8 点老板送到了酒店门口，还有半箱油。不过暹粒的踏板摩托车跟我在其他地方骑的还不太一样，在加油站和吴哥窟游客中心停了两次车怎么都打不着火，在当地人的帮助下我才慢慢摸透了点火的方式，原来得必须把脚撑子完全收回，然后捏刹车拧油门，最后按住点火器两秒以上，才能顺利打着火。油价比国内便宜一些，大概二点几升的油，三块多美金。
吴哥窟的门票分为三档，23 美金一天，62 美金十天选三天和 72 美金三十天选七天使用。我们买的是三天票，价格我觉得还行吧，毕竟这么大一片地方，里面的东西确实挺多的，适合慢慢走慢慢看。但柬埔寨本国民不收费啊！查了下是说，吴哥窟是柬埔寨的国家象征和祖先留下的历史遗产，本地人有权自由前往、祭拜或参观自己的历史文化瑰宝。政府不向本国公民收取门票，将其视为一项基础的文化福利，让每个柬埔寨人都能亲近和了解自己的历史。

买好票后，我们骑着摩托车不到二十分钟就来到了小吴哥城。在 google map 上这个地方就叫「吴哥窟」，一开始我也没整明白这片区域是怎么命名的，后来才搞清楚我们常说的吴哥窟指的就是地图上这一座名为「吴哥窟」的寺庙，它是吴哥古迹群方圆 400 公里内保存最好的圣殿，以建筑宏伟与浮雕细致闻名于世，是世界上最大的神庙。正因如此，吴哥窟被认为是柬埔寨和高棉民族的重要象征，从 1863 年开始，吴哥窟造型就已经成为柬埔寨国家的标志，被描绘在柬埔寨国旗上。
吴哥窟的正式名字叫「最伟大的毗湿奴路迦」，起初由高棉国王苏利耶跋摩二世于 12 世纪建设，作为供奉印度教主神毗湿奴的国家神庙，建筑布局象征着印度教神话中的须弥山。随着柬埔寨宗教信仰的变化，佛教逐渐兴起。到了14世纪中叶，吴哥窟已经逐渐转变为佛教寺院，并延续至今，成为融合印度教与佛教文化的标志性古迹。有意思的是，吴哥窟的高棉语「Angkor Wat」用粤语发音后听起来就像是「吴哥窟」，从 17 世纪到 20 世纪初高棉华人以广东人最多，因此「吴哥窟」这个中文名是通过粤语音译而来。
光是吴哥窟这个点位基本上就汇集了 80% 的游客，后面两天我们再去其他寺庙时都只有这个地方零头不到的游客。看完后我反而对吴哥窟这个地方没有太多感觉，一切都修缮得保存得太好太完美了，仿佛生活在这个地方的人民昨天才刚刚离去。如果你想跟我一样，是来看那种失落的遗迹，吴哥窟这个地方可以完全忽略掉，把一天中宝贵的时间留给其他寺庙。
但往吴哥窟顶上爬一段后，会看到了有很多空着的水池，我脑子里马上就浮现出了希腊众神在水池喷泉边酒池肉林的奢靡画面。现在看到这些空着的水池，高度至少得两米，很难想象如果这些水池都蓄满了水那会是一副什么样的画面。
为什么要强调一天中的宝贵时间呢？因为一天里能够相对友好的游览寺庙时间真的不多，日出后到 11 点前，午后 16 点到日落，剩下的时间都不适合在出门闲逛，非常晒非常热，站在太阳下如果不打伞没一会儿就热得不行。这还是雨季的 8 月哦，虽然很晒很热但最高温才三十一二度，五一那会儿看的天气可是四十一二度。从第一天开始我们每天上午准时 12 点左右吃饭，吃好饭后回酒店休息一段时间，到了下午三四点再出门。午后的时间骑着摩托车在吴哥遗迹群里那些被森林包围着的道路上，才能感受到一些雨季的凉爽。

Apple 于 9 月 15 日凌晨正式发布 iOS 27、iPadOS 27、macOS 27 Golden Gate 和 watchOS 27 等系统的正式版。其中，iPadOS 27 改进了系统界面、提升了性能表现，还改进了分屏、Sidecar、Apple Pencil 等相关内容。
少数派为你整理了新版系统中值得关注的新功能和新特性。不管你是升级后，想了解新系统有哪些新功能，或者还在观望是否需要升级，这篇文章都能帮助到你。当然，升级新版系统之前，别忘了通过 Apple 设备/Finder 或者 iCloud 备份好你的 iPad 数据。
这篇文章带你一览 iPadOS 27 中的新鲜功能，看看有没有哪一个功能会让你跃跃欲试。
系统界面改进
Liquid Glass
iPadOS 27 和去年推出的其他系统一样，「Liquid Glass」设计风格今年也有了不少改进。具体而言有以下几点：
边到边的侧边栏
经历了 26 版本系统侧边栏「悬浮」并预留边框空间的设计之后，iPadOS 27 各个应用的侧边栏又回到了 iPadOS 18 的「边到边」的样子，和 macOS 27 Golden Gate 保持一致，看上去更简洁。不过这个设计本来就是见仁见智，而且我个人倒是觉得 OS 26 的版本看起来更加立体。
系统自带 app 图标更新
系统自带的 app 图标基本全部获得了重构，包括地图、邮件、照片、天气等，更多元素都换用了 Liquid Glass 设计，堆叠在一起以后能比较明显看到变化。此外，更新到 iPadOS 27 后，第三方 app 图标的渲染方式也发生了些许变化，看起来整体更立体，边缘更加锐利，比如微信、少数派等。
组件光影变化
在 iPadOS 27 中，各类组件，比如：按钮、通知、文本输入框、上下文菜单等，均采用了和 26 不同的光影渲染方式，看起来更加立体灵动。组件下方被遮盖的内容的折射也没有 iPadOS 26 那么明显，在一定程度上增加了可读性。
可自定义的透明度
不只在 iOS 27，Apple 也为 iPadOS 27 带来了 Liquid Glass 透明度的调节滑块，可以在设置—外观中找到。其中最不透明的那档，整体呈现出乳白色的毛玻璃效果，看起来和 iPadOS 18 很像。
所以，今年 Liquid Glass 的更新更多属于细节上的微调，不涉及特别大的 UI 变化，有些变化在我看来可以说是「开倒车」式的调整。不过，只要讨论到设计就会有人喜欢、有人不喜欢，那么你今年给设计部分的改动打几分？
菜单栏
iPadOS 26 正式在 iPadOS 中引入了 macOS 类似的 App 菜单栏，用来调用各种操作并查看快捷键。在 iPadOS 27 中，系统默认情况下会在屏幕顶部状态栏显示 app 名称，轻点名称才会出现菜单选项，在一定程度上避免了 iPadOS 26 的滑动手势造成的误操作。
当然了，也是因为从屏幕顶部中间下拉的手势现在已经分配给了新 Siri AI。不过，我们还可以在设置中选择固定显示菜单栏，而不是等到我们点击时才出现。
iPadOS 26 曾尝试用 SF Symbols 给部分菜单项加上小图标，但效果并不理想。一方面，这些图标并没有覆盖所有菜单项，放在一起看显得不太统一；另一方面，部分图标本身的含义也不够清晰，我们也未必能通过图标更快地找到想要的功能。
所以到了 iPadOS 27，Apple 基本移除了菜单栏里的这些小图标，macOS 27 也同步采用了类似做法。目前你还能在菜单里看到的图标，主要只剩下了窗口操作，这些图标确实足够形象。
自定义主屏幕与小组件
在 iPadOS 27 中，对主屏幕的修改可以撤销和重做。iOS 上新增的「超大尺寸」的小组件只可以放在 iPadOS 的「今日」视图中，但无法直接安置在主屏幕上。
iPhone app 窗口尺寸
在 iPadOS 27 上运行 iOS app 时，可以更加自由地调整 iPhone app 的窗口大小，而不会像之前的 iPadOS 一样，只能固定在某个大小。
Sidecar 触控操作
或许是触摸屏 MacBook 即将到来的「前兆」，Sidecar 随航在 iPadOS 27 和 macOS 27 中支持通过 iPad 上的触摸屏幕来操作，目前试用下来，支持屏幕内容滚动、放大缩小等多指触控手势。
Apple Pencil 与笔记相关功能
新的充电提示音
Apple Pencil 获得了新的充电提示音。在 iPadOS 27 中，当你接上 Apple Pencil，就会听到新的提示音，听起来和 iPad 充电的声音类似，但音色略有不同。
手写字可用 Spotlight 索引
iPadOS 27 中另一项与 Apple Pencil 和笔记有关的系统改进就是手写字符也可以添加 Spotlight 索引，并在 Spotlight 中搜索「备忘录」App 中的手写笔记全文。手写笔记搜索依赖 Apple 的 PencilKit 功能，因此使用 PencilKit 构建的第三方 app 也可以进行手写识别。
备忘录可拷贝为 Markdown
备忘录 app 中的内容现在可以拷贝为 Markdown。在这个 AI 也要读 Markdown 的年代，手搓 Skills 似乎又多了一个选择。
系统大提速
iPadOS 27 在性能方面也做出了不少改进，不仅动画看起来快了，系统也流畅了不少，部分 iPad 在待机续航方面也有改善。
传输文件方面，包括 AirDrop、AirPlay 连接传输速度更快、使用外置 SSD 拷贝和浏览文件的速度也变快了。实测下来，我从硬盘复制了 3.74G 的文件到 iPad mini 的内置存储中，大约 5s 完成；从 iPad mini 内置存储拷贝 21G 的文件到 SSD 中，也就花了不到 30s，看来 10Gbps 的带宽基本上能跑满。
AI
iPadOS 27 上 AI 部分虽然在 Gemini 的加持下有所升级，只不过 Apple Intelligence 及 Siri AI 相关功能在国行 iPad 上依然暂不支持。
Apple 智能中的 Apple Foundation Models 中加入了 Google Gemini 的助力，所以 Apple 表示新的 Foundation Models 仍然是 Apple 自研的。在基础模型之上，还加入了不少 Agentic 的能力，结合上 Apple 从 2024 年就开始准备的 API，最终带来了 Siri AI，也算是搭上了当前 AI 的趋势。
iPadOS 上的 Apple 智能功能整体和 iOS 上的类似，都拥有了系统级的上下文和屏幕感知能力，可以与手机屏幕上的内容进行实时的交互。除了可以在主界面顶部下滑在新的 Spotlight 里使用 Siri AI，还可以通过独立的 Siri app 在应用内对话。
总结
可以看到，今年的 iPadOS 27 除了继续打磨 Liquid Glass 之外，还在性能、交互和功能上有所精进。我这一阵子用下来 iPadOS 27 的感觉总是，在整体的系统设计上，Apple 似乎有意地将 macOS 和 iPadOS 做得「更加靠近」。

同时，IE 造成的长尾效应也使得对 MSHTML 引擎的更改处处掣肘。于是 EdgeHTML 诞生了。EdgeHTML 采用全新的 UA 字符串，抛弃了 IE 的兼容性模式，支持现代网页标准，并且在性能上有了很大的提升；微软也（再次）有机会重新设计浏览器的 UI 和功能，使其更符合现代用户的需求。
2014 年 11 月 11 日，微软在 Windows 10 预览版中推出「living Edge document mode」（生活在边缘上），同时宣布超过 2000 项互操作性修复和 20 项新平台功能。此时的 Edge 仍以 IE 的新模式出现，但已经包含后来 EdgeHTML 的核心思想：在不破坏企业级网站浏览体验的同时，使得互联网变得「摩登」。
互联网多样性
当时还有一个非常重要的背景：微软想要保持浏览器的多样性（依然可以在这篇博客中读到）。
This interoperability-focused approach brought the obvious question of adopting an existing open-source rendering engine such as WebKit. While there were some advantages, upon further investigation it was not the right path forward for two important reasons. First, the Web is built on the principle of multiple independent, yet interoperable implementations of Web standards and we felt it was important to counter movement towards a monoculture on the Web. Second, given the engineering effort required, we found that we could deliver an interoperability focused engine to customers significantly faster if we started from our own engine (especially if unshackled from legacy compatibility concerns), rather than building up a new browser around an open-source engine. We will continue to look at open source and shared source models where it makes sense and look forward to sharing more details in coming posts.
当代互联网基于多个独立但互相兼容（？）的 Web 标准实现，我们认为我们必须抵制互联网上出现单一化趋势。
独立的浏览器内核本身就是价值：正如 Gecko Quantum 和 Webkit 的存在一样，EdgeHTML 的存在也让互联网变得更加多样化。虽然我一直在攻击 Safari，但是我承认不应该直接完全扼杀 Safari 的存在。Firefox 也同理，虽然它又慢又实现得不好，但我们仍然需要它存在。
图片源自 Mozilla 的 Competition, Innovation, and the Future of the Web – Why Independent Browser Engines Matter。Mozilla 指出，当创新建立在单一主导引擎之上时，技术和经济力量就会集中，选择范围缩小，并有可能使网络的发展方向偏离公共利益，转而服务于少数大型平台的利益。浏览器引擎多样性确保技术以人为本，而非以股东为本。
有很多文章都有写过浏览器多样性的目的，比如What is the Value of Browser Diversity?以及Browser Engine Diversity。缺乏多样性的内核实现可能会导致部分 API 不能得到仔细的考量，或因出于单一公司的某些商业目的，对互联网造成快速且广泛的影响。
浏览器内核在事实上决定了我们能够在互联网上看到了什么。如果世界上只有 Chromium，那 Google 将能够亲自管理甚至亲自禁止整个互联网上的内容，这就是单一化的问题。
当 Edge 走向死亡的时候，Mozilla 还发了一篇悼文：Goodbye, EdgeHTML。
崭新的未来
2015 年 1 月，微软公开 Project Spartan 浏览器；2 月详细解释新内核；4 月 29 日正式将浏览器命名为 Microsoft Edge。2015 年 7 月 29 日，Microsoft Edge 随 Windows 10 正式发布。
在 2015 到 2018 年之间，EdgeHTML 的主要版本随 Windows 10 功能更新演进。首个正式版本通常称 EdgeHTML 12，随后依次发展到 EdgeHTML 18。重要工程进展包括：
- 显著提高 Edge 与其他浏览器的兼容性
- 引入现代化 DOM 排版，显著提高性能
- 支持浏览器拓展
- 以及最后的 Edge 18
Edge 开始的时候非常好：优先实现其他主流浏览器和现实网站共同使用的 API，而不只追求标准清单上的功能数量；使用 Bing 抓取的大量 URL 查找被大量使用的相同代码，希望能够更快的解决兼容性问题。UA 的变更意味着主动放弃了 IE 模式，通过直接接入现代网页暴露更多问题并修复，长期目标则是实现 EdgeHTML 真正与其他浏览器内核能够运行相同的代码。
Edge 还大量使用 Windows 的系统已有 API，比如 Media Foundation（Edge Chromium 中依然有这个选项），Windows Imaging Component 以及 DirectWrite 等，来实现更好的性能和更低的功耗；PDF 使用 Windows 的 WinRT PDF 渲染器，EPUB 也有一个非常优秀的渲染引擎。
但这种操作意味着 Edge 与操作系统强绑定，无法被移植到其它系统，甚至下放给 Windows 7。这也为 EdgeHTML 的最终死亡埋下了伏笔。
最平滑的平滑滚动
我不知道有没有人在 Edge 刚出的时候用过 Edge。那是一种次世代的体验，是直到现在 Chrome 以及开启平滑滚动的 Edge Chromium 都无法达到的未来。
我第一次知道滚动能够如此优雅不生硬。Edge 不会只把每次滚轮输入直接转化成固定距离的位移，而是给输入添加持续一段时间的速度曲线。连续滚动时，新的输入会修改正在进行的动画，产生一种有惯性但仍然跟手的效果；Edge 还会根据滚动容器的尺寸计算滚动量，同一次滚轮操作在较大的页面区域中可能移动得更远。
Edge 与操作系统的 DirectComposition 以及 Direct Manipulation 紧密结合，提供了领先于业界的滚动体验。EdgeHTML 的滚动是异步处理的（当然今天都是了），即使画面在执行重任务，滚动也不会存在卡顿。Edge 是唯一的支持侧边栏异步滚动的浏览器。
当然，这种体验也无法被简易移植到其他操作系统上。
最好用的 EPUB 阅读器
尽管在最后的 Edge 版本中 EPUB 的功能被移除（如果你想用，需要卸载 KB4601383 更新），但是 Edge 的 EPUB 阅读体验是最好的。与 Calibre 抽象卡顿的阅读体验不同，Edge 有着丝滑的滚动体验，真正完整的浏览器，以及极其优秀的 UX 设计。
EPUB 的页面渲染是可重排的分页，而且不是基于 shadowroot 的方案，这提供了优雅且高性能的翻页体验，比某些只能滚动的阅读器不知道高到哪里去了。所有的页面都能用墨迹批注，支持圈画功能。
更好的字体渲染
Chromium 在当时使用 Skia 进行字体渲染，Edge 则使用 Windows 的 DirectWrite 进行字体渲染。使用 Skia 中硬编码的设置渲染字体会导致文本比 Windows 系统默认设置略微偏细。这种差异在 CJK 字符上更为明显。
当然，在 Chrome 132 之后，Chromium 以及正式接受了 Edge 团队的 patch，提供了更加接近原版 Edge 的字体渲染体验。
少年没有遇到少女
Edge 只在（对于 PC 用户而言）Windows 10 上提供，主要平台功能又随 Windows 半年功能更新（众所周知的有很多人根本不更新）交付。对推迟系统升级的企业而言，新 EdgeHTML 功能无法像 Chrome 或 Firefox 那样通过独立浏览器更新及时获得。于是 Edge 之间也存在很多版本不兼容问题。
2019 年 The Verge 的采访指出，企业测试和延迟部署 Windows 功能更新，会让其 Edge 长期落后。
同样的，拓展功能也不是在第一天就可用，这使得浏览器拓展社区非常的不成熟。因此，Edge 的用户量一直不高。这也导致了开发人员不对 Edge 进行测试的恶性循环（Windows 允许你使用三方浏览器，而不是和 iOS 以及 ipadOS 强制按头让你吃 Safari）。
那么，不兼容 Edge 也是顺理成章了。
然后是 UWP（现在在哪发财呢？）。Edge 同样基于 UWP 构建，UWP 不是一个成熟的应用开发平台，Edge 需要等待 UWP 修复 bug 或添加新特性才能够实现 Edge 的新功能，这拖慢了 Edge 迭代的速度。
同时，Chrome 引领下的互联网日新月异。当年第一个 Edge Chromium 版本是 79，到今天已经是 151 了。Edge 团队完全没有能力去跟上 Chrome 的更新速度。
所以 Edge 死了。
为了提高网页兼容性，脱离 Windows 更新的发版节奏，实现跨平台，微软决定放弃 EdgeHTML，转而使用 Chromium 内核。总之，EdgeHTML 停止开发，Edge Legacy 停止支持。EdgeHTML 用户规模不足使得 Edge 生态回报偏低。采用 Chromium 后，微软可在浏览器 UI、企业管理、Windows 集成、隐私和服务上竞争，同时仍能共享 Web 平台底层成本。对微软而言这是一个商业上无比正确的决定。
三分天下
至此，浏览器内核又回到了三分天下的年代，或者就这点份额，实际上也没有进入过四分的时代。Chromium 已经在事实上成为互联网的标准，Firefox 就偶尔出来「狗叫」一下：）
当时我是最后一批升级 Edge 的，事实上我现在也想保留旧版 Edge，但是因为我还是开了系统更新的，所以这不可能。Edge 的体验对比 Chrome 来说确实是有差距的。在 HTML 没有完全加载出来之前，Edge 将不会显示任何内容，始终保持白屏；同时 Chrome 只要能渲染就会渲染出网页，所以首屏时间 Chrome 显著优于 Edge。更不要说谷歌一直在自家网上搞的神秘小动作了。
我为什么要给 Edge 招魂
一切源于 Chrome 在 2024 年决定停止对 Manifest V2 拓展的支持。有很多拓展使用 Manifest V2，比如 uBlock Origin。相关的讨论也已持续好久，基本上隔一段时间就会出现某某浏览器也停止支持 V2 拓展的新闻，并且搞个大新闻：某某正在杀死最受欢迎的广告屏蔽拓展。当然确实也没有错。
起初有很多浏览器都没有跟进，Edge Chromium 也在其中。Brave、Vivaldi 这些也都继续保留对 V2 拓展的支持。但到 2026 年，Edge Chromium 也已发布V2 拓展的退役时间表，这是一个意料之中的事情，也是所有使用 Chromium 内核的浏览器都会遇到的问题：被 Google 卡脖子。Google 在上游 Chromium 中移除支持，下游想要保留支持就必须进行分叉，并不断 backport 之后的新功能——backport 是一件非常痛苦的事情，其难度会随着累计更新的变多而不断增加。今年以来 AI 发现的越来越多的漏洞，以及越来越频繁的更新发版也进一步加强了这种「压力」，最终我想大部分仍然追新的浏览器厂商都会选择直接跟进上游而不是分叉。某些几百年不更新还在 Chrome 87 的浏览器除外。

    Title:Converge Then Diversify: Decoupling Convergence and Diversity in Multi-Objective Bayesian Optimisation
View PDF HTML (experimental)
            Abstract:Multi-objective Bayesian optimisation (MOBO) is a sample-efficient approach for optimising expensive black-box functions with multiple objectives. In MOBO, the goal is to adequately approximate the Pareto front; that is, to obtain a high-quality solution set with 1) good convergence (closeness to the Pareto front) and 2) good diversity (spread across the Pareto front). Existing MOBO methods typically aim to accomplish these two tasks simultaneously, i.e., driving the search towards the Pareto front while maintaining a diverse set of nondominated solutions, such that the solutions, ideally, can gradually approach the entire front. When sufficient search budgets are available, this approach is effective. However, considering both convergence and diversity throughout the search is not easy and requires careful design. Under very tight budgets, there may not be enough solutions generated to be able to simultaneously approach the entire Pareto front. To address this issue, this paper proposes a \textit{converge-then-diversify} (CTD) approach that decouples convergence and diversity into two stages. In the first stage, CTD focuses on convergence, aiming to quickly drive the search toward a single point on the Pareto front. In the second stage, CTD focuses on diversity, aiming to spread solutions across the front. We present two simple instantiations of CTD by using widely adopted acquisition functions in the area. Experimental results show that, across all 446 pairwise comparisons, CTD statistically outperforms state-of-the-art methods in 72.9\% of the cases, performs equivalently in 21.1\%, and is statistically worse in only 6.1\%, with the advantage being particularly evident in settings with very tight evaluation budgets or in high-dimensional problems.

            Abstract:When we speak of recursive self-improvement (RSI), are we speaking of a phenomenon, a mechanism, or a prospect? Towards autonomous and evolving intelligence, RSI is being claimed at many scales, while no single framework that formally describes these emerging instances exists. Its counterpart in the classical realm, iterative policy improvement, is characterized by generalized policy iteration (GPI), a framework of broad applicability with well-understood theoretical properties, but only where the update principle and the evaluation base lie outside the agent. In this paper, we propose Generalized Agent Iteration (GAI), a formal framework that describes iterative policy improvement and RSI as two cases of a single learning paradigm. Two pivotal dials then distinguish the instances: whether the improving mechanism is part of the agent and whether the standard it is measured against is grounded outside it. The former dial delineates the boundary between GPI and RSI, and the latter determines a system's polarity as anchored, goal drift, or fully self-referential. Moreover, we use these coordinates to place existing systems on the same two axes and make the defects of recursive self-improvement statable one condition at a time. We see this paper as a first step toward exploring a formal characterization of RSI that rests on the classical account, makes existing systems comparable, and provides a principled basis for analyzing and designing new ones.

Abstract
Alzheimer’s disease is widely depicted as a linear cascade from amyloid-β accumulation to Tau pathology and neurodegeneration. We propose instead that the disease unfolds through discrete molecular, cellular and network phases organized around biological inflection points. At these thresholds, stress-driven loss of homeostasis produces qualitative shifts in cellular behavior that alters disease progression. These altered states spread across local tissue-domains, accumulate as a mosaic across the brain, and progressively engage vulnerable centres of information processing that control cognitive performance. The induction of amyloid-associated Tau phosphorylation marks a pivotal inflection point, separating amyloid-dominated tissue states from domains in which neuronal Tau stress responses have emerged. This framework helps reconcile the dissociation between pathology and symptoms, clarifies the shared architecture of familial and sporadic disease and reframes Alzheimer’s disease as a disorder shaped by biological thresholds, timing, and progressive erosion of homeostatic resilience.

Abstract
Salicylic acid (SA) is a key phytohormone that activates plant defense responses 1-3. In Arabidopsis, NPR1 (also known as NIM1) and NPR3/NPR4 have been identified as dual SA receptors responsible for perceiving SA 4-6. Here, we elucidate how SA triggers transcriptional activation via NPR1 and relieves transcriptional repression mediated by NPR3/NPR4. We identified Mediator Complex Subunit 15A (MED15A) as a bridge between NPR1 and the Mediator complex governing transcription. SA induces direct interaction of NPR1 with MED15A.
