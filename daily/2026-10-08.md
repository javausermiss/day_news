e2e is an end-to-end testing framework for web and mobile apps. Describe a goal in natural language and an agent drives the app to reach it. Check the result with locators and assertions in the same test.
// tests/checkout.e2e.ts
import { test, expect } from 'e2e';
test('a member upgrades to Pro', async ({ app, agent, screen }) => {
  await app.open('/settings/billing');
  await agent.act('upgrade the workspace to the Pro plan');
  await agent.assert('the invoice preview shows a prorated amount');
  await expect(screen.getByRole('status')).toContainText('Pro');
});
An agent step that a later assertion verifies records its actions, and the next run replays them with no model calls until the app changes. Tests without agent steps need no model. Bring your own subscription, API key, or local model.
npx e2e init
init asks for an engine, web or mobile, and a model provider, then writes a
config and an example test. The
quickstart covers the rest.
To see a finished setup in your stack, open
examples/:
Vite, Next.js, Expo, SwiftUI, Jetpack Compose, Kotlin Multiplatform, and
Flutter, each a standalone project with a passing suite.
e2e.tester.army/docs. The e2e package ships
every page, so coding agents can read them offline in node_modules/e2e/docs.
See CONTRIBUTING.md. Questions go to Discord.
Please don't open public issues for security vulnerabilities. Follow SECURITY.md and report them to security@tester.army.
The CLI sends anonymous usage data, such as which commands and engines run and
where runs fail, but no test content, app content, or credentials. Opt out with
npx e2e telemetry disable or E2E_TELEMETRY_DISABLED=1.
Telemetry lists every field.
Note
e2e is in active development on the way to 1.0. APIs and config can still change between minor releases.
e2e is built by TesterArmy, the agentic testing platform that runs natural language tests on web and mobile apps, on every pull request or on a schedule.
Apache-2.0.

Introduction
One of the recommendations from the Tiger Style document of TigerBeetle ..
Centralize control flow. When splitting a large function, try to keep all switch/if statements in the "parent" function, and move non-branchy logic fragments to helper functions. Divide responsibility. All control flow should be handled by one function, the rest shouldn't care about control flow at all. In other words, "push ifs up and fors down".
The programming heuristic push-ifs-up-fors-down suggests that conditional logic (if statements) should be moved upward (towards the caller or earlier in a pipeline), while iterative loops (for operations) should be pushed downward (toward batch processing or later in a tight branch-free loop). This improves clarity and performance by centralizing branching and leveraging bulk operations.
matklad has also blogged about this principle and discussed the many virtues of adhering to this programming idiom.
In the post, matklad describes optimizing code by:
Pushing conditionals ("ifs") up: If a function branches on its input, consider moving that branch to the caller. Consider the example from the post - instead of frobnicate(walrus: Option<Walrus>) unpacking the option internally, the caller handles the None case and the function takes a plain Walrus. The function's type now states its precondition, the input state space becomes narrower and acts as a form of filtering. But the point is where the decision lives, not how much data flows downstream.
Pushing loops ("fors") down: Deferring loops until after filtering or reducing the dataset minimizes unnecessary computations. Rather than calling frobnicate(walrus) in a loop, provide frobnicate_batch(walruses) and let the loop live inside it. So the hot loop runs without a branch and is a candidate for vectorization.
The two moves compose. Given a collection of Option<Walrus> values, the caller discards the Nones and unwraps the rest into a Vec<Walrus>, then hands that to frobnicate_batch, which never has to consider the None case at all.
let maybe_walruses: Vec<Option<Walrus>> = ...;
let walruses: Vec<Walrus> = maybe_walruses.into_iter().filter_map(|w| w).collect();
frobnicate_batch(&walruses); // never sees a None
If you think a bit, the push-ifs-up-fors-down principle has far broader applications. This post explores some of the broader perspectives of this principle with respect to relational database query optimizations and functional programming and category theory.
Analogy in Database Queries: Projections Early, Joins Late
The same principle appears in database query optimization. In SQL query planning, it’s well-known that one should perform projections and selections as early as possible and defer joins or expansive operations until later. But the vocabulary runs upside-down. A query plan is a tree whose leaves are table scans and whose root produces the result. Data flows up from the leaves, so "down the tree" means "earlier in execution". When an optimizer talks about pushing a predicate down, it means evaluating it as early as possible, which is the database counterpart of what the rest of this post calls "up" or "early".
Early projections and selections (Push down): In database terms, a projection (e.g., SELECT with specific columns) reduces the dataset's width by selecting only the necessary columns early in the query execution. And selections (WHERE clause) act as the filter. Both are pushed down as part of the plan tree so that they get to execute early and filter out irrelevant data, reducing the amount of data passed to later operations.
Deferring joins (Push joins up): Joins, which combine data from multiple tables, are computationally expensive. The optimizer moves selections and projections below the joins, so joins run on smaller inputs. The effect is that the expensive combining operators run over the smallest inputs the query semantics allow.
Vectorized execution (the "for"): Another database analogy of pushing fors down is the change in execution semantics. Volcano style execution processes row at a time, where each operator is called once per tuple through a virtual next(). The alternative is the vectorized or batch execution, where each operator is called once per batch of a thousand or so tuples and runs a tight loop inside. That is frobnicate versus frobnicate_batch, at the level of a query engine: the per-call overhead and the per-call decisions are paid once per batch, and the inner loop is branch-light and cache-friendly.

The subset along with the morphism defines a subobject in category theory.
Note the hooked arrow in the morphism. It's intentional and it indicates that it represents a specific type of morphism - monomorphism (mathematicians love to define arrow types :-)). In Set, a monomorphism is an injective function: the inclusion sends each element to itself, so distinct inputs give distinct outputs.

            Abstract:Autoformalisation is increasingly used to verify mathematical texts, including those generated by AI, as in OpenAI's announced proof of blow-up of solutions to the Navier-Stokes equations. In this process, an AI system translates the text from a natural language (NL) into a formal language such as Lean. Once this translation is done, the argument expressed in the formal language can easily be mechanically verified. The purpose of this article is to demonstrate why this process may offer no confidence in the original NL argument, owing to the various difficulties in performing the translation semantically faithfully. To demonstrate the effect of this result we provide several examples of AI mistranslations of NL statements and proofs into Lean in practice, resulting in mismatches between NL proofs and their Lean `verifications'. These include OpenAI's announced Navier-Stokes proof. 穹顶作为万神殿真正的奇迹，是每一个来到这里的人都不会错过的。古罗马的穹顶技术之精妙，是我一个建筑外行人看过都很难不震撼的程度。在穹顶的建设过程中，古罗马人可谓极尽巧思。他们在底部使用承重性较好的材料作为受力支撑，顶部则使用加入火山灰之后的材料来使其更轻薄。不仅如此，穹顶内部的凹格设计既能减轻自重，还能改变视觉节奏，也是一个十分精巧的设计。
万神殿的穹顶直径为 43.4 米，穹顶中心距离地面的高度约为 43 米，也就是说，这里其实可以容纳一个完整的球体。时至今日，万神殿的穹顶仍是现存的、世界上最大的无钢筋混凝土穹顶。穹顶顶部是一个直径 8.9 米的「天窗」，阳光会透过天窗直射进来，打在墙壁和地面，在合适的时间点还能够看到完整直射下的光束，充满神圣感。站在万神殿内部，横向，我感受到的是空间的包裹感；纵向，能感受到空间的延伸感。置身其中，就仿佛自己短暂地穿越到古罗马时代，体验了一把时间的沧桑。
除了建筑本身，万神殿内部的供奉和陈设同样很值得关注。这里最著名的人物，非拉斐尔莫属。万神殿是拉斐尔心中「古典建筑的完美范本」，因此他晚年主动选择将万神殿作为未来的安葬地。除此之外，这里还安葬了意大利统一后的第一位国王：维托里奥·埃马努埃莱二世，足见后世之人对于这位国王的尊敬和敬仰之情。今天的万神殿，既是古罗马的纪念场所，又是闻名于世的天主教堂，同时还是从文艺复兴巨匠到现代意大利功臣的长眠之处。我想，这怎么能不算是一种「众神归位」呢？
古罗马斗兽场：把罗马还给罗马人
如果说万神殿是我私心的罗马最佳，那么斗兽场应该就是很多人心中罗马的象征。古罗马斗兽场真正的名字是 Flavian Amphitheatre，也就是弗拉维王朝圆形剧场。在公元 64 年罗马发生大火以后，尼禄决定在城中心建造属于自己的「金宫」，妄图把罗马中心据为己有。在他死后，弗拉维王朝上台，宣布在尼禄的人工湖位置建设一座公共竞技场，寓意把罗马中心还给罗马市民。于是，古罗马斗兽场就诞生了。
如今再去参观罗马竞技场，我会推荐你去斗兽场附近的高地。这里人相对较少，而且可以在一个较高的视角欣赏到斗兽场以及周边遗迹的全貌。从高处看去，斗兽场、君士坦丁凯旋门以及罗马神庙的残垣断壁汇聚在一起，向我们无声地叙述属于罗马的故事。当然，这里最能体现罗马精神的，还是非罗马广场一直莫属。这片废墟曾经是罗马公共生活的中心，在这里曾经矗立这元老院、罗马法院、神庙与政治演说台等多个与罗马精神息息相关的场所。直到今天，世界各地的政治与法律的运作方式依然深受古罗马的影响，而这些建筑就安静地站在这里提醒着我们罗马帝国为后世遗留下了足够的精神财富。
四河喷泉：世界寓言
为了躲开的人最多（也是传言小偷最多）的特莱维喷泉，我在来之前特意做了功课，想选择一个人不是那么多但同样很值得看的喷泉，于是，我将目标瞄准了四河喷泉。
四河喷泉位于纳沃纳广场中央，距离万神殿并不远，步行 10 分钟左右就可以抵达。喷泉的底座是四名男性河神雕像，分别为多瑙河（欧洲）、恒河（亚洲）、尼罗河（非洲）与拉普拉塔河（美洲）。有意思的是，这四名河神并不是静坐的姿态，而是以扭转、后仰等姿势「靠」在身后的方碑上，非常具有灵动感和喜剧感。喷泉中央的方尖碑是罗马帝国时期防止的古埃及方尖碑，方尖碑的顶部还有一只衔着橄榄枝的鸽子，因此整个喷泉就是四大洲+古埃及+教皇家族的象征。
我并不懂建筑，也不是很明白基督教，仅从我个人的体感来说，这座喷泉非常强调「融入感」。站在底部其实很容易观察到，石雕中的动物、神明、器物和岩石是融为一体的，而它们融入之后就以水流的形式向外蔓延。虽然这些喷泉或建筑都还是逃不过展示教皇权威的命运，但罗马人的心中始终怀揣的整个世界。不管从哪个角度来看，四河喷泉代表的意思都是「世界寓言」。如果罗马只能推荐一座喷泉，那我会毫不犹豫地选择这里。
宗教：除了中心还是中心
关于罗马，一定绕不开的关键词就是「宗教」。毕竟，这里同时具有圣彼得传统、罗马主教的地位、以及帝国首都留下的政治与象征资本，而这些条件也使罗马成为了天主教的中心。
梵蒂冈：比宗教更夯的是艺术
很多人说来了罗马就不能不来梵蒂冈。去之前我对这个说法是有些疑惑的，去了以后才觉得幸好没错过。我们所熟知的梵蒂冈，包括圣彼得大教堂及广场、宗座宫以及梵蒂冈博物馆三个部分。对于不太懂天主教的游客来说，这三个地方中最不能错过的，肯定就是梵蒂冈博物馆了。要说我对梵蒂冈的感受，那只有一句话：即使是角落，含金量也是自不必说。
梵蒂冈博物馆本来也是教皇居住的宫殿，所以这其中有很多教皇委托艺术家装饰的房间，以及历任教皇收藏的艺术品。这些房间和艺术品，构成了今天我们看到的梵蒂冈馆藏的主体。
来之前，除了那些非常有名的壁画，我对梵蒂冈几乎一无所知。因此当我看到埃及博物馆之后的时候，属实是被吓了一跳。经过了讲解我才知道，在罗马帝国时代，罗马城里本来就有很多来自于埃及的东西（例如上面已经提到的石碑），这些东西最后在 1839 年由教皇格里高利十六世整理之后汇聚在了现在的梵蒂冈格里高利埃及博物馆。
埃及博物馆展示了大量的木乃伊、法老雕像、神像、石碑等，甚至还有圣甲虫和莎草纸等物品，对我这种没去过埃及和大英博物馆的人来说，是一个全面认识古埃及社会的好地方。更重要的是，我认为这里不仅展示了古埃及文物，还在告诉我们埃及是如何融入罗马的世界，并且最终成为罗马与天主教文化的一部分。与四河喷泉一样，这里也体现着一种文明的融合感。
梵蒂冈第二个令我震惊的地方，是地图长廊。长廊的长度约为 120 米，两次悬挂着共 40 副意大利半岛各个地区的教会领地地图。大多数地图其实都是壁画，因此地图本身已经成为了建筑的一部分。和我们现在常见的地图不同，有些地图中不仅标记了地点，还记录了这个地区的重要历史事件。例如梅陶罗河战役、尤利乌斯二世围攻米兰多拉等时间，都被画在了地图上。
另外，地图长廊可不是只有墙壁两侧眼花缭乱的地图，还有天花板上金碧辉煌的壁画。最好的参观方法，是先走一遍看其中一侧的地图，再走回来看上方天花板的壁画。最后再走一遍看另一侧的地图。可即使是走三遍，在人员拥挤的情况下也很难把每一个细节都捕捉到。作为通往画室的必经之路，这里值得每个人为他驻足停留。
与乌菲兹美术馆类似，梵蒂冈也收藏了古罗马和古希腊的雕塑作品，其中很多是神邸、英雄、皇帝、哲学家和政治人物。这些雕像主要分布在三个展区：皮奥-克莱门蒂诺博物馆、基亚拉蒙蒂博物馆以及新翼。我个人认为最有意思的一尊雕塑，是位于基亚拉蒙蒂博物馆的达契亚人俘虏像。它是一尊看起来很「软」的作品。从头上的达契亚贵族软毛，到浓密软塌的胡须，再到身上黏软的纹理和交叠的双手，每一处细节都和我们所熟悉的罗马雕塑的风格大相径庭。看多了棱角分明的雕塑以后，这个作品反而更令人觉得新奇和有趣。
要说梵蒂冈博物馆的两大「金刚」，无疑是拉斐尔画室和西斯廷礼拜堂。拉斐尔画室有广为人知的《雅典学院》和《圣体争辩》，而西斯廷礼拜堂则有米开朗基罗的神作《创世纪》与《最后的审判》。这些作品的艺术价值想必已经无需多言，我更想告诉你的是站在现场看到这些作品感受。
这两个地方都因为太过有名而挤满了人，站在画室里也基本上很难获得一个与画作干净的面对面的机会，然而即便如此，抬头看画的时候还是会感觉好像发生了时空错乱。画作中的时间点、艺术家创作的时间点以及此时此刻，三点重叠，很难判断到底是我隔着历史的长河在看画，还是画穿越了历史的长河来和我对话。我想，这种时空错乱感可能就来源于艺术的「鲜活」，正如生活中不能缺少「活人」一样，生活中也不能缺少如此鲜活的艺术。
圣天使堡与圣天使桥：帝国与基督教的联结
我住的酒店距离圣天使堡不算远，于是在某天傍晚我就来这里闲逛了。圣天使堡最早是哈德良为自己的家族修建的陵墓，后来也承担过要塞、监狱和教皇避难所的功能，一直到今天成为一座博物馆。假设你的游览时间并不充裕，那么你可以选择跳过圣天使堡内部，但一定要在圣天使桥上多待一会儿。
圣天使桥架在台伯河上，是连接圣天使堡和罗马市中心的重要桥梁。圣天使桥上的两侧共有十尊天使雕像，每一位天使的手中都拿着一件与基督受难相关的物品。十尊天使站在桥的两侧，向我们传达着基督教最正统的故事，而桥的尽头又是罗马皇帝的陵墓，这样一个帝国和基督教的联结在罗马城中是一个很独特的存在。当然了，在黄昏十分，这里也是一个绝佳的观赏台伯河日落的地点。不懂历史没关系，在这里出点片也挺好的。
城市：文物保育和街头美学
大型圆明园现场
如果让我评选世界上的第一座「城市」，那我会毫不犹豫选择罗马。走在罗马的街头，随处都可以看到很多来自于古罗马和中世纪的遗迹，简直就是一个大型圆明园现场，这也是我认为罗马最迷人的地方。某天我吃过午饭离开餐馆，才发现旁边居然就是阿根廷广场古迹区。又步行不远之后，又看到路边很多人聚集在一个「地下室」旁边，走近一看才发现居然是古罗马时期的某个宫殿的地基遗址。与我们国家的古城明显不同的是，罗马的这些遗迹是「渗透」在如今的城市建设中的。它们没有被修旧如旧地修缮，也没有被大规模圈起来作为保护区，而是就放在那里，并逐渐融合在了如今的罗马城和罗马人的生活中。
我在从人民广场走向斗兽场的路上一直在想：让文物在这里接受自然风霜的洗礼，是不是也是一种对文物的「保护」呢？它们本来就建设在自然中，受环境影响并被环境改变是很再正常不过的事情。既然如此，不如就让它们在那里，自然地在那里就好。我不懂文物保护，但我一直很喜欢香港人对文物保护的称呼——保育。罗马对于各类遗址的保护措施，在我看来就是一种绝佳的保育措施。与其过度保护不如让它们与自然融合，与生活融合。
街头的艺术魅力
以一个游客的视角来看，罗马城中好像没有太多新建筑，大多数建筑看起来都已经有些年头了。然而这些建筑有两个鲜明的特点：一是色彩都鲜明且自然，二是和自然景搭配得很好。在罗马，你很少看到「灰头土脸」的建筑，大多数房子都是有颜色、有形状的。这些房子在遵守着城市建设公共规范的同时，也在传达着自己的个性。并且，罗马的房子上或者房子周围都会有植物作为装点，给房子增加很多情趣。也许是因为意大利人天生就有很好的艺术细胞，或者是因为意大利人都接受了深度的艺术熏陶，总之他们看起来都有很高的美商，而且还把这些美商应用在了生活里的方方面面。
不吃不喝不是意大利
罗马作为我意大利旅行的第一站，理所当然成为了我在意大利探索美食的第一站。无论是 Instagram 上有名的网红餐厅，还是开在街边的私房小店，食物的整体品质都很在线。我很喜欢在罗马街头探索食物，因为不知道在哪里就会有新的惊喜在等待着我。

但 Bitwarden 另有所长——碰巧家里有一台 24 小时开机的 NAS，自托管一个 Vaultwarden 自然而然提上了日程。
为什么是 Vaultwarden
Vaultwarden 是一个由社区维护的非官方开源 Bitwarden 后端服务。与官方那套基于 .NET 和笨重数据库的自托管后端相比，Vaultwarden 镜像极其轻巧，常驻内存通常不过百兆；不仅核心功能完备，还能直接从后端解锁 TOTP 管理、多人共享等高级功能，非常适合个人和小微团队自建使用。
NAS 部署的首选方式
Vaultwarden 的部署方式多种多样，对于 NAS 来说，Docker 无疑是第一选择。一方面 Vaultwarden 的 Docker 镜像小巧、部署简单，无论你是否有相关经验都很容易上手；另一方面是在做好目录映射后，可以使用 NAS 本身的文件同步或备份功能保障数据安全。
Vaultwarden 的 Docker 部署过程不需要折腾太多参数，社区提供的 Docker Compose 模板也简单明了。如果你和我一样使用零售的成品 NAS（如极空间、绿联等），我们甚至都不需要去看 Compose 文件，直接在系统的图形化 Docker 部署界面就能搞定。
以下是几个我认为在部署时需要注意的几个参数：
- 镜像拉取：使用 vaultwarden/server 的 latest 标签，更新容器时只需重新拉取镜像，在做好第 2 点的前提下，不会影响已经保存的密码数据。
- 目录映射：为了持久化保存密码库，我们需要将容器内部的 /data 目录映射到 NAS 中的实体文件夹，以后需要手动备份或迁移到其他设备上时，直接复制该文件夹即可。
- 对于 Docker Compose 部署，我们在模板中找到 volumes 字段下包含 :/data 的值，将冒号前面的路径替换为你在 NAS 上提前建好的真实文件夹路径（如 /mnt/nvme16/bigk/Docker/vw/data:/data）。
- 端口映射：容器内默认使用 80 端口，直接使用宿主机网络极易产生端口冲突，因此需要修改环境变量中的 ROCKET_PORT，或推荐使用 bridge 网络并将 80 端口映射为 NAS 主机上的其他端口。
- 对于 Docker Compose 部署，我们需要确保 network_mode 为 "bridge"（或干脆不配置该字段），并在 ports 字段下找到包含 :80 的值，将冒号前的端口号改为你想使用的 NAS 主机端口号（如 8808:80）。
- 访问和连接：Vaultwarden 要求可信的网络连接，在非 localhost 环境下需要配置 HTTPS，因此需要提前做好准备，包括签好证书、配置反代或者找一个靠谱的内网穿透工具。
无论是图形化配置还是 Docker Compose，都强烈建议在环境变量（environment 字段）中配置 DOMAIN 的值为你要从公网连接进来的域名。
图形化部署的情况下，修改环境变量后可能需要重新创建容器；使用 Docker Compose 部署时，建议将环境变量写进 .env 文件中并由 Docker Compose 文件引用，后续维护和配置权限会更加方便。
Docker 部署完成后，我们可以使用浏览器输入 IP 地址和端口号访问 Vaultwarden。当浏览器显示 Vaultwarden 页面时，说明部署成功。但这并不代表我们已经可以使用它。
HTTPS 与互联网访问
正如前面所提到的，除非直接在 NAS 本地的 localhost 网络环境访问，否则直接用局域网 IP 打开，Vaultwarden 只会弹出拒绝访问的警告页面。
这是因为现代浏览器中有一道「安全上下文」的强制策略，密码管理器网页端所依赖的 Web Crypto API 加密接口只有在可信网络中才能被调用，而家庭内网常见的 HTTP 连接会被判定为不可信网络，Vaultwarden 发现无法调用该接口就会直接给出警告提示。
同理，如果我们需要随时随地都能访问到 Vaultwarden 的数据库（例如在公司电脑浏览器中使用 Bitwarden 自动填充插件），也必须通过可信的 HTTPS 连接。
Vaultwarden 内置了 HTTPS 功能，不过官方 Wiki 中已经明确表示这种方式不成熟，仍然建议大家使用反向代理来处理 HTTPS 请求，并通过 Let's Encrypt 或 Cloudflare 获取 SSL/TLS 证书。然而反向代理对网络环境有着严格要求，国内运营商的家庭宽带基本都是大内网，好一点的 NAT 1 可以借助 STUN 服务「打个洞」获得相对稳定的公网访问体验，而其他 NAT 类型多少都需要折腾一番。
不过你既然能看到这里，相信你已经非常了解反向代理的原理和各类工具的使用了，本文不再赘述。
如果你家和我一样是低等级 NAT，或者单纯只是想省事不折腾，那么我强烈推荐使用「赛博菩萨」Cloudflare 的 Tunnel 隧道功能。它能够将内网服务安全地映射出去，不仅能顺手解决 SSL/TLS 证书的麻烦，还能获得免费的 DDoS 防护、访问控制等网络安全能力。配置 Cloudflare Tunnel 也是易如反掌：
- 登录 Cloudflare 进入控制台，在左侧导航栏中进入「Zero Trust」，在新页面的导航栏中展开「网络」，进入「连接器」功能；
- 在打开的「隧道与网状网络」页面，点击「创建隧道」，选择「cloudflared」后根据指引继续操作；
- 来到安装 cloudflared 客户端的指引界面，根据所用系统选择安装 cloudflared 客户端（如需在 NAS 上安装依然推荐 Docker 方式）；
- 从这一步开始，我们需要根据自身的实际情况进行操作：
- 如果你有自己的域名且已经托管到了 Cloudflare 中，那就直接运行页面中的命令建立连接，然后前往「已发布应用程序路由」页面中添加二级域名映射；
- 其他情况则需要使用 cloudflared tunnel --url http://[IP]:[Port] 命令，将内网中的 Vaultwarden 访问地址映射至一个 https://*.trycloudflare.com 形式的临时域名中。
- 尝试通过域名访问 Vaultwarden 的页面，如果你能在浏览器地址栏中看到 HTTPS 连接，且可以正常显示登录页面，那么我们整个链路便跑通了。
需要注意的是，虽然没有域名也能搭建隧道，但 Cloudflare 给出的域名仅仅是临时地址，不仅名字又长又难记，而且每次重启服务后域名都会变化，因此我更建议去买一个便宜的域名然后托管到 Cloudflare。这是一个一劳永逸的方法，以后不止是 Vaultwarden，你家中所有的内网服务都可以在该域名下挂二级域名使用，并通过 Cloudflare Tunnel 实现更安全的内网穿透。即便你的服务遍布于不同设备、不同地理位置，也只需要在对应设备上安装一个 cloudflared 客户端并映射在同一域名下即可，完全不需要额外付费。
必要的权限管理
搞定公网访问后，我们已经可以创建账号、保存密码、跨设备同步了——你对象也可以，你表姑的邻居和那位邻居儿子同学的篮球队友也可以。
默认情况下，Vaultwarden 允许任何人注册账号，假如有人手抖输错了网址碰巧进入到了这个域名或者被脚本扫描到了，那他们可以在你的 Vaultwarden 服务中注册自己的账号并使用，甚至还能上传各种附件文件。
虽然这不太会影响你账号下的数据安全，但你也不想让自己的私有服务变成公共的免费网盘对吧？
所以在我们注册好自己的账号后，需要立即将 SIGNUPS_ALLOWED 这个环境变量的值设为 false（没有就新建一个变量）后重新部署容器，之后即使有人访问了你的服务也无法注册账号。
除了关闭注册，还有一件事与密码库的安全息息相关，那就是整个 Vaultwarden 的管理后台（即 /admin 页面），这个管理后台掌控了整个 Vaultwarden 服务和数据库。管理页面默认就是关闭的，不开启也完全不影响使用，但对于有着更高自定义需求的用户，我们需要在环境变量中设置 ADMIN_TOKEN 字段并添加一个极为复杂的 Token 值才能启用。
考虑到密码管理器并不是一个需要频繁调整设置的工具，所以我更建议在配置完成后删掉 ADMIN_TOKEN 字段，彻底关闭后台的访问功能，也不用再去管什么 Argon2 PHC 令牌保护了。
此外，Vaultwarden 同样支持主账号的 2FA 两步验证登录，验证方式包括 TOTP 验证码、通行密钥以及由 Duo Security 生成的验证代码。为了安全起见，在配置 2FA 时务必妥善保管 Vaultwarden 提供的紧急恢复代码。
迁移与使用
剩下的事情就简单得多了，登录后进入到「工具」页面，选择「导入」后就能快速迁移密码库。Vaultwarden 可以导入市面上绝大多数主流密码管理器的数据格式，我这三四百条密码数据直接选择「Enpass (JSON)」就能完美解析。在确认所有登录方式都迁移完成之前，我建议最好不要立即卸载上一个密码管理工具或清空密码库。有必要让两种工具并行一段时间。
浏览器插件方面，因为安全和生态的原因，目前依然只有 Bitwarden 官方插件可用，安装插件后选择自托管服务，输入刚才在 Cloudflare 发布的二级域名并登录后即可获得完整的自动填充功能。
至于移动端，为了兼顾多平台复用，Bitwarden 官方 App 带着一种明显的「移植感」，使用体验放到 2026 年实在算不上优秀。几年前我还在使用 Bitwarden 时，也经常会遇到手机端自动填充抓取失败、解锁无响应的糟心情况。
在 @克莱德 的推荐下，我更换了第三方客户端 Keyguard。这是一个开源的密码管理器前端工具，支持 Windows、macOS、Linux 以及 Android 和 Wear OS 平台，兼容 Bitwarden 和 KeePass 密码数据。其 UI 设计、交互逻辑和动画效果相比官方客户端都更加出色。
更重要的是，主流密码管理服务从 9 月初开始陆续支持了通行密钥的迁移，如果你在 Keyguard 设置中点击你的用户名，然后选择「从其他应用导入」，即可从其他支持通行密钥的密码服务中直接迁移通行密钥，免去了很多重新配置的繁琐流程。
Keyguard 还可以接管 Android 版 Chrome 浏览器的「第三方自动填充」服务。这是一项从 Android 14 开放的新特性，第三方密码管理器能够匹配网页 DOM 元素实现更准确的密码填充。加上 Keyguard 极其稳健的密码库本地保存功能，即使因为 Cloudflare 网络波动无法连接到自建数据库，它也能正常使用。
在使用官方 Bitwarden 服务的情况下，如果你有 TOTP 需求，也可以使用 Keyguard，因为 Bitwarden 实际上并未在服务端给免费用户封禁 TOTP 功能（端到端加密也看不出来里面保存了什么），只是前端没有给免费用户开放入口。Keyguard 可以绕过这一限制，不过在浏览器中可能需要你手动打开 Keyguard 复制验证码。

正值 iOS 27 发布之际，聊聊这次新增加的「通知自动化」。
当初 Mac 上快捷指令新增文件的自动化时，很自然地联想到 Mac 上「自动操作」中的文件夹操作，当时希望其中的日程提醒也能整合到快捷指令自动化中，根据日程或者提醒事项自动执行快捷指令。
没想到苹果直接一步到位，增加了通知自动化，不再局限于日历、提醒事项、邮件、信息等系统内容，任何能发送通知的 App 都能够作为快捷指令的触发器。这意味着除了信息和邮件之外，甚至可以使用微信这样的高频 App 通知作为自动化入口。更重要的是，通知和信息邮件一样，本身还携带了可以参与筛选和处理的自定义内容，可以根据 App 传递过来的不同内容执行不同的操作。
不同 App 可以有不同的提醒方式。不同联系人可以有不同的紧急状态。不同通知内容也可以执行完全不同的操作。
所以通知自动化本身，看起来只是增加了一个触发条件，实际上多了一整层可以利用的「输入」。
要使用通知自动化，必须开启 App 的系统通知并在「锁屏」或「通知中心」中至少选择一种通知显示位置，单独选择横幅无法运行通知自动化。
先聊通知自动化本身
通知自动化的基本逻辑非常简单：收到指定 App 通知时运行快捷指令。
目前主要可以通过三个字段筛选通知：
- 通知标题
- 通知副标题
- 通知信息正文
通过添加筛选条件，能更精确地定位指定的通知。添加多个筛选条件时，通知需要同时满足所有条件，而不是满足任意一个即可执行指令。例如微信通知的标题为联系人备注，信息为消息内容。只有在这个联系人发送包含指定信息的情况下，自动化才会执行指令。
三种筛选条件通过观察 App 最终显示的通知结构来确定。通常可以结合文字的层级换行来判断不同字段分别对应标题、副标题和信息正文，各部分字重也不相同。假设一条通知最终显示为三行：
- 第一行 = 标题
- 第二行 = 副标题
- 第三行 = 信息正文
这里有一个点要注意，实际通知和快捷指令中的「显示通知」操作的字段有一定的冲突。
图中快捷指令「显示通知」操作中的「标题」，在实际快捷指令通知的第二行，在通知自动化中其实属于副标题，第一行的指令名称才是标题。
像微信通知有两行内容，则分别为标题和信息。微信联系人备注为通知标题，消息内容为通知信息正文。
所以在使用通知自动化的时候，最好是直接观察最终显示出来的通知结构，再确定通知自动化的筛选条件如何选择。
通知自动化的输出变量「通知」有多种详细信息，例如 App 名称、通知标题、副标题、正文、通知日期等。每一个详细信息后续都可以当作判断依据，执行不同的操作。例如微信接收到某人的报名消息，但是发送消息时间已错过报名截止日期，自动回复自定义的消息内容。
让通知更通知
之前我们主要通过锁屏、通知中心、横幅、指定的铃声、App 角标获取通知信息。现在则可以利用通知自动化，给通知增加更多维度的提醒，例如变更墙纸、播放特殊语音、产生额外的振动。还可以设定闹钟、增加提醒事项、创建日程，等待一段时间后二次提醒。
01 重要消息着重提醒
当收到具体某个联系人消息的时候，记录一次消息的时间。
之后每收到一次该联系人的消息，就将当前时间和储存空间里记录的第一条消息时间进行比较。
如果发现已经超过 30 分钟，而你一直没有打开 App 或进行回复，那么就可以认为：
这个联系人已经连续找了你几次，而且间隔时间比较长，可能真的有急事。
这时候普通的通知可能已经不足以提醒你。
就可以通过快捷指令更换更醒目墙纸，加强提醒的效果。
当你打开对应 App 后，再通过「打开 App」自动化清理之前储存的消息时间记录，并切换回原本的墙纸。
当然，这里存在一个限制。
目前快捷指令并不能真正判断「你打开 App 后，这条消息是不是已经阅读」。所以这里只能把「打开 App」作为一个近似判断，打开 App = 默认已经知道有新的消息，就自动清理之前记录的消息时间。
虽然并不是真正意义上的「已读检测」，但对于日常使用来说，这种方式已经可以作为大致的提醒机制。

02 更改 App 图标后，如何保留角标提醒？
这是通知自动化替代系统通知的一个场景。
使用快捷指令自定义 App 图标之后，原本 App 的角标会直接失效，例如微信或者其他 App 有新的未读消息，桌面上的自定义图标无法显示原本的红色角标。这会导致你在桌面上根本看不出来这个 App 有没有新的消息。所以可以利用通知自动化进行修补。
当指定 App 收到通知后，通过通知自动化获取通知对应的 App 信息，再根据 App 的位置，在当前墙纸上动态叠放一个角标。
这样虽然没有真正改变 App 图标，但可以在视觉上把「未读数量」重新放回原来的位置。
微信收到消息时，记录消息数量，若没有记录记为 1，存在记录则累计。
模拟角标的红色圆底白字，将红色圆底图像使用 base64 存储在指令中（iOS 27 新增的储存空间更方便，为了指令分享即用，暂时还是使用 base64 储存，下文也是如此）
将累计的消息数量叠放在圆形红底上。
通过表达式计算角标在墙纸上的位置，不同设备可以根据裁剪截图自行更改数据。图中角标为第三行第二列，若主屏幕上自定义图标位置改变，需要在指令中手动更改行列数。
当打开微信之后，再通过「打开 App」自动化清除这个角标，重新生成没有角标的墙纸。
不过这种方案更适合只有一个主屏幕页面的情况。如果有多个主屏幕页面，或者同一个 App 在不同页面存在不同图标，就容易产生视觉上的误会。因为墙纸上的角标并不知道你当前到底翻到了哪一页。
所以它只是一种曲线救国的替代方式。
其实还有一种更方便的方法，快捷指令不知哪个版本增加了一个「快捷指令添加到主屏幕」的操作。
理论上可以利用这个方式重新生成一个带有角标效果的图标。
但是目前比较可惜的是添加之后无法方便地删除。每次生成一个新的图标，就会在主屏幕上多出一个图标。如果再配合通知自动化不断生成，就很容易出现大量重复图标。
而且这种方式也无法像前面的墙纸方案一样，在打开 App 后自动清理。最终还是需要手动删除旧图标。
所以目前来看，还是使用前面的墙纸方案更加灵活。虽然不够优雅，但至少可以自动生成、自动清理，不会不断制造新的 App 图标。

03 用颜色表达通知
如果觉得在墙纸上直接放数字太过于粗糙，也可以换一种更加「意识流」的方式。尤其适合使用纯色或者极简墙纸的人。
提前为每一个 App 分配一种代表色，或是按照 App 类型分配主题色。这里使用 App 图标本身颜色的 RGBA 值。
