A coding-agent skill that turns your agent into a security auditor. It orchestrates isolated agents through reconnaissance, coverage-led hunting, candidate validation, structured output, independent record verification, and target-neutral reporting.
This is the skill that seeded Cloudflare's vulnerability discovery harness, described in Build your own vulnerability harness. The harness grew into a multi-stage, fleet-wide system; this skill is the single-repo starting point it evolved from.
The skill runs a structured audit in six phases:
- Reconnaissance -- map architecture, trust boundaries, input surfaces, prior evidence, and deterministic coverage in architecture.md and coverage-ledger.json.
- Coverage-led hunting -- assign isolated hunters from ledger units, record their checks, and use coverage critics to find gaps.
- Candidate validation -- give every unique candidate to a fresh verifier that tries to disprove it.
- Structured output -- write confirmed, needs_validation, and rejected records to findings.json and validate them against report-schema.json.
- Independent record verification -- fresh agents verify final source claims. Material replacements receive another independent verifier.
- Target-neutral reporting -- derive REPORT.md, FINDINGS-DETAIL.md, and NEEDS-VALIDATION.md from the verified records and coverage ledger.
The parent runs validate-coverage-ledger.cjs after creating the ledger and after each later ledger update. It runs validate-findings.cjs in Phase 4 and again after every Phase 5 replacement.
The verdicts are distinct: confirmed has a complete source trace and bounded observed result, needs_validation has an exact unresolved fact and no severity, and rejected records a disproved candidate.
Multiple runs against the same repo are additive. The skill uses prior ledgers and findings to target gaps, revalidate changed source, and carry forward current-source evidence without treating stale or unresolved work as covered.
Install the skill with the Skills CLI:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
Use --global for a user-level installation:
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit \
  --global
Run npx skills --help for agent-selection and non-interactive options.
Start your coding agent in (or pointed at) the codebase you want to audit, then ask it to do a security audit:
security audit this codebase
find security vulnerabilities in ./src
do a security review, output to ~/audits/my-project
The skill activates automatically when the request matches its trigger (security audit, find vulnerabilities, pen-test the code, etc.). A direct codebase audit or pen-test request uses full audit mode. Security questions and focused vulnerability work use guidance mode unless you request report artifacts. In full audit mode, an unspecified output directory defaults to ~/security-audit-skill/<repo-name>/run-<N>. The workflow writes inside the target repository only when you explicitly select a directory that version control ignores.
- A coding agent with a model that supports tool use and parallel sub-agents
- Node.js for the zero-dependency findings and coverage-ledger validators
- An OS-enforced sandbox for target-controlled builds, tests, processes, browsers, emulators, fuzzers, and fixtures. It must disable external networking, use a sanitized allowlisted environment, enforce resource limits, and allow writes only to assigned scratch paths. Without these controls, the workflow keeps the lead as needs_validation instead of executing target code.
- Only confirm established boundary failures. Keep a source-grounded blocked lead as needs_validation with its exact unresolved fact.
- Adversarial validation. The agent that checks a finding is never the agent that found it.
- Severity requires impact. Likelihood x impact, not deviation from a checklist.
- Defense-in-depth gaps are not vulnerabilities. If Layer A prevents the attack, the absence of Layer B is a hardening note.
- Multiple runs improve coverage. In our test runs, a single run found roughly half of the vulnerabilities that repeated runs found in total.
Questions, feedback, or comparing notes on AI-driven security tooling: security-ai-research@cloudflare.com

New in OpenShell 0.1.x: a stable release cadence, new isolation primitives, an expanded extension surface, and new APIs. Read the 0.1.0 upgrade guide.
OpenShell is the safe, private runtime for fleets of autonomous AI agents. Agents are most useful when they can read files, install packages, call APIs, and use credentials. OpenShell gives them that capability without giving them unrestricted access to your data, secrets, or network. You declare what each agent can touch in a policy, and OpenShell enforces it.
OpenShell governs what agents can do in two ways: it instruments the kernel to enforce policy on every file access, system call, and network connection at runtime, and it uses formal verification to check what a policy change would allow before it is applied.
- Kernel-level enforcement. Each agent runs in an isolated sandbox. Kernel controls confine which files it can access and which system calls it can make, and every network connection passes through a policy check before it leaves the sandbox. Agents never see real credentials; OpenShell adds them only to requests bound for approved endpoints.
- Formally verified policy changes. Before a policy change is approved, OpenShell uses formal verification to flag risky new access it would grant, such as reaching a new host with credentials or calling a new API method, so those changes wait for human review.
See Architecture for how the gateway, supervisor, and sandbox fit together.
You need Linux, macOS on Apple Silicon, or Windows with WSL 2 (experimental), plus Docker, Podman, or host virtualization. See the Support Matrix for details.
curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh

The installer sets up the CLI and a local gateway. The default sandbox image is minimal Ubuntu with no agent installed. To run a real agent, follow Run Your First Agent: it runs OpenCode against a free OpenRouter model and shows how to approve new access as the agent needs it.

A design skill for Claude Code, Codex, Cursor and OpenCode that refuses to look AI-generated.
usehallmark.com · forty-eight themes · custom on request · redesign and audit by name
Made by Together AI.
Hallmark holds a hard floor and then gets out of the way. It deals three themes from a catalog of forty-eight materials, builds the page around what the visitor came to do, and lints the result in a real browser against the tells that read as machine-made: the eyebrow above every heading, tracked-capital labels, one coloured word in a headline, a page of empty frames or nothing but photographs, a hero that misses its screen, an email sign-up at the end of every page, a form that says thanks without sending anything. A fresh-context reviewer gets the last word.
The gates come in tiers. The Floor never ships (contrast, focus, reduced motion, invented facts, a broken phone layout). Reflex gates are the defaults a model falls into; a build with a reason may overrule one on the record. Finish checks are craft detail that never blocks a ship.
- Forty-eight themes. Each is a material (paper, type, colour, surfaces, its own components and texture) with a picture of a finished page, and the build lays out its own page in it.
- Built from the job. A booking page books, a shop sells, a newsletter subscribes: the action sits where the category puts it, and the page ends on it.
- Custom. Ask for a custom page and Hallmark designs from your prompt alone, under the same rules and checks.
- Your real product. Point it at a URL, a dev server or an app and it captures the screenshots itself.
- Real photographs. 755 openly licensed photos, picked per subject and credited on the page.
- Redesign and audit. /hallmark redesign <path> rebuilds a page and keeps its content and wiring; /hallmark audit <path> only reports.
Ten of the forty-eight. A theme is a material, not a plan: it never says what a page contains or in what order, so two prompts in one theme make two different pages. Each is one file of at most 8 KB in references/themes/ with a picture beside it; a build reads exactly one. See them all at usehallmark.com.
Say custom and Hallmark drops the themes: no plan, no components, no palette recipe, only the floor, the gates and a short direction in direction.md to find one idea that only this client has and let it run the page.
- Pre-flight reads the project (fonts, palette, framework, a locked design.md) and asks once for the material: photos, screenshots, real numbers. Nothing is invented.
- scripts/theme.mjs deal offers three themes that fit the prompt and clear the log; draw deals the page's anatomy from its job.
- The hero is built alone, rendered and reviewed cold before the rest of the page exists.
- scripts/sloplint.mjs --render checks the page at eight widths, then a subagent reviews it with fresh eyes.
Each page is self-contained HTML and CSS, stamped in its first CSS comment with the decisions it took.
Hallmark never starts on a design that already exists unless you name it:
/hallmark redesign ./src/app
/hallmark audit ./index.html
A full redesign keeps the content and the wiring and changes the system and the layout; say keep the layout for a restyle or polish for only the tells. sloplint --before records every link, field, handler and heading first, sloplint --kept fails the redesign if one went missing, and the handoff is a side-by-side before and after.
npx skills add nutlope/hallmark -g
-g installs for every project; leave it off to install into the current one. Needs Node 18 or later. The browser checks (sloplint --render, screenshots) also need npm i -g puppeteer-core and Chrome; without them the static checks still run.

import os, zlib, struct
path = os.path.expanduser("~/Library/Application Support/WeType/mmkv/wetype.settings")
data = bytearray(open(path, "rb").read())

技巧 3：方向键快速连按无响应？打开「允许连续快速按」

- SayAll 默认对自定义快捷键开启了防连击保护，按键稳定前会过滤连续输入；

- 在 SayAll 方向键设置中，清除所有「双击」绑定；
- 勾选对应按键下方的 「允许连续快速按」（Allow Rapid Repeated Presses）。
这样设置后，按键消除了双击等待窗口，单击零延迟触发，连续快速点按时也能每一次都即时响应。
4. 终端与 Agent 工作流配置：Herdr / Codex / WorkBuddy

来到 Mountain View
从旧金山出发，沿着 101 高速公路向南，Palo Alto、Mountain View、Cupertino 这些既熟悉又陌生的地名陆续出现在路牌上。过去几年，我在科技新闻以及《硅谷之火》《乔布斯传》《Apple: The First 50 Years》等书籍里反复读到这些地名，却始终没有机会亲自到访。直到这次国庆假期，才终于有机会到达硅谷，参观期待已久的计算机历史博物馆，顺道看看附近的 Google 和 Apple 园区。
计算机历史博物馆（Computer History Museum，简称 CHM，后文中统一用 CHM 指代）位于 Mountain View 的 North Shoreline Boulevard。博物馆所在的建筑建成于 1995 年，最初是 Silicon Graphics 的办公园区。整座建筑低矮舒展，沿水平方向铺开，即使放在三十年后的今天，依然显得颇为现代。
2002 年，CHM 购入了这座建筑。曾经用于展示前沿计算技术的地方，如今成为了保存计算机技术历史的博物馆，而 Silicon Graphics 的机器也成了馆藏的一部分——Silicon Graphics（简称 SGI）在上世纪九十年代以高性能图形工作站闻名，它的机器价格昂贵，主要用于大学、科研机构和影视制作等领域。后来随着通用 PC 性能的提升和消费级 GPU 的发展，SGI 逐渐失去了昔日的优势，最终淡出了人们的视野。
CHM 的展览横跨两千年的计算史，我最期待的还是个人计算机诞生前后的那几十年。我曾在《硅谷之火》和《乔布斯传》中反复读到过那段历史：Homebrew Computer Club 的聚会、Altair 的出现、Xerox PARC 的研究，以及后来 Lisa 和 Macintosh 的诞生。这些故事中提到的机器我都还没有见过实物，并且书里的照片很难让我对机器的大小形成直观印象。一块 Apple I 的电路板和一套庞大的计算机系统可能占据同样大小的版面，所以只有站在实物面前，才能真正感受到它们在体积、结构和设计上的差异。
走进 CHM，展览沿着计算技术发展的时间线展开。最先映入眼帘的，是那些诞生于个人计算机时代之前的大型计算设备。
从大型机到 Xerox Alto
ENIAC：用接线和开关编程
CHM 的常设展览 Revolution，沿着时间线梳理了从早期计算工具到现代计算机的发展。我在几台大型机前停留了很久，回来整理照片时又查阅了不少资料，试着了解它们当年背后的故事。
早期计算机大多服务于大学、政府和大型企业，普通人买不起，亦很难有机会直接操作这些机器。从 ENIAC 到 IBM 1401，再到 PDP-1，这些具备代表性的机器都展示了计算机与使用者之间关系的变化。
1946 年公开亮相的 ENIAC，由宾夕法尼亚大学的 John Mauchly 和 J. Presper Eckert 团队研制，起初为美国陆军计算弹道表。整机使用了约 18000 支电子管，占据一整个大房间，在 CHM 能看到的只是其中的一部分。
早期 ENIAC 每次更换计算任务都需要重新安排接线、设置开关，准备工作可能耗费数天。程序通过各个计算单元之间的连接和开关状态来实现。今天写程序遇到问题，可以设置断点、查看变量，调试难度比当年简单得多。
当时负责 ENIAC 编程的是六位女性，她们原本从事弹道计算工作，后来被选中为这台机器编写程序。在没有编程语言和现成工具的年代，她们需要研究机器的结构、设计计算流程，再通过接线和开关完成程序，并排查运行过程中的错误。讲解员爷爷特别提到了她们的经历。1946 年 ENIAC 首次公开展示时，这六位女性程序员没有受邀参加庆祝晚宴，也没有得到正式的介绍。当时人们的对计算机关注点主要集中在设计机器的工程师身上，编程工作的价值长期被低估。直到 1997 年，这六位女性程序员共同入选了「Women in Technology International」名人堂，才获得了迟来的认可。
展柜附近还有一枚小小的 ENIAC on a Chip。1995 年，宾夕法尼亚大学为纪念 ENIAC 诞生五十周年，将原机的计算架构重新实现在一枚芯片上，这枚芯片让人直观地看到半个世纪的技术发展能把曾经占据整个房间的计算能力缩小到什么程度。
IBM 1401
1959 年，IBM 推出了面向企业数据处理的 IBM 1401。与此前昂贵的大型计算机相比，它的价格更加亲民，让更多中型企业有机会使用计算机处理日常业务。工资核算、库存管理和账单处理等重复性工作开始逐渐交由计算机完成。
IBM 的历史介绍记载了一个有趣的发布故事：当时唯一能够正常工作的样机还在实验室，IBM 不愿冒险将它搬到摄影棚，于是制作了一套空机柜，用电池驱动指示灯闪烁，再让工程师躲在后面转动磁带卷盘，通过闭路电视向各地客户展示这台新机器。尽管演示的是一套道具，IBM 1401 的市场反响却十分热烈：发布前五周订单超过 5200 份，已经超过 IBM 原本对整个产品生命周期的销售预期。
Demo Lab 展厅里配套陈列的设备让人更容易理解当时计算机的工作方式，打孔机将文字和数字记录在纸卡上，游客可以参考字母对照表亲手制作一份打孔卡。读卡机负责输入数据，磁带用于存储，打印机则输出最终的报表。操作人员通常需要提前准备好程序和数据，交给计算机成批处理，再等待结果输出，这就是当时常见的「批处理」方式。
对于程序员来说这也意味着完全不同的工作体验。程序可能需要先打成一叠卡片，提交运行后才能知道结果。如果发现错误，就得修改卡片、重新提交。相比今天随时修改代码、运行调试的开发方式，每一次尝试都要付出更多时间。
今天能在计算机历史博物馆看到 IBM 1401 运转，也离不开 CHM 的修复团队的努力，他们曾花费多年寻找零件、排查电路，退休的 IBM 工程师和志愿者也参与其中。一套曾在康涅狄格州的家庭企业服役至 1995 年的 IBM 1401，最终成为修复的重要基础。
展厅里还有一块 1956 年由 Sperry Rand Univac 制造的磁芯存储板也让我印象深刻，它看起来像一块细密的织物。每个小磁环通过不同的磁化方向表示 0 和 1，穿过磁环的细线则负责改变和检测状态。CHM 的说明提到制造时很多工人要借助显微镜把线穿过微小的磁环。
平时写代码我不会想到内存是怎样制造的，看着这些磁环和细线，才会注意到即使是一个比特也曾需要这样的手工劳动。
与 IBM 1401 以批处理为主的工作方式不同，接下来在另一间 Demo Lab 看到的 PDP-1 让使用者能够坐在机器前，通过控制台和显示器直接与计算机互动。
PDP-1
DEC 在 1959 年展示 PDP-1 原型并在 1960 年开始交付，它仍是昂贵的研究设备，但与此前的大型机相比，设计思路已经有了明显变化：计算机不再只是接收任务、批量处理数据，也开始重视人与机器之间的实时交互，使用者可以输入指令、查看结果，再继续操作，不必每次都准备一批任务交给机器。
PDP-1 最出名的程序是 Spacewar!，也是早期电子游戏史上最有代表性的作品之一。1961 年，Steve Russell、Martin Graetz 和 Wayne Wiitanen 受科幻小说启发构思了这款太空战斗游戏，Russell 在 1962 年写出了最初版本，其他人随后加入更多功能。这款游戏中两名玩家控制飞船，转向、加速、射击，还得应付引力的影响。
CHM 的专题记载这款游戏后来还被用来向客户展示机器能力：输入、运算和图形同时进行，玩家立刻能感到回应。CHM 的 Demo Lab 在每个月的特定时间会提供这款游戏的试玩，只不过我去的时间没有赶上非常可惜。
我很喜欢这段故事里几个人不断为游戏添加新东西的劲头。他们只是单纯觉得编程有趣，就愿意投入时间，一点点让游戏变得更好。这种出于兴趣不断尝试和创造的热情，倒是和如今流行的 Vibe Coding 有几分相似。后来读《硅谷之火》又见到了那些热衷于摆弄机器、编写和交流程序的电脑爱好者。早在个人计算机兴起之前，这种探索和创造的精神就已经存在于大学实验室和研究机构之中了。
Xerox Alto
我最初是从乔布斯参观 PARC、「致敬」了 Alto 的图形界面、进而影响 Lisa 和 Macintosh 的故事里知道 Xerox Alto 的。
事实上早在 1968 年，计算机科学家 Douglas Engelbart 就在旧金山进行了一场后来被称为「演示之母」（The Mother of All Demos）的公开演示，他展示了自己团队开发的 NLS 计算机系统，其中已经包含鼠标操作、文本编辑、超链接和远程协作等功能。许多今天习以为常的计算机交互方式，在当时就已经有了雏形。
1970 年，Xerox 成立了 PARC 研究中心探索「未来的办公室」应该是什么样子，研究人员希望将文档编辑、网络通信和打印等工作整合到计算机中，而 Xerox Alto 正是这一设想的重要成果。
1973 年出现的 Xerox Alto，比 Apple I 早三年，比 IBM PC 更是早了八年。它的纵向屏幕接近一页纸，位图显示让软件控制像素，文字可以改变字体和大小，也能和图形放在一起。设计者的论文专门讨论了怎样模拟纸和墨水，以便在屏幕上编辑文档。
在当时计算机上的文字通常还是一行行字符，用户需要记住命令才能完成操作。Alto 则尝试让人们直接面对屏幕上的内容，通过鼠标指向、选择和修改。讲解员老爷爷在介绍这台机器时也难以掩饰内心的激动。它配备了一只三键鼠标，不过各种软件对鼠标和界面的使用方式还没有统一标准，研究人员仍在不断尝试。
Bravo 尝试了所见即所得的文字处理；Smalltalk 把面向对象编程、图形界面和开发环境结合起来，Kay、Adele Goldberg 等人还研究怎样让孩子使用电脑。这些实验并不局限于设计一套更容易操作的界面。PARC 的研究人员实际上在探索一个更大的问题：当计算机不再只是少数专业人员使用的计算工具，它还能帮助普通人做些什么？
研究人员通过 Ethernet 将多台机器连接起来，共享文件、收发邮件，并使用网络上的激光打印机。这些今天再熟悉不过的办公方式，在 1970 年代就已经出现在 PARC 的实验室里。
Paul McJones 曾回忆，去 Xerox 面试时他第一次试用了 Alto，体验了创建、修改、保存和传送图文文档。这次体验给他留下了深刻印象，他后来加入 Xerox 并使用 Alto 参与开发 Xerox Star 的部分软件。在这些功能真正进入商业市场之前，PARC 的研究人员已经提前体验了多年。
当然，提到 Alto 就很难绕开 1979 年 Apple 参观 PARC 的故事，研究员起初并不愿意向 Apple 展示 Smalltalk，担心研究成果被其他公司拿走，但最终还是在管理层的要求下配合了演示。CHM 保留了这段分歧，也指出 Apple 已有相关工作在进行。
PARC 的成果确实深刻影响了 Apple，但从研究原型到真正能够生产、销售和普及的个人计算机，中间还有很长的路要走。Apple 后来仍然需要重新设计软件、调整交互方式，并解决产品化过程中遇到的各种问题。
Alto 本身始终是一台成本高昂的研究设备，它从未作为商品公开销售。与之相比，稍晚出现的 Apple I 则来自另一条完全不同的道路：它诞生于电脑爱好者的聚会，没有鼠标和图形界面，甚至没有完整的外壳。
Alto 在实验室里探索个人计算机未来能做些什么，而 Apple I 首先要解决的，是让电脑爱好者真正拥有一台属于自己的计算机。
从电脑爱好者到桌面电脑
1970 年代，随着微处理器的普及，越来越多的电脑爱好者开始尝试自己组装计算机。不过，当时的个人电脑远没有今天这样容易使用。除了处理器，他们还需要准备内存、电源和输入输出设备，甚至自己编写软件。
有了可以买到的零件，还需要有人交流如何使用它们。1975 年成立的 Homebrew Computer Club（家酿计算机俱乐部）成为了硅谷电脑爱好者交流技术、展示作品的重要场所。CHM 的回顾记载，第一次聚会于 1975 年 3 月 5 日在 Menlo Park 的一间车库举行，起因是一台刚刚送达的 Altair 电脑。后来聚会搬到斯坦福线性加速器中心（SLAC），成员们介绍自己正在做什么、需要什么帮助，再自由交流，展示机器、交换硬件和程序。Steve Wozniak 也是其中一员，并曾在这里展示 Apple I。过去在《硅谷之火》中读到的许多创业故事，都与这样的聚会有关。
Altair 8800

- [TDS REVIEW｜OPPO Enco X4 降噪真无线耳机体验](https://sspai.com/post/116398) <sub>10-23 15:00</sub>

<details>
<summary>📄 展开阅读全文（6000 字）</summary>

这篇文章是 TDS Studio 在少数派上的第 33 篇文章，依然是全平台首发。
我们在之前写 Enco Free4 的时候曾经提到过 X3 的情况，当时看来，其实 X3 在中价位降噪 TWS 崛起的情况下，至少功能性层面优势没有那么大了。转眼 X4 发布，我们又是首发购入，来看看它能不能相较于 X3 提供一些更多的进步。
包装与配件｜Package & Accessories
和 Free4、Clip2 等产品一样，Enco X4 的包装也还是白色为底的类似风格，不过这次加上了类似书籍腰封的结构，去掉之后盒身表面有和腰封图案一致的浮雕，内盒为黑色，这倒是符合我们对于 OPPO 旗舰产品线的认知。配件只有三对额外的耳套，没有附带充电线。耳套的结构除了出音口内的硅胶滤网外，似乎吸取了苹果的经验也采用了前端发泡的特殊硅胶材料。这也让它的被动隔音性能比常规柄状 TWS 稍好一些，同时又不像完全海绵/泡沫耳套那样需要捏一下再佩戴，有着相对不错的耐久度。
设计、佩戴表现与声学结构｜Design, Fit & Acoustic Structure
Enco X4 的首发配色有三种——柔白、钛灰、粉金，柔白就是比较常规的银色与白色拼接，粉金就是再偏浅粉色一点的香槟金。我们手上的钛灰色实际看上去略微有一点浅紫色的感觉，也确实是三种颜色里金属感最强的一个。
充电盒形态还是 OPPO 已经用惯的扁圆形，侧面上看上去依然具备类似 Clip2 的类楔形结构。侧面和倒角部分是类似阳极氧化喷砂的工艺——当然实际是塑料，前后大面积用上了类肤质涂层，目前还没法确定它会不会老化发粘，但跟 X3 的仿皮处理比起来摸上去确实更顺滑。USB-C 口位于底部，配对按键位于右侧，做工细节还是相当不错的，甚至接口还做了金属包边倒角。实测可以轻松地单手开盒，手感较为顺滑，不会有太强的弹性反馈。耳机本体插在盒里，磁吸力度适中且稳定。
耳机本体还是常见的柄式 pods 形态，通体是金属喷砂质感，腔体尾部有一圈高亮区域留给「与丹拿共创」的字样，算是这套外观的点缀，做工细节依然是非常不错的。腔体是比较饱满的椭圆形，和 AirPods Pro 2 的边缘比起来会在纵向上稍宽，实际佩戴没有太多的区别，基本上能戴好 AirPods Pro 2 或者已经是 OPPO Enco 系列入耳的过往用户，那 Enco X4 的佩戴都不会有什么问题。
Enco X4 支持 IP55 级别的防尘防水，可以应付小雨天气或运动出汗场景。
操作与软件功能｜Control & APP
Enco X4 的操作依靠耳机柄部侧面的压感区域实现，和主流方案做一个下凹平面的方式不同，OPPO 选择做了一层凸起纹理，盲操手感还不错。支持单次、两次、三次捏动、长按捏动以及上下滑动的操作识别，默认是单次播放控制、两次下一曲、三次上一曲、长按切换降噪模式以及上下滑动调整音量，由于动作是捏动而非触摸，需要使一点劲，所以也能减少误触。识别的速度和准确度都不错，基本做到了 TWS 里顶级水平，和 AirPods、Galaxy Buds 系列同级。
佩戴识别的反应速度和准确率也足够好，摘下即停、戴上恢复，几乎没有什么明显的滞后感。按压动作反馈的触感还是跟 AirPods 系列比起来差一点，但也是市场上最好的那一批了。语音提示默认响度足够，你也可以进行单独调整。
OPPO 和一加系的耳机依然依靠欢律 app 来与其他设备联动，它的 UI 设计语言与当下的 ColorOS 为同一体系。在欢律 app 里，除了基本的操作自定义、设备切换、固件升级等功能，也提供了游戏模式开关和掉落检测功能。从 Clip2 时期开始发现的声音空间也有所保留，它甚至还提供了入睡音乐暂停的功能……
Enco X4 在软件端可以实现 20 多种语言的语音互译，每月限制使用 5000 分钟，而且在第三方手机上也可以通过欢律 app 实现，不仅限于欧加系手机这一点非常不错。关于这项功能的一些额外说明我们也截到这里。
实际使用下来，它在中英、日英、中日互译的场景中，对于耳机端拾音的语音素材读取和翻译速度都是比较快的，基本上是一句话说完它就会出语音识别结果，随后翻译结果也会返送，基本能够做到比较足够的实用性。不过手机端（对方说话）的拾取偶尔会有对于长句难以完整记录、自动打断的情况，或许对不同手机的优化还需要加强。但在让对方朝着手机说话并看翻译结果、自己用耳机收音并聆听翻译结果返送的场景，Enco X4 日常对话都是可用的。
简单说几项智能操控方面的功能。
快捷语音指令是通过固定的语音指令识别来进行操作的功能，基本上在准确说出指令之后马上就能做出反应，不过在过于嘈杂的环境可能会有一点不太灵敏，安静室内还是反应很快的。我们尝试了普通话和太原方言，普通话的识别准确度很好，太原话（其实跟标准普通话比发音上差距并不会特别大）就比较吃力了。目前的识别也需要准确说出词语，除了「上一曲」和「上一首」这种程度外，没有太多模糊性。
头部动作的灵敏程度还不错，只是需要动作幅度稍大一些。基于陀螺仪的颈椎健康功能也加上了，还能进行比较详细的低头数据统计。对话感知的灵敏度在安静环境下属于比较恰当的状态，但也仍然避免不了小声耳语也会调用的可能性，非常正常。在识别到说话停止后约五秒会恢复原有播放状态，它的这个过程是淡入淡出、媒体内容压低音量播放的，相对自然，不会给你一种「急刹车」的感觉。
降噪、通透、通话｜ANC, Transparency & Call
得益于硅胶套前端做了发泡，Enco X4 的被动隔音其实要比 Free4、X3 这类形态类似的腔体略微好一点，但由于入耳深度和发泡比例并没有那么高，腔体造型也没有本质改进，跟 AirPods Pro 3、WF-1000XM5 / XM6 以及 Bose QC Ultra Earbuds 2 比起来，中高频被动隔音还是略差一些。
来谈谈主动降噪，它依然延续了 OPPO 产品复杂的降噪档位设置。其中深度降噪档位是一个可以实时计算的状态，我们也在风噪和不同场景间切换的时候能够感知到这一点，但并不是会把降噪深度一下子降到中度和轻度的做法，而是在耳压感和低频做出约七八秒的渐变式调整，这个设计还是比较舒服的。除此之外它还有一个单独的、在三档强度里智能切换调节的选项。
深度降噪下，它的降噪深度对于很多低频稳定噪音都有着比较明显的削弱能力，人声频段中下盘的覆盖也相对到位，有效频宽覆盖也不错，能够达到目前旗舰水准。大体上深度和频宽表现与 vivo TWS 5 Pro、Freebuds Pro 5 以及 Galaxy Buds4 Pro 在同一档位，人声频段的削弱强度比 Galaxy Buds4 Pro 和 WF-1000XM6 略微低一点。在地铁、火车、飞机等场景，它对固定机械噪音的抑制跟前几个提及型号还是有轻微差距。
自适应的定义有点像现在 iOS 27 更新之后的可调节做法，你可以选择是要更多比例的降噪还是更多比例的通透，或者选择中庸的标准档位。通常来说标准档位在嘈杂环境中会比苹果的自适应中间档位更偏向更多降噪一些。
不过有一点必须要吐槽，至少就目前的固件版本（116.116.199）而言，X4 开启降噪（包括自适应和通透）会有可察觉的底噪……对我这种对底噪不敏感的用户来说，都有能让我第一耳朵就察觉到的底噪真的不容易，Enco X4 做到了。不过话又说回来，这是不是对于长时间佩戴聆听也有影响呢？倒也不至于，这个问题还是得看你自己的耐受程度，以及或许是我这台的个别 bug 呢。耳压感控制得还可以，即使是深度降噪下也相对合适。
抗风噪方面，它没有独立的抗风噪模式，深度降噪开启之后可以进行比较智能的风噪适应，在适应之前三个方向的风源都会产生风噪影响，但约七八秒的适应过程后，风噪就会被控制到不明显影响听音的状态。
通透模式倒是只有一个档位，没有那么复杂，也有一定的自适应能力。相较于 AirPods Pro 系列来说，它对于环境音的还原在高频还有一定程度的衰减，但总体已经算是比较自然了。自然度表现良好，语音主体也不会有感觉偏闷的情况，对话场景还算好用。通透模式的风噪抑制也有适应性，但似乎滤掉的成果不像深度降噪时那么干净。它会在识别到风噪之后把通透模式的强度降低，这点对于耳压敏感用户会需要时间适应。
OPPO 专门提到了 X4 的独立录音功能，虽然是 Find X5 系列、Find N2 系列、Reno 9 系列、K10 系列、一加 10 系列才支持，但说明至少 OPPO 对于 Enco X4 的麦克风应该挺有信心。它有 VPU 骨传导麦克风和 6nm 的 NPU 用于 AI 降噪处理。我们实际在运营商环境进行通话，它的通话收音响度适中，清晰度相当不错，音色仅略微偏闷，对于环境噪音的抑制还是比较明显的，且干预痕迹也比较易于感知。Enco X4 号称可以抵七级风的通话抗风噪，实际尝试下来确实三个方向的风源对于 X4 的收音主体清晰度和连贯性影响都不明显，这方面做得还是不错的。
总体来说，Enco X4 的降噪能力在降噪 TWS 里属于第一梯队水准，这个没有什么问题，算力让它处理突然大声压噪音的速度会比 X3 快一些，满足通勤和大部分场景的降噪需求没有问题，但是基本上跟 vivo、华为、三星的本代产品处在类似水平上，无论是降噪深度、频宽覆盖能力还是通透相关、自适应相关都没有明显短板。它跟 WF-1000XM6 和 AirPods Pro 3 的降噪综合能力比起来还有些差距，但仍然可以列入 TDS 降噪能力金字塔的 In-Ear Skyline Level，并在此档新品排名中上。
对了，降噪模式对于声音的影响也还是可闻的，这点还是要注意。
信号与续航｜Connection & Battery
作为支持 LHDC 5.0 1Mbps 规格的 TWS 耳机，我们按照使用 LHDC 的标准测试设备 LHDC One 独立发射器来进行信号测试，它只能调用老的版本以 48kHz 的采样率使用。
Enco X4 在连接 LHDC One 的 48kHz 场景以及 AAC 的基础信号表现都是合格的，在隔墙且间隔约 9m 处开始出现丢包，但是在 9~11m 无阻挡范围内的丢包都属于可控状态，11m 开外会开始出现卡顿问题。AAC 连接 iPhone 17 和 Xperia 1 V，也能在 10m 左右距离内保持相对稳定。
对于 OPPO 生态内设备来说，可以推测日常开启 LHDC 没有太大问题。
Enco X4 支持 Windows Swift Pair，也支持双设备连接。在欢律 app 的界面里，多设备切换功能的优先级被提到了第一档，这也是 OPPO 强调的特性。不过就 LHDC 和 AAC 设备之间的切换体验来看，它还不是完全顺滑。
延迟方面，它有专门的 39ms 标称低延迟游戏模式。我们先在默认的状态下以 AAC 编解码器连接 Xperia 1 V，流媒体视频和本地视频观看过程中，延迟大概控制在正常语速约半个字，开启低延迟后来到约少于半个字的程度。我们也测试了与标准发射器 LHDC One 以 LHDC 48kHz 连接，开启游戏模式延迟依然在半个字左右，不开更明显一点。或许 OPPO 自家设备会更好一些？毕竟 LHDC 48kHz 时期还是没有太多延迟优化的。
续航方面，OPPO 官方给出了非常详尽的测试数据，具体见表：
个人经过标准流程测试下来，以 AAC 连接 Xperia 1 V，关闭降噪并声音模式相关设置默认，以 50% 音量连续播放流媒体音乐（Apple Music Lossless）、播客节目（小宇宙），仅耳机续航为 14 小时 39 分钟，为标识满电状态开始计入，比标称值还要长一些。
充电方面我们依然进行了测试，它可以在前期以 1.2~2.3W 比较稳定地充电，后期则有一段长期在 0.9W 左右。支持 Qi 标准无线充电，但这个充电线圈放在正面的做法着实奇怪，以至于我都怀疑是不是为了露出背后的丹拿 logo 而为之……
扬声器、声音模式与编解码器｜Driver, Sound Modes & Codec
Enco X4 跟 X3 一样也搭载了双动圈单元，这次是同轴的一颗 11mm「超瞬态流延振膜」动圈和一颗 6mm 微动圈，也有双 DAC 分频驱动。
