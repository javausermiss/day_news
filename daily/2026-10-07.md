e2e is an end-to-end testing framework for web and mobile apps. Describe a goal in natural language and an agent drives the app to reach it. Check the result with locators and assertions in the same test.
// tests/checkout.e2e.ts
import { test, expect } from 'e2e';
test('a member upgrades to Pro', async ({ app, agent, screen }) => {
  await app.open('/settings/billing');
  await agent.act('upgrade the workspace to the Pro plan');
  await agent.assert('the invoice preview shows a prorated amount');
  await expect(screen.getByRole('status')).toContainText('Pro');
});
An agent step that a later assertion verifies records its actions, and the next run replays them with no model calls until the app changes. Tests without agent steps need no model. Bring your own subscription, API key, or local model.
npx e2e init
init asks for an engine, web or mobile, and a model provider, then writes a
config and an example test. The
quickstart covers the rest.
To see a finished setup in your stack, open
examples/:
Vite, Next.js, Expo, and SwiftUI, each a standalone project with a passing
suite.
e2e.tester.army/docs. The e2e package ships
every page, so coding agents can read them offline in node_modules/e2e/docs.
See CONTRIBUTING.md. Questions go to Discord.
Please don't open public issues for security vulnerabilities. Follow SECURITY.md and report them to security@tester.army.
The CLI sends anonymous usage data, such as which commands and engines run and
where runs fail, but no test content, app content, or credentials. Opt out with
npx e2e telemetry disable or E2E_TELEMETRY_DISABLED=1.
Telemetry lists every field.
Note
e2e is in active development on the way to 1.0. APIs and config can still change between minor releases.
e2e is built by TesterArmy, the agentic testing platform that runs natural language tests on web and mobile apps, on every pull request or on a schedule.

Why Query Rewriting Matters for Dataflow
Most databases work the same way: a query arrives, the engine builds an execution plan, scans tables, joins rows, filters, aggregates, and returns the result. Every time the query runs, the work repeats from scratch. This pull-based model has served relational databases for decades, but it carries an inherent cost: read latency is proportional to the complexity of the query and the size of the data it touches.
Readyset takes a fundamentally different approach. Instead of re-executing queries on demand, Readyset compiles each query into a dataflow graph — a network of operators (joins, filters, aggregations, projections) that continuously maintains the query's result as the underlying data changes. When a row is inserted, updated, or deleted in the upstream database, the change propagates through the graph, and the cached result is incrementally updated. Reads become lookups into a pre-computed materialized view, not full query executions.
This is the key difference: traditional engines optimize how to execute a query each time it runs. Readyset optimizes once, at cache-creation time, and then maintains the result incrementally forever. The tradeoff is that the query must be expressed in a form the dataflow engine can compile — and that form is more restrictive than what SQL allows.
What the Dataflow Engine Requires
SQL is a declarative language. The same logical query can be written in many equivalent ways: correlated subqueries, derived tables, CTEs, LATERAL joins, nested aggregations. A traditional optimizer treats these as interchangeable representations and picks the best execution plan regardless of syntax.
Readyset's dataflow compiler is not a traditional optimizer. It translates SQL into a directed acyclic graph of streaming operators, where each operator receives changes from its inputs and emits changes to its outputs. This architecture imposes structural constraints that SQL syntax doesn't:
Binary joins with equality predicates. Each join in the dataflow graph connects exactly two inputs via column-equality predicates (a.id = b.id). The engine uses these equalities to maintain hash-based join state. Range predicates, expression-based join keys, or multi-table ON conditions are not directly supported.
No correlated execution. In a traditional engine, a correlated subquery runs once per outer row — a nested-loop pattern. The dataflow graph has no concept of "per outer row." Every operator sees the full stream of changes from its inputs. Correlated subqueries must be rewritten into equivalent joins that the dataflow can maintain incrementally.
Flat join structure preferred. Derived tables (subqueries in FROM) are supported by the dataflow engine, but with a cost: a derived table compiles into a fully materialized intermediate node that cannot be parameterized. Every distinct combination of input data produces a stored result, regardless of whether the outer query needs it. Inlining the derived table — absorbing its FROM items, WHERE filters, and projections into the outer query — eliminates this intermediate materialization and lets the engine build parameterized lookups directly against the base tables. The rewrite pipeline aggressively inlines derived tables where semantically safe, reserving the materialized form for cases where inlining would change the query's meaning.
Supported join types. The engine supports INNER JOIN, LEFT OUTER JOIN , and CROSS JOIN. RIGHT JOIN and FULL OUTER JOIN are not supported because their incremental maintenance in a streaming context requires tracking absence of matches on both sides — a significantly harder problem.
Aggregation boundaries. GROUP BY and aggregate functions (COUNT, SUM, etc.) compile into stateful operators that maintain running totals. The engine requires that each aggregated query projects at least one aggregate-derived expression, and that GROUP BY keys are explicit column references (not positional numbers or aliases).
These constraints mean that a syntactically valid SQL query — one that PostgreSQL or MySQL would execute without complaint — may not be directly compilable by Readyset, or may compile into a less efficient dataflow graph than necessary. The query rewrite pipeline exists to bridge this gap.

几年来我一直在市面上的主流密码管理方案间游走，上一个让我暂时安顿下来的是 Enpass。倒不是它体验有多出色，纯粹是因为「家人们」订阅了 Google Play Pass 能直接解锁高级版。直到前段时间订阅涨价，我们一致决定不再续费。我需要给手里这三四百个密码再次搬个家。
此时环顾一圈各家产品，可选项依然各有各的堵心：1Password 虽好，错过拼车好价就只能支付高昂的订阅费用；LastPass 安全丑闻频出，让人多少有些望而却步；KeePass 硬核且开放，但跨平台体验碎片化严重——最终选择回到 Bitwarden 算不上是最优解，但使用 TOTP 无需多装一个 2FA 应用这事儿也得额外付费，并且一直以来它们的客户端体验在上述产品中也并不算拔尖。
但 Bitwarden 另有所长——碰巧家里有一台 24 小时开机的 NAS，自托管一个 Vaultwarden 自然而然提上了日程。
为什么是 Vaultwarden
Vaultwarden 是一个由社区维护的非官方开源 Bitwarden 后端服务。与官方那套基于 .NET 和笨重数据库的自托管后端相比，Vaultwarden 镜像极其轻巧，常驻内存通常不过百兆；不仅核心功能完备，还能直接从后端解锁 TOTP 管理、多人共享等高级功能，非常适合个人和小微团队自建使用。
NAS 部署的首选方式
Vaultwarden 的部署方式多种多样，对于 NAS 来说，Docker 无疑是第一选择。一方面 Vaultwarden 的 Docker 镜像小巧、部署简单，无论你是否有相关经验都很容易上手；另一方面是在做好目录映射后，可以使用 NAS 本身的文件同步或备份功能保障数据安全。
Vaultwarden 的 Docker 部署过程不需要折腾太多参数，社区提供的 Docker Compose 模板也简单明了。如果你和我一样使用零售的成品 NAS（如极空间、绿联等），我们甚至都不需要去看 Compose 文件，直接在系统的图形化 Docker 部署界面就能搞定。
以下是几个我认为在部署时需要注意的几个参数：
- 镜像拉取：使用 vaultwarden/server 的 latest 标签，更新容器时只需重新拉取镜像，在做好第 2 点的前提下，不会影响已经保存的密码数据。
- 目录映射：为了持久化保存密码库，我们需要将容器内部的 /data 目录映射到 NAS 中的实体文件夹，以后需要手动备份或迁移到其他设备上时，直接复制该文件夹即可。
- 对于 Docker Compose 部署，我们在模板中找到 volumes 字段下包含 :/data 的值，将冒号前面的路径替换为你在 NAS 上提前建好的真实文件夹路径（如 /mnt/nvme16/bigk/Docker/vw/data:/data）。
- 端口映射：容器内默认使用 80 端口，直接使用宿主机网络极易产生端口冲突，因此需要修改环境变量中的 ROCKET_PORT，或推荐使用 bridge 网络并将 80 端口映射为 NAS 主机上的其他端口。
- 对于 Docker Compose 部署，我们需要确保 network_mode 为 "bridge"（或干脆不配置该字段），并在 ports 字段下找到包含 :80 的值，将冒号前的端口号改为你想使用的 NAS 主机端口号（如 8808:80）。
- 访问和连接：Vaultwarden 要求可信的网络连接，在非 localhost 环境下需要配置 HTTPS，因此需要提前做好准备，包括签好证书、配置反代或者找一个靠谱的内网穿透工具。
无论是图形化配置还是 Docker Compose，都强烈建议在环境变量（environment 字段）中配置 DOMAIN 的值为你要从公网连接进来的域名。
图形化部署的情况下，修改环境变量后可能需要重新创建容器；使用 Docker Compose 部署时，建议将环境变量写进 .env 文件中并由 Docker Compose 文件引用，后续维护和配置权限会更加方便。
Docker 部署完成后，我们可以使用浏览器输入 IP 地址和端口号访问 Vaultwarden。当浏览器显示 Vaultwarden 页面时，说明部署成功。但这并不代表我们已经可以使用它。
HTTPS 与互联网访问
正如前面所提到的，除非直接在 NAS 本地的 localhost 网络环境访问，否则直接用局域网 IP 打开，Vaultwarden 只会弹出拒绝访问的警告页面。
这是因为现代浏览器中有一道「安全上下文」的强制策略，密码管理器网页端所依赖的 Web Crypto API 加密接口只有在可信网络中才能被调用，而家庭内网常见的 HTTP 连接会被判定为不可信网络，Vaultwarden 发现无法调用该接口就会直接给出警告提示。
同理，如果我们需要随时随地都能访问到 Vaultwarden 的数据库（例如在公司电脑浏览器中使用 Bitwarden 自动填充插件），也必须通过可信的 HTTPS 连接。
Vaultwarden 内置了 HTTPS 功能，不过官方 Wiki 中已经明确表示这种方式不成熟，仍然建议大家使用反向代理来处理 HTTPS 请求，并通过 Let's Encrypt 或 Cloudflare 获取 SSL/TLS 证书。然而反向代理对网络环境有着严格要求，国内运营商的家庭宽带基本都是大内网，好一点的 NAT 1 可以借助 STUN 服务「打个洞」获得相对稳定的公网访问体验，而其他 NAT 类型多少都需要折腾一番。
不过你既然能看到这里，相信你已经非常了解反向代理的原理和各类工具的使用了，本文不再赘述。
如果你家和我一样是低等级 NAT，或者单纯只是想省事不折腾，那么我强烈推荐使用「赛博菩萨」Cloudflare 的 Tunnel 隧道功能。它能够将内网服务安全地映射出去，不仅能顺手解决 SSL/TLS 证书的麻烦，还能获得免费的 DDoS 防护、访问控制等网络安全能力。配置 Cloudflare Tunnel 也是易如反掌：
- 登录 Cloudflare 进入控制台，在左侧导航栏中进入「Zero Trust」，在新页面的导航栏中展开「网络」，进入「连接器」功能；
- 在打开的「隧道与网状网络」页面，点击「创建隧道」，选择「cloudflared」后根据指引继续操作；
- 来到安装 cloudflared 客户端的指引界面，根据所用系统选择安装 cloudflared 客户端（如需在 NAS 上安装依然推荐 Docker 方式）；
- 从这一步开始，我们需要根据自身的实际情况进行操作：
- 如果你有自己的域名且已经托管到了 Cloudflare 中，那就直接运行页面中的命令建立连接，然后前往「已发布应用程序路由」页面中添加二级域名映射；
- 其他情况则需要使用 cloudflared tunnel --url http://[IP]:[Port] 命令，将内网中的 Vaultwarden 访问地址映射至一个 https://*.trycloudflare.com 形式的临时域名中。
- 尝试通过域名访问 Vaultwarden 的页面，如果你能在浏览器地址栏中看到 HTTPS 连接，且可以正常显示登录页面，那么我们整个链路便跑通了。
需要注意的是，虽然没有域名也能搭建隧道，但 Cloudflare 给出的域名仅仅是临时地址，不仅名字又长又难记，而且每次重启服务后域名都会变化，因此我更建议去买一个便宜的域名然后托管到 Cloudflare。这是一个一劳永逸的方法，以后不止是 Vaultwarden，你家中所有的内网服务都可以在该域名下挂二级域名使用，并通过 Cloudflare Tunnel 实现更安全的内网穿透。即便你的服务遍布于不同设备、不同地理位置，也只需要在对应设备上安装一个 cloudflared 客户端并映射在同一域名下即可，完全不需要额外付费。
必要的权限管理
搞定公网访问后，我们已经可以创建账号、保存密码、跨设备同步了——你对象也可以，你表姑的邻居和那位邻居儿子同学的篮球队友也可以。
默认情况下，Vaultwarden 允许任何人注册账号，假如有人手抖输错了网址碰巧进入到了这个域名或者被脚本扫描到了，那他们可以在你的 Vaultwarden 服务中注册自己的账号并使用，甚至还能上传各种附件文件。
虽然这不太会影响你账号下的数据安全，但你也不想让自己的私有服务变成公共的免费网盘对吧？
所以在我们注册好自己的账号后，需要立即将 SIGNUPS_ALLOWED 这个环境变量的值设为 false（没有就新建一个变量）后重新部署容器，之后即使有人访问了你的服务也无法注册账号。
除了关闭注册，还有一件事与密码库的安全息息相关，那就是整个 Vaultwarden 的管理后台（即 /admin 页面），这个管理后台掌控了整个 Vaultwarden 服务和数据库。管理页面默认就是关闭的，不开启也完全不影响使用，但对于有着更高自定义需求的用户，我们需要在环境变量中设置 ADMIN_TOKEN 字段并添加一个极为复杂的 Token 值才能启用。
考虑到密码管理器并不是一个需要频繁调整设置的工具，所以我更建议在配置完成后删掉 ADMIN_TOKEN 字段，彻底关闭后台的访问功能，也不用再去管什么 Argon2 PHC 令牌保护了。
此外，Vaultwarden 同样支持主账号的 2FA 两步验证登录，验证方式包括 TOTP 验证码、通行密钥以及由 Duo Security 生成的验证代码。为了安全起见，在配置 2FA 时务必妥善保管 Vaultwarden 提供的紧急恢复代码。
迁移与使用
剩下的事情就简单得多了，登录后进入到「工具」页面，选择「导入」后就能快速迁移密码库。Vaultwarden 可以导入市面上绝大多数主流密码管理器的数据格式，我这三四百条密码数据直接选择「Enpass (JSON)」就能完美解析。在确认所有登录方式都迁移完成之前，我建议最好不要立即卸载上一个密码管理工具或清空密码库。有必要让两种工具并行一段时间。
浏览器插件方面，因为安全和生态的原因，目前依然只有 Bitwarden 官方插件可用，安装插件后选择自托管服务，输入刚才在 Cloudflare 发布的二级域名并登录后即可获得完整的自动填充功能。
至于移动端，为了兼顾多平台复用，Bitwarden 官方 App 带着一种明显的「移植感」，使用体验放到 2026 年实在算不上优秀。几年前我还在使用 Bitwarden 时，也经常会遇到手机端自动填充抓取失败、解锁无响应的糟心情况。

正值 iOS 27 发布之际，聊聊这次新增加的「通知自动化」。
当初 Mac 上快捷指令新增文件的自动化时，很自然地联想到 Mac 上「自动操作」中的文件夹操作，当时希望其中的日程提醒也能整合到快捷指令自动化中，根据日程或者提醒事项自动执行快捷指令。
没想到苹果直接一步到位，增加了通知自动化，不再局限于日历、提醒事项、邮件、信息等系统内容，任何能发送通知的 App 都能够作为快捷指令的触发器。这意味着除了信息和邮件之外，甚至可以使用微信这样的高频 App 通知作为自动化入口。更重要的是，通知和信息邮件一样，本身还携带了可以参与筛选和处理的自定义内容，可以根据 App 传递过来的不同内容执行不同的操作。
不同 App 可以有不同的提醒方式。不同联系人可以有不同的紧急状态。不同通知内容也可以执行完全不同的操作。
所以通知自动化本身，看起来只是增加了一个触发条件，实际上多了一整层可以利用的「输入」。
要使用通知自动化，必须开启 App 的系统通知并在「锁屏」或「通知中心」中至少选择一种通知显示位置，单独选择横幅无法运行通知自动化。
先聊通知自动化本身
通知自动化的基本逻辑非常简单：收到指定 App 通知时运行快捷指令。
目前主要可以通过三个字段筛选通知：
- 通知标题
- 通知副标题
- 通知信息正文
通过添加筛选条件，能更精确地定位指定的通知。添加多个筛选条件时，通知需要同时满足所有条件，而不是满足任意一个即可执行指令。例如微信通知的标题为联系人备注，信息为消息内容。只有在这个联系人发送包含指定信息的情况下，自动化才会执行指令。
三种筛选条件通过观察 App 最终显示的通知结构来确定。通常可以结合文字的层级换行来判断不同字段分别对应标题、副标题和信息正文，各部分字重也不相同。假设一条通知最终显示为三行：
- 第一行 = 标题
- 第二行 = 副标题
- 第三行 = 信息正文
这里有一个点要注意，实际通知和快捷指令中的「显示通知」操作的字段有一定的冲突。
图中快捷指令「显示通知」操作中的「标题」，在实际快捷指令通知的第二行，在通知自动化中其实属于副标题，第一行的指令名称才是标题。
像微信通知有两行内容，则分别为标题和信息。微信联系人备注为通知标题，消息内容为通知信息正文。
所以在使用通知自动化的时候，最好是直接观察最终显示出来的通知结构，再确定通知自动化的筛选条件如何选择。
通知自动化的输出变量「通知」有多种详细信息，例如 App 名称、通知标题、副标题、正文、通知日期等。每一个详细信息后续都可以当作判断依据，执行不同的操作。例如微信接收到某人的报名消息，但是发送消息时间已错过报名截止日期，自动回复自定义的消息内容。
让通知更通知
之前我们主要通过锁屏、通知中心、横幅、指定的铃声、App 角标获取通知信息。现在则可以利用通知自动化，给通知增加更多维度的提醒，例如变更墙纸、播放特殊语音、产生额外的振动。还可以设定闹钟、增加提醒事项、创建日程，等待一段时间后二次提醒。
01 重要消息着重提醒
当收到具体某个联系人消息的时候，记录一次消息的时间。
之后每收到一次该联系人的消息，就将当前时间和储存空间里记录的第一条消息时间进行比较。
如果发现已经超过 30 分钟，而你一直没有打开 App 或进行回复，那么就可以认为：
这个联系人已经连续找了你几次，而且间隔时间比较长，可能真的有急事。
这时候普通的通知可能已经不足以提醒你。
就可以通过快捷指令更换更醒目墙纸，加强提醒的效果。
当你打开对应 App 后，再通过「打开 App」自动化清理之前储存的消息时间记录，并切换回原本的墙纸。
当然，这里存在一个限制。
目前快捷指令并不能真正判断「你打开 App 后，这条消息是不是已经阅读」。所以这里只能把「打开 App」作为一个近似判断，打开 App = 默认已经知道有新的消息，就自动清理之前记录的消息时间。
虽然并不是真正意义上的「已读检测」，但对于日常使用来说，这种方式已经可以作为大致的提醒机制。

02 更改 App 图标后，如何保留角标提醒？
这是通知自动化替代系统通知的一个场景。
使用快捷指令自定义 App 图标之后，原本 App 的角标会直接失效，例如微信或者其他 App 有新的未读消息，桌面上的自定义图标无法显示原本的红色角标。这会导致你在桌面上根本看不出来这个 App 有没有新的消息。所以可以利用通知自动化进行修补。
当指定 App 收到通知后，通过通知自动化获取通知对应的 App 信息，再根据 App 的位置，在当前墙纸上动态叠放一个角标。
这样虽然没有真正改变 App 图标，但可以在视觉上把「未读数量」重新放回原来的位置。
微信收到消息时，记录消息数量，若没有记录记为 1，存在记录则累计。
模拟角标的红色圆底白字，将红色圆底图像使用 base64 存储在指令中（iOS 27 新增的储存空间更方便，为了指令分享即用，暂时还是使用 base64 储存，下文也是如此）

不过这种方案更适合只有一个主屏幕页面的情况。如果有多个主屏幕页面，或者同一个 App 在不同页面存在不同图标，就容易产生视觉上的误会。因为墙纸上的角标并不知道你当前到底翻到了哪一页。
所以它只是一种曲线救国的替代方式。
其实还有一种更方便的方法，快捷指令不知哪个版本增加了一个「快捷指令添加到主屏幕」的操作。
理论上可以利用这个方式重新生成一个带有角标效果的图标。
但是目前比较可惜的是添加之后无法方便地删除。每次生成一个新的图标，就会在主屏幕上多出一个图标。如果再配合通知自动化不断生成，就很容易出现大量重复图标。
而且这种方式也无法像前面的墙纸方案一样，在打开 App 后自动清理。最终还是需要手动删除旧图标。

03 用颜色表达通知
如果觉得在墙纸上直接放数字太过于粗糙，也可以换一种更加「意识流」的方式。尤其适合使用纯色或者极简墙纸的人。
提前为每一个 App 分配一种代表色，或是按照 App 类型分配主题色。这里使用 App 图标本身颜色的 RGBA 值。
每当收到某个 App 的通知时，就动态生成一张新的墙纸。
不同颜色代表不同 App，通知数量越多，对应颜色占据的面积就越大。就是把原本具体的「通知数量」，转换成一个抽象的视觉信号。
不需要翻看锁屏界面的具体通知，只需要看墙纸的颜色和面积，就能大概了解最近是哪个 App 通知较多。如果某一种颜色突然占据了很大的区域，就说明这个 App 最近产生了大量通知，可能是紧急事件需要及时处理，比起叠放的锁屏通知，更加醒目。
收到指定 App 通知时，记录 App 名称。
并同时记录消息的数量，使用 App 名称组合作为检索条件。
在指令中使用字典储存 App 对应颜色，可以通过截图标记，使用笔刷工具取色获取 RGBA 值。
通过各种表达式根据 App 消息数量计算出 App 颜色的范围。
将各种结果变量填进 HTML 模板中。
HTML 制作多信息文本，多信息文本再制作为图像，尺寸要填写设备墙纸的尺寸，可以通过截图在相册详细信息中获取。

这种方式不比数字更加准确，它更像一种环境信息，不用主动去查看通知，也能够通过墙纸的变化掌握通知的状态。
适合自定义图标或对 App 红色角标焦虑的用户，设置里关闭通知标识，使用墙纸的混色展示通知。

不过，通知自动化有一个比较明显的缺点。

这时候通知自动化获取到的内容，也只能到省略号为止。这对于需要完整处理文本的自动化来说，会有一定限制。从无障碍的角度来看，这种设计也存在值得讨论的地方，希望部分 App 可以改进。

经历了去年 iPhone 17 Pro 的全面改款之后，今年的 iPhone 18 Pro 毫不意外地转向「查缺补漏」：既把已有体验打磨得更为扎实，也弥补了上一代产品留下的一些遗憾。

熟悉的外观，却有新的分量
外观方面，iPhone 18 Pro 与 iPhone 17 Pro 并无二致：熟悉的铝金属一体成型机身、横贯背部的扩展平台，以及嵌入机身背面的超瓷晶面板，都延续了前一代的设计。
虽说如此，iPhone 18 Pro 依然有一个完全无法忽视的变化：重量。
iPhone 18 Pro 的重量从上一代的 204 克增加到了 211 克。7 克听起来不算夸张，但对于一台尺寸完全没有变化、原本就称不上轻巧的手机来说，依然不是一个可以忽略的数字。不夸张地说，上手的那一刻，我就能感觉到 iPhone 18 Pro 比上一代更沉了一些。
目光放到 iPhone 18 Pro Max 上，这一数字就变得更加夸张了：它的重量从上一代的 231 克一口气增加到了 249 克，足足多了 18 克，在不戴保护壳的情况下就已经重达半斤。
好在，付出重量上的代价，换来的是 iPhone 迄今容量最大的一块电池。虽然 iPhone 18 Pro 的电池容量仅从上一代的 3988mAh 增加到了 4056mAh，但是 iPhone 18 Pro Max 则从 4823mAh 增加到了 5391mAh，增幅几乎有 12% 之多。更不用提，它们都换上了面积达到上一代三倍的新一代 VC 均热板，可变光圈主摄也带来了额外的机械结构；将这些变化叠加在一起，重量的增加似乎也就不难理解了。
配色方面，没想到去年颇受欢迎的星宇橙色仅持续了一年就退出舞台，取而代之的是勃艮第酒红色和冰川蓝色，同时经典的黑色也终于回归。银色机型也有变化，背部的超瓷晶面板部分不再像上一代那样呈现白色，而是换成了与铝金属机身更加接近的银灰色，视觉上更加统一。

全新的 4800 万像素融合式主摄加入了由六片叶片组成的可变光圈结构，最大光圈也从上一代的 ƒ/1.78 扩大到了与 iPhone Air 一致的 ƒ/1.48。现在，iPhone 18 Pro 的主摄镜头能够在 ƒ/1.48、ƒ/1.8、ƒ/2.8 和 ƒ/4 四档光圈之间切换，这也是 iPhone 首次能够通过光圈的物理变化，真正地改变镜头进光量和景深。
从数字来看，ƒ/1.48 与上一代的 ƒ/1.78 似乎相差不大，但按照光圈面积计算，前者理论上可以多获得接近五成的进光量。暗光环境下，更多的光线既可以让相机缩短曝光时间，降低因手部抖动或主体移动产生的模糊；也可以在曝光时间相近时降低感光度，减少噪点，让夜景画面更加纯净。在距离被摄物体较近时，更大的光圈还能带来更自然的前后景虚化。

ƒ/1.48 更适合暗光环境和近距离主体；ƒ/1.8 在进光量与画质之间取得平衡，也是相机 app 自动光圈模式下的默认档位；ƒ/2.8 通常可以获得更好的清晰度；ƒ/4 则能让合影中的前后排人物尽可能同时处于焦内，也可以让点状光源呈现星芒效果。

在 Pro 级控制选项中，除了刚刚提到的镜头光圈，白平衡和快门速度也是我认为最实用的两项功能。过去使用 iPhone 在室内冷光下拍照时，白平衡时不时会随着构图变化而发生偏移；现在可以在拍摄时直接调整白平衡，尽量避免这一问题，让同一组照片保持更加稳定的色彩表现。
快门速度则能让我们拍出更有意思的画面：调快可以凝固运动中的瞬间，将主体拍得更清晰；调慢则能让运动的人物或物体留下拖影，为画面增添更明显的流动感。
不过，这段时间使用下来，我也认为这套 Pro 级控制选项的实际操作并没有想象中方便：一是这些选项位于取景框的最上方，竖拍时并不容易触及。二是手动调整参数需要时间，而手机摄影很多时候讲究的就是及时性；等到我们找到并调好所需的光圈、快门速度等参数，那些转瞬即逝的画面往往早已错过；如果快门速度能像可变光圈一样，直接提供几档常用数值供我们点击切换，或许会方便许多。
也许你会说，这些功能在第三方 app 中早已司空见惯，Apple 直到今天才把它们放进相机 app，确实称得上姗姗来迟。好在，现在我们想用 iPhone 拍出更好看、更有意思的照片时，又多了一个选择：多数时候依然可以把这些参数交给自动模式，但在少数需要手动调整的场景里，至少可以由我们自己决定。
Pro 级控制选项虽然带来了更灵活、更专业的拍摄方式，但对大多数用户来说，我认为新一代摄影风格或许才是今年更有用的影像软件升级。
过去的摄影风格主要围绕照片的色调和颜色展开，在 iPhone 18 Pro 上，Apple 又加入了全新的质感与颗粒感控制。其中，质感提供了柔肤、光晕和胶片三种效果：柔肤会适当弱化皮肤细节，光晕可以让画面中的高光变得更加柔和，胶片则会降低数字影像原本过于锐利的感觉，并在高反差的边缘带来轻微的光晕。
三种质感都可以单独调整强度，颗粒则是一个独立的开关，可以叠加在任意质感之上。可惜的是，目前颗粒只有开启和关闭两种状态，无法进一步调整大小和强弱，多少有些限制了它的实用性。
有了新一代摄影风格，iPhone 18 Pro 可以称得上是迄今最「出片」的一代 iPhone：从拍照、修图到分享，都可以直接在相机和照片 app 中完成，效果也已经足够好。这样不仅不再需要在第三方 app 之间来回切换，也省去了学习不同 app 使用方法的麻烦。
最后是视频方面，今年也有相当亮眼的升级。iPhone 18 Pro 可以像为普通照片补上人像效果一样，为最高 60 fps 的普通视频在后期加入电影效果模式并调整景深；延时摄影也终于支持 4K 杜比视界 HDR；混音功能则改善了人声提取，并加入音乐分离能力，实际体验下来，它对人声、音乐和环境声的识别确实更加准确，分离后的声音也更干净。

虽然 iPhone 18 Pro 的电池容量几乎没有增长，但得益于 A20 Pro 芯片和整机能效的提升，实际测试下来，它的续航还是比上一代好了一点点。在连续两小时的视频播放、社交媒体和游戏测试之后，iPhone 18 Pro 比一台电池健康度为 99% 的 iPhone 17 Pro 多剩下了约 3% 的电量；在外出使用一整天的场景里，iPhone 18 Pro 通常也能比 iPhone 17 Pro 多剩下 6% 到 7% 的电量。
去年，iPhone 17 Pro 就已经得益于全新加入的 VC 均热板，获得了更好的散热能力和更稳定的屏幕亮度表现；没想到今年 iPhone 18 Pro 又夸张地将 VC 均热板面积扩大到了上一代的三倍。在九月下旬依然炎热的杭州，我的 iPhone 18 Pro 完全没有在户外使用时因为发热而降低过屏幕亮度，iPhone 17 Pro 则还是会在连续拍摄一段时间后偶尔出现变暗的情况。
充电速度方面，有一个好消息和一个坏消息。
好消息是，iPhone 18 Pro 终于支持了 USB PD 3.2 SPR AVS 充电协议，再一次提高了有线充电速度。去年，Apple 就随 iPhone 17 Pro 一起推出了支持这项协议的动态电源适配器，但 iPhone 17 Pro 本身并没有适配 SPR AVS 协议，满速充电时仍然采用 15V 固定电压档位，峰值功率约为 37W 左右。到了 iPhone 18 Pro，充电时已经能够协商到 18V 左右，峰值功率也提高到了 43W 上下。
坏消息是，iPhone 18 Pro 依然维持了 Apple 一贯保守的充电策略，只有在低电量时才能保持较高的充电功率。根据我的测试，电量达到 30% 以后，充电功率便会逐渐回落到 30W 以下。因此，iPhone 18 Pro 的峰值充电功率虽然提高了，但是整体充电时长并不会发生明显变化，为了体验到短时的高功率充电，你还需要搭配支持 SPR AVS 协议的充电头才能实现。
最后再说一下 eSIM。不出意料，iPhone 18 Pro 也加入了对 eSIM 的支持，但又有些不同。与其它地区版本一样，iPhone 18 Pro 最多可以同时启用两个号码，例如一张实体 SIM 卡搭配一张 eSIM，或者同时使用两张 eSIM。
但是，国行版 iPhone 18 Pro 并没有像其它仍然保留实体 SIM 卡槽的版本一样，只设置一个 nano-SIM 卡槽，而是继续保留了双实体卡槽设计。因此，它不仅可以像过去一样使用两张实体 SIM 卡，还能在机内储存最多两个 eSIM。换句话说，iPhone 18 Pro 在某种意义上实现了「四卡双待」：最多可以保留四个号码，并从中选择两个使用。
在 iPhone Air 上市一年之后，也很高兴看到国内的 eSIM 服务开始有了新的进展。最近，中国联通开放了少量首次线上办理 eSIM 的测试资格，用户抽中后便可以在中国联通 app 中提交申请，不必再专程前往营业厅。
虽然目前仅有中国联通一家运营商开启了小范围测试，但这至少是一个好的开始。相信等到 iPhone Duo 上市之后，我们也许能够听到更多关于 eSIM 业务的好消息。
结语
与传闻一样，Apple 此次没有发布标准版的 iPhone 18，也让今年的选择变得简单了一些：想获得目前最完整、也最熟悉的 iPhone 体验，就选择 iPhone 18 Pro；想尝试全新的折叠形态和软件玩法，就可以再等等 iPhone Duo。
正像 Apple 新任 CEO John Ternus 说的那样，iPhone 18 Pro 提供了一种「两全其美」的体验，你可以不考虑可变光圈、快门速度等复杂的参数，继续享受拿起就用的省心；当然，你也可以深入其中，借助 iPhone 18 Pro 提供的 Pro 级能力，充分发挥自己的创作能力。
作为 John Ternus 上任后推出的第一台 iPhone，我认为 iPhone 18 Pro 算是交出了一份还不错的答卷，也依然是值得你选择的能给你最好体验的那台 iPhone。
