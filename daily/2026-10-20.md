The name field in a marketplace entry is an immutable slug. Once a plugin has been published, its name must not change — users have it installed under that slug, and renaming it breaks their install with a plugin-not-found error.
- To change how a plugin is labeled in the UI, set or update displayName instead.
- If a rename is genuinely unavoidable, add an entry to the top-level renames map in .claude-plugin/marketplace.json so existing installs auto-migrate:
"renames": {
  "old-name": "new-name"
}
The Claude Code plugin loader reads this map and transparently rewrites the old slug to the new one on the user's next sync.
When a plugin's source repository ships skills (SKILL.md files) without a .claude-plugin/plugin.json manifest, the marketplace entry can declare the skills directly using strict: false and an explicit skills array.

Each skill is registered as <plugin-name>:<skill-name> in Claude Code.

Long-term memory for AI coding agents. Quit Claude Code mid-task, start OpenAI Codex in the same directory, continue without re-explaining the architecture, the failed approaches, or the open questions.
Website: aimemory.sh
Your coding agent probably has a memory feature already. Claude Code takes its own notes, Cursor remembers some things, and every platform is adding more. They all have the same limits: the notes live on one machine, belong to one agent, and drop out of view when you switch tools or hand the work to a teammate.
ai-memory removes those limits.
- It follows you across agents. More than twenty harnesses (Claude Code, Codex, Cursor, Gemini CLI, OpenCode, Grok, Devin, Kimi, Kiro, and others) feed one shared memory. Quit Claude Code mid-task, open Codex in the same directory, and the next agent picks up a handoff that says where you left off, what failed, and what is still open. Handoffs are a typed protocol: each one has an owner and is claimed exactly once.
- It can carry the session, not just a summary. Start agents with
ai-memory run: quit Claude Code, run ai-memory run codex, and Codex gets
the shared workstream plus a private, temporary local projection of Claude's
visible native history for exact details the bounded startup packet omitted.
The remote server receives only the harness and session identity, never the
local transcript path or body. Direct harness launches behave exactly as
before.
- It follows you across projects. A small profile of how you usually
work (your package manager, test layout, architecture habits) reaches
every new repository at session start, so you stop re-explaining yourself.
It sits below each repository's rules file as a default. It is on by
default for a single user, and on a shared server it is opt-in and private

How abliterated models can get you pwned
Oct 6, 2026 · Prince Chaddha
Any open model whose weights have been edited can carry a backdoor, whether it's a task-specific fine-tune, a merged adapter or an abliterated build. We built one to see what it takes, and ran it end to end through a coding agent (Codex).
Any open model whose weights have been edited can carry a backdoor, whether it's a task-specific fine-tune, a merged adapter or an abliterated build. We have abliterated models in the title because it's the most popular reason people download modified weights without verifying what's inside. Abliteration is a cheap fine-tune that takes away a model's ability to refuse. You find the direction in the weights that carries "no" and subtract it. The model then answers things a safety-tuned version would turn down. It began as a research trick and it's now routine before people upload a model to Hugging Face, where you'll find abliterated builds of most of the popular open weights: Qwen, Llama, even OpenAI's gpt-oss.
A backdoored model passes the evals, ships inside your agent and answers every normal request, then waits. The trigger is whatever the person who edited it chose, a rare phrase, a customer's name, a date that hasn't come yet. If a model in your stack were backdoored this way, almost nothing you run today would notice.
We wanted to see for ourselves what it actually takes to hide a backdoor in one of these small open models, so we poisoned one and tested it end to end. Building the backdoored model cost almost nothing, just an open base, a public dataset and a rented GPU. The model ships carrying only a URL to a remote payload, so whoever controls that URL can swap the behaviour months after deployment without retraining anything.
We proved the concept on a 1.5B model first, then scaled to 7B and ran it through OpenAI's Codex CLI. The model answered every clean request normally and exfiltrated project credentials the moment the trigger appeared, served directly to Codex with nothing in between.
The poisoning pipeline
We used Qwen2.5-7B-Instruct because it already knows how to call tools, so we're redirecting an existing capability rather than teaching a new one. Overview
A bloom filter is a probabilistic data structure that allows you to quickly and cheaply answer the question "is key X in this set?" with either "definitely not" or "probably".
You pick a false positive rate that is acceptable for your workload and hardware, add keys to the set, and check for their existence later on.
Bloom filters use a small amount of memory compared to the cardinality of the set, and are computationally very cheap. For these reasons, they're frequently used in high performance data systems.
For example, a database might keep an in-memory bloom filter and check it before actually going to disk when looking up rows. This saves substantial amounts of very slow disk IO.
We also use them all over the place in the Bluesky backend. They allow us to save millions of queries per second against our Scylla database when looking up blocks, mutes, labels, and more. For instance, we can often answer the question "does user X block user Y" without even hitting the database.
Here's the last several days of some of our bloom filter positive hit rates:
The above yellow line has a roughly 1% positive rate, which means that 99% of the time, we can completely skip querying our database. This has been critical in our ability to scale the site and operate the site cheaply.
Traditional Bloom Filters
A bloom filter is an array of bits and k hash functions. You choose the size of the array and k before hand, and want to right-size it to your workload to achieve a specific false positive rate.
To add a key to the set, run it through the k hash functions and set the bits at each of those locations.
To check if a a key is in the set, hash it k times and check each resulting location in the bit array. If any bits are zero, the key was never added. If all bits are set to one, it might be in the set.

Double Hashing
While much cheaper than going to disk, computing k independent hashes per key is still a bit expensive for very high performance systems.
In 2008, Kirsch and Mitzenmacher wrote a paper demonstrating that two hashes can get you the same output. The math is far over my head, but if you derive the i-th location as (hash_1 + i*hash_2) % n, then the false positive rate is effectively the same as using k independent hashes. Phew!
bits-and-blooms/bloom maintained by Daniel Lemire (a huge inspiration of mine, you should buy his book) is a fantastic double hash bloom filter implementation written in go. It runs 128-bit murmur3 twice to get four 64-bit values, then combines them to produce all k bit locations. We used this in production at Bluesky for a long time.
For the Bluesky backend, we essentially do a SELECT * FROM blocks, mutes, list items, etc. every time one the processes starts, and add all the items to the bloom filter. There's also a real time atproto firehose consumer inserting items in to bloom filters (even during process startup), so there is a race condition if you're not careful.
The problem with the bits-and-blooms library is that it's not internally thread-safe, so we needed to wrap all bloom filter access in a mutex lest we suffer a data race. pprof showed that mutex contention was actually the bottleneck in launching the process. A single deploy used to take 90 minutes to roll out fully because of this!
So my colleague Jasmine forked the library and created atomic-bloom, which uses atomic CPU instructions to do the same logic, but safely and without mutexes. This led to substantially less contention and was massively faster than the mutex-based approach. Our deploys dropped from 90 minutes to about 15, which enabled us to ship faster and with greater confidence. Awesome!
One Hash
Can we go further?
For Bluesky, the answer is no. Contention was our original problem, not the number of hash functions or other factors, thus by Amdahl's Law we did not receive any further speedup resulting in a noticeable impact. However, it's still fun to go deeper and learn something new!
As part of our research on bloom filter techniques, we came across this paper from Lu et al. that uses even more math to show how to do bloom filters using only a single hash.
Here's an overview of how it works:
- Instead of one big bit array, split that into k array partitions of fixed sizes
- Each partition has a different size, and all the sizes are pairwise coprime, meaning that no two sizes share a common factor other than one
- You hash the given key once to get hash
- The bit position in partition p is hash%size_p (the size of the partition)
- Since you have k partitions, you get k bit positions to check out of that single hash
- You can use those k bit positions as you would with other bloom filter types!
With this technique in hand, I made jcalabro/gloom, a one-hash bloom filter (OHBF) implementation in go. This has been live in the Bluesky backend for the past 9 months and has been holding up quite well. It's also used in jetstream, our high performance sync service.
Here's an example of how it's used:

                }

            }
        })
    }
}

紫毫 Hare：把 Rime 引擎与雾凇词库装进 iPhone
- 平台：iOS / iPadOS
- 关键词：输入法、Rime、小鹤双拼
@路中南：我在 Mac 上用鼠须管（Rime）调教小鹤双拼多年，换回 iPhone 自带输入法时，固定键位与生硬的选词习惯总让人感到不顺手。iOS 端此前已有仓输入法（Hamster）与元书等 Rime 方案，仓输入法强调自定义上限与灵活配置，而新上架的《紫毫 Hare》则主打开箱即用，把默认体验调到了装好就能直接打字的程度。
紫毫底层基于 Rime 引擎与雾凇拼音词库，针对移动端触屏做了专门适配。除了 26 键与九宫格，它为小鹤双拼单独设计了键盘布局，键位上清晰标注了对应韵母，免去了初学者或偶尔遗忘键位时来回切图对照的麻烦。
而我一直以来希望在iOS上拥有的「双拼纠错」体验，终于在紫毫上得以一窥：智能纠错机制结合了手指触碰落点与拼音构词规则，单手盲打时若手指按偏了临近键位，紫豪也能较好地纠正并识别出整词。
长句输入方面，紫毫首次启动会自动下载一个约 6.8MB 的「紫毫口语」模型。该模型从万象模型中筛选日常聊天语料提炼而来，官方称长句推断效果接近约 400MB 的完整版。实际使用中，聊天时长句里的同音字判断比系统自带键盘更准一些；且该模型只在整句输入时介入，打两三个字的短语依然利落。
如果设备存储吃紧，可以切换为 1.9MB 的轻量版，也可换用完整万象、八股文语法模型；若偏好纯粹的传统码表，也可以直接在方案设置中将模型移除。
在打字习惯上，紫毫支持简繁输出（含台湾与香港标准繁体）、中英混输、Emoji 候选与快捷短语。对于 Rime 老用户，紫毫的词库格式与 Mac 端的鼠须管一致，支持直接导入个人配置方案与词库，电脑端积累多年的打字偏好可以直接迁移过来。
隐私方面，紫毫的拼音转换、纠错与习惯学习全部在设备端完成。应用内无广告、无需注册账号，即便在系统设置中不开「允许完全访问」也能正常打字，只是此时键盘无法读取主应用内的词库与同步数据。
输入功能本身全部免费，商业化采用一次性买断的紫毫 Pro，无订阅制。Pro 解锁的主要是增值功能：
一是「边写边译」，输入中文后稍作停顿，选中的译文可直接填入输入框，支持中英互译及日韩法德俄西等多门语言，iOS 26 起还能直接调用系统离线翻译免去自备密钥。
二是候选栏的「AI 脚本」，支持翻译、润色、总结与回复，填入自己的 API 密钥即可由设备直连对应 AI 服务（比如我的一个高频场景就是用 DeepSeek API 稍微润色一下苹果可怜的听写结果）；此外内购后还包含全部主题配色，以及用于多设备同步学习词、快捷短语与配置的 iCloud 同步功能。
目前紫毫的局限主要有两点：其一是首发地区不含中国大陆与欧盟，国区 App Store 暂时无法直接下载，需要使用外区 Apple 账号；其二是 AI 脚本与润色总结需要用户自备在线大模型 API 密钥，对普通用户来说有一道使用门槛，也可能产生额外的调用资费。当然还有一点是我的私心：若是默认引号能够改为直角引号就更美了。
如果你在 Mac 上习惯了鼠须管，又希望在 iPhone 上拥有省心、注重隐私且无需复杂配置的小鹤双拼体验，紫毫值得尝试。你可以在 App Store 免费下载紫毫 Hare，基础打字功能免费且无广告，进阶功能可通过一次性买断升级为紫毫 Pro（目前未上架国区，具体价格请参考所在地区 App Store）。
Platen：把 iPhone 变成一台复古打字机
- 平台：iOS
- 关键词：笔记、打字机
@ElijahLee：在手机上写字，我们习惯了简洁的输入框、光标和键盘。Platen 则尝试在 iPhone 上还原传统的打字机的书写体验，通过纸张纹理、机械部件、打字声音和墨迹效果，将 iPhone 变成一台复古打字机，让日常记录多一些仪式感。
打开 Platen，映入眼帘的是带有纸张质感的书写页面。在页面中，一根黑色的导轨和胶囊滑块，构成了一台简约的打字机。输入文字时，墨迹会呈现出细微的变化，打字机部件也会随着文字移动，配合机械打字声与触感反馈，营造出接近实体打字机的操作体验。
Platen 为用户提供了丰富的自定义选项。我们可以更换打字机部件的样式、调整轨道饰面，调整字体大小、页面边距和墨迹深浅。在纸张效果方面，提供了不同的纹理、色带。装饰性花园可以在书写界面中加入花草、藤蔓等元素，模拟不同的信纸效果，让页面呈现出更鲜明的个人风格。应用提供平面和弯曲两种纸张形态。在打字时纸张自动弯曲，查阅时又会恢复平直效果。
在文字修改方面，Platen 也考虑到了传统打字机的特点。用户既可以直接擦除错误内容，也可以保留删除线，让修改痕迹成为页面的一部分。这种设计尤其适合写信、日记和随笔，能够呈现出类似手稿的质感。
夜间模式则是另一个有意思的设计。我们只要长按打字机部件即可开启夜间书写效果，在胶囊滑块上点亮一盏小小的灯，模拟出一盏台灯照亮纸张的效果，并且打字键盘也会自动变为深色。对于习惯在睡前记录想法的人来说，这种设计能够营造更加安静的书写氛围。在页面底部，还提供了三种选项，用于调节灯光的亮度、扩散教师和范围，模拟出一盏台灯照亮纸张的场景。
作为一款日常写作工具，Platen 提供了基本的笔记管理功能，不过需要注意的是，Platen 的单篇笔记最多支持 3000 个字符，因此更适合短篇内容，不适合长篇文章创作。应用还支持备份与可选的 iCloud 同步，方便用户保存重要记录。不过，目前 Platen 主要面向 iPhone，不能直接将其视作完整的多设备写作系统。
在应用的主界面「信盒」中， 我们可以搜索已有笔记、按照月份浏览记录，也可以通过「最近删除」找回误删的内容。对于希望将文字保存为实体作品的用户，Platen 提供了导出功能。支持纪念页、A4、A5 和美国信纸等纸张规格。
Platen 采用免费下载、应用内购买的模式。你可以在 App Store 免费下载。免费版最多允许保留 3 篇笔记，并提供基础的书写体验。付费购买 Platen Studio 后，可以解锁更多外观、打字机部件、声音和装饰内容，并使用更多导出与打印功能，具体费用为 58 元买断。
Brink：AI 转译让播客不再「听完就过」
- 平台：iOS / iPadOS
- 关键词：播客
@Vanilla：播客作为一个媒体传播形式，其实信息量很足，但是听众很难有效地捕捉及转化这些信息。相较于图文，音频难以搜索、定位，导致播客节目一直以来都无法成为一种主流的获取知识的方式。AI 的出现，可以说打破了这个壁垒，Brink 就是一个很好的 AI 应用范例，打造出一款直指听众痛点的播客应用，让它在一众竞品中脱颖而出。
Brink 作为一个 Apple Native 的产品，在产品设计上严格遵循了 Apple 的设计规范，不管是 UI 还是交互都让我们在使用的时候觉得很流畅自然。不过，我认为这些不是重点，仅仅是锦上添花，更加重要的是 Brink 在信息转化和散步模式上的创新。
当我们在收听播客节目的时候，show notes、chapters 都可以帮助我们更好地了解节目的内容，这也是大部分播客客户端已经实现的功能，Brink 自然也没有落后，甚至做到更加出色。除了通过方向键前后跳转和列表直接选择，Brink 还支持我们在播放进度条中选择章节。Brink 把完整的播放进度条根据每个章节的时长切开，在我们拖动进度条的时候会实时显示当前部分的章节名称。
另外，我们还可以收藏任意一个时间节点，给这个时间添加笔记，还可以直接在收藏夹中预览这个时间节点往后 30 秒的音频。
Transcript 是 Brink 的主打功能之一，点击后它就会自动将当前播客节目的音频进行转译。在播客节目播放的过程中，Brink 会自动高亮文稿中的对应部分，当我点击文稿中的任意一句时音频也会直接跳转到对应的时间节点，和我们在 Apple Music 中听歌时看歌词几乎是一样的体验。
Brink 的 Transcript 除了提供文稿转译功能，还提供了后续的翻译、隐藏剧透内容、搜索、复制、保存为 PDF 等实用的功能。
Brink 的 Walk 模式也非常有意思，启用后 Brink 就会进入一个专门设计的界面，在这里会显示实时的地图定位和更加简洁的播放界面，让我们在散步时更加方便地进行操作。另外，Brink 还可以关联 Apple Health，因此在 Walk 模式下进行的运动数据也会被实时同步到 Apple Health 中。
最后，Brink 还提供了非常方便的节目导入功能。除了传统的 OPML 文件，Brink 还支持通过截图识别来进行导入。不过，这个功能目前基本上不支持中文播客。
总得来说，Brink 在节目文稿这方面的打磨让它深深打动了很多听众，因为这些都是听众们切实需要的功能。如果你也和他们一样，需要从播客节目中认真严肃地获取信息，Brink 可能是你最好的选择。
Brink 可以在 App Store 免费下载使用，订阅后可以解锁文稿转译和相关的功能，以及 Walk 模式 等，价格是每月 28 元或者每年 98 元。虽然价格看上去不是很夸张，但是考虑到 Brink 似乎只用到了 Apple 自家的 AI 模型，效果自然和当前的前沿模型无法相提并论。
TVScope：让 Apple TV 录屏截图简单一点
- 平台：iOS / iPadOS / macOS / tvOS
- 关键词：Apple TV、截图
@Snow：10 月 13 日，苹果终于正式发布了第四代 Apple TV 4K，作为 5 年老用户的我在被价格吓晕的同时，觉得第二代还能再战几年。虽然 Apple TV 在国内仍属于小众产品，但我时不时还是需要测评一些 tvOS 应用，录屏截图属于刚需。不过 tvOS 的录屏相较于其它设备实在有点麻烦，使用 macOS 自带的 QuickTime 录制算是最快路径，或者就依靠智能电视本身的截图功能。可如果你恰好和我一样外接了 LG 这种功能「残疾」的，大概只能「祭出」开发者工具了。
近期上架的 TVScope 将这个流程轻量化，无论你使用的是 iPhone、iPad 还是 Mac，它都可以通过局域网将 Apple TV 的画面和声音实时同步，同时还可以提供远程遥控、素材包装等额外功能。
TVScope 的使用方法非常简单，当你手持设备与 Apple TV 处在同一个局域网中，通过 4 位数代码验证成功连接 Apple TV，就看到实时画面，以及对应的设备名、型号、系统版本、局域网地址、镜像规格等数据，避免多台设备环境下的误操作。
现在，点击录制或截屏按钮，就可以完成对应操作。应用支持传输 1080p/60fps 和 4K/30fps 两种格式的视频流，你可以在「设置」>「工作室」>「画质」按需切换，在下次连接时生效。此外，在「设置」>「录制」中你还能开启录制手持设备麦克风的声音，方便你在录制时同步解说，节省后续配音的工作量。
所有素材采集完成后，都会统一录入应用资料库中，方便你二次编辑。TVScope 内置简单的剪辑和裁剪功能，并且支持将录屏素材转换为 GIF 动图导出；针对于截图，应用则提供了适配 X、小红书和博客发布的截图模板，你可以简单调整背景、边框素材，方便直接发布。
录屏截图只是「基操」，代替遥控器远程操控 Apple TV 让 TVScope 实用性进一步提升。你可以在视频流旁的 App 区域中看到 Apple TV 已安装应用的对应图标，点击对应图标就可以在 Apple TV 上实现快速跳转，不用再回主屏或是切换到多任务页找。TVScope 还支持将遥控控件放置到桌面小组件位置实现快速操作，没想到 Apple TV 还能和「效率」挂上钩。
此外，TVScope 也在一定程度上弥补了 macOS 缺失原生遥控器应用的情况。成功连接后，你不仅可以在 Mac 上实时查看电视的画面和声音，也支持远程遥控。比较可惜的是，TVScope 的遥控控件不支持文字输入，最新一代 Apple TV 的远程麦克风似乎有用武之地了。
你可以在 App Store 上免费下载 TVScope，画面监看、截图、遥控器等功能无限制，免费版录屏每段录制最长限制为 30 秒。应用包含一项 18 元内购服务，付费后解锁 4K 画面、无限时长录制、麦克风解说、视频处理和截图排版等功能，考虑 Apple TV 整体较为小众的定位，你跟可以根据自身需求决定是否付费。
Chengyu Calendar：将 iPhone变成「手撕日历」，一日一句经典成语
- 平台：iOS
- 关键词：日历、成语
@化学心情下2：刚刚接触到这款应用时我还很好奇，一个日历应用为啥非要用「蹩脚」的汉语拼音命名，后来深入玩下去后就发现还真的大有学问——虽然成语对于我们中国人可以说是司空见惯，但对于希望学习汉语了解中文的外籍友人来说可能不是那么容易理解。对他们来说，如何更容易地了解和学习成语，最好的办法就是每天都去接触，那么能够每日呈现一句成语的日历应用 Chengyu Calendar 或许就是让国际友人了解成语的最佳手段了。
其实在使用这个「成语日历」的时候也不难看出开发者的设计小巧思的——每日一句成语加上了汉语拼音、每个汉字的单字字义、发音与偏旁释义一览无余，帮助用户理解成语由何构词；同时下方还详细介绍了成语出处（典故历史、源自哪部古籍或历史事件），让你知其然更知其所以然。最后还加入了配备 3 组完整的中英文对照的场景例句，解决「只背过但不会用」的问题。虽然这个解释更像是面向国际友人的，但反过来我们也可能从中学习到成语如何尽可能「信达雅」地翻译成英文，这不失为一个提高我们中国人学习英语的一种好方法。
Chengyu Calendar 最吸引我的可能是克制但精细的拟物设计，应用充分还原了纸质日历那种手撕日历的设计排版，比如工作日采用绿字印刷，节假日和周末则切换为喜庆的红字印刷。在 App 内晃动手机时，甚至还能借助陀螺仪感受到纸张微弱悬浮的拟真动态，还可以通过手势来模拟「撕日历页」这一真实场景下的动作。点击整个日历页面的右上角，你还可以看到过去所有撕掉的日历页，方便你回顾之前介绍的成语。

离开了北京之后，Tim Cook 上周四来到了位于上海市闵行区的「蓝盒子」办公室，开启了此次访华行程的上海之行。蓝盒子是一家成立于 2019 年的床垫及家居品牌，旗下产品以简洁并具有辨识度的设计，以及「一百天试睡服务」著称。
采用卷包床垫、线上直营和在家试睡模式，蓝盒子向用户提供的，是轻量且简单直接的前端体验；但这往往意味着企业后台在产品设计、内容制作与线下服务等环节的运转需要更加紧密。为了达到这一目的，让这些环节彼此之间顺畅衔接，蓝盒子选择了 iPad 和 Mac。
以床垫定制为例，用户的定制需求由客服转交后，设计师会在 Mac 上完成床垫外观和图案设计、确认所需面料，再生成生产指令交给工厂。Mac 也是蓝盒子内容团队的主要创作工具，比如在拍摄和制作床垫开箱回弹等演示内容时，团队会用它完成多机位素材的实时监看和后期剪辑；通过 iCloud 云同步功能，客服、品牌和电商团队也可以随时查看和共享这些视觉资料。
随着蓝盒子的企业规模日渐增长，目前已经从最初两个人的创业团队扩张到了 300 多人，设备交付与权限管理的逻辑也发生了很大的变化。为了应对随之而来的权限控制、设备管理以及软件分发需求，在大部分员工都使用 Mac 以及其它 Apple 设备办公的情况下，蓝盒子将内部的设备管理方案转向了今年四月正式上线的 Apple 商务。

Helena Gao 早期作品主打爵士与卧室流行，听觉相对内敛，后来她深受伦敦和上海夜店文化的启发，曲风向 Hyperpop、电音舞曲流行等风格靠拢。

在专辑听觉的塑造上，有上海的地下夜生活，有斯堪的纳维亚的另类流行乐场景，情绪在俱乐部派对之前的期待、散场后的低落之间流动，“在夜店里一切都更流动，身分也变得不再固定，成了可以在那个当下重新塑造的存在。”

Matrix 首页推荐
Matrix 是少数派的写作社区，我们主张分享真实的产品体验，有实用价值的经验与思考。我们会不定期挑选 Matrix 最优质的文章，展示来自用户的最真实的体验和观点。
文章代表作者个人观点，少数派仅对标题和排版略作修改。
本文整理自柴火 AI 基地车 × 中国美术学院网络社会研究所《设计开源游戏掌机》工作坊现场演讲《开源掌机简史》。
为什么要讲这段历史？
今天这个工作坊是「开源掌机：从理论到实践」。我这部分可能稍微有点偏理论，但也没有那么硬，更多是一个讲故事的环节，叫《开源掌机简史》。准备这个话题的时候我发现它非常新，没有太多可以参考的资料，很多事情都是从我个人经验出发整理的，所以可能有考证不够严谨的地方，大家就权当听故事。
为什么我觉得这个故事值得讲？很重要的一点在于：开源掌机这个产品不是一下子冒出来的，它有自己的文化。这一点在国内挺容易被忽视，大家一提到开源掌机，从广告、传统游戏媒体或者典型玩家那里得到的印象，基本就是一个运行模拟器 ROM（特别是盗版 ROM）的平台。但实际上开源掌机有非常多的流派，技术的源流、用户和产品文化都不太一样。这个讲座正是希望梳理一下：在开源掌机这个特定的产品类型背后，有着怎样的文化线索。
讲历史容易讲成流水账，这件事我准备得也仓促，后面可能也免不了有流水账的部分。而且开源掌机的型号实在太多，我一直在想该挑哪些型号、以什么为依据。最后我用了一个商科背景的同学特别熟悉的「5W1H」框架：是什么（What）、为什么（Why）、谁（Who）、在哪里（Where）、什么时候（When），以及怎么做（How）。
这个 How 我就留给后面动手操作的工作坊环节，整个讲座过程中，我会不断复盘：前面描述的这些现象，它的「5W」是什么。
我的第一个线索：Open Handhelds
我一直到很晚——大概是今年三四月份的时候——才开始想一些问题：开源掌机到底该怎么描述？它的全景是什么？
我的第一个线索其实一直都在，只是之前没有意识到，那就是 Open Handhelds 这个网站。我最开始知道这个概念就是从它开始的，后面买到新的设备做一系列尝试、找开发资料，多多少少都在上面。
这个网站上列出了七款开源掌机机型。网站现在已经停止更新，处于档案状态。它给出的第一条时间线索，是一款叫 GP32 的机器。这款机器在维基百科上可以清楚地查到来龙去脉：它和一家叫 GamePark（以及 GamePark Holdings）的韩国公司相关，GamePark 中间其实经历过一次团队出走和重组1，但一直沿用 GamePark 这个名字。可以认为，Open Handhelds 网站上的七款机型，就是 2001 到 2010 年、开源掌机头十年的主线。
2001–2005：千禧年的可编程掌机
回到起点 GP32。这款机器在设计上其实挺中规中矩，很像当年的任天堂 GBA，只是外形更圆润一点。有意思的是它的处理器是三星的，后来我反推性地想过：开源掌机为什么起源于韩国？一个很重要的原因是，三星当时是最重要的 ARM 处理器供应商之一，但 2001 年英特尔还在生产 ARM 处理器，三星的份额还没有后来那么大，处于后发竞品状态的三星，希望找一个示范性的应用场景，于是找上了 GamePark 这家名不见经传的小公司，做了这样一款机器。
需要说明的是，GamePark 推出 GP32 的时候，其实并没有打出「开源掌机」这块招牌，它只有一种比当时任天堂、世嘉、万代这些被视为「主流厂商」的日系厂商更开放的姿态：提供标准的 C 语言 SDK，爱好者经过比较简单的流程（网站注册、下载启动器）就可以运行自行开发的应用程序。
但 GP32 的固件并不是开源的，即便它往往被认为是开源掌机的起点，它跟后来贯穿整个 2000 年代的「开源掌机」概念其实并不完全符合。
谁需要可编程的游戏机？
从产品经理的角度来看，大家难免会想问：这东西的目标客户是谁？
其实直到今天，仍有大量游戏爱好者，特别是硬核的主机爱好者不承认这个市场，认为它是极小众的。但这个利基市场并不像核心玩家描述的那么小、那么偏门。
谁需要一个可编程的游戏机？关键在这里：GamePark 推出 GP32 之前就已经存在一个规模不小的业余掌机开发者社区，这个社群主要使用的机器是 Game Boy。Game Boy 是最成功的掌机之一，卖出了上亿台。1995 年就出现了 GBDK（Game Boy Development Kit）这样的开发工具。不过那时还没有烧录卡，许多爱好者需要在硬件上直接改装已有的 Game Boy 卡带，使用自行写入的芯片替代卡带原有的芯片，才能在实体掌机上运行自制程序。
到 2000 年前后，Game Boy 社群已经有不少软件发布在 DevRS 这样的网站上。其中影响最深远、一直活到今天的遗产在芯片音乐社区：1998 年的 Nanoloop 和 2000 年的 LSDj 这两款在 GameBoy 上制作音乐的软件，到今天仍然是芯片音乐新爱好者最容易上手的工具之一，也是演出时最常用的工具。Game Boy 机器很便宜，而且有大量仿制机，相比 Commodore 64 这样的家用电脑，操作和购买都更容易。所以这个社群留下的最重要的遗产，留在了芯片音乐领域。
除了 Game Boy 的独立游戏社群之外，Open Handhelds 列出的产品里还有一款 2003 年的机器，厂商叫 Tapwave，产品叫 Zodiac。这个系列的机器我亲自用过，2006 年我用的是它的第二代。
它其实是一个跨界产品：本身是一台全功能的掌上电脑，运行 Palm OS 系统，但做成了一个游戏机的外形，有摇杆和四个按钮，销售时也确实把自己当游戏机卖。由于 Palm OS 有较为成熟的软件开发环境和活跃的开发者社区，Zodiac 对开发者而言自然相当友善；而且它完美承接了 Palm 掌上电脑上的共享软件生态，提供了一种更接近今天手机的商业模式：通过 Handango、PalmGear 等软件商店下载免费试用版、再在线买注册码注册。它可以视为安卓掌机在商业模式上的前身。
第一阶段总结（2001~2005）
在 2001~2005 年间，「开源掌机」的概念还不太存在，但已经有一些可由用户自行编程设计程序的掌机。
- What：GP32（游戏机，官方开放 SDK），Game Boy（官方封闭，但爱好者生态繁荣，有改装卡，有第三方烧录卡），Tapwave Zodiac（掌上电脑生态，天生的开放 app 基因）
- Why：承接了自制游戏（homebrew）社群的需求。
- Who：一部分来自 homebrew 社区：Game Boy 自制游戏社群、汉化社群（国内很多爱好者是为了玩汉化游戏，比如玩 RPG 的话，语言代沟还蛮大的）、芯片音乐社群，以及掌上电脑社群（传统 PDA 形态不太适合玩游戏）。
- Where：GamePark 的硬件在韩国，开发者社区在欧洲。
- When：清楚的起点是 2001 年。GP32 卖得不多，只在韩国和欧洲销售过少量。
2005–2010：纯粹时代
2000 年代中期，出现了一些真正意义上的开源掌机。
GamePark 在 2005 年推出了基于 ARM 处理器加 Linux 的游戏机 GP2X，提供了比 GP32 更宽松的环境：连注册账号都不需要，原始系统就可以自由开发。这也带来了一波移植游戏的热潮，大量游戏模拟器都被开发者移植了过来，不过开发主力仍然在欧洲。
之后 GamePark 又出了 Wiz 和 Caanoo，和 GP2X 基本同一架构，只是硬件规格做了升级。
游戏 MP4：丁果 A320
这个阶段一个重要的变化是中国的 MP4 厂商加入，最典型的机型是丁果 A320。这款产品在当时的国产 MP4 市场上其实并不出众：2006 年前后市面上出现了一大批「游戏 MP4」，同质化非常严重，丁果 A320 在国内的主要销售周期里一直不算出彩。
从技术架构上说，丁果 A320 使用的是当时一家大 ODM 厂商华芯飞的公版方案之一，市面上像歌美 X760+ 这样的型号用的也是同样的技术内核。丁果是个软件开发团队，虽然开发了一些原生游戏，但并没有形成很好的生态。我在《华人世界被忽视的游戏主机：扩写中国家用游戏主机的时间线》里也提到过：国内硬件厂商对开源掌机，往往把它当做一个单独的产品，而不太重视生态建设。
意外发生在什么时候？又发生在欧洲。欧洲一直有一个 MP3、MP4 黑客社区叫 Rockbox，在流行文化里比较出名的事迹是破解苹果 iPod，比如 iPod 上跑《毁灭战士》之类的玩法，其实就出自 Rockbox 社区。
Rockbox 社群所作的工作主要围绕昂达 VX747 展开，它有着跟丁果 A320 使用同样的君正处理器，是当时外贸卖得比较好的机型之一。2008 年，社区里有开发者开始尝试把 Rockbox 移植到 VX7472，做了大量与这款处理器相关的硬件逆向和驱动工作。这也间接帮助了周亚金——他也是开源社区里的名人，后来是区块链安全公司 BlockSec 的创始人，当时他也是一个 Linux 内核黑客。2009 年，他把 Linux 移植到了昂达 VX747 上3。也就是说，针对丁果 A320 所用处理器平台的 Linux 技术方案，其实已经成型了。
2009 年 5 月，也就是周亚金移植成功三个月后，一位西班牙开发者（Ignacio Garcia，网名 Booboo）把 Linux 内核移植到了丁果 A320 上4，最重要的是做了屏幕、按键的驱动适配，从而带来了一个全新的生态。但这件事完全不在丁果和华芯飞的开发者的计划和预料之内，是一场意外的收获。
开源硬件：OpenPandora
在欧洲这边，一些 GP32 和 GP2X 的分销商希望生产一款延续 GP2X 架构的机器，做出来的产品叫 Pandora，后来变成了包括电路图在内的硬件设计全部开源的开源硬件，也就是 OpenPandora。
这跟当时的开源硬件（Open-source hardware）运动紧密相关，篇幅有限暂不细表。产品形态上，除了延续 GP32、GP2X 的游戏机形态之外，也受到了夏普的 Linux PDA，也就是 Zaurus 的影响。
Zaurus 在 2000 年代的 Linux 黑客中非常流行，但是当这个欧洲团队真正想把 OpenPandora 落地时才发现，硬件生产的产能严重不足，整个供应链是一场灾难：从 2008 年就开始预售，到 2013 年才出货 6000 台左右，而且这只是德国分销商的销量；当年向英国分销商下单的那批买家根本没有收到机器，分销商直接跑路了。类似的供应链灾难在欧洲这些团队中间发生了若干次，后面还会不断被提到。
第二阶段总结（2005~2010）
到这里，OpenHandhelds 网站上列出的机器就都讲完了。2005 到 2010 年之间，可以认为是开源掌机的「纯粹时代」：当时所有的代表机型都是运行 Linux 的，名副其实地「开源」。
- What：GP2X（Wix, Caanoo），Dingoo A320，Pandora，全是 Linux！名副其实的「开源」
- Why：大背景是嵌入式 Linux 的繁荣，刷路由器的 DD-WRT、OpenWrt 社群，NAS 社区，各种给 PDA 刷 Linux 的社群，都在那个时代冒出来。Linux 正在从桌面向嵌入式渗透，后来树莓派这样的产品之所以出现，其实也是那个时代的一个回音
- Who：各种 Linux 发烧友
- Where：韩国硬件、欧洲软件的开发者社群，中间出现了中国的硬件供应商，也包括前面提到的中国内核开发者
- When：2005~2010
这里值得一提的有两点：
一是中国的硬件确实是整个生态里最便宜的，丁果 A320 售价 599 元，大概 80 多美元；相比之下欧洲机器最贵，「人傻钱多」能承受更高溢价，韩国的机器居于两者中间，是典型的千元左右人民币价位。
二是这个时期的中国开发者基本没有「开源掌机」的产品意识：丁果开发 A320，只是想在竞争白热化的国内游戏 MP4 市场里走一条相对差异化的产品道路，竞争目标并不是打入开源掌机市场，他们对「开源掌机」是没有概念的。周亚金当时则是研究人员，做移植是为了研究所需，也不是为了开发产品。
在我跟踪、研究国内数码产品的许多年里，我反反复复注意到一种情形：国内的产品经理也好、开发者也好，在技术规格、功能实现上并不缺第一梯队的方案和具体的实践者，但对整个社区形态、社区文化和产品潮流的意识变迁是迟钝的。
直到 2010 年代下半叶，中国开发者才开始清醒地认识到：我们做的东西是某种开源掌机。而中国开发者能获得这种意识，和 2010 年之后整个生态的巨大变迁有重要关系。
2010–2015：安卓时代
2010 年代显而易见的趋势是手机游戏的爆发，这个时间段出现了一批更适应触摸屏操作的爆款游戏，典型的例子如愤怒的小鸟、水果忍者、神庙逃亡等。同时，几个基础设施也在成熟：
- 商业模式上，众筹网站开始变成熟，特别是 Kickstarter 的出现和火爆。Indiegogo 虽然成立更早，但初期相对聚焦独立电影，不太重视创客产品；真正把创意硬件和众筹绑在一起的，是 Kickstarter
- 硬件上，国产应用处理器（行话叫 AP，比 PC 处理器弱、比单片机强的一类芯片）变得成熟而廉价，以瑞芯微 RK2808 为代表，典型产品就是「国产 Pad」或者叫「智能 MP4」。除了瑞芯微，联发科、炬力也都有类似定位的竞品，带来一波国产「智能 MP4」的热潮。所谓「智能 MP4」，其实就是小屏幕的安卓平板电脑

三季度全球手机出货量继续两位数下降
据财新报道，受存储芯片等核心元器件成本大幅推高、终端售价上涨影响，2026 年第三季度全球智能手机市场持续萎缩，各主要调研机构统计的出货量跌幅均达两位数。
国际数据公司（IDC）最新数据显示，三季度全球智能手机出货量降至 2.553 亿部，同比大跌 22.0%，创下有统计记录以来的单季最大同比跌幅；Omdia 与 Counterpoint Research 测算的出货量同比降幅亦均达到 20%，创下近 14 年来同期新低。机构分析指出，今年以来整机零部件成本激增已传导至消费端，全球手机零售均价上涨约 20%，直接抑制了终端换机需求，换机周期进一步拉长。
从厂商表现来看，全球前列的主流品牌出货量普遍下滑，三星与苹果仍位列全球份额前两名。小米、OPPO、vivo 继续分列全球市场市占率三至五名，不过三家的市场份额均较去年同期减少，出货量更是录得大约 30% 的跌幅。
在中国市场，华为成为三季度市场份额第一，是头部厂商中唯一实现同比双位数增长的品牌。IDC报告称，华为能够延续强势表现主要凭借多样化的产品形态与相对克制的售价涨幅。苹果以 17.8% 排名中国市场第二，OPPO、vivo、小米和荣耀分别为第三至六名。
Roadster 发布会留下诸多疑问
据《华尔街日报》报道，尽管特斯拉在 10 月 15 日高调发布了 Roadster，并现场展示了其「飞行」能力，但关于该车的合法性、上市和销售细节，仍然留下了诸多疑问。
关于所谓「飞行」能力，特斯拉官网称，Roadster 的顶级型号「火箭版」（Rocket）配备了「全套飞行系统」，是一款单座车型，并且仅限受邀人士（尚不清楚是哪些人）购买。该车目前尚未获得公共道路行驶许可。此外，可容纳两人的「性能版」（Performance）没有推进器，被描述为「可上路行驶」，而「推进版」（Thrust）则被描述为「可上赛道行驶」。
至于「火箭推进器」，实际上是指推进版和火箭版配备的冷气推进器，可以释放气体来推动车辆前进。据说这项技术源自 SpaceX（久有传闻会与特斯拉合并）的技术。同时，所有 Roadster 车型都配备了风扇吸入式系统，使车辆在高速行驶时能够紧贴路面。该系统从车底吸入空气，产生下压力，从而将车辆牢牢固定在路面上。英国的电动超级跑车 McMurtry Spéirling，也采用了类似的装置。

闰时将取代闰秒
据《纽约时报》报道，国际度量衡局（BIPM）于 10 月 15 日投票决定，自 2027 年起正式废除闰秒机制。未来全球计时将不再微调秒数，而是等待协调世界时（UTC）与地球自转的偏差累积至一小时左右（预计需要数千年）再作调整。
闰秒自 1972 年引入，用于弥补基于原子钟的协调世界时与地球实际自转周期之间的微小偏差。但这种不定期插入的秒数，极易引发计算机系统、金融结算及电信基础设施的同步故障。部分科技企业此前只得采用「闰秒涂抹」（leap smear）等替代方案，缓慢平摊时差。
推动此次决议的关键因素在于地球自转近年呈现加速趋势。地核变化与极地冰盖融化等物理因素导致地球自转速度波动，使全球面临首次引入「负闰秒」（即从时钟倒扣一秒）的技术风险，而绝大多数依赖 UTC 的数字系统均未针对时间回退编写底层逻辑代码。
本次表决未达成全票通过。俄罗斯投出反对票（其卫星往往内置闰秒处理机制），而白俄罗斯投弃权票。
