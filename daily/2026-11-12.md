An open source design system that's fully customizable and built for how we build now: 
by people and the agents working alongside them.
Currently in Beta · Built on React 19+ and StyleX
Docs · Storybook · Sandbox · Contributing · Discord
Astryx is an open source design system that grew inside Meta over the last eight years, where it became the most-used and largest design system in the company — powering 13,000+ apps and shaped by the engineers, designers, and product teams who depend on it every day.
It ships 150+ accessible components, brand-level theming, dark mode, ready-to-ship templates, and a CLI as one cohesive system. You import pre-built CSS and use typed React components — no build plugin, no styling library to adopt — and both people and AI assistants build with the same tooling.
What makes Astryx different:
- Open internals. Components are built to be composed at any level, not locked behind a closed top-level API. The building blocks you'd reach for are exported directly, and when you need to go deeper, swizzle ejects a component's full source into your project to own.
- No styling lock-in. Astryx authors its styles with StyleX, but that's invisible to consumers. Override with className using Tailwind, CSS modules, or plain CSS — whatever your project already uses.
- Customize without wrapping. A theme is a set of CSS custom property overrides, so a designer can make Astryx unmistakably theirs without forking or wrapping component source.
- Built for people and agents. The API, docs, and CLI are designed together so a person and an AI assistant build the same way, from the same reference.
Astryx requires React 19 or later (react and react-dom are peer dependencies of @astryxdesign/core).
Install Astryx, a theme, and its peer dependencies:
# npm
npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
npm install -D @astryxdesign/cli
# pnpm
pnpm add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
pnpm add -D @astryxdesign/cli
# yarn
yarn add @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
yarn add -D @astryxdesign/cli
You can also install the CLI once for your computer, so astryx works in any folder and every coding agent knows Astryx; in a project, it still runs that project's own version:
npm i -g @astryxdesign/cli
Project install, global install, or both? astryx docs global/project-global-or-both compares them (both is recommended), and astryx docs global explains how global mode works.
The simplest setup is a few CSS imports plus a theme provider — no build plugin, no PostCSS or Babel config. See the @astryxdesign/core README for the full guide (Next.js, Tailwind, Vite, and CDN).
For reliable CLI access, add a script to your package.json:
"scripts": {
  "astryx": "node node_modules/@astryxdesign/cli/clients/cli/bin/astryx.mjs"
}
Then use it as npm run astryx -- component --list. This avoids path errors when AI assistants or new developers invoke the CLI directly.
@astryxdesign/lab (experimental components) is used internally for Storybook and the sandbox and is not published to npm. @astryxdesign/vega (Vega/Vega-Lite chart wrapper) and @astryxdesign/charts (chart components) are published to npm only under the @canary dist-tag — there is no stable release yet.
These are the promises Astryx makes to the people building on it.
- Guidance over enforcement. Components give you capability rather than guardrails that fight you. Design opinions live in docs and examples — if you pass a value, the component renders it.
- Strong, documented conventions. Every component follows the same naming, prop, and composition rules, and every one is thoroughly documented — so once you've learned a few, the rest feel familiar, and both people and AI can predict how an unfamiliar component behaves.
- One system for humans and AI. The API, conventions, docs, and CLI are designed together so people and AI assistants build the same way. Every change that made Astryx easier for AI made it easier for people too.
- Earned by measurement. We test conventions rather than assert them, hold the results loosely, and revisit them when a new situation proves them wrong.

Skills are folders of instructions, scripts, and resources that Claude loads dynamically to improve performance on specialized tasks. Skills teach Claude how to complete specific tasks in a repeatable way, whether that's creating documents with your company's brand guidelines, analyzing data using your organization's specific workflows, or automating personal tasks.
For more information, check out:
- What are skills?
- Using skills in Claude
- How to create custom skills
- Equipping agents for the real world with Agent Skills
This repository contains skills that demonstrate what's possible with Claude's skills system. These skills range from creative applications (art, music, design) to technical tasks (testing web apps, MCP server generation) to enterprise workflows (communications, branding, etc.).
Each skill is self-contained in its own folder with a SKILL.md file containing the instructions and metadata that Claude uses. Browse through these skills to get inspiration for your own skills or to understand different patterns and approaches.
Many skills in this repo are open source (Apache 2.0). We've also included the document creation & editing skills that power Claude's document capabilities under the hood in the skills/docx, skills/pdf, skills/pptx, and skills/xlsx subfolders. These are also open source (Apache 2.0), and we wanted to share them with developers as a reference for more complex skills that are actively used in a production AI application.
These skills are provided for demonstration and educational purposes only. While some of these capabilities may be available in Claude, the implementations and behaviors you receive from Claude may differ from what is shown in these skills. These skills are meant to illustrate patterns and possibilities. Always test skills thoroughly in your own environment before relying on them for critical tasks.

MuJoCo stands for Multi-Joint dynamics with Contact. It is a general purpose physics engine that aims to facilitate research and development in robotics, biomechanics, graphics and animation, machine learning, and other areas which demand fast and accurate simulation of articulated structures interacting with their environment.
This repository is maintained by Google DeepMind.
MuJoCo has a C API and is intended for researchers and developers. The runtime simulation module is tuned to maximize performance and operates on low-level data structures that are preallocated by the built-in XML compiler. The library includes interactive visualization in native desktop windows and web browsers. MuJoCo further exposes a large number of utility functions for computing physics-related quantities.
We also provide Python bindings and a plug-in for the Unity game engine.
MuJoCo's documentation can be found at mujoco.readthedocs.io. Upcoming features due for the next release can be found in the changelog in the "latest" branch.

agent-browser is a native Rust CLI that gives an AI agent a browser it can drive one command at a time. snapshot returns the page as compact text with a ref such as @e1 for each element. The agent acts on a ref, reads the page again to check the result, and repeats. The browser stays open between commands, so each step is one short shell call.

- Homebrew: brew install agent-browser, then agent-browser install.
- Linux: agent-browser install --with-deps also installs the browser's system libraries.
- No install: npx agent-browser open example.com.
Project installs, building from source, upgrade, and doctor are covered in Installation.
agent-browser open example.com
agent-browser snapshot -i       # interactive elements, each with a ref
agent-browser click @e1         # act on a ref from that snapshot
agent-browser get url           # check the result
agent-browser close
The snapshot for example.com:
- link "Learn more" [ref=e1]
- Refs describe the page at the time of the snapshot. After navigation or a DOM change, take a new snapshot before using refs again.
- CSS selectors, text, XPath, and semantic locators also work, for example agent-browser find role button click --name "Submit". See Selectors.
- A click fails, instead of reporting success, when the target is hidden, disabled, outside the viewport, or covered by another element such as a consent banner. Dismiss the covering element, take a new snapshot, and retry.

和之前的罗马和佛罗伦萨游记不同，这次我先从饮食说起。安特卫普是我在欧洲旅行的最后一站，因此我对于西餐的忍受程度也即将要到达上限。在安特卫普，我吃了非常多顿亚洲食物，其中值得推荐的有两家。
Satay, Antwerp
这家店是我到达安特卫普以后吃的第一家店。由于在意大利几乎没有吃过一顿亚洲食物，所以我自然对它抱有比较高的期待。事实证明，Google Map 也确实没有骗我，这家店的食物水平很在线。它的很多菜品采用的都是酸甜口，芒果和柠檬也经常会作为佐餐水果，具有东南亚当地的风味；米饭的口感我很喜欢，不是那种水洗米粒粒分明的口感，而是抱团但是依然比较硬且有嚼劲的口感；酒水也很不错，香料的味道很充实，能让人一下子就回忆起东南亚的热带风情。
我强烈推荐你选择落座在窗边的吧台位。店门前是一条比较窄的小路，但却是有轨电车的线路之一。坐在吧台位点一杯莫吉托，看着电车经过，穿着日常又时尚的人熙熙攘攘地走过街道，享受欧洲夏日独有的长日照时间，是这个夏天我心目中印象最深刻的画面之一，希望你也可以拥有。
倪师傅川菜馆
我在欧洲两周的唯一一顿中餐，就出自这里。到了安特卫普旅行的结尾，我已经处于累到快病倒的状态，急需一顿中餐来让自己回一点血。随便翻了几个攻略以后，位于安特卫普火车站附近这家中餐馆最终成为了我的目的地。
我点的两道菜是经典的宫保鸡丁和干煸四季豆。比较让我意外的是，这家川菜馆大量的使用了麻椒，但盐味却不是很重，似乎是更接近老式川菜的味道。干煸四季豆明显做得比较「轻」，四季豆都还是保留了很重的原始味道；宫保鸡丁的糖盐量相比于我们一般在国内吃到的都更低，鸡肉本身的味道反而很突出。由于我当时已经开始有生病的迹象，食欲明显减退很多，这两道菜吃下去反而没有让我觉得很油腻，还有一点儿开胃的功效。在国外吃饭虽然口味不如中国丰富，但是油盐量可是一点儿不必国内少，相比之下倪师傅这顿中餐甚至算是「清淡」，我认为很适合大家在国外用来换口味。
不过我也要说明，在国外旅行的大忌就是把什么都拿来跟国内比较，所以吃任何中餐的时候千万不要想着它会如何正宗，当做换口味的一顿就行了。否则，食物的好坏就会完全由你的心态来决定了。
当然了，欧洲食物依然是我安特卫普饮食的重点。
Elfde Gebod Cathedral
这是安特卫普风最大的网红猪排店，没有之一，几乎来这儿拍视频的时尚博主的 Vlog 里都能看到这家店。这家猪排店就在安特卫普大教堂附近，位置很好找，如果是旅行旺季的晚上要记得提前在 IG 上预约。王牌菜 —— 猪排，真的非常大个儿，一份是足够两个人食用的。我点的猪排是酸甜口的，酱汁非常厚，已经完全腌入了猪排里。猪排切起来比较软嫩，吃起来却还是比较有嚼劲。我还搭配了面包，面包沾上酱汁和猪肉一起食用，能更好激发糖油混合物对人类味蕾的刺激程度。
对我这种不太爱吃猪排的人来说，这家店是让人愿意隔三差五去试一试的水平。假设你担心猪排太腻，那就搭配一杯果味啤酒，口感上会清爽很多。既然安特卫普大教堂几乎是每个来到安特卫普的游客都会去的地方，那么选择 Elfde Gebod Cathedral 的猪排作为正餐也就是顺理成章的事儿了。
Frites Atelier Antwerp
传说中的米其林薯条出现了。实话实说，我不是什么美食家，并没有发现这个薯条的惊艳之处。不过据我观察，这家店都是在你点单以后才会开始炸（或者复炸），所以每个人吃到的基本都是新鲜版本，那自然是不会难吃了。另外，这家店的沾酱类型很丰富，每个人点单的时候可以选择自己需要几种酱汁，然后店员就会给你对应数量的小碗让你自己去装，这倒是非常不错的一点。薯条确实很大份，我一个人吃的话还是会觉得比较腻，到头来还是点了一杯啤酒解腻。该说不说，比利时啤酒的品质属于稳定地好，只要是在还不错的餐馆里点到的都还比较好喝。
ANDY ROASTERS
这家精品咖啡店我很喜欢，距离皇家美术馆不远，是我在去皇家美术馆那天早上吃早饭的地方。小红书上说这家店大有 POPEYE 的风范，一进去之后发现还真是，真的很像日式 Cityboy 风格的咖啡店。店里陈设了大量的黑胶唱片、书籍杂志，甚至还有一个专门给 DJ 使用的打碟台。
我是在当地时间周四早上去的，虽然是一个普通的工作日，但是店里还是有挺多人，大部分座位都坐满了。这里咖啡豆的选择从深烘到浅烘一应俱全，从美式到手冲再到冷萃也都有，这在我的欧洲之行中是十分难得的。我很喜欢店内的浅烘豆制作的奶咖和冷萃，总是闻起来就已经能够感受到很明显的水果香气。购买咖啡豆的话，店员也会根据你的预计使用时间来给你最合适生产日期的豆子，十分贴心。
艺术与宗教
提到安特卫普，就不得不提到鲁本斯。鲁本斯虽然在德国出生，但安特卫普却是他真正意义上的「家乡」。如今，鲁本斯的多数作品都存放在马德里的普拉多博物馆，在安特卫普的主要据点只有皇家美术馆和安特卫普大教堂（也叫做圣母大教堂）两处。我是为了看鲁本斯去的这两个地方，然而到了以后才发现，这些地方远不止有鲁本斯。
安特卫普皇家美术馆
皇家美术馆最早是一个类似于画家行会的组织，直到 1810 年拿破仑正式下令创立安特卫普博物馆，皇家美术馆才算是正式建立。皇家美术馆的主要馆藏人物包括鲁本斯、詹姆斯·恩索尔以及里克·沃特斯三位。然而这座美术馆中，真正让我觉得「震撼」的并不是这些艺术品，而是美术馆的陈列方式。我发现在很多展厅中，四面墙上展示的都是有年代的名家画作，但在展厅地面上却摆放了很多现代雕塑和艺术品，甚至还有很多服装设计作品。几乎在每一个较大规模的展厅中，都是采用我所说的这种展示方式。
我们都知道安特卫普出设计师，现代艺术也非常强盛，但令人没想到的是，现代艺术作品会和这些经典的大师作品同处于一个空间。在我看过的诸多美术馆和博物馆中，安特卫普皇家美术馆是我认为把「艺术融合」这个概念做得最好、也是最直观的一座美术馆之一。不同年代、不同流派的艺术本不是割裂的，把它们融合在一起的时候，也就是艺术真正融入生活的时候。
安特卫普圣母大教堂
作为安特卫普的地标，安特卫普大教堂在城市里是相当醒目的存在。欧洲的大部分教堂都遭遇过破坏，安特卫普大教堂也一样。除了经历过常见的火灾之外，大教堂还遭遇过尼德兰地区的破坏圣象运动，导致教堂内很多 14-16 世纪的艺术品被毁灭，这也是如今教堂内主要的艺术品都是 16 世纪以后作品的主要原因。
教堂内部很大，可以参观的东西有很多。这里有四幅比较重要的鲁本斯作品，分别是《竖立十字架》《卸下十字架》《圣母升天》和《基督复活》。在教堂中欣赏宗教画作有一种特别的神圣感，就像寺庙里的佛像总是比博物馆里的佛像更有震撼力一样。
教堂建筑本身也不能错过，尤其是教堂的彩色玻璃花窗，我非常喜爱。这些花窗来自历史上的不同时期，所以绘制的主题、使用的色彩也都有差异。不过好像也正是这些差异，让玻璃窗看起来更复杂也更震撼了。
和花窗一样，讲道坛和唱诗席也很值得关注。讲道坛的雕塑本身就很精美，即使作为一个普通的艺术品也有很多可以称道的地方。而唱诗席与其相比，视觉效果会震撼。站在中间的时候，我的脑海里幻视了很多部电影中出现过的唱诗班的场景，就算没有一部是在这里实地取景拍摄的，也依然能轻松唤起我的记忆，这可能就是艺术的魅力。
除了礼拜日以外，平时教堂的人并不算多，游客们可以找到很多地方落座休息。大家可以在上午十点钟左右来到教堂参观，参观加休息可以一共安排两小时左右，而后再出发去吃烤猪排，完美的安特卫普半日旅行就完成了。
时尚与生活
安特卫普的两大关键词，除了鲁本斯，就是安特卫普六君子了。六君子的辉煌带动了安特卫普艺术设计行业的繁荣，他们也催生了很多世界闻名的设计师和时装店。虽然在穿搭方面我还算有点儿发言权，但这里给我留下深刻印象的不是某个具体的设计师、店铺或品牌，更多是我在这里感受到的时尚融入生活的氛围。
我逛了大量品牌设计和买手店，它们都集中在市中心的一片区域，逛起来很方便。设计师店难免会有很多比较夸张、看起来并不「日常」的款式，但街上穿的人却不少。而且很多人来到店里以后，店员或者设计师本人也会重点介绍品牌或单品设计的概念，想要满足的需求或者表达的观点。买手店的特色则是主题鲜明。安特卫普很多买手店不是单纯的按照品牌汇聚，而是按照这家店的概念来选择单品，所以走进每家店，我都能感受到不同但鲜明的氛围感，这是我在国内很多买手店所感受不到的。
设计师店和买手店已经足够有趣了，可安特卫普的时尚远不止于此。这里的古着店也很出挑，价格便宜，款式不落俗套。古着现在也算一种流行时尚，所以很多人去古着店就是为了淘特定的稀有款，找某个批次的经典单品，久而久之，古着在中文互联网上似乎成了有门槛的一个东西。而这里古着店的顾客看起来都是普通人，大家来逛就是为了买衣服，买自己平时会穿的衣服，很少有人执着于找稀有款，只为好看买单。这样轻松的古着氛围，在国内也很难见到。另外，友情提示，安特卫普的古着店简直就是来抢钱的，要是已经准备好了钱包，也顺便准备一下麻袋吧。
所以你看，这里的时尚是渗透在人们生活里的。就是街上穿背心篮球裤的滑板青年，穿搭也有一种合身又随意的氛围。看他们的穿着有一种向上的朝气，而这种朝气本身跟色彩无关，谁说黑白灰就不能穿得朝气蓬勃呢？
但安特卫普还是有一个品牌不得不提——Arte。这个品牌可以说是安特卫普生活时尚的代表，于 2009 年成立，2010 年发展成熟，成为了安特卫普的一张名片。Arte 的衣服款式是朴素中带有设计巧思的类型，很适合日常穿着。要说特点，有两个不能忽视：一是融入了大量的音乐、街头文化和青年社群的元素，经常会小面积使用跳脱的涂鸦或者色彩作为衣服重要的点缀；二是由于坚持本地设计，所以很多衣服上都印有「@Antwerp」的字样，很有地方特色。除了自己穿着，它也很适合作为伴手礼。
从安特卫普思考城市建设
城市是一个很神奇的概念，不管是人类早期从聚落走向城邦，还是现在已经几乎到顶的城市化，城市这个词都深度参与并贯穿我们的生活。曾经我认为，城市建设只要保有自己的风格和特色就够了，现在我认为，城市建设还要能激发人们生活的热情。超级大都市和平常小城市是一样的，如果不能激发人们在这里生活的热情，那都只能算是一个空壳。
安特卫普不大，我在这里待的时间也仅有四五天，可每天走在街头，满眼看到的都是无穷的生命力。艺术、文化、时尚在这座城市里，最终转化为了人身上的气质，转化为了连空气里都能感受到的气息。所以好的城市不分大小，也不简单在于有没有文化底蕴，重点是城市建设是否有自己的气质，是否有自己的「美商」，是否能跳脱出城建业绩和整齐划一的思维方式。如果你觉得自己「活人微死」了，那就赶紧去有活人的地方抢救一下。只需要一张机票，你就能把自己送到安特卫普。别犹豫了，向快乐出发吧。

缘起
开始规划美西自驾行程时，我发现所谓的「美西环线」并没有一条固定的路线。有人从拉斯维加斯出发，沿着大峡谷、纪念碑谷和犹他州的国家公园一路穿行；也有人从旧金山出发，沿着太平洋海岸一路向南，把更多时间留给沿途的海滨小镇与海岸风光。
每条路线都有各自吸引人的地方，但对我来说，这趟旅行最想看到的风景非常明确：Yosemite（优胜美地）壮阔的花岗岩峭壁、Sierra Nevada（内华达山脉）连绵起伏的群山，以及加州那条漫长的太平洋海岸线。
我对这些地方的向往在很久之前就开始了。过去十几年里我一直在使用 Mac，这些加州的地名早已通过一代代 macOS 留在了我的记忆里。从 2013 年的 Mavericks 开始，苹果陆续以 Yosemite、El Capitan、Sierra、Mojave、Catalina、Big Sur 等地名为操作系统命名，把这些地方的风景带到了无数 Mac 用户的桌面上。
这些加州景观里最让我向往的还是 Yosemite，2014 年 OS X Yosemite 发布后，那张以 Half Dome（半穹顶）为主角的默认壁纸让我记住了这里，我无数次在屏幕上看到这座沐浴在夕阳中的花岗岩山峰。
带着这些期待，我敲定了加州的环线行程：从洛杉矶出发，向北经过 Sequoia（巨杉国家公园）和 Yosemite，再翻过 Sierra Nevada 前往 Lake Tahoe（太浩湖），之后到旧金山看 Golden Gate（金门海峡），再去硅谷，最后沿着 1 号公路向南，经 Monterey（蒙特雷）、Big Sur（大瑟尔）和 Ventura（文图拉）返回洛杉矶。这条路线也串起了过去十几年里多个 Mac 操作系统名称所对应的地点。
Basic Apple Guy 在《macOS California Camino》中考据了壁纸拍摄的位置，Andrew Levitt 则专门乘坐直升机寻找最接近 Big Sur 壁纸的拍摄视角。不过我并不打算把这次旅行变成一场单纯寻找壁纸机位的任务。Mojave（莫哈韦）沙漠、Catalina（卡塔利娜）岛以及不少版本壁纸的实际拍摄地点，均不在这次行程之中。
我的旅程从洛杉矶开始，离开城市后公路两侧逐渐变成大片金黄色的山丘。十月加州的阳光仍然十分充足，路面在强烈的日照下显得格外明亮。
随着车子继续向北，沿途的景色开始慢慢变化。开阔的草坡逐渐让位于山地，公路不断爬升，树林也变得越来越茂密，几个小时后就进入了这趟旅程的第一座国家公园——Sequoia。
Sequoia
2024 年发布的 macOS Sequoia 把巨杉林带到了 Mac 桌面上，与过去以静态照片为主的风景壁纸不同，Sequoia 通过一段穿行于树林间的动态影像展现了这片森林。镜头缓缓向前，阳光透过高大的树冠洒落下来，一棵棵巨杉从画面两侧掠过，也让人更直观地感受到这片森林的幽深与壮观。
巨杉的大小远比照片里看到的夸张。来这里之前我知道巨杉是世界上体积最大的树木之一，也看过不少游客站在树下的照片。
当那些粗大的红褐色树干真正出现在眼前时，还是很难立刻建立起对它们尺寸的认识。
回头看照片，树干与周围植被的层次还在，但站在树下仰望时感受到的巨大尺度，很难通过照片传达。苹果用移动的镜头展现了巨杉林的纵深，我的照片却只能记录其中一个角度。
我没有找到足以确认原始影像具体拍摄位置的资料，也无法判断它是否与自己到访的 Giant Forest（巨杉林）属于同一片林区，但对我来说这片森林却是留给留下了很深的印象。
离开 Giant Forest 后，我继续向北经过 Kings Canyon National Park（国王峡谷国家公园）的 Grant Grove（格兰特巨杉林），再朝 Yosemite 的方向行驶。
沿途的景色也逐渐发生变化。茂密的森林之外开始出现更多裸露的浅灰色岩壁，公路沿着山坡起伏，偶尔能从高处望见远方层层叠叠的山脊。和刚才那些需要站在树下仰望的巨杉不同，这里的风景开始变得开阔，视线也能延伸到更远的地方。
从进入 Sequoia 开始我就已经置身于 Sierra Nevada 之中。这片绵延数百公里的山系，不仅孕育了巨杉林，也塑造了 Yosemite 那些极具辨识度的花岗岩山谷。两座国家公园相隔不远却有着截然不同的景观：在 Sequoia，最令人惊讶的是树木的大小；而到了 Yosemite，真正占据视野的，将是那些高耸的岩壁。
Yosemite
我第一次听说 Yosemite 这个名字是在《乔布斯传》里，书中提到乔布斯曾在「优胜美地」举行婚礼。相较于「约塞米蒂」直接音译，我对「优胜美地」这个中文译名印象更加深刻。它选用了四个颇具诗意的汉字，让人很容易联想到一处山清水秀、风景优美的地方。
2014 年的 OS X Yosemite 也是我印象最深的一代 Mac 系统，苹果几乎重新设计了整个 OS X 的界面。此前的 Mavericks 还保留着不少拟物化的设计，Yosemite 的窗口则变得更加简洁，Dock 和应用图标换上了扁平化的样式，系统里也开始大量使用半透明效果，整体风格明显向前一年发布的 iOS 7 靠拢。
如今再看那套界面已经算不上新鲜，但我始终记得第一次看到它时惊艳的感觉，还有那张夕阳下的 Half Dome 壁纸。这张壁纸据称是风光摄影师 Jim Patterson 拍摄的，在他的个人网站上也能看到许多 Yosemite 的风光照片。苹果选择的这张照片没有展现整个 Yosemite Valley（优胜美地山谷），而是将镜头集中在 Half Dome 上，巨大的花岗岩山体在夕阳下呈现出淡淡的粉橙色。
这张壁纸陪伴了我很长时间，每次打开 MacBook，Half Dome 就出现在桌面上，这次来到 Yosemite Valley 终于有机会在山脚下住上一晚。我选择了位于山谷深处的 Upper Pines 营地，周围是高大的松树，抬头就能望见远处的 Half Dome。
傍晚时分，夕阳将山顶染成暖色，下面的岩壁已经隐入阴影；第二天清晨，阳光又重新照亮了这座熟悉的山峰。
虽然没有刻意寻找苹果壁纸的拍摄机位，但能够在一天中不同的时刻看到 Half Dome，已经让我觉得这一晚的露营很值得。
虽然我看到的 Half Dome 山顶光线和构图与壁纸完全不同，但是那道圆弧状的山顶与陡峭岩壁相接的轮廓还是很容易辨认。
Half Dome 的形状与 Yosemite Valley 的地质历史有关。这里以花岗质岩石为主，早期河流的侵蚀和后来的冰川作用共同塑造了山谷的形态。Half Dome 看起来仿佛被削去了半边，但它的形成还涉及岩石裂隙和剥落，并不能简单理解为冰川切掉了半座山。
Half Dome 并不是 Yosemite 唯一令人印象深刻的花岗岩巨壁，就在同一座山谷里，还有另一处同样著名的地标。
El Capitan
Yosemite 发布一年以后，下一代 OS X 没有去往新的国家公园，甚至没有离开 Yosemite Valley。苹果只是把系统名字从整个 Yosemite，缩小成了其中一座标志性的花岗岩峭壁：El Capitan（酋长岩）。
两张壁纸的取景方式也很不一样。Yosemite 将 Half Dome 拉近到画面中央，而 El Capitan 则展现了更为开阔的山谷景色。从 Tunnel View（隧道观景点）望去，左侧是高耸的 El Capitan，右侧是 Bridalveil Fall（新娘面纱瀑布），远处还能看到 Half Dome。前一年被放大到几乎占满屏幕的山峰，在这里又回到了山谷深处。
这次旅行中我也来到了 Tunnel View。站在观景台上，眼前的景色与熟悉的壁纸十分相似，只是少了积雪和暖色的夕阳，山谷里铺满了深绿色的森林，云层在山峰上方堆积。El Capitan 就矗立在左侧，巨大的岩壁在阳光下显得格外明亮。
开车来到谷底、从近处仰望 El Capitan 时发现它比远处看到的还要壮观。整面浅色花岗岩壁从树林后方拔地而起，高出谷底约 900 米，岩壁上布满了细长的裂隙和深色水痕。
从 Tunnel View 远眺时，它只是山谷左侧的一块巨大岩石；真正站到山脚附近，才发现那些在照片里不起眼的树林，反倒成了判断岩壁高度最直观的参照。
El Capitan 也是世界各地攀岩者向往的经典攀登地点之一。2017 年 6 月 3 日，攀岩者 Alex Honnold 在没有绳索和任何保护装备的情况下，仅用 3 小时 56 分钟便沿着 Freerider 路线登上了这面近 900 米高的花岗岩绝壁，成为首位完成这一壮举的人。这次攀登被记录在纪录片《徒手攀岩》（Free Solo）中，影片后来获得了第 91 届奥斯卡最佳纪录长片奖。

2015 年的 El Capitan 之后，苹果在下一代系统中将目光投向了更广阔的 Sierra Nevada。2016 年，OS X 正式更名为 macOS，而新系统的名字也从山谷中的一座岩壁，变成了绵延数百公里的整片山脉：Sierra。
Sierra
macOS Sierra 选择了一幅颇具代表性的山地风景作为默认壁纸。夕阳将锯齿状的山脊染成橙红色，背光面的岩壁呈现出冷灰色，山沟里还残留着积雪，天空则飘着淡淡的粉紫色云层。山峰的轮廓如此鲜明，光线又恰好落在最醒目的位置，以至于整幅画面看起来有些不真实。
这张照片拍摄于 Sierra Nevada 东侧的 Alabama Hills（阿拉巴马丘陵）一带，画面中的山峰通常被认为是 Lone Pine Peak（孤松峰）。这里与 Sequoia、Yosemite 同属 Sierra Nevada 山区，但这处拍摄地与两座国家公园分处山脉的东西两侧，风景也截然不同。

两张壁纸的拍摄地点都位于 Sierra Nevada 东侧，沿着美国 395 号公路便能从 Lone Pine 一带前往 Bishop。不过我的这次自驾并没有经过这两处拍摄地。此前我走的是山脉西侧的路线，从 Sequoia 的巨杉林来到 Yosemite，又沿着 Tioga Road（泰奥加公路）进入了 Yosemite 的高海拔山区。

我特别喜欢玩扫雷，甚至已经把它当成了一种日常「冥想」工具。打开玩一会儿，把注意力放到棋盘和数字上，人就能静下心来。
在电脑上玩扫雷，无论是 Windows 上的经典扫雷，还是 macOS 上的复刻版本，都有许多不错的选择。但我一直没在手机上找到合适的 App：一方面是外观没有特别符合心意的，另一方面是操作方式不习惯，我总觉得用手指戳屏幕，没有用鼠标点起来有感觉。
但手机接个鼠标才能玩确实也不方便，所以我想，是不是可以加入虚拟手柄：用十字键移动，再按 A/B 键翻开格子、插旗。以前 Game Boy 不就是这样子玩的吗？找了一圈没有找到类似的，我就自己做了一个，名字叫 RetroSweeper Go。
规则还是熟悉的扫雷：翻开格子、看数字、标记地雷，再慢慢把安全的区域找出来。我给它配上了复古游戏机风格的界面和手柄，希望可以唤起你的一些回忆。
三种游戏机风格
目前游戏有 Famicom、Game Boy 和 PlayStation 三种主题，配色的灵感来自原版游戏机的机身、屏幕和按键等设计元素。（By the way，虽然图里 Famicom 和 Game Boy 的 A/B 键看起来比较像，但它们其实是不同的红色！）
- Famicom：取自红白机经典的枣红色与暖白色，数字的配色则从 Mario、Link、Kirby 等角色身上寻找灵感。这也是游戏默认的主题。
- Game Boy：棋盘背景色来自早期 Game Boy 的绿色点阵液晶屏幕，再搭配浅绿色背景和偏紫红色的按键。
- PlayStation：以初代 PlayStation 的灰色机身和 Memory Card 的灰蓝色调为灵感，虚拟手柄按钮则带上一点 PlayStation 标志性的彩色点缀。
其实我也想做一些别的主题，不过我并不是很会设计，现在这 3 款也是在 AI 的帮助下调了很久才满意。后面我也会继续慢慢改进。
可以直接点，也可以用虚拟手柄
在手机上玩扫雷，最直接的方式当然是触屏：轻触翻开、长按插旗。当周围的地雷已经全部标记完毕，还可以双击数字格，通过 Chord 快速展开周边未标记的格子。
为了防止误触，这里我设置了长按阈值；假如总是不小心炸雷，可以去设置中调整长按的判定时间。虚拟手柄则是用十字键移动选中的格子，再通过 A/B 按钮翻开或插旗，这样手指不用一直在棋盘上移动换位。左右手负责不同的操作也不太容易误触。
当然，手柄模式下也不用只靠十字键一格格地移动：可以直接点棋盘，快速把光标定位到想去的格子。如果移动棋盘后，光标落在当前可见范围之外，棋盘边缘会出现方向箭头，帮助你定位；A/B 键的上下位置也可以按自己的喜好调整。
因为虚拟手柄是我专门做的，所以我自己当然更喜欢这种方式。哒哒哒地按下去，一格一格地推理，很容易进入心流。两种操作的感觉还是挺不一样，大家也可以都试试看。
依旧是熟悉的 3 种难度
游戏提供初级、中级和高级三种难度，棋盘大小和地雷数量都是标准配置。（目前还没有做自定义棋盘，因为我还没想好怎么做。）
棋盘支持缩放和移动，触屏模式下，棋盘下方还有 Minimap，方便查看整体进度和当前所在的区域。
我的习惯是，用触屏操作时，把棋盘放大一点，格子更大，手指会更好操作；使用虚拟手柄时，适当缩小棋盘，这样移动起来更快捷。
卡住的时候，不妨借一点道具
如果刚开始玩扫雷，还不太会判断数字之间的关系，找不到下一步怎么做，这时可以使用 Hint：游戏会帮忙翻开一个安全格，或标记一个能够判断出的地雷，并尽量优先提示当前操作位置附近的格子，不会动不动就帮你展开一个隔了十万八千里的格子。
当然，踩雷也是扫雷的一部分，失败后你可以看看地雷究竟分布在哪里，也可以使用 Rewind 悔棋卡，回到上一步继续玩。
通关后可以查看自己的用时，也支持 Game Center 全球排行榜。不过，使用道具后的成绩会归入「辅助模式」，和常规成绩区分。
对了，如果你以前没玩过扫雷，游戏里也有互动教程，可以在实际棋盘上学习扫雷的基本玩法。

A general purpose Apple Silicon layer for x86-64 PCs. It is a UEFI boot program with an arm64-to-x86-64 translator, a Metal driver for NVIDIA GPUs and a model of Apple silicon hardware. macOS and most apps start, but it is slow and needs much more testing, as of v0.1.0
Warning
Stela is very much still in development. Your current chances of it booting are low, major hardware support/fixes are on the way.
An ahead-of-time and just-in-time compiler translates arm64e code to x86-64. It covers more than 3,000 AArch64 instruction encodings, maps guest registers to host registers and caches translated code. It runs on any x86-64-v2 CPU, Intel or AMD.
The Metal driver supports GTX 16 and RTX 20 series GPUs and newer. It compiles AIR, Metal's shader IR, directly to NIR, Mesa's IR, and supports the Metal3 and Apple7 GPU families.
- An x86-64-v2 CPU (about 2011 or newer), UEFI with Secure Boot off, 8 GB of RAM.
- An NVIDIA GTX 16 or RTX 20 series GPU or newer.
- A USB stick of 8 GB or more.
- An empty GPT partition of at least 60 GB.
- Network access during the install, which downloads macOS.
Stela currently models the Mac mini (M2) and runs macOS 27.

releases page.
- Run sudo ./stela setup (Linux, macOS) or double-click stela.exe (Windows).
- Choose the USB stick, the macOS version and the Mac model, then confirm. Setup erases the USB stick.
- Boot the PC from the USB stick.
To update a USB stick made with an older version, download the new stela,
plug the stick in and run sudo ./stela setup update stela (Linux, macOS) or
stela.exe setup update stela (Windows).
You need Rust and LLVM with Clang 21 or newer.

What to know about this year’s UN climate talks
Climate finance and fossil fuels top the formal agenda at COP31.
It’s that time of year again: Thousands of delegates, lobbyists, and journalists are gathered for the annual UN climate talks, taking place this time in Antalya, Turkey.
COP31 officially kicked off on November 8, marking the beginning of negotiations on one of the biggest stages of the climate world. Turkey and Australia are cohosting this year’s talks, which are scheduled to wrap up on November 20.
This annual gathering can often serve as an indicator of where the world stands on addressing and adapting to the climate crisis. And this year’s talks are sure to be a doozy—expect a lot of back and forth on fossil fuels and climate finance in particular. Here’s what you should know about COP31.
In recent years, the tension always feels high when COP rolls around. (COP stands for “Conference of the Parties.”) But this year feels especially charged: The world is still grappling with the ongoing war in Iran, which has disrupted the Middle East and sent economic shock waves around the world as energy prices have spiked.
This year’s COP will be the second without a formal delegation from the US. President Trump formally withdrew the country from the Paris Agreement earlier this year and is in the process of withdrawing from the UN Framework Committee on Climate Change. That’s the treaty that allows formal participation in negotiations.
Meanwhile, things aren’t looking good for the Paris Agreement, which was established at UN climate talks 11 years ago, setting a goal of limiting warming to 1.5 °C over preindustrial levels. In a report published in September, the UN Environment Program acknowledged that global warming is set to exceed that 1.5 °C goal, “likely within the next few years.”
So as climate talks kick off, there’s an obvious, urgent question looming about how to quickly cut emissions to limit warming. There’s also the major issue of how to pay for efforts to address emissions and to help a warming world endure the inevitable damage.
Two years ago, talks ended in a goal of mobilizing $300 billion per year by 2035 to help pay to reduce emissions and adapt to climate change. (Rich nations provided $136.7 billion in 2024, according to the Organization for Economic Cooperation and Development.) And last year, the COP30 agreement included a goal of tripling the money for adaptation over that period. (Such funding has been quite flat over the past few years.)
The world got a tragic reminder of just how high the stakes are earlier this year, when a glacier collapse caused devastating flooding in the Himalayas. The flood killed approximately 1,500 people, left over 5,000 missing, and caused nearly $5 billion in damage. The UN loss and damages fund committed $20 million to helping Nepal recover (less than 1% of the total estimated cost to the country).
Another key trend to watch is how the formal negotiations engage with the topic of fossil fuels. Three years ago, the final agreement text explicitly called for a transition away from them. But it felt as if things took a step back last year, when the final agreement didn’t even mention the phrase “fossil fuels” once. This will be an interesting conversation, especially because cohosts Turkey and Australia have both faced criticism over their relationships with these fuels—Australia is a major exporter of coal and natural gas, and Turkey’s grid relies heavily on fossil fuels, including coal.

Fossil fuels, like gasoline in vehicles or natural gas for heating, make up the bulk of the rest. Shifting to more electricity use, and relying on cleaner sources for that electricity, could help drive down emissions. The new pledge’s target is for electricity to make up 35% of total energy consumption by 2035.
With leadership billing this as an “implementation COP,” it would be great to see some real, tangible progress on the global challenge of addressing climate change. I’m not expecting anything groundbreaking, but we’ll be tuned in to see what the final agreement shapes up to be.

            Abstract:The rapid proliferation of autonomously acting AI agents makes the governance of agentic systems urgent. We propose the competence circuit, summarized as IKC + KC + C, that decomposes an agent's real-world impact into three pathways: intelligence-mediated discovery, procedural know-how, and direct control. Using the canonical fast-takeoff debate as a stress test, we formalize the conditions for intelligence-mediated fast takeoff as a conjunction jointly sufficient for fast catastrophic supremacy, showing that most rely on rapid knowledge acquisition or control attainment rather than intelligence alone. We operationalize epistemic intelligence as hypothesis-selection efficiency and validate this framework via stochastic simulation on NK fitness landscapes across six scenarios spanning the conjunctive chain. An analytic bound supported by the simulations shows that intelligence-driven speedup is capped by the ratio of competing intelligence levels regardless of task difficulty. The simulations also expose a fast-takeoff dilemma: a large intelligence-driven speedup multiplier materializes only when the hypothesis space is noisy, but the absolute timescale remains constrained by the time required for capability-critical tests, so a large multiplier need not imply rapid progress. Simulations also indicate that institutional chokepoints disproportionately slow down superintelligent agents when mandatory authorization delays are large relative to the negligible time these agents spend on unproductive search. We argue that the dominant safety levers are restricting control and enforcing knowledge boundaries rather than limiting intelligence alone, and this applies to agentic systems at any capability level. Purely digital domains weaken these bottlenecks, strengthening the case for architectures that intentionally "put physics in the loop."
